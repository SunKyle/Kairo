## P0 · 数据安全与正确性（会丢用户东西）

### 1. 自动清理会吃掉「已标记」的图

**证据**：`pruneHistory()`（[idb.ts:811](../src/lib/idb.ts#L811)）的避让集合只认作品集 —— `.filter((r) => !r.collectionId)`（[idb.ts:843](../src/lib/idb.ts#L843)），**`marked` 完全不参与**。

**为什么是问题**：「标记」是用户逐张挑出来的收藏（`ResultItem.marked`，按张记，见 [types.ts](../src/types.ts)）。空间一紧张，这批最老的精挑图会被静默删掉，且不可恢复 —— 而作品集里的同类图被保护着。

**改法**：把「含 marked 张的记录」并入避让集合；更精确的做法是清理时只删未标记的那些张。顺带在清理提示里说明「保留了你标记的 N 张」。

### 2. 高频写入路径上的存储体检（含每次重开连接）

**证据**：`addHistoryRecord()` 结尾无条件 `return await pruneHistory()`（[api.ts:1617](../src/api.ts#L1617)）。prune 内部先 `openDB()` 再 `navigator.storage.estimate()`，**超出 80% 水位才全表 `getAll()`**（[idb.ts](../src/lib/idb.ts) 的 `pruneHistory`）。

> 初版文档把这里写成「每次都全表扫」，校准后不准确：配额充足时它在 `getAll()` 之前就返回了。真正的问题是两个：

**为什么是问题**：

1. **`openDB()` 没有缓存连接** —— 原实现每次读写都重新 `indexedDB.open()` 一次异步握手。落盘一条记录、读一屏消息、量一次缩略图，全都各握手一次；而一个连接本来就能被任意多的事务复用。这是比体检本身更大的开销，且影响**所有**读写路径，不只是 prune。
2. **体检没有节流** —— 每次写入都问一遍 `estimate()`；并发出图时三条一起落盘就是三次。更糟的是占用真的超过水位线那一刻：多个并发写入会各自看到「超标」，于是同时发起多个全表扫描 + 多个删除事务。

**改法**：缓存连接（并在 `versionchange` 时让开、清缓存）；体检按「距上次 ≥ 30s 或新增 ≥ 20 条」节流。两项均已落地（见 [优化计划.md](优化计划.md) 的 T0.3）。

> **补记**：缓存连接本身带来一处新风险 —— 连接若**意外**关闭，缓存就永久指向死连接，而失败都被 catch 成「空」。已补 `onclose` 清理与「连接已死就重开一次」（见 [优化计划.md](优化计划.md) 的收尾 A1）。

### 3. 多标签页无同步 + 全量覆盖写

**证据**：全仓没有 `storage` 事件监听，也没有 `BroadcastChannel`；`saveCharacters()` 是整份覆盖写回（[api.ts:2032](../src/api.ts#L2032)），配置 / 提示词 / 作品集同理。

**为什么是问题**：两个标签页同时开着，B 页的「删角色」会被 A 页下一次保存**整个覆盖回来**，用户会看到已删的东西复活。

**改法**：监听 `storage` 事件重载目录 + 给一条「另一标签页已修改」提示；要更彻底就上 `BroadcastChannel`。

### 4. 大图局部编辑会撞 15MB 请求上限

**证据**：前端 `/api/edit` 走 **JSON + data URL**（[api.ts](../src/api.ts) 的 `body: JSON.stringify({...})`，image 与 mask 都是 base64），逐段解析的约定见 [types.ts](../src/types.ts) 的 `EditParams`；服务端是 `express.json({ limit: '15mb' })`（[server/index.js](../server/index.js)）。

**为什么是问题**（实测数据，见 [优化计划.md](优化计划.md) 的 T1.1）：画布把当前画面**一律编成 PNG 全分辨率**再 base64。一张 3840×2160 的照片编完是 **27.8MB** —— 在 4K 图上做局部编辑**必然失败**，而且失败信息还是服务端默认的 HTML 错误页，前端只显示一句 `Request failed (413)`。

**改法**（已落地）：按长边 2560 收窄（厂商的编辑输出上限更低，收窄不损失结果质量），并按内容选格式 —— 照片走 JPEG（12.4MB → 2.7MB）、带透明的走 PNG（[lib/payload.ts](../src/lib/payload.ts)）；同时把服务端的超限响应翻成 JSON 人话。真正的二进制传输留作后续，只有需要 >2560 的编辑输入时才值得做。

## P1 · 可维护性（最大的长期成本）

### 5. 三个巨型文件 = 全项目近一半代码

`App.vue` 5412 行 / `CharacterPage.vue` 5177 行 / `CanvasEditor.vue` 4042 行。`App.vue` 一个文件同时是 store、持久化层、路由、模板和样式。

**拆法（不必大重写）**：

1. 先按业务域抽 composable：`useConfigs` / `useGeneration` / `useCharacters` / `useChat` / `useHistory`，模板基本不动；
2. `CanvasEditor` 先把「ops 重放引擎」抽成纯函数（`rotate/flip/crop/ai` 的弹栈重放，这部分天然可测）；
3. `CharacterPage` 拆 列表 / 详情 / 向导 / Voice 四块。

### 6. 同构代码重复得比较厉害（拆分前更划算的一步）

| 重复的东西 | 出现在 |
| --- | --- |
| `trapTab`（焦点陷阱） | CharacterPage、ChatPage、ImagePreview |
| 「点外收起」`onDocPointerDown` | 6 个文件 |
| Esc 分层退出 | 7 处 |
| 「挑当前配置」`find(id && kind===X) \|\| find(kind===X)` | `App.vue` 的 `onMounted` 里四段同构（约 60 行），且 `kind !== 'text'` 是硬编码 |

抽 `lib/ui.ts`（`useFocusTrap` / `useOutsideClick` / `useEscLayers`）+ `pickActiveByKind(configs, kind, activeId)`，能一次性消掉两三百行。

### 7. 无测试 / 无 lint / 无 CI / 无 README

优先给三块**纯逻辑**补最小测试：

- 能力表与尺寸归一化（`allowedSizeFor` 那段「比比例的对数距离」很容易写错）；
- `idb` 的迁移与 prune；
- 服务端的错误翻译与请求归一化。

这三处出错的表现都是「用户以为数据没了 / 图就是出不来」，最难靠手测发现。CI 跑 `typecheck + build` 就够。

### 8. 文档引用方式本身在腐烂

现在大量使用「文件 + 行号」引用，而代码每天都在动（文档说 IndexedDB 建表升到 v9，实际已是 v11）。建议把引用换成**符号名**（函数名 / 常量名），行号只当辅助。

## P2 · 性能

### 9. 启动一次性把整个库读进内存

`loadHistory()` 走 `getAll()` 读全部记录（含 Blob），`loadCharacters()` 连参考图一起取，`loadPrompts()` 连封面一起取。库龄一长，首屏 IO 与反序列化线性增长（记录上限 `HARD_LIMIT` 是 500 条）。

**改法**：游标分页，先取最近 N 条，往前翻再读 —— 这个交互心智历史页已经有了（图墙 12 格 + 往前翻）。

### 10. `backfillThumbs()` 对全部老记录逐张解码 + canvas 重编码

在首屏之后持续占 CPU，老库越久越明显。

**改法**：串行 + `requestIdleCallback` + 只处理可见范围 + 单次会话限量。

### 11. 历史页没有虚拟滚动

[HistoryPage.vue:60](../src/components/HistoryPage.vue#L60) 把记录摊平成图块后全量渲染（模板 [HistoryPage.vue:389](../src/components/HistoryPage.vue#L389)）。500 条 × 每记录多张 ≈ 上千个 `<img>` 节点。图墙是等高网格，做增量渲染或虚拟列表都不难。

### 12. 画布在主线程做 `toBlob` + data URL 编码

大图是几百毫秒级卡顿。可以挪到 `OffscreenCanvas` + Worker，至少先 `await` 一帧再算。

### 不用急的

CSS 152KB、icons chunk 291KB。图标已经 tree-shake 干净（验证过没有未使用图标），属于正常体量。

## P3 · 安全与部署

### 13. 公开部署 = 无鉴权的开放代理

`/api/generate`、`/api/test` 接受请求方指定的任意 `baseUrl`。SSRF 私网拦截已经有了，但没有域名白名单，也没有任何调用方身份校验。自用无碍；一旦上公网，等于替所有人付带宽和函数额度。

**改法**：加一道共享密钥 / 口令，或上游域名白名单，或默认只允许本机访问。

### 14. 限流是内存滑窗

Serverless 下按实例生效，等于没有全局配额。真要防滥用需外部存储。

### 15. API Key 明文在 localStorage

全仓无 `v-html`，XSS 面很小，这个取舍（本地优先）站得住。但设置页应当明说，并可选提供「仅本次会话保存」。

## P4 · 产品与体验

### 16. 无路由 → 无法深链

刷新回首页，也没法把「某个角色 / 某条记录 / 某段对话」发给人。把 `page` 与 `charId / entryId` 映射到 hash 成本很低，收益（分享、刷新不丢位置）不小。

### 17. 界面文案全英文、注释与文档全中文

若面向中文用户，建议统一，或引入轻量 i18n。

### 18. 未提交改动量大且在涨

分批提交应排在所有重构之前。

## 反过来：这几处「看着像问题」，其实别动

| 看着像问题 | 为什么别动 |
| --- | --- |
| object URL 用 WeakMap 缓存 + 显式 `releaseEntryMedia` | 设计是对的。「谁卸载谁 revoke」会让图墙 / 抽屉 / 预览互相把图撤掉 |
| prune 用配额水位而不是固定条数淘汰 | 固定条数会在空间充裕时静默删记录（代码注释已解释） |
| 四套独立 AbortController（生成槽 / 设定图 / 对话 / 改写） | 语义不同，合并只会更难懂 |
| `CONNECT_HINTS` 那一大坨错误中文化 | 它替代的是用户面对一句 `fetch failed` 束手无策，成本花得值 |
| 密钥不放服务端 | 这是「本地优先」的核心取舍。为了安全叙事把 Key 搬上后端，会把产品变成必须登录的东西 |
