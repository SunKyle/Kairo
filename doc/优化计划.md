> 依据：[优化建议.md](优化建议.md)。
> 本轮范围：**Phase 0 数据安全 / Phase 1 传输体积 / Phase 2 消重复 / Phase 3 性能**。

> 三条硬规矩：

## Phase 1 · 传输体积

> 目标：4K 图能真的用画布编辑。

- [x] **T1.1 编辑载荷收窄 + 超限时给人话**
  - 现状（实测，Pillow 生成同类内容测得）：画布把当前画面**一律编成 PNG 全分辨率**再 base64。一张 3840×2160 的照片编完是 **27.8MB**，而服务端请求体上限 15MB —— 在 4K 图上做局部编辑**必然失败**。而且厂商的编辑结果本身有上限（gpt-image-1 最大 1536、本站给的档位最大 2560），送 4K 进去换不到更大的结果
  - **方案调整（与原计划的「改二进制」不同）**：原计划是改传输协议（FormData/裸二进制）。实测后改用更省的路线 —— `lib/payload.ts` 里定长边上限 2560 与 8MB 预算，画布按内容选格式：

    | 内容 | 3840 PNG b64 | 2560 PNG b64 | 2560 JPEG b64 |
    | --- | --- | --- | --- |
    | 照片类 | 27.8 MB ❌ | 12.4 MB | **2.7 MB** |
    | 截图类 | 0.04 MB | **0.02 MB** | 1.1 MB |

    照片走 JPEG、带透明的走 PNG（JPEG 会把透明压成黑块），超预算再退一档（×0.7，下限 0.25）。这样不必新增依赖、不必自定义线格式，且**画质无损**：厂商的输出上限低于 2560，收窄不会换来更差的结果
  - 改动：新增 [lib/payload.ts](../src/lib/payload.ts)（纯函数：`dataUrlBytes` / `payloadScaleFor` / `shrinkScaleFor` / `payloadOverBudget`）；CanvasEditor 的 `editPayload` 让原图与 mask **共用同一个缩放系数**（尺寸不一致上游会判参数错误）；服务端补一条错误兜底，把 `entity.too.large` 与非法 JSON 翻成 JSON
  - 验证（单测 15 个）：字节折算、4K→2560 的比例、上下限、预算边界
  - 验证（服务端端到端，实起进程 + curl）：

    | 请求 | 改动前 | 改动后 |
    | --- | --- | --- |
    | 16MB 请求体 | **HTML 错误页 + 绝对路径堆栈**（前端只能显示 `Request failed (413)`） | `413 {"error":"The request body is too large","detail":"…up to 15mb…"}` |
    | 非法 JSON | HTML 错误页 + 堆栈 | `400 {"error":"The request body is not valid JSON"}` |
  - 验证（手测）：导入一张 4K 照片 → 套索局部重绘 → 应成功（改前必失败）；再用一张带透明的截图试「去背景」，确认透明没被压成黑底
  - 未做（留作后续）：真正的二进制传输。若将来需要 >2560 的编辑输入，再走那条路
- [x] **T1.2 尺寸策略归一**
  - 现状：「喂给模型的参考图」上限本来是**五处各写一个 1024**：首页参考图（[App.vue](../src/App.vue) 的 `compressImage(url, 1024)`）、`compressImage` 的默认参数、画布的 `REF_EDGE`、角色识图的 `VISION_MAX_EDGE`、聊天附图的 `CHAT_IMAGE_MAX`
  - 改动：收到 [lib/payload.ts](../src/lib/payload.ts) 一处 —— `REF_IMAGE_EDGE`（参考图）、`REF_ARCHIVE_EDGE`（只作复现凭据的存档）、`EDIT_PAYLOAD_EDGE`（编辑载荷），五处调用全部改用它；注释里的字面量也一并改成常量名
  - 验证（单测 3 条不变式）：参考图上限必须小于编辑载荷上限（两者取舍不同，不能混成一个数）；编辑载荷上限不得低于本站给出的最大档 2560（否则「选 2560 出图」会变成实际只送了更小的进去，且不报错）；三个数必须是正整数
  - **顺带发现（未修，记在这里）**：角色参考图那条路 [charRefSrcs](../src/App.vue) 最多送 4 张视图、**全程不压缩**，是唯一带「张数乘数」的参考图路径。按当前视图尺寸（≤1024×1536）估算约 8MB base64，仍在 15MB 以内，所以是**潜在风险而非现行缺陷**；真要修应该按字节预算而不是像素上限（压到 1024 会让全身视图掉到 683×1024，损失的是"像不像本人"这件事）

- [x] **T2.3 能力门控集中**
  - 现状：尺寸候选、默认档、手填尺寸归一、种子、扩展参数、逐模型尺寸校验、角色取景尺寸全都写在 `App.vue`，而它们只看厂商能力表，与界面无关；其中「按比例挑尺寸」还写了**两套度量**（编辑用对数距离、角色取景用差值）
  - 改动：全部收到 [api.ts](../src/api.ts) 一处并导出 —— `vendorOf` / `FREE_SIZES` / `normalizeSize` / `sizeOptionsFor` / `sizeIsFree` / `defaultSizeFor` / `sizeClosestTo` / `sizeForVendor` / `seedFor` / `extraParamsFor` / `acceptableSize`；`App.vue` 只剩「问一句能不能」与渲染
  - **写测试时抓出三个真问题**（都不是我原以为的样子）：
    1. **Gemini 的宽幅/竖幅档位根本不会生效**：候选里的 `1792x1024` / `1024x1792` 约分是 **7:4 / 4:7**，而服务端只认它自己那张比例表（含 16:9、9:16），于是选这两档时 `aspectRatio` **根本不发** —— Gemini 退回自己的 16:9 默认值。也就是说「选竖幅」以前拿到的是**横图**。已换成能干净约分的 `1536x864`（16:9）与 `864x1536`（9:16），并加了一条不变式测试：Gemini 的每一档都必须能约成服务端认的比例
    2. **平手被浮点末位决定**：`log(1.75)` 与 `|log(1/1.75)|` 只差 1.1e-16，同一组候选换个顺序就换个结果。已把差距量化到 1e-9，并留了一条判别用例（方图目标下横竖档同样远，平手由顺序决定 —— 换成差值度量就永远偏向竖档）
    3. **`auto` 的判定有两个来源**：厂商级 `autoSize` 与档位列表。`openai` 的 `autoSize` 是 true（那是给 gpt-image-1 的），而 `dall-e-3` 的档位列表里没有 auto —— 两处各判各的就会放行一个必被拒的值。已统一为「只看档位列表」
  - 顺带补掉一个洞：从提示词库/历史复现时套用 `auto`，落到认枚举尺寸的厂商（豆包、dall-e-3）上会被原样采用，而它们收到枚举外的值直接 400 —— 现在由 `acceptableSize` 拦下并保留当前值
  - 验证（单测 30 条，`api.test.ts` 共 39 条）：手填尺寸归一的容忍与拒绝、不认 auto 的厂商要摘掉 auto、OpenAI 两代模型的档位差异、不限尺寸厂商拿到常用值、Gemini 每档都能约分、默认档不能拿字面量 auto 当基线、按比例挑选（含平手判别）、逐模型退回第一档、种子（空/认不出/超范围/厂商不认/unknown 照发）、扩展参数门控、`acceptableSize` 四种情形
  - **有意的行为变化**：① Gemini 选 16:9 / 9:16 现在真的会发 `aspectRatio`（原来不发、竖幅退化成横图）；② 角色取景尺寸的度量从差值改为对数距离（只在平手时可能换一档）；③ 套用历史尺寸时不合法的值不再被采纳（保留当前值，而不是发出去被拒）
  - 端到端兜底：`npx vite build` 通过

> 用法（先起服务）：`npx vite preview --port 4173 &` 再
> `node scripts/measure-history.mjs --url http://localhost:4173/ --records 500`
> 也可当回归门用：加 `--max-dom-nodes 6000 --max-ms 400 --max-heap-mb 20`，超了就非零退出。

- [x] **T3.1 历史页分段渲染**

- [x] **T3.2 启动分页读取 —— 实测后判定「不做」**
  - 原计划：`loadHistory / loadPrompts / loadCharacters` 一次性 `getAll()` 改成先取最近 N 条
  - **实测结论：启动没有随库变大而劣化，不值得为此增加复杂度**

    | 库规模 | 启动到首页图墙首块 |
    | --- | --- |
    | 500 条 × 2 图 | 87.6 / 100.1 ms |
    | 2000 条 × 4 图（8000 张） | **104.9 ms** |

    原因：IndexedDB 反序列化记录时并不把图片字节读进 JS 堆（`Blob` 只是句柄），而首页图墙只渲染 12 块 —— "库变大就卡"的两个通常来源在这里都不成立
  - **更重要的理由：分页读会破坏筛选的正确性**。「Marked」与作品集筛选必须看到**完整**集合，只读最近 N 条会让筛选静默缺项、计数虚低。真要分页，得先有一张只存 `id / createdAt / marked / collectionId / prompt` 的轻量目录表（写入时维护），让筛选走目录、字节按需取 —— 那是一次带迁移的架构改动，不该在没有数据支撑时做
  - 触发条件（记在这里，够线再做）：启动到首块 > 300 ms，或记录数达到万级。届时按上面「轻量目录表」的路子做，并复用本轮的测量脚本验证
- [x] **T3.3 `backfillThumbs` 空闲化 —— 真正的问题不是卡，是慢**
  - 先量了再改：**主线程一个长任务都没有**（>50ms 才算，256/1024px 图都是 0 个）—— Chrome 的解码与编码本来就在别的线程，所以「逐张解码会卡住页面」这个前提不成立
  - 真问题是**吞吐**：每条固定等 300ms，且一次会话只补 `BACKFILL_MAX = 60` 条 → 500 条老记录要开九次页面才补得完，实际等于永远补不完；而缺缩略图的记录在图墙里要按原图解码，正是缩略图当初要解决的那件事
  - 改动（[api.ts](../src/api.ts)）：`thumbsToFill` 先筛后取 + `shouldProcessNow` 余量判断 + `nextIdle`（`requestIdleCallback`，`timeout: 1000` 兜底；没有它的环境退回定时器）；上限 60 → 400。节奏交给浏览器：有空就多做几条，用户一滚动/点击立刻让位
  - **顺带修掉一个逻辑缺陷**：原来是「扫前 60 条、跳过不缺的」，于是前 60 条都补好时什么也不做、后面的照样缺。改成先筛后取
  - 验证（实测，500 条无缩略图的老记录、1024px 图、**同样静置 5 秒**）：

    | 指标 | 改动前 | 改动后 |
    | --- | --- | --- |
    | 补好的缩略图 | 16 条 | **243 条**（≈15×） |
    | 长任务数 / 总阻塞 | 0 / 0 ms | **0 / 0 ms**（没有变卡） |
  - 验证（单测 9 条）：只挑缺的且保持新→旧顺序、前面都补好时照样补后面的、上限只限制补的条数不限制扫描范围、尺寸缺一项也算缺；空闲余量的三种情形（够 / 不够 / 被 timeout 叫起）
- [x] **T3.4 画布编码 —— 实测后判定：不需要 Worker，把同步 API 换掉就够了**
  - 探针实测（同一台机器，合成噪声图）：

    | 编码方式 | 主线程阻塞 | 产出 |
    | --- | --- | --- |
    | `toDataURL('image/jpeg')` 2560×1440 | **34.2 ms 全同步** | 1.77 MB |
    | `toDataURL('image/png')` 2560×1440 | **102.3 ms 全同步** | 9.08 MB |
    | `toBlob` + `FileReader`（同尺寸） | **2.2 ms**（编码在别的线程） | 字节完全一致 |

    4K 下差距更大：JPEG 82.8 ms、PNG 238.7 ms 全同步 —— 60fps 一帧只有 16.7 ms，这就是「点完按钮卡一下」的来源
  - 结论：**编码本身早就不在主线程上，问题只是用了同步那个 API**。所以不做 `OffscreenCanvas` + Worker（那是为"编码占满主线程"准备的），只把 `toDataURL` 换掉：`encodeAt` / `refShot` / `scaleDataUrl` 一律走 `toBlob` + `FileReader`（[CanvasEditor.vue](../src/components/CanvasEditor.vue)）。只剩步骤条那张 64px 小图仍用 `toDataURL`（微秒级，注释里写明为什么可以留）
  - 这同时修掉了我自己在 T1.1 引入的回归：那次写的 `encodeAt` 用的正是同步 `toDataURL`
  - 验证：探针数字（上表）+ `grep toDataURL` 在画布编辑路径只剩 64px 那处 + typecheck 与 106 个单测通过 + 全量复测无回归（历史页 3,016 节点 / 148 ms / 10 MB，均在预算内）

    2. `ChatStreamOpts`（[api.ts](../src/api.ts)）加 `lastAt?: number`；**`nowLocal` 不由调用方传** —— 它是"此刻"的事实，晚一拍都不对，`chatStream` 里现场 `localStamp()`
    3. `chatSystemPrompt(character, memory, time)` 把时间块插在 `Who you are` / `How you behave` 之后、`What has happened so far` **之前**（`CHAT_TIME_CHARS = 200` 截断，**不过 `chatOneLine`** —— 它会把换行压成空格，而那两行正是靠换行分开的）
    4. `CHAT_RULES` 补一条：知道时间也只在真的相关时提

  - 决定：
    - **时区归前端，措辞归服务端** —— 服务端不知道用户在哪个时区，而"改措辞不该要求用户重装前端"是这个仓库既有的分工（与人格字段同一条）
    - 间隔由 **epoch 差**算，与夏令时无关；"现在是几点"从 RFC3339 的偏移推回来，不依赖服务器时区；**星期几用 `Date.UTC` 算**，与两端时区都无关
    - **只认带 ±HH:MM 偏移的形状**：`Z` 与光秃秃的 `2026-10-05T23:41` 都不收 —— 没有偏移就说不清是哪个时区的 23:41，而这一块宁可没有
    - **不存在的日期不认**（`Date.parse('2026-02-31')` 会悄悄滚到 3 月 2 日，实测过）：拿 UTC 拼回去逐项比，否则 system 里会出现一个假的日期
    - 坏偏移（`+99:99`）会让 `Date.parse` 给 `NaN`，而 **NaN 参与比较全部为假** —— 不拦的话那句会变成 `last spoke NaN days ago`。基准值先验一次
    - 不精确到秒；2 分钟以内不算"上次"；超过 30 天不报间隔；未来时间不报（不写"昨天"也是同一个理由：26 小时前按日历算并不是昨天）
    - 认不出来**整块丢掉、不报错** —— 手搓的请求、老前端、时钟坏掉的机器都走这条退路，为一个装饰性字段把整轮对话挡回去是把主次弄反了

- [x] **T6.2 打字节奏器**
  - 依据：设计 §3.2.2 —— 唯一一条不改模型、不改提示词、不改成本就能去掉机器感的改动
  - 现状：`onDelta: (delta) => { if (reply) reply.content += delta }`（[App.vue#L1526](../src/App.vue#L1526)）—— 增量到即渲染，所以吐字速度**就是**模型的吐字速度，而模型是匀速的

    1. 新增 [lib/typing.ts](../src/lib/typing.ts) —— 一个**不碰计时器、不碰 DOM、不读时钟**的纯状态机：`nextChunk(buf, seed, budget)`（这一刻放到哪、放完等多久）+ `Pacer`（`push` / `take` / `flush`）。什么时候再问一次由调用方拿返回的 `wait` 决定 —— 于是整套节奏能在几毫秒里断言完，不必靠 sleep

    - **它调的不是"人的打字速度"，是"标点后面的停顿"**。真人中文一秒两三个字，按那个速度一句八十个字要打半分钟 —— 那不叫像人，叫坏掉。所以只压标点：句末 150ms、逗号 80ms、换行 260ms（各有 0.7~1.3 的抖动）

    - 抖动来自 `msg.id` 的哈希而**不是** `Math.random()` —— 重播一致、可断言
    - **标点后紧跟的收尾符号一起放**（`走吧。」` 里的 `」`），否则引号会在停顿之后孤零零地冒出来
    - **三处必须 `flush()`**：收尾（紧接着就落盘，扣着就存进半句）、按 Stop、页面被切走（`document.hidden` 之后转成不压模式，直接贴）
    - 节奏器**只活在渲染层**：落库仍是完整正文（[App.vue#L1574](../src/App.vue#L1574) 一次写入那条不动），重进页面不会重演打字

    - **一个字都不能丢**（第一组，全是这条）：分片流进来一路放完 = 输入；中途 Stop（`flush`）后"已放出 + 剩下"仍 = 输入；放出的永远是收到内容的**前缀**（不多、不乱序）；`flush` 幂等
    - 节奏落在标点上：一次只放一句 / 无标点整段放 / 标点正好在末尾时不等 / 收尾符号跟着走 / 句末 > 句中、换行 > 句末 / 单次停顿有上限

    - 抖动：同 id 两次同一套节奏；不同 id 节奏不同
    - **按驱动协议整体跑一遍**：上游每 10ms 推 3 个字、定时器按 `wait` 唤醒，两条时间线交错推进 → 一字不丢且总多等 ≤ 预算；以及"上游推完时手里还扣着字，收尾必须冲出来"
  - **覆盖边界（如实记）**：`--probe-chat` 的对话是**播进库**的（不走流式），所以节奏器**拿不到浏览器端到端覆盖**。上面那组"驱动协议"用例是它最接近端到端的替代：它把协议当整体跑，能抓住"收尾漏冲""定时器重排错"这一类真 bug，抓不住的是"接线有没有接上"（那一处的兜底是 typecheck + 手测）
  - 验证（手测清单）：真聊一轮 —— 句末有可见的停顿、Stop 之后立刻停住且文字完整、重进页面**不重演**打字、切到别的标签再回来不出现"一次性冒出半屏"
  - 风险与**待查**：节奏的可见度取决于上游吐字的连续性（上游一个 token 一个网络往返时，停顿本来就在，节奏器基本不起作用）。另一头：**首字节如果本来就慢，这条的收益更小** —— T6.0 的数字拿到之后要回来看一眼，必要时把 `PACE_BUDGET_MS` 调小（甚至关掉）

- [ ] **T6.9 钉住记忆**
  - 依据：设计 §3.1.2；兑现 [角色对话功能设计.md](角色对话功能设计.md) §7.11 里那条**仍未解决**的风险（用户手改过的记忆会被下一轮压缩重写）
  - 改动：`ChatSummary` 加 `pinned?: boolean`（**不加索引、不改 keyPath，所以不需要升 `DB_VERSION`**）；`maybeSummarize` 在 pinned 时**不把旧记忆喂回模型**，只让新消息往后接；记忆块上多一枚"钉住"
  - 决定：钉住之后那段文字**停止进化** —— 这是"可信"与"会成长"的取舍，所以要**由用户按下去**，不能替他决定；`upToAt` / `covered` 一个字不动（它们说的是"哪些消息进过了"）

### 这一轮不做

| 项 | 为什么 |
| --- | --- |
| **主动消息** | 准入条件见设计 §3.3.3（权限由角色在对话里申请、默认关、内容挂真实锚点、只做应用内）。**不满足就先不做** |
| **自定义音色** | 设计已定（[角色对话功能设计.md](角色对话功能设计.md) §8.5），但那是一条**引擎替换**链路（缓存 / 中断 / 计费 / 合规），与这一轮的"表现层"不共用代码，单独排 |

| **语音输入** | 维持"先放着"（§8.4）：支持面窄、识别质量不稳 |
| 伪造类拟人化（假在线 / 假忙 / 故意错字 / 撤回） | 设计 §5 的反模式。**本身就是破功点**，不做 |

### 验收口径

这一轮的验收**不是**"更好看"，而是设计 §6 那套：

| 类型 | 指标 | 怎么取 |
| --- | --- | --- |
| 破功（主指标） | 每会话 `notice` 触发次数 | 手测计数（T6.0 不做面板）；探针里凡有提示条断言的，顺带记一笔 |
| 在场 | 首字节耗时 | T6.0 的 `console.debug` |
| 行为 | 人均轮次/会话、回访间隔、角色切换率、重生成率 | 本地无法自动采集（无埋点、不上报，这是本项目的既定取舍）→ **定性复述**代替：关掉页面十分钟，复述的是"它说了什么"还是"界面怎么用" |

**最后一条要写清楚**：这个项目**没有、也不该有**行为埋点（本地优先、无账号）。
所以"沉浸感有没有变好"最终只能靠**手测 + 复述**判断，上表那三行行为指标是**设计目标**，不是可采集的看板。
把它写成看板会是这一轮最容易犯的错。

### 顺带记下的一处测试基建问题

`probe-chat-photo.mjs` 的 `finally` 里有 `await once(app, 'exit')` ——
子进程要是**早就崩了**，这个 await 永远不 resolve；而那时事件循环里已经一个句柄不剩，
Node 于是**静静地退出、退出码还是 0**，探针只打了一行标题就没了，连服务端 stderr 都来不及打。
这次排查它花的时间比修 bug 本身还长。现在先判 `app.exitCode === null` 再 await。
（之所以会撞上：`str.replace(..., 1)` 用了一个**不唯一**的锚点 `let upstream = null`
—— 那份文件里有六处，`const who` 被插到了**另一个端点**里，
chat 那条于是抛 `ReferenceError`。锚点必须唯一，这跟"探针要能自己说话"是同一条教训。）

## Wave G · 自拍判对了（T6.20）

> 依据（用户 2026-10-05 晚）："角色对话生图的时候，对于自拍的理解总是不好，
> 老是会生成他拍视角的图片。"

### 根因：视角被交给了信息**更少**的那一层

这条链上"谁拿的相机"当时由**摄影指导**（一次文本调用）判（见
[角色配图构图与光影设计.md](角色配图构图与光影设计.md) 的决定九）。而它拿到的
**只有一行场景串** —— 看不到对话、看不到聊天模型写标签时的意图。两个后果都实测到了：

1. 场景只写"我在阳台"（设计文档自己的例子）时，它按自己那条规则
   ——"somebody else is holding the camera, **or when nobody could be**"——
   判成 `third`。于是**绝大多数本该是自拍的图都成了他拍**；
2. 场景**明写"自拍"**时，它写的 `Shot: third` 还会把那个唯一的硬证据覆盖掉
   （`applyDirector` 当时就是这么设计的：视角一变就重拼整套模板）。

再加上第 0 层的问题：标签当时只有"在不在画面里"这一位（`self:`），
聊天模型**根本没有地方**说"这是我举着手机拍的"。

### 改法：让唯一知道答案的那一层说话

- [x] **T6.20 视角进标签**
  - `server/index.js` 的 `CHAT_RULES`：三个前缀各是什么（`selfie:` 相机在自己手上 /
    `third:` 相机在别人手上 / 不写前缀 = 画面里没有人），并明说
    **"拿不准就写 `selfie:`"**；
  - `server/chatTags.js`：`parsePhotoIntent` 认 `selfie:` / `third:`（`self:` /
    `me` 那几种保留原义：在画面里，但相机没说），`splitTags` /

别人拍那半画出来更像一张通用相机照。而且他拍那一档当时**没有硬约束层**，

- `lib/chatPhoto.ts` 的 `third` 模板：medium 改成

  自拍"相机在它自己手上" / 他拍"手机在别人手上"）—— 它们本来就是同一件事：
  "这一档不可让渡的那一句，摄影指导换不掉"。原先分成 `noPeople` 与 `selfiePin`
  两个字段，是同一条规则的两份实现；
- `shotBrief('third')` 与 photo 档的系统提示都改成说"**手机**在别人手上"，

验证：`chatPhoto` 新增一条"两档读出来都是手机拍的"断言（自拍占 `/phone front

## Wave H · 设定图的"正面"要真的是正面（T6.21）

> 依据（用户 2026-10-05）："创建角色的时候，如果上传的参考图是侧面图，
> 则生成的正面图也是侧面的。"

### 根因：参考图是最强的机位来源，而那句提醒一处分都没落

正面的 suffix 一直写着 `single front-facing headshot` —— 也就是说**提示词没错**。
错的是它一个人顶不住：这一步走的是图生图，而 i2i 的默认行为就是**保住输入的姿态**，
一句 `front-facing` 拗不过一张侧脸底图。

这正是 [角色配图构图与光影设计.md](角色配图构图与光影设计.md) **决定五** 早就写下的判断
（"参考图同时是同一张脸的唯一保证，又是最强的机位与光线污染源"，所以提示词里要**明确写出来**
"只取这张脸、不要它的人像构图"）。而那句话当时只落进了**提示词改写**那条路
（`server/index.js` 的 `REF_NOTE`，只给 `/api/enhance` 用），**没有落到设定图上** ——
设定图的提示词是在 `App.vue` 里手拼的 `[characterDesc(c), view.suffix]`，没有第二句。

而正脸是整条链的锚：它歪了，其余四张（都以它为参考图）跟着歪，封面/头像也跟着歪。

### 改法

- [x] **T6.21 设定图的提示词收成一处纯函数**
  - `api.ts` 新增 `characterViewPrompt(c, kind, hasRef)`：`characterDesc` + 该格 suffix
    + （有参考图时）`REF_IDENTITY_ONLY`。`App.vue` 的 `genCharView` 改走它 ——
    提示词从此只有一处出处，也才测得了；
  - `front` 的 suffix 把"正面"拆成**可判定**的条件（两眼齐平且都可见、鼻尖朝向镜头、
    头不转不歪）+ 三个否定（profile / side view / three-quarter）+ **把失败场景直接写进去**
    （`the face turned front-on even if the reference image shows the person from the side`）；
  - `REF_IDENTITY_ONLY`：参考图只管"这个人是谁"（脸、特征、头发、体型），
    **忽略它的姿态、机位与光，并且不许跟着它朝的方向抄**。有参考图才追加 ——
    纯文生图时它会去找一张并不存在的图；
  - 尾注：**转面那一格（Angles）不受影响** —— 它要的正是左右正侧与俯仰，
    "别抄姿态"指的是别抄**参考图**的姿态。

- **验证**：`api.test.ts` 新增 9 条（正面那几个可判定条件、三个否定、失败场景那句、
  参考图那句"在不在/在最末"、五格都带上它、转面那格仍然要四个方向、
  认不出的 kind 给空串、老角色退回 desc）；typecheck + **498 条单测** + build + 探针全绿。

- **没覆盖到的**：真模型认不认这几句，只能靠实际生成一次看。若某个模型仍然照抄侧脸，
  下一手是在那一步加"重跑一次、第二次把话说得更硬"，而不是继续加词 —— 到那时再说。

- **顺带记一句 UX 判断**：向导第 1 步那句 "One front-facing headshot." **没有改**。
  它说的是"理想输入"，而真正要修的是"输入不理想时也不该歪" ——
  在没实测过之前，不该在界面上承诺"侧脸也行"。

## Wave I · 特写判对了（T6.22）

> 依据（用户 2026-10-06）："感觉角色对话生图对于特写图还是不太能理解。"
> 追问后收窄成一句可验收的："**让角色拍特写图，总是变成自拍。**"

### 根因：景别根本没有归属

Wave G 把"**谁拿的相机**"从摄影指导手里拿回来、交给了聊天模型（`selfie:` /
`third:`）。但一张照片的取景还差一格 —— "**离得多近**"，而那一格从来没被单独
拿出来过：它**写死在模板的机位句里**（自拍那句"脸和肩膀占满上半幅"是半身，
他拍那句"全身和手都在画面里"是全身）。

于是"特写"这个需求在整个链路里只剩一个落点：场景串里的那两个字。而它干的事
恰好是反的 —— `close-up` / `特写` 当时在 `LENS_RE` / `LENS_ZH` 里，
命中就把**景深那一句整条删掉**（那正是特写最需要的一句）。

拼出来是这样（真实输出，不联网可复现）：

```
… close-up of my eyes, looking right at you, …
selfie taken at arm’s length, front camera,
face and shoulders filling the upper half of the frame, …
the arm holding the phone partly visible in frame,
… the place clearly readable right behind the shoulders, close enough to touch, …
```

**"特写"与"半身自拍"在提示词里正面打架**，模型挑的是那条说得最具体的。
用户看到的因此是一张臂展自拍 —— 与 Wave G 修好的那件事（视角）不是一回事，
它是视角**修好之后**才露出来的下一层。

还有一处是 Wave G 的措辞反噬：规则里"**拿不准就写 `selfie:`**"，
于是模型拍桌上那杯咖啡时也写 `selfie:` —— 它把"我拍的"读成了"自拍"，
提示词里就长出一张脸。

### 改法：把景别做成正交的第二位，并钉死"缺省＝从前"

- [x] **T6.22 景别进标签，与视角并列**
  - `server/routes/chat.js` 的 `CHAT_RULES`：新增一条 —— 什么时候写 `close:` /
    `full:`（不是惯常距离时才写），并明说
    **"拿着的东西 / 正看着的东西的特写不是自拍"**，人不在画面里就只写 `close:`；
    结尾再点一句"他们说特写就是特写，不是把脸伸出去拍的一张"。
  - `server/chatTags.js`：`parsePhotoIntent` 认第二枚前缀（顺序不挑），
    `[photo:selfie:close:…]` 与 `[photo:close:…]` 都认；`splitTags` /
    `stripStandaloneTags` / `done` 事件多带一个 `photoFrame`。
    **景别那一类必须要求一个分隔符** —— `close` / `medium` / `full` 本身就是常用词，
    不要求的话 `[photo:close to the window, the rain]` 会被剪成 `to the window, the rain`；
    长写法还要排在短的前面，否则 `full-length:` 被 `full` 吃掉一半。
  - `types.ts` / `api.ts` / `App.vue` / `useChat.ts` / `useGeneration.ts`：
    与 `photoShot` **完全同路**（流式带上、存进消息、重画与导出都带上）。
  - `lib/chatPhoto.ts`：`ChatFrame = close | medium | full`，
    `TEMPLATES` 的机位/景深/环境按 **(视角 × 景别)** 查表，
    但 `FRAMING` 表里**只登记"不是缺省的那两档"**；缺省值按视角给
    （自拍半身、他拍全身、空镜中景），于是**这一位不存在时拼出来的提示词逐字等于从前那三句**。
    判据四级：标签 > 场景明写（特写 / 半身 / 全身三组词，中文那侧用
    `全身(?!心)` 挡掉"全身心投入"）> 这一档的缺省。
  - `lib/photoDirector.ts`：新增 `frameBrief(frame, self)`，与 `shotBrief` 并列，
    把景别当**事实**告诉它；`DIRECTOR_SLOTS` 一个词没动 ——
    景别进的是独立的 `frame` 层，摄影指导结构上就换不掉
    （与 Wave G 给视角加 `pin` 是同一个解法）。

- **验证**：typecheck 零报错；**559 条单测全绿**（+55：`chatPhoto` 的景别判据、
  模板覆盖、`frameLine`；`photoDirector` 的"改不了景别"；`chatTags` 的新前缀）；
  `npm run build` 通过；探针全绿（新增用例 3c：带前缀的 / 空镜的 / **半身的** /
  没说的 / **中段那枚标签** —— 两条路的字段是分开解构的，漏一处就静默降级）。

- **交出去之前自查了一遍，抓出三处真错**（详见构图文档 §10.6）：
  ① 特写那档把"手臂伸直"与"贴到眼睛那么近"写在了一起，物理上互斥 ——
  改成"一只手举近"，而"相机在它自己手上"由 `pin` 那层保着，另外三个自拍信号
  一个没少；② 全身那档凭空添了一面镜子（镜子是场景里的实物，不许编）；
  ③ **半身那一档是死代码** —— 他拍那档的缺省就是全身，而场景词表与
  `CHAT_RULES` 都没有"半身"的入口，"拍张半身照"这句话落不到任何一档。
  第 ③ 条是这一轮最有价值的一次自查：**三档建好了不等于三档都通**。

- **三条钉验收线的单测**：
  1. 「让角色拍特写，不许退回一张臂展自拍」——特写那档的提示词里
     **半身自拍那三件套一件都不许在**；
  2. 「**缺省那一档逐字不变**」——两条路拼出来的必须是同一串，不是"差不多"。
     这是这次改动唯一真正的风险；
  3. 「摄影指导拉不回来的那一张，特写还在」——它写一句"wide shot"照样被换掉
     `camera` 层，而 `frame` 层一个字没动，且排在机位之前（顺序就是权重）。

- **老数据不受影响**：库里已有消息没有 `photoFrame`，那一位留空 → 按场景判 →
  再不行落回缺省（＝从前的行为）。

- **没覆盖到的**：真模型照不照新措辞写 `close:`、以及特写最终长什么样，
  只能靠用起来看 —— 探针里的"模型"是写死的假上游。
- **同日晚些时候补上了**（见上面总览那一行）：`shotViewOrder(shot, frame)` ——
  特写把全身像摘掉（正面像打头、`closeups` 紧跟），全身把全身像提到最前，
  半身不登记。`closeups` 那张 2×2 网格这次**只在特写下进到第二位**，没有推到
  第一位：头一张留给唯一一张单张人像（正面像），版式先验不往上堆 ——
  背景图那条路吃过一次亏（详见 [角色配图构图与光影设计.md](角色配图构图与光影设计.md) §十）。
