## 0. 三条共同的边界（先划红线）

这三条不是免责声明，是**架构与合规的硬约束**，后面每一段设计都受它管：

1. **本地优先意味着没有可信的后台时钟。** Kairo 无账号、无服务端数据库、无常驻进程（README「信任边界」）。所以「主动联系」在物理上只能发生在**应用被打开、且页面可见**的时候——浏览器在页面关闭时不可能替角色发消息，Service Worker 定时推送需要服务器、与本地优先冲突。T6 的一切设计以此为准：**不承诺 PRD 之外的离线触达**。
2. **关系与偏好都不许改写人格。** PRD §3.2-D 反复强调「偏好是指导，不是重写人格的命令」，§3.2-C 强调「核心人格稳定」。T1 已经在服务端把这句边界写死（`chatGuidance.js` 里那句 `It never overrides who you are`）。T5 的关系注入必须沿用**同一句式、同一位置纪律**：关系改的是「你们此刻的相处温度」，不是「这个角色是谁」。
3. **颜色与数字不做装饰、不解锁内容。** PRODUCT.md 反参考里点名「dashboard 式大数字与指标卡」。T5 要「等级/进度对用户可见」，但可见 ≠ 一排仪表盘百分比；T6 的频率上限 ≠ 消息数排行榜。落地时按「克制 · Editorial」表达（三档命名 + 一条细进度，而不是三个 0–100 的大数字）。PRD §3.2-C 明写「等级不解锁内容」，所以**没有任何 UI 处把关系等级做成「解锁 X」的门**。

## 1. PRD §9 未拍板项：推荐默认值

§9 把「关系维度权重与阈值」「主动联系默认频率/免打扰」「虚拟生活」列为尚未拍板。按用户要求，这里**先给一版推荐默认值把设计做完整**，落地时数字改一处常量即可。每条形如「推荐值 —— 理由 —— 改动点」。

### 1.1 关系维度（喂给 §3.2-C）

| 项 | 推荐默认值 | 理由 |
|---|---|---|
| 维度 | 三轴：`familiarity`（熟悉）· `trust`（信任）· `affection`（亲近） | PRD 举例就是这三项，不再加第四轴（认知负担） |
| 内部刻度 | 每轴 `0..100` 整数 | 便于算进度条；对用户**不暴露裸数字**，只暴露下面三档标签 |
| 对用户可见档位 | 每轴三档：`Getting to know` / `Warming up` / `Close`（阈值 34 / 67） | 三档与 PRODUCT「不做大数字」一致；阈值取三等分，好记 |
| 每次评估的单轴变化量 | `Δ ∈ [-3, +8]`，四舍五入取整并 clamp 到 0–100 | 上限 +8、下限 −3：亲近是攒出来的、不是崩出来的；负值只用于「明确的疏远信号」，刻意给得小 |
| 结构约束 | `affection ≤ trust`；`trust ≤ familiarity`（取 min 封顶） | 挡「刚认识就掏心掏肺」的失真；也挡模型把 affection 单独拉高 |
| 缺席衰减 | **不做**。时间流逝只冻结、不扣分 | PRD §3.2-C 硬要求「不因缺席扣减」；天然满足即不写衰减函数 |
| 驱动源 | 只在「压了一批记忆」时评估（见 §2.3 触发点），**不逐条消息算** | PRD「受有意义互动影响而非消息数」。压记忆＝一段实质对话滑出窗口，正是「有意义」的天然节拍 |

改动点：`src/lib/relationship.ts` 顶部的 `DIM_MAX / STAGE_THRESHOLDS / DELTA_MIN / DELTA_MAX` 四个常量 + `clampOrdered()` 里的不等式。**改数字不碰链路。**

### 1.2 主动联系（喂给 §3.2-J）

| 项 | 推荐默认值 | 理由 |
|---|---|---|
| 全局每日上限 | 默认 **1 条/天**，可调 0–3 | PRD 给 0–3 区间；默认取 1，「产品主动出现」但绝不轰炸。这是**所有角色共享**的配额（PRD 明确共享） |
| 角色优先级 | 三档：`Quiet` / `Balanced` / `Eager`，默认 `Balanced` | 权重 `{0.2, 0.5, 1.0}`，决定共享配额里谁更有资格发 |
| 免打扰时段 | 默认**关**；开启时默认 22:00–08:00（用户本地时区） | 时区只有前端知道（`chatTime.js` 的 `localStamp` 已经带偏移），判 DND 在前端算 |
| 通知正文 | 默认**只显示角色名**，正文可选（每角色开关） | PRD §3.2-J 隐私默认；避免在锁屏泄露私密对话 |
| 未回复处理 | 同一角色**连续 2 条未回**→ 自动降为 `Quiet`，直到用户回话才恢复；**不降关系** | PRD「未回复不降关系」。这是「相处礼仪」层，不是关系状态层，刻意分开放在 `proactiveGate` |
| 触发时机 | 应用打开 / 页面转可见时评估；可见期间软轮询**不早于 6 小时** | 本地无后台。`6h` 与情绪窗 `CHAT_MOOD_HOLD_MS=6h`（`chatMood.js`）同一把尺子，隔夜才算「有新东西想说」 |

改动点：`src/lib/proactiveGate.ts` 顶部 `DAILY_CAP_DEFAULT / PRIORITY_WEIGHT / QUIET_HOURS / REPLY_COOLDOWN / MIN_GAP_MS`。

### 1.3 虚拟生活（喂给 §3.2-G）

| 项 | 推荐默认值 | 理由 |
|---|---|---|
| 话题来源 | 角色 `persona.interests` / 新增 `habits` / `goals`（additive 字段） | PRD 要求「稳定兴趣/目标/习惯」，但不做后台模拟 |
| 分享频率 | 走 T6 消息通道；资格权重 = 关系 `affection` 档 × 角色优先级 | 不新造一套调度，复用 §3 |
| 虚实分明 | 只能分享角色**自己**的虚拟日常；**绝不虚构发生在用户身上的现实事件** | PRD §3.2-G「不做复杂后台模拟、虚实分明」；`memorySection` 已有一句「别把推断说成他讲过的话」，同理 |

## 2. T5 · 关系状态系统

### 2.1 数据模型（additive，**零迁移**）

关系状态**挂在 `Character` 上、走 localStorage**，与 `origin` / `pinned` / `staleViews` 完全同一条路子（见 `types.ts:524` 那三项的注释——「additive 字段，不动 `DB_VERSION`，新字段被 `JSON.stringify` 自动带上」）。

```ts
// src/types.ts 追加
export interface RelationshipState {
  familiarity: number   // 0..100
  trust: number         // 0..100
  affection: number     // 0..100
  updatedAt: number     // 最近一次评估
}
// Character 追加：relationship?: RelationshipState
```

为什么不进 IndexedDB：它是「每个角色一条轻量数值」，与角色目录同生命周期（导出 zip 要带走它、删角色要带走它），条数=角色数，放 localStorage 正合适；放 IndexedDB 反而要为它写一次 `DB_VERSION` 升级与迁移兜底（T2/T10 那两次迁移的代价，本文档刻意避免）。

**读盘收口**：仿 `prefs.ts` 的 `coercePrefs`——写一个 `coerceRelationship(raw): RelationshipState`，非有限数、越界、NaN 一律落回 `{0,0,0,updatedAt:0}`，`affection≤trust≤familiarity` 在这里再夹一次（防御性冗余，同 `selectMemories` 那句「不能指望写数据的人永远记得」）。缺省（老角色）读作**全 0、`updatedAt=0`**（「从没评估过」与「评估到 0」在读法上同形，与 `origin`/`pinned` 那条一致）。

### 2.2 评估链路（复用 enhance 分档）

关系怎么变由模型判（PRD 要「AI 情境判断」），但**判完要过一道基础阈值闸门**（PRD 要「基础阈值 + 情境辅助」）。分工：

- **AI 给方向与幅度** → 走 `/api/enhance` 新增一档 `relationship`，与 `memory` 档同一套「固定前缀行、坏一行丢一行」（见 `memory.ts:parseExtractedMemories`，不用 JSON 的整段理由照搬）。
- **基础阈值做闸门** → 纯逻辑层把模型的 Δ 结合「会话数 / 是否首次 / 已有分值」收口。

`server/routes/enhance.js:55` 的 `enhanceMode` 那串三元分档（顶上第 49 行注释「只认这几档」就是它的白名单语义，落不进的默认按保守档 `quick` 处理）里加一支 `mode === 'relationship'`，`server/enhancePrompts.js` 的 `ENHANCE_PROMPTS` 与 `ENHANCE_TEMPERATURE` 两张表各补一个 `relationship` 键（温度取最低一档附近，与 `summary`/`memory` 同：`0.2`，「编出来的关系比没有关系更糟」）。输出格式：

```
familiarity|+2
trust|-1
affection|0
```

前端 `src/api.ts` 加 `evaluateRelationship(cfg, context): Promise<string>`，形态照 `extractMemories`（`api.ts:2420`，`mode:'memory'` 那段）抄——同样传 `known`（当前三轴分值 + 一句「这段关系现在什么状态」的简报）以免震荡重复。

### 2.3 触发时机（挂在已有的 `onSummarized`）

`useChat.maybeSummarize` 压完一批记忆后调 `deps.onSummarized(id, batch)`，App 当前把它接到 `useMemories.autoExtract`（见 `App.vue:264`、`282`）。**同一根线多接一个下游即可**：

```
onSummarized(charId, batch)
  ├─ autoExtract(charId, batch)            // 已有：抽记忆
  └─ evaluateRelationship(charId, batch)   // 新增：判关系
```

两者互不认识、都尽力而为、都静默（失败就退出，不打断用户）——与 `useMemories` 顶上那段「两条平行的线，刻意不互相引用」同一手法。这一节拍本身就实现了「非消息数驱动」：**只有一次实质对话滑出窗口才评估一次**。

### 2.4 纯逻辑 `src/lib/relationship.ts`（必须有单测）

把「关系该不该动、动到哪、怎么摊成提示词」收在这一层，像 `memory.ts` 那样能被构造数据直接断言：

- `applyEvaluation(prev, deltas): RelationshipState` —— 应用 Δ、clamp、再按 `affection≤trust≤familiarity` 封顶、`updatedAt=now`。**关键不变量**（写测试钉死）：
  - `Δ` 之和再大也不能一次跨两档（防跳级）；
  - 缺席（时间久、`Δ` 缺省）不得使任一轴下降（PRD「不因缺席扣减」）；
  - 纯 `familiarity` 涨不会自动带高 `affection`（要靠显式 delta，挡「聊得多就自动变亲密」的懒惰推断）。
- `relationshipStage(v): 0|1|2` —— 分值→对用户可见的三档。
- `relationshipLines(state)` —— 摊成几行 `- ` 指令（供注入）。
- `parseRelationshipDelta(raw)` —— 读模型那三行，认不出的行跳过（照 `parseExtractedMemories`）。

### 2.5 注入链路（复用 `guidanceSection` 的逐行白名单）

新建 `server/relationship.js`，导出 `relationshipSection(raw)`，与 `chatGuidance.js` **逐行白名单 + 边界话留服务端** 两条纪律一模一样：只收 `- ` 开头的行、行数行长封顶；空则整段不出现（不留空壳）。边界话写死，例如：

> `How close you two have become — this shapes warmth and familiarity only. It never changes who you are, and you do not perform closeness you have not earned.`

在 `server/routes/chat.js:105` 的 `chatSystemPrompt(...)` 里多接一个 `relationship` 入参。**插入位置**：紧跟 `memorySection`（记忆条目）之后、`guidanceSection`（相处偏好）之前。理由沿用该文件现成的分层逻辑——关系与记忆同属「你们之间发生过什么、现在什么状态」这一层，而偏好/关系都是「软指令」要留在硬规则 `CHAT_RULES` 之前；顺序上先铺「记得什么」再讲「熟到什么程度」最后才是「希望被怎么对待」。`/api/chat` 请求体解构里加 `relationship` 字段（`chat.js:222`）。

### 2.6 界面

- **角色详情页**（`CharacterPage.vue`）在资料表前加一块「How close you are」：三轴各一行「档位名 + 细进度条」，**不显示裸 0–100**（§0 红线 3）。进度条复用现有 `.meter`/接触影语言，不引入 dashboard 卡片。
- **聊天页头部**：一枚极简的关系档指示（与现有 mood 药丸区分开——mood 是「这一句的情绪」，关系是「长期状态」，二者本就不是一回事，见路线图 §2-C 附注）。
- 关系**只在对话与角色两处出现**，不进设置、不进记忆中心（那是另一条隐私轴）。

### 2.7 验收（对齐 §3.2-C）

- 每角色独立关系状态 ✓（挂 `Character.relationship`）
- 等级/进度对用户可见 ✓（三档 + 进度条）
- 受有意义互动影响而非消息数 ✓（触发点=压记忆节拍；不变量测试钉死）
- 等级不解锁内容 ✓（无任何门控读取关系值去解锁别的功能）
- 不因缺席扣减 ✓（`applyEvaluation` 不写时间衰减 + 测试断言）

### 2.8 明确不做

- 关系**不驱动出图/语音/其它功能的开关**（§3.2-C「不解锁内容」，架构上也不让别处读它当门）。
- 不做关系的**历史曲线**（要另存时间序列，代价大且 dashboard 化）；只存当前态。
- 不逐轮评估（贵、且会让关系「一天一个样」，反而失真）。

## 3. T6 · 主动联系

### 3.1 本地优先的诚实边界（写进设计，不承诺过头）

「主动联系」只能这样落地，三处都受 §0 红线 1 约束：

- **没有真·后台推送。** 触发点是「应用被打开 / 页面从隐藏转为可见」的那一刻，加上可见期间的软轮询（`MIN_GAP_MS=6h`，且只在页面活着时）。Service Worker + Push 需要服务器与订阅，与本地优先冲突，明确不做。
- **浏览器通知是尽力而为的补充**，不是主渠道：`Notification` 在页面关闭时不可达。主渠道是**站内**——见 §3.4。
- 这套边界要在设置分区里用**一句人话**讲清楚（「角色会在你打开 Kairo 时主动打招呼并留言；关掉浏览器时它没法联系你——这是本地存储的代价」），否则用户以为通知坏了。

### 3.2 数据模型（站内消息：新增 `inbox` store）

主动消息要能跨会话留存、带已读态，量级会涨，所以它**适合进 IndexedDB**，照 v14 `memories` 的加法（`idb.ts:243`——建表 + `createIndex` 都是同步结构操作，无整表重建风险）：

```
DB_VERSION 14 → 15
v15 新增 INBOX_STORE = 'inbox' { keyPath: 'id' }，createIndex('charId')，createIndex('createdAt')
```

```ts
export interface ProactiveMessage {
  id: string
  charId: string
  text: string          // 角色主动说的那句（可能带 [photo:] 意图，见 §3.6）
  createdAt: number
  read: boolean
  delivered: boolean    // 是否已作为一条助手消息并进对话流
  photoScene?: string   // 若它想同时发一张图
}
```

删除角色时连带清 `inbox`（照 `deleteChatOf` / `deleteChar` 那几处按 charId 回收的写法）。**「落盘成功后才更新计数」**：与 `memoryMigrate.ts`「先落盘再写地标」同一条——计数写前、消息没写成，会变成「今天额度已用完但其实一条没发」。

频率/冷却状态是轻量文本、要同步读，走 **localStorage `kimage.proactiveState`**，照 `prefs.ts` 的**「先重读盘上那份再合并」** 写法（多标签页并发不互相抹掉）：

```ts
// { lastContactDay: 'YYYY-MM-DD', sentToday: number, perChar: { [charId]: { unanswered: number } } }
```

### 3.3 生成内容（enhance 新增 `proactive` 档）

复用 §2.2 的 enhance 分档路子，加一档 `proactive`：输入 = persona + 关系三轴（`relationshipLines`）+ 记忆条目（`selectMemories`）+ 上次说到哪 + 此刻时间/间隔（`chatTime`）；输出 = 一句自然的主动开场。温度取中档（它要「像它自己」又要有变化，与 chat 同量级 `0.8` 附近，不是 summary 的 `0.2`）。

- 它是**对话驱动出图以外**的第二个「角色自发起草」场景，但**不新造模型**：内容照样吃 §2 的关系与既有记忆，只是发起方从「用户说话」变成「该不该主动说一句」。
- 这一档同时是 **T8 虚拟生活**的落点（§4），一次建两处用。

### 3.4 投递方式：注入既有对话流（推荐），而非新建收件箱页

PRD 要「站内消息收件箱」。两种形态，**推荐 A（轻量）**：

- **A（推荐）· 注入对话流 + 未读徽标**：一条主动消息**不立即**变成气泡，而是先进 `inbox`。用户下次打开该角色（进 `#/chat/:id`）时，把未投递的主动消息按时间顺序作为「助手消息」追加进对话流（复用 `useChatFlow.pushChatMessage` + `putChatMessage`），并标 `delivered/read`。首页 `ChatRail` / 角色卡上给一枚未读点。这样：① 不新增导航页（nav.ts 六页已够）；② 主动消息天然落在它该在的对话上下文里，能被 `maybeSummarize` 正常纳入后续记忆；③ 未打开时它就是「攒着等你回来的留言」，语义正确。
- B · 独立「消息」页 + `#/inbox` 路由：更贴「收件箱」字面，但要动 nav/router/导航图标，且与「消息属于某段对话」的定位分家。**PRD 并未强制独立页**（§5 只列「主动联系与通知」管理入口），故 A 即可满足；若日后要聚合「所有角色最近说了啥」再升级到 B。

浏览器通知：在 A 之上，当 `inbox` 新增一条**且此刻页面可见、且用户开了通知、且不在免打扰**时，调一次 `Notification`（默认 title=角色名、body 空；每角色可开正文）。**权限只在用户显式打开通知开关时请求**，绝不在首屏弹（PRODUCT「可信」+ 浏览器规范都要求用户手势触发授权）。

### 3.5 频率闸门（纯逻辑 `src/lib/proactiveGate.ts`，必须有单测）

「今天能不能发、发给谁、这条会不会打扰」全部收在这一层，像 `selectMemories` 那样可被构造数据断言：

```ts
canReachOut(state, char, now, opts): { ok: boolean; reason?: 'cap'|'dnd'|'cooldown'|'unanswered' }
nextEligible(state, characters, now): charId | null   // 共享配额里按优先级+冷却选一个
markSent(state, charId, now): ProactiveState
```

不变量（测试钉死）：

- 全局每日 `sentToday ≥ DAILY_CAP` → 任何角色都 `false`（**共享上限**，PRD §3.2-J）。
- 免打扰时段内 → `false`，**不补发**（PRD「免打扰、不补发」）。
- 单角色 `unanswered ≥ REPLY_COOLDOWN` → `false`，直到用户回话；恢复靠用户消息（`useChatFlow` 里 `sendChat` 触发清 `unanswered`）。**此处绝不写任何 `relationship.* -=`**（「未回复不降关系」，测试专门断言闸门与关系两层互不触碰）。
- 与 `MIN_GAP_MS` 比较用同一把 `chatTime` 的本地钟（离线/时钟漂移时 `at>now` 当新鲜，不报错——照 `chatTime.intervalLine` 那条容错）。

## 4. T8 · 角色虚拟生活（复用 T6 通道，不新造系统）

### 4.1 结构化「生活」字段（additive）

`CharacterPersona` 已有 `traits/voice/...`。加两个 additive 可选字段：`habits?`（日常习惯）、`goals?`（近期目标）；`interests` 已可由 `traits` 承载或单列。走 §2.1 同样的「additive、零迁移、`charSpec.js` 行清单里加槽 + 起稿提示词加判据」路子（与 T9 给 origin 加槽完全同构，注意 `characterSpec.test.ts` 里断言行数/必填枚举的那几条要同步）。识图档里 `habits/goals` 一律 `[pending]`（图片读不出一个人的生活，同 `identity` 那条不凭空推断）。

### 4.2 话题＝主动消息的一种内容

**虚拟生活不新造触发器**，它就是 T6 `proactive` 档在选题时的一种倾向：当闸门判「这个角色现在够格主动说一句」，且 `affection` 到档、优先级允许时，`proactive` 提示词让角色**分享一段自己的虚拟日常**（今天做了什么、在想哪个目标），而不是没话找话。频率权重 = 关系 `affection` 档 × 优先级，落在 §3.5 的 `nextEligible` 里，不另立调度。

### 4.3 虚实分明（红线）

`proactive` 提示词写死一条禁则（与 `memorySection` 那句「别把推断说成他讲过的话」同族）：只谈角色**自己**的生活，**绝不把现实事件安到用户身上**、不假装知道用户线下发生了什么。测试：`enhancePrompts.test.ts` 里断言 `proactive` 档提示词含这条禁则（照 `characterSpec.test.ts:240` 那几条 `toContain` 的写法）。

### 4.4 验收 / 不做

验收：话题符合人格 ✓ · 适时（走关系×频率门控）✓ · 不虚构现实事件 ✓（禁则 + 测试）。不做：复杂后台生活模拟、离线时间线演算、连续视觉状态。

## 5. 数据迁移与风险

- **关系（T5）**：additive 挂 `Character`，**不碰 `DB_VERSION`**、不动 IndexedDB。老角色读作全 0。风险≈0。导出 zip 会自然带上（`writeCharacterZip` 序列化 Character）。
- **主动联系（T6）**：一次 `DB_VERSION 14→15` 新增 `inbox` 表。**建表是同步结构操作、安全**（`idb.ts` v12/v13/v14 三次同类型升级的成熟路子），无需整表重建，中途失败风险低。但**升级不可逆**：沿用路线图风险 §3「每条迁移都要有迁移前导出 zip 兜底」——角色导出链路已存在，可直接提示用户。`proactiveState` 走 localStorage additive，无迁移。
- **虚拟生活（T8）**：persona 加 additive 字段，**不碰 `DB_VERSION`**；起稿/导入包的 `origin` 缺省读作 `user`（同 T9）。
- **共同**：`crossTab` 的 `SyncKind` 若要跨标签页同步 inbox/关系，加一个 kind（照 `'memories'` 那条）；不加的话「另一页打开着该角色、这边攒了主动消息」不会即时出现，但下次进该角色会补上（A 方案是进对话时投递，天然自洽），可接受。
