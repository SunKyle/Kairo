## 0. 四条路径一张图

角色生图不是一件事，是**四条独立链路**。它们只共享同一个上游产物：结构化设定。起稿本身不出图，详细创建流程见[角色创建与形象.md](角色创建与形象.md)，本篇不展开。

```
        ┌──────────────────────────────────────────────┐
        │  起稿（文本 / 识图，文本模型，不出图）          │
        │  server/charSpec.js 行定义 ← 唯一真源          │
        └───────────────┬──────────────────────────────┘
                        │ 产出：name + CharacterFields + CharacterPersona（+ origin）
                        ▼
        ┌──────────────────────────────────────────────┐
        │  结构化设定（localStorage + IndexedDB 图）      │
        └───┬───────────┬───────────┬───────────┬──────┘
            │           │           │           │
     ①设定图      ②创作区套角色  ③对话发图   ④对话背景图
  characterViewPrompt  composedPrompt  planChatPhoto  planChatBackdrop
   （默认 5 张，        （用户提示词    （最复杂：六层  （横构图，
     不入历史）           + 面貌）        + 摄影指导）    给字让位）
```

| # | 路径 | 组装入口 | 提示词来源 | 参考图 | 进历史 |
| --- | --- | --- | --- | --- | --- |
| ① | 角色设定图（默认 5 张） | [genCharView](../src/App.vue) | `characterViewPrompt` | 正脸：底图；其余：正脸(+底图) | 否（只存 `char_views`） |
| ② | 创作区套角色 | [composedPrompt](../src/composables/useGeneration.ts) | 用户提示词 + `characterFaceDesc` | 用户挑的 + 角色 4 张 | 是 |
| ③ | 对话里角色发图 | [planChatPhoto](../src/lib/chatPhoto.ts) | 六层模板 + 摄影指导 | 按视角/景别挑，≤4（实发 3） | 是（`source: 'chat-photo'`） |
| ④ | 对话背景图 | [planChatBackdrop](../src/lib/chatPhoto.ts) | 固定横构图层 | 固定 2 张（`full` + `front`） | 是（`source: 'chat-backdrop'`） |

**四条共同的纪律**（写错任一处都会出现"图不像 / 图死板"，但不报错）：

1. **顺序就是权重** —— 越靠前的话对图像模型越硬。「这一张要画什么」永远在「这个人是谁」之前。
2. **只补不覆盖** —— 场景 / 用户已经说过的位，模板不重复写（否则模型挑一处丢掉）。
3. **失败逐层降级，不 reject** —— 摄影指导挂了退回模板，参考图读不出来退回纯文生图。
4. **上限在最后一刻截断** —— 截掉的正是垫在末尾的负面约束，所以上限必须留够（见 `CHAT_PHOTO_PROMPT_CHARS`）。

## 1. 权威定义层：charSpec 与三种投影

### 1.1 一个角色是什么，只有一份定义

**唯一真源**是 [server/charSpec.js](../server/charSpec.js) 的 `CHAR_SPEC_LINES`。它同时喂五个消费方，任何一处漏改都**不报错、只静默失配**。

| 字段 | 含义 |
| --- | --- |
| `group` | `name` / `field`（长相）/ `persona`（人格，只服务对话） |
| `key` | 在 `CharacterFields` / `CharacterPersona` 里的键 |
| `label` | 提示词里那行的标签，**也是前端解析时认的词**（改它等于改协议） |
| `desc` | `<...>` 里那句"这一栏该写什么"；**给对象则分 `character` / `vision` 两档** |
| `always` | 必须有个值，进 "… must always have a value" 枚举 |
| `sheetOnly` | 只喂设定图、不进普通创作提示词（`outfit` / `marks`） |
| `enumValues` | 模型只能从这几个词里挑（`style` / `gender`） |

### 1.2 行的顺序（= 拼提示词的顺序，也是跨图一致性的基础）

```
Name → Style → Gender → Identity → Face → Height → Build → Muscle → Posture
→ Hair → Brows → Eyes → Nose & mouth → Facial hair → Face marks
→ Outfit → Marks
┈┈ 以上 group=field，共 17 行（含 name） ┈┈
→ Language → Personality → Voice → Address → Boundaries → Speech samples
┈┈ 以上 group=persona，共 6 行 ┈┈
```

- **共 23 行**（`CHAR_SPEC_LINE_COUNT`，由数组算出来，不手工维护）。
- `always` 的 13 项：`Name, Style, Gender, Identity, Face, Height, Build, Hair, Brows, Eyes, Nose & mouth, Facial hair, Outfit`。
- 身材刻意拆四行（Height / Build / Muscle / Posture）：写在一行里模型会平均成"中等身材"，而这正是这条链要治的漂移。
- `Style` 排在最前：它是唯一**能被文字左右、又必须在五张图之间一致**的东西。
- **人格六行不进任何出图提示词**，它是给扮演这个角色的模型读的。
- 每行还有一个来源标记槽（`Identity: [user|ai|pending] <...>`），解析侧由 `splitOrigin` 摘掉；起稿产出另带 `origin`。那是《角色创建与形象》的话题，出图只消费值。

### 1.3 派生的纯函数（所有消费方都走它们，不各抄一份）

| 函数 | 产出 | 谁在用 |
| --- | --- | --- |
| [charSpecLinesText(mode)](../server/charSpec.js) | `Name: <...>\nStyle: <...>` 整块 | 起稿系统提示 |
| [charSpecAlwaysSentence(mode)](../server/charSpec.js) | `Name, Style, … and Outfit` | 起稿系统提示（两档不同：识图档少 `Identity`） |
| [charSpecKeys(group)](../server/charSpec.js) | 某组的键序 | `api.ts` 的字段顺序 / 人格键序 |
| [charSpecEnumOf(key)](../server/charSpec.js) | 枚举行 | 前端性别 / 风格下拉 |
| [charSpecOriginRule(mode)](../server/charSpec.js) | 交代三个来源标记（`user` / `ai` / `pending`）的那条规则，**两档判据不同**（文字档问"说没说过"，识图档问"看不看得见"） | 起稿系统提示 |

**五个消费方**（改数组要跟手的地方）：

1. 起稿系统提示的**行正文**（`charSpecLinesText`）；
2. `exactly N lines` 里的 **N**；
3. "… must always have a value" 的**枚举**；
4. 前端解析回填的**标签 → 字段对照表**（[parseCharacterDraft](../src/api.ts) 动态建表）；
5. 前端字段顺序 / 必填枚举 / `sheetOnly` 分组（[api.ts](../src/api.ts)、[characterSpec.ts](../src/lib/characterSpec.ts)）。

> [src/types.ts](../src/types.ts) 的 `CharacterFields` / `CharacterPersona` 键必须与之一一对应，单测 [characterSpec.test.ts](../src/lib/characterSpec.test.ts) 把关。

### 1.4 起稿：上游只做这三件事

这一层**不出图**，但它产出的设定就是后面四条链的输入，写歪了后面全歪。

| 步骤 | 落点 | 要点 |
| --- | --- | --- |
| 系统提示两档 | [enhancePrompts.js](../server/enhancePrompts.js) 的 `character` / `vision` | 行清单都引用 `charSpec`；`character` 允许把没提到的编具体，`vision` 只写看得见的；温度分别 0.7 / 0.4（`ENHANCE_TEMPERATURE`） |
| 回填解析 | [parseCharacterDraft](../src/api.ts) | 剥装饰、`Label: value` 认表、"没有"归一（`facialHair → clean-shaven`）、"跟着走"归一 |
| 回填表单 | [useCharacterDraft.ts](../src/composables/useCharacterDraft.ts) | 名字只在空着时补；`fields` 整份覆盖；人格只在真写出来时覆盖；`aiFilled` 给图例；`draftSeq` / `visionSeq` 防串台 |

### 1.5 同一份设定，三种投影

同一份 `CharacterFields`，按**用在哪条链**投影成三种不同的字符串。**这是整条链最重要的接缝。**

| 投影 | 项数 | 用在 | 空值 / 老角色退路 |
| --- | --- | --- | --- |
| `characterDesc` | 16（全部 field 值 + 自由描述 `desc`） | 设定图 | 退回 `desc` |
| `characterFaceDesc` | 14（= 全部 field − `outfit` / `marks`） | 创作区套角色 | 退回 `characterDesc` |
| `characterAnchor` | 9（`ANCHOR_KEYS`） | 对话出图 | 返回空串，**不退回全量** |

- `characterFaceDesc` 为什么这么细：只给 hair + eyes 时，肤色、骨相、眉形全靠模型从零重编，换个场景就不是同一个人。
- `characterAnchor` 的 9 项顺序即优先级：`face → hair → eyes → brows → noseMouth → facialHair → faceMarks → marks → build`；触上限从后往前丢，`build` 垫底。
- **刻意只留身份，做减法**：全量清单会把表情、姿态、机位一起锁死，交出来的是一张证件照。`style`（属于媒介层，由模板给 `photographic`）与 `identity`（是身份叙事不是长相）刻意不进。
- `faceMarks` / `marks` 是 2026-10-08 并入的：它们是用户亲手写下的身份特征，从前到不了锚点，只剩参考图一条路，而小痣在缩略图里根本看不见。两项常为空，`filter(Boolean)` 滤掉。
- 性别单独走 [characterGender](../src/lib/chatPhoto.ts)，**只在特写那一档**用（见 `partLine`）；把它并进锚点句会改掉这条路上每一张图。

## 2. 设定图路径

### 2.1 拼装公式

[characterViewPrompt](../src/api.ts)：

```
characterDesc(c)  +  ", "  +  view.suffix  +  (hasRef ? ", " + REF_IDENTITY_ONLY : "")
```

顺序：**设定 → 取景 → 参考图那句**。参考图那句压最末，因为它是"怎么读上面那些话"的元指令，排前面会把"画什么"挤下去。

### 2.2 视图表（当前是七条、分两组）

**默认组**是 `front / full / side / outfit / body` —— 只有这一组参与"一次补齐"与"还差几张"的计数；`detail` / `closeups` 属 `extra`，只在详情页的「其他设定图」出现，**不再默认生成**。

| kind | label | framing | group | suffix 要点 |
| --- | --- | --- | --- | --- |
| `front` | Front | square | default | 单人正面头肩、两眼齐平可见、鼻尖朝镜头；末尾三个否定（not profile / side view / three-quarter）+ "即使参考图是侧脸也转正" |
| `full` | Full body | portrait | default | 单人全身站姿，头到脚完整入画 + 少许留白 |
| `side` | — | — | default | 2026-10-15 新增，各自多一条 `suffix`（本表不展开） |
| `outfit` | — | — | default | 同上 |
| `body` | Body | square | default | 2×2 肢体：手 / 前臂 / 腿 / 脚；同一人同光同背景 |
| `detail` | Angles | square | extra | 2×2 头部转面：左正侧 / 右正侧 / 高角度 45° / 低角度 45°（相机高度，不是让人抬头低头） |
| `closeups` | Details | square | extra | 2×2 细部：眼睛 / 皮肤与脸部标记 / 手 / 面料与配件；`no text, no labels` |

**两条禁词（写错就画错）**：

- 绝不出现 `character reference sheet` —— 那是很强的排版概念，模型真会给你拼一张版；
- 不写 `filling the frame` —— 会让人物头顶顶到画面上沿，切掉发型轮廓 / 帽子这些认人线索。改成"完整入画 + 头顶留白"。

**排最后一位的代价**：创作区那条路**不传 order**，取的就是这张表的顺序、而且**只取前 4 张**（`MAX_CHAR_REFS = 4`）—— 所以 `body` 在创作区那条路上自动出局。这正是把它排最后的原因。

> 2026-10-15 的这次对齐只动了"生成哪些格"：`detail` / `closeups` 退役进 extra，新增 `side` / `outfit`。**对话参考图的那几条顺序刻意没动** —— 要不要把新增两格纳进来，得拿真图 A/B 才敢改（[产品路线图.md](产品路线图.md) §7.8）。

### 2.3 REF_IDENTITY_ONLY（有参考图才拼的那句）

> reference images are only about who this person is: their face, features, hair and build; ignore the pose, the camera angle and the lighting in them, and do not copy the direction the person is facing there

- 来由：上传的底图是侧脸，生成的正脸也是侧脸 —— 根因是 **i2i 默认保住输入姿态**，一句 "front-facing" 拗不过它。所以明说三件事（管什么 / 不管什么 / 不许抄朝向），顺序即重要性。
- **写成复数**是有意的：正脸格只送一张，其余格送两张。
- `hasRef = false`（纯文生图）时不拼 —— 说了是噪声，模型会去找一张不存在的图。

### 2.4 参考图怎么选（`genCharView`）

```
source = c.sourceRef ?? (kind==='front' ? c.ref : undefined)
front 格：refBlobs = source ? [source] : []          ← 没底图就是纯文生图
其余格：front 必须在（没有就直接拦下），refBlobs = multiImage==='no' || !source ? [front] : [front, source]
```

- 正脸用**第一步上传的底图**（`sourceRef`），它就是"这个人原本的样子"；老数据退回 `c.ref`。
- 其余格送 `[正脸, 底图]`：正脸定"这张脸"，底图补正面头像交代不了的（发型轮廓、体态、服装轮廓）。
- 不认多图的模型只送正脸 —— 正脸是不可少的那个。

### 2.5 尺寸与生成后的副作用

- [viewSize](../src/composables/useCharacters.ts)：`square → 1:1`，`portrait → 2:3`（`PORTRAIT_RATIO`；9:16 会把人缩小、3:4 容易切脚）；在 `FREE_SIZES` 或 `allowedSizes` 里按**对数距离**挑最接近一档（`sizeClosestTo`）；刻意不沿用创作区当前尺寸。
- 成功才 `putCharView` 落库；**中断保留旧图**（只有成功写入那一刻才作数）。
- 正脸成功后**写回 `c.ref`**（封面 / 头像），底图不被顶掉（另存 `sourceRef`）；重跑正脸后其余格已存在时只提醒、**不替用户删**。
- 状态与中断手柄按 **(角色, 视图)** 维度分开（`charViewBusy` / `charViewControllers`），不同角色可同时生成。

## 3. 创作区套角色路径

### 3.1 拼装公式

```
用户提示词  +  ", "  +  characterFaceDesc(activeCharacter)
```

- **顺序不能反**：用户写的是"这一张要画什么"，角色设定是加在场景上的约束。前段权重更高。
- 没角色时原样返回用户提示词。

### 3.2 参考图

```
refList = [用户挑的参考图, ...charRefSrcs()]   （去重，用户那张排最前）
```

- `charRefSrcs()` **不传 order** → 走 `CHARACTER_VIEWS` 原序（正面打头），上限 4 张。
- 上传的底图**不在** `charRefSrcs` 里（它只为生成正脸服务一次，之后 `c.ref` 已是正脸）。

### 3.3 与提示词改写的关系

- 改写键（`quick` / `creative`）只动**用户提示词本身**；`characterFaceDesc` 是发起生成时才追加的（`composedPrompt`）。
- 改写走 `/api/enhance` 时若 `hasRef` 为真会追加 `REF_NOTE`，并始终追加 `targetNote`（目标厂商的结构偏好）。
- 对比出图（`doRace`）走同一条 `composedPrompt` + 同样的 `refList` 快照，逐模型套各自的能力表。

### 3.4 为什么这条路的清单一个字没动

对话出图换成锚点句时，**没有往 `characterFaceDesc` 上加东西，也没有删它一个字**。创作区要的是"像素级约束"——用户已经把场景说清了，这里只需要把这个人钉死；目标不同，清单的副作用也就不同。两条路各用各的投影，是 §1.5 那张表存在的理由。

## 4. 对话发图路径

这是四条里最复杂的一条。主线：

```
聊天模型报意图（tool call）
   → 服务端归一化成四个扁平字段
   → 客户端确定性拼装（六层）
   → 摄影指导补四位（可选、可降级）
   → 出图 + 落两处
   → 气泡渲染（骨架 → 图）
```

### 4.1 产品决定与协议（tool calling）

#### 四个已确认的决定

1. **图片来源只做「现场生成」**。不发自己的设定图，也不发已有作品 —— 那两条零成本路线明确不做（§8）。
2. **生成的图进历史，并归到角色名下**（2026-10-05 改；原决定是"只活在对话里"，已被推翻）。连带那张单独生成的对话背景图。落点是 `saveChatWork` + `HistoryEntry.source/scene` + [chatWork.ts](../src/lib/chatWork.ts)。**字节两处各留一份**（对话那份在 `chat_images` / `chat_backdrops`，作品那份在 `history`）：两边生命周期不同（清空对话要回收前者，存储清理会淘汰后者），互不牵连才不会因为对方的删除而裂掉。
3. **只在图确实有用时发**：被要求、或场景本身值得看。**不设频率上限**（2026-10-03 改，见 4.1.2）。
4. **排期**：先把 Phase 4 切片 6b 收口，再动这个功能 —— 已按这个顺序落地。

前提是输入侧早已完整：附图键、压到长边 1024、发送时交出 Blob、图存 `chat_images`、消息上只挂 `imageId`、**这一轮自动切到识图配置**、历史里的图不重发（一张上千 token）、气泡渲染与导出 / 导入带图。**所以"多模态"要补的只有输出侧**：角色 → 用户发图。

#### 协议：模型表达意图，客户端执行

模型产出不了图片字节，只能产出**意图**。

- 模型在正文之外调用一次 `emit_message_meta`（[server/chatTools.js](../server/chatTools.js)），参数是 `mood` 与可选的 `photo { scene, shot, frame }`；`shot` 取 `selfie / third`，`frame` 取 `close / medium / full`。
- 服务端累加 `delta.tool_calls` 的分片，在 `done` 事件里下发旧的扁平字段 `photo / photoSelf / photoShot / photoFrame`；正文与元数据是两条独立信道，**不再需要扣尾取意图**。
- 旧方括号标签只在历史消息兼容层清理（[server/chatTags.js](../server/chatTags.js)），**不顶替** tool call；`splitTags` 现在只服务这条历史路径，以及"模型把旧前缀误写进场景"的兜底。
- 客户端拿到 `photo` 后：**先出字，图位占一个固定比例的骨架**，图生成完再贴上。

| 字段 | 含义 | 缺省 / 认不出来时 |
| --- | --- | --- |
| `photo` | 收敛成一行、截到 400 字的场景原文 | 空 = 这一轮不发图 |
| `photoSelf` | 画面里有没有它本人 | 由 `shot` 或场景推断 |
| `photoShot` | `selfie` / `third` / 空 | 空 = 客户端按场景判 |
| `photoFrame` | `close` / `medium` / `full` / 空 | 空 = 客户端按该视角缺省 |

#### 要处理的坑（当前仍成立）

1. **场景描述要限长 + 清洗**。它是模型写的自由文本，会进提示词、可能带引号 / 换行。要截断、去控制字符，并且**永远不当作指令**（只当一段被包装过的描述）。
2. **失败不阻断文字**：出图报错 / 超时就撤掉骨架，改成**一行小字 + 重试**（见 4.7）。**不能只是把骨架悄悄撤掉** —— 那样"没收到图"和"本来就没打算发图"在界面上长得一模一样。
3. **异步与流式的顺序**：图比文字慢得多。不能等图出来才显示文字，也不能让图到达时把已经读完的气泡顶下去 —— 骨架必须是固定比例。
4. **用当前生效的出图配置**（`config`），不要另开一条。
5. **这一张里有没有它本人** —— 决定带不带锚点与设定图（见 4.1.1）。
6. **两处落盘**：图字节存 `chat_images`（与用户附图同一张表），消息上挂一个**与 `imageId` 分开**的字段（`photoId`）。语义不同：一个是"对方发来的"，一个是"它给你的"，渲染位置、清理时机、撤销语义都不一样。**在此之上**，同一张图再经 `recordFor` + `persist` 落一条历史（`source: 'chat-photo'`，`characterId` 是对话里那个角色）。
7. **导出 / 导入**：`photoId` 的字节并进 `ImportedChat.images`（那里已经是 `{ id, blob }[]`）；新消息的 `photo / photoSelf / photoShot / photoFrame` 作为 `ChatMessage` 字段一起搬运，旧消息里的文本标签走兼容解析。
8. **`types.ts` 里那句「只有用户消息会带 imageId」是文档约束**，输出侧落地之后这句**已经不再成立**（语义改由 `photoId` 承担），发现时按实际代码改。
9. **识图与出图是两条配置**：用户发图那一轮已经切到识图配置；若同一轮角色又回图，就是「识图模型看进来 + 出图模型画出去」——两个配置各管一段，实现时**不要**把它们搅在一起。

> 旧协议时代还有两条坑：重算 `CHAT_TAIL`、只认最后一枚标签。它们随 tool calling 一起失效，只留在 §7.3 当历史。

#### 4.1.1 这一张里有没有它本人（`photoSelf`）

早期实现是**每张都带**：提示词里拼上 `characterFaceDesc`，设定图当参考图送进去。结果是纯场景图被拽着跑偏 —— 模型往那个人的脸、发型、衣着上靠，甚至在一张风景里凭空长出一个穿那身外套的人。

**判据由模型给，不由客户端猜。** 它报的场景本来就是"它想给你看什么"，再让它回答"画面里有没有它自己"：

| 它报的 | 意思 | 出图时 |
| --- | --- | --- |
| 只有场景，没有它 | 它**看到**的东西 | 提示词只有场景，**一张参考图都不发**；空镜模板 |
| `shot: 'selfie'` | 它**在画面里**，**它自己的手机**在它手上 | 拼锚点 + 设定图当参考图；自拍模板 |
| `shot: 'third'` | 它**在画面里**，**别人的手机**在别人手上 | 同上，但他拍模板 |
| 场景里写了它自己、但没报 `shot` | 在画面里，没说谁拿的手机 | 按场景文本判，认不出就**按自拍** |

**默认（不写它）= 场景照。** 取舍的理由：一张风景里长出一个人是**整张废掉**，而一张自拍少了参考图只是"不像本人"；猜错的代价不对称，所以默认落在伤害小的那一侧。

> 表里"只有场景，没有它"是**归一化之后**的结论，不是字面判据：模型什么都不报时，服务端还会用场景文本兜一遍 `self`（点了角色名、出现身体部位词都算"在画面里"，见 4.4.3），兜出来是"有人"就不再走空镜 —— 没说谁拿相机时按场景判，认不出即自拍。

**2026-10-05：视角也由聊天模型直接回答（`shot`）**。原来只有"在不在画面里"这一位，"谁拿的相机"交给摄影指导去猜 —— 它只看得到那一句场景、看不到对话，于是猜出来大多是**他拍**。用户原话："角色对话生图的时候，对于自拍的理解总是不好，老是会生成他拍视角的图片。" 现在这件事由**唯一知道答案的那一层**直接说，四级判据见 4.4；摄影指导仍然补机位 / 镜头 / 光 / 环境，但**视角它改不了**。

**协议之外仍保留的容错**（历史消息、或模型把前缀误写进场景时）：

1. `selfie:` / `self-portrait:` —— 相机在它手上；标记**剪掉**（它不是内容）；
2. `third:` / `third-person:` —— 相机在别人手上；同样剪掉；
3. `self:` / `myself:` / `me:` / `me,`，或直接以 `me at my desk` / `I'm on the balcony` 开头 —— 在画面里，但没说相机；纯标记剪掉，代词那几种只置位不剪（剪掉就只剩 `at my desk`）；`\b` 保证 `meeting` / `selfish` 不会被误判；
4. 兜底：描述里**点了自己的名字**也算它在画面里 —— 角色名由服务端传进解析（它手上有角色卡）。名字这条**不回答相机那一项**。

`scene:` / `view:` 是模型偶尔多写的噪声，抹掉。身体部位词（指甲 / 手腕 / 肩膀 / 皮肤 / 纹身…）也参与 `self` 的兜底，中文刻意不收单字"手"（会撞"手机 / 手艺"）。

#### 4.1.2 频率：不设上限（决定）

**结论：角色对话里发图不设频率上限。** 提示词里那句 "Use the tag rarely, at most once every few messages" 已经删掉，客户端**也不加**「连续 N 轮最多一张」那类兜底。

| 决定 | 为什么 |
| --- | --- |
| 提示词里的频率那句删掉 | 它是唯一存在过的频率限制。留着的话，"多发几张"这种再自然不过的要求会被一条模型自己都记不牢的规矩压着 —— 而频率该由**对话本身**决定：问它要照片就该给，一句普通寒暄就不该配图 |
| 客户端不加兜底（原坑 4 作废） | 兜底要挑一个 N（几轮算合适？），而任何 N 都是替用户做判断。真要被烦到，用户关掉的是这个功能，不是"每三条准发一张" |
| **保留"只有图确实有用时才发"这个判据** | 去掉它才是真的失控：模型会把发图挂在每一句后面。它管的是**相关性**（要照片 / 场景本身值得看），不是频率 |
| 保留"绝不能拿发图代替说话" | 图是补充，不是回复。一轮只有一句话的时候更要想清楚 |
| 一轮一张（协议层）不变 | 一次工具调用只带一个 `photo` —— 这是协议决定的，不是频率限制 |
| 成本仍然是用户的 | 每张图都是一次真出图调用。没有频率上限，就意味着"多聊几句、多要几张"会直接反映在账上 —— 这是有意的：这个功能的卖点就是角色**会**给你看 |

顺带：服务端的 `rateLimit` 中间件（`RATE_MAX = 30` 次 / 60 秒，按 IP，挂在 `/api/generate` 等各条路上）照旧管着 —— 它是防滥用的，不是产品意义上的频率限制，正常聊天撞不到。

#### 4.1.3 落两处、导出与已知边界

- **落两处**：字节进 `chat_images`（消息要显示它），同一条记录再进 `history`（`source: 'chat-photo'`；背景图是 `'chat-backdrop'`）。两条路刻意互不引用：历史被清理掉，对话里那张还在；清空对话，历史里这张也还在。
- **导出**：`readChatForExport` 把消息与图一起带走；没有 `photoId` 的消息**不再带 `photo` / `photoSelf` 进包**（包里没有"失败"这个状态，带过去只会变成一条永远在画的消息）。
- **导入**：`coerceImportedChat` 从前把 `photo` / `photoId` 一起丢了（包里有图、消息上没有引用键，导入回来"它给你看过什么"整段是空的），现已一并收进；`photoId` 的字节并进 `ImportedChat.images`。
- **已知边界**：对话里生成的那些图的历史记录**不进角色包**。包带的是设定图、参考图与那段对话，没有 `history` 里那批 `source: 'chat-*'` 的记录 —— 导入方拿到的是一个"聊过但作品墙空着"的角色，直到自己再生成几张。要一起搬得给 `ImportedCharacter` 加一截作品清单，那是另一件事。

### 4.2 六层拼装

#### 定位与签名

这一层只回答一个问题：**「这一张照片，文字部分该长什么样」**。它把四个输入摊成**一串带槽名的层**，再拼成一段字符串。

```ts
planChatPhoto(
  scene: string,      // 场景原文，永不改写
  self: boolean,      // 画面里有没有它本人
  anchor = '',        // 身份锚点句
  shot?: ChatShot,    // selfie / third / scene
  frame?: ChatFrame,  // close / medium / full
  gender = '',        // 只在特写用
  mood = ''           // 只在有脸时用
): ChatPhotoPlan
```

输出 `prompt`（真正发给上游的整段）、`useRefs`（要不要发设定图）、`shot` / `frame`（最终定下的两位）、`layers`（分层结构，摄影指导按它逐位替换）。**没有场景就直接返回空提示词** —— 调用方据此放弃这一张，而不是拼出一段只剩外貌的人像。

#### 六层总览（概念六层，落地 13 个槽）

文件头把这套结构叫「**六层提示词**」；它是**职责分组**的说法，落到代码里是 **13 个带槽名的层**。**顺序即权重，不能反**。

| 层（概念） | 具体槽（`layers[i][0]`） | 出现条件 | 内容来源 | 摄影指导可否改 |
| --- | --- | --- | --- | --- |
| ① 媒介与视角 | `medium` | 总是 | 模板 `tpl.medium`（`onBody` 时换） | ✘ |
| ② 内容 | `scene` | 总是 | 上游 `photo.scene`（**永远原样**） | ✘ |
| ③ 身份 | `anchor` | `self && 锚点非空 && !onBody` | `characterAnchor` | ✘ |
| ③ 身份 | `expression` | `self && frame≠close && 心情合法` | `expressionLine(mood)` | ✘ |
| ③ 身份 | `part` | `self && frame==close` | `partLine(gender)` | ✘ |
| ④ 不可让渡 | `pin` | 模板有 `pin`（三档都有） | 模板 `tpl.pin`（`onBody` 时换） | ✘ |
| ④ 不可让渡 | `frame` | 总是 | `frameLine(self, frame, onBody)` | ✘ |
| ⑤ 工艺 | `camera` | 总是 | 模板 / `FRAMING` / `BODY_DETAIL` 覆盖 | ✔ 可整句替换 |
| ⑤ 工艺 | `lens` | 场景没说镜头 | 模板 or `FRAMING` 覆盖 | ✔ |
| ⑤ 工艺 | `light` | 场景没说光 | 模板 / `lightWet` / 覆盖 | ✔ |
| ⑤ 工艺 | `env` | 总是（无条件） | 模板 or `FRAMING` 覆盖 | ✔ |
| ⑤ 工艺 | `action` | 场景没说动作、非特写、**且场景不是中文** | 模板 `tpl.action` | ✘ |
| ⑥ 约束 | `negative` | 总是（垫最末） | `NEGATIVE` 常量 | ✘ |

**四条读法**（写错了都会"图不对味但不报错"）：

1. **顺序即权重**：越靠前对图像模型越硬。所以"这一张要画什么"（`scene`）永远在"这个人是谁"（`anchor`）之前。
2. **槽名 = 权限**：摄影指导只认 `camera / lens / light / env` 四个槽，其余槽它**结构上拿不到**（见 4.5）。
3. **只补不覆盖**：`lens` / `light` 只在场景确实没说时才出现（见 4.2.5）。
4. **负面约束垫最后**：整段被截断时，它是最后一个被丢的。

#### 4.2.1 `medium`：媒介与视角

`medium` 说**用哪种媒介成像**，并且承载"这是手机拍的"这层语境：自拍 `shot on a phone front camera`、他拍 `a casual snapshot taken on a phone by somebody else`、空镜只有 `photographic`。

**为什么排最前**：图像模型没有"自拍"这个概念，它只有"画一个人"。能把"画一个人"掰成一张自拍的，是 `front camera` 这类具体的词。这一层先定介质与拍摄方式，后面的 `camera` 再补距离与机位。

**`style` 不在这里、也不在锚点句里**：介质由这一层给，角色设定里的 `style`（anime / photorealistic…）刻意不进对话出图链 —— 两边都写会重复，重复且措辞不一致时模型会丢掉一个。

#### 4.2.2 `scene`：内容层

**场景原文一字不改地进来，而且永远在第二个位置。**

- 它是"这一张画的是什么"，是用户的意图，不是可以优化的东西 —— **任何一层都不许改写它**（摄影指导拿到它作输入、但只回写另外四位）。
- 排第二（在 `medium` 之后、`anchor` 之前）是有意的：它必须**在身份锚点之前**。反过来写等于把固定的长相顶在最前面。
- 上游已经把场景收敛成一行、截到 `PHOTO_SCENE_CHARS = 400`；这一层只做 `replace(/\s+/g,' ').trim()`。

#### 4.2.3 `anchor` / `expression` / `part`：身份的三面

三层说的是同一件事的几面：**"这个人是谁"** 与 **"此刻他/她什么样"**。三者都只在"画面里有人"（`self`）时才可能出现。

| 槽 | 来源 | 条件 | 要点 |
| --- | --- | --- | --- |
| `anchor` | `characterAnchor(c)`，9 项 | `self && 锚点非空 && !onBody` | 只做减法；老角色返回空串，不退回全量（那会把治好的病请回来） |
| `expression` | `expressionLine(word)`：`a <word> expression on the face, not acted out` | `self && frame≠close && moodWord(mood)` | **排在 anchor 之后**：先立住"是谁"，再给"此刻什么样" |
| `part` | `partLine(gender)`：`a detail of that same person — <gender, >same age, same skin and same build as the reference, not a generic stand-in` | `self && frame==close` | 特写是锚点句**结构上失效**的唯一场景：画面里往往没有脸，模型会退回它画过最多的那只手 |

- `expression` 的三个护栏各有理由：`self`（空镜里没有脸）、`frame≠close`（特写常只有一只手，请它"在脸上写神情"＝请它把脸画进来）、`moodWord`（**词不合法就什么都不做，绝不猜**）。一个词，不做词表 —— 词表一旦出现就要维护，模型一出表外词就出错。`not acted out` 冲的是"只写 angry，模型演成一个动作"。
- `part` 的性别**单独给、不并进锚点句**：并进去会改掉这条路上**每一张**图；只补这一档，一个字的代价也不外溢（有单测钉死）。性别为空（老角色）仍保留后半句 —— 它治的是"退回一只通用的手"。

#### 4.2.4 `pin` / `frame`：不可让渡的两层

这两层的共同性质：**摄影指导换机位是"整句替换 `camera`"，而这两层不在它的权限里**，所以它们必须自己站得住。

| 层 | 说什么 | 换掉的后果 |
| --- | --- | --- |
| `pin` | 自拍：相机在**它自己手上**（臂展 / 镜子）；他拍：手机在**别人手上**；空镜：画面里**没有人** | 画成别人拿相机 / 退回一张谁拍的都不知道的通用照片 / 风景里凭空长出一个人 |
| `frame` | 这张是哪种景别（人与空镜两套说法） | 摄影指导写"整个地方都看得见"就能把特写抹掉 |

- `pin` 三档共用**一个槽名**，因为它们是同一件事：**这一档不可让渡的那一句**。它不重复 `camera` —— `camera` 说"怎么拍"，`pin` 说"谁拿的相机、拿的是什么"。
- `frame` 也单独成层：`FRAMING` 会整句替换 `camera`，而"推多近"必须有一条它碰不到的地方落脚。空镜里没有"整个人"这回事，写 "the whole person" 就是给"风景里长出一个人"递刀。

#### 4.2.5 `camera` / `lens` / `light` / `env` / `action`：工艺层

这是唯一**让渡给摄影指导**的一层（前四位），也是"图死板、没有光影"的主要病灶 —— 模板补不上"这个场景具体的光"，只有模型知道。

| 槽 | 出现条件 | 模板给了什么 | 景别能否覆盖 |
| --- | --- | --- | --- |
| `camera` | 总是 | 机位句（三档各一套） | ✔ |
| `lens` | **场景没说镜头** | 景深句 | ✔ |
| `light` | **场景没说光** | 光句（下雨走 `lightWet`） | ✔ |
| `env` | **无条件** | 纵深句 | ✔ |
| `action` | 场景没说动作、**且非特写、且场景不是中文** | "此刻在做什么" | ✘ |

三处容易看走眼的取舍：

- **`env` 无条件补**：环境是**事实**（"在阳台"），纵深是**相机原理**，两者不冲突 —— 场景说了地点照样需要一句"画面要有纵深"（那正是"人和环境融不进去"的药）。做成"没说才补"的结果是几乎每个场景都提过窗 / 桌 / 墙，这句永远不出现。
- **`action` 特写不补**：模板那两句是以"画面里有脸"写的（自拍是 `mid-moment, looking into the camera`），请特写"看向镜头"＝请它把眼睛画进来。
- **中文场景也不补**（2026-10-08）：这一层的偏置与其余各层**相反** —— 漏判不是"落回默认"，是"补一句与场景打架的动作"，而中文动作太自由、那张英文表认不出（见 `ACTION_RE`）。判据是 `hasHan(scene)`。
- **`light` 的下雨分支不走景别覆盖**：光与景别无关 —— 一处光不会因为推近就换个来源。

#### 4.2.6 `negative`：约束层

- 来源 `NEGATIVE` 常量，**垫在最末**。整段被截断时它是最后一个被丢的（有单测钉住 `layers[last][0] === 'negative'`）。
- 它挡三类东西，每类都有明确来路：

| 挡什么 | 词（摘） | 来路 |
| --- | --- | --- |
| 证件照那套默认构图 | `not a character sheet` / `not a passport or ID photo` / `not centered neutral expression` / `not flat lighting` | 参考图与全量清单会互相加强成证件照 |
| **多出来的、长错的**肢体 | `no extra limbs` / `no extra or fused fingers` / `no deformed or duplicated hands` | 用户报的"四肢畸形、缺手少腿" |
| 拼贴 / 接触印相 | `not a collage` / `not a contact sheet` / `no panels` | 我们发的参考图里有 2×2 网格，模型会漏成拼版 |

- **刻意不写 `no missing limbs`**：那句会与特写构图（"其余身体出画"）打架 —— 模型读到"不许缺"最省力的解法是**把镜头拉远**，正是这一轮刚修好的毛病。"缺"治在机位句上，不是治在负面词上。
- 不写 `no text`：背景图那一层自己带着，写两遍只是重复。

#### 4.2.7 只补不覆盖：`missingSlots`

这是"模板不许和场景打架"的**唯一权威**（模板与摄影指导合并都用它）。守的位只有两位：

| 位 | 判据 | 为什么只这两位 |
| --- | --- | --- |
| `light` | `LIGHT_RE` + `LIGHT_ZH`（光 / 灯 / 影子 / 逆光…） | 场景说过的光再说一句＝自相矛盾 |
| `lens` | `LENS_RE` + `LENS_ZH`（镜头 / 焦段 / 景深 / 虚化…） | 两个焦段凑一张提示词＝打架 |

三条容易看错的地方：

- **没有"环境"位**：环境是事实，纵深是原理（见 4.2.5）。
- **没有"时间 / 天气"位**：那是事实不是修辞，编一个"黄昏"会和对话矛盾。唯一例外：`isWet`（已在下雨 / 下雪）→ 补"湿处反光"，那是**必然推论**，不是新事实。
- **`lens` 的判据里拿掉了 `close-up` / `macro` / `特写`**（2026-10-06）：它们其实是**景别**的词，现归 `frameFromScene` 管 —— 否则场景一写特写，景深那句（正是特写最需要的）反而不补了。

判据取窄的理由：**宁可漏判（以为没写、于是补一句），也不误判**（把 `sunny` 判成写了 sun、把 `lens` 判成提到镜头）。

#### 4.2.8 特写落在**身上**（`onBody`）

特写里还有一件**正交**的事：这一格拍的是**脸**（眼、唇、睫毛…），还是**身上**（手、脚、肩、纹身…）。它不是第三个协议位 —— 由前两位加上场景串自己判出来，聊天模型一个字都不用多写。

```
onBody = self && frame === 'close' && closeOnBody(scene)
```

判据是两张词表：**身上那张命中、且头上那张一个都没命中**。两张表的宽严方向**相反**，因为误判代价不对称 —— 命中头上的词＝保持今天的做法（安全，取宽）；命中身上的词＝改掉今天的行为（取窄，中文刻意不收单字"手"，它撞"手机 / 手艺"）。

它为真时，下面这些位置**一起让路**，每一处都是"上身被一起塞进画面"的来源：

| 层 | 变化 |
| --- | --- |
| `medium` | 自拍去掉 `front camera`（拍自己的脚用的不是前置镜头） |
| `anchor` | **不拼**（那几项全是头部特征，画面里没有脸时只会把镜头往回拽；身份由 `part` 接管） |
| `pin` | 自拍的"相机在自己手上"不变，换掉举例 `at arm's length or in a mirror` → `held down or out over that one part` |
| `frame` | 明说 `the rest of them, head and all, is cropped out` —— "其余出画"不够，**得连头一起说** |
| `camera` | 手机出画：`one part of the body fills the frame, everything else, the head and the rest of them alike, out of frame` |
| 参考图 | `shotViewOrder(shot, frame, onBody)` → `['body', 'closeups', 'front']`（见 4.6） |

跟它一起变的还有摄影指导那两句话（`shotBrief` / `frameBrief` 各多收一个 `onBody`）—— 它写的就是 `Camera:` 那一行，不告诉它，"头出画"会被它整句替换掉。

#### 4.2.9 拼装与截断

```ts
export function composeChatPrompt(layers: ChatLayer[]): string {
  return layers
    .map(([, value]) => value)
    .filter(Boolean)          // 空值丢掉，不留空逗号
    .join(', ')
    .slice(0, CHAT_PHOTO_PROMPT_CHARS)   // 6000
}
```

- 截断发生在**最后一步**，砍掉的正好是垫在末尾的负面约束 —— 所以上限从 1200 放宽到 **6000**：不产生任何新调用，只是不再让最后那几层被无声吃掉。
- 拼接符号是 `, `，槽名不进最终字符串（`layers` 里的槽名只服务摄影指导的逐位替换）。

### 4.3 三套模板 × 景别

#### 4.3.1 三套模板的固定句

| 槽 | `selfie` | `third` | `scene` |
| --- | --- | --- | --- |
| `medium` | `photographic, shot on a phone front camera` | `photographic, a casual snapshot taken on a phone by somebody else` | `photographic` |
| `pin` | 相机在自己手上（臂展 / 镜子） | 手机在别人手上 | 画面里没有人 |
| `camera` | 臂展、前置、**从腰以上**（脸与上半身）、略高机位、轻微广角、手臂入画 | 第三人称、随手拍、偏离中心、全身与手入画、构图随意 | 相机架着 / 稳持，普通视点 |
| `lens` | `shallow depth of field, background softly out of focus` | `mild background blur, reading as a phone photo rather than a studio portrait` | `shallow depth of field with a soft, readable foreground` |
| `light` | 落在脸上的自然光，从一侧打 | 有明确来源的方向光，一侧脸更亮 | 来自可见光源，扫过场景 |
| `lightWet` | 阴天平光 + 湿处反光，脸被它照亮 | 柔和阴天光 + 地上墙上的湿反光，主体被勾边 | 阴天光 + 湿处反光 |
| `env` | 身后那地方读得出来，近得能摸到 | 有纵深：前景遮挡 / 中景主体 / 后面化开 | 前景 / 中景 / 更远处 |
| `action` | `mid-moment, looking into the camera` | `caught mid-movement, unaware of the camera` | 无 |

- 两档"有人"的模板都必须读成**手机拍的** —— 只是拿手机的人不同（用户 2026-10-05 的原始要求："要能理解自己用手机拍摄的视角，和别人用手机拍摄的视角"）。他拍那档刻意不写 portrait / 写实摄影那类词，免得被推向影棚。
- **为什么模板是必要的**：图像模型没有"自拍"这个概念的权重，它只有"画一个人"。"前置、臂展、畸变、手入画"这几个词才是**唯一**能把"画一个人"掰成"一张自拍"的东西。
- **他拍那档曾经根本没提手机**（medium 只有 `photographic`）：于是用户那句要求只满足了一半，别人拍的那半画出来更像一张通用相机照。现在 medium、camera、lens 三处都写明是手机快照。
- **`pin` 为什么不并进 `camera`**：摄影指导补机位的办法就是整句替换 `camera`，而它看不见"谁拿的手机"，所以这三句话必须各自独立成层。

**已知的取舍**：他拍把"手机快照"写成了默认介质。若某场戏明说是专业摄影师 / 胶片机拍的，`shot` 仍然是 `third`，于是"手机"与场景里那句会轻微打架（模型自己权衡）。当前判断是这种场景不值得再加一个协议词。

#### 4.3.2 景别覆盖 `FRAMING`

景别只改 **camera / lens / light / env** 四样；光与"谁拿的相机"跟景别无关。**缺省那一档在表里没有条目** → 今天所有图的提示词**逐字不变**。

| 视角 | 景别 | 覆盖哪几个槽 |
| --- | --- | --- |
| `selfie` | `close` | camera / lens / light / env（臂展换成"一只手举近"，三个自拍信号一个不少） |
| `selfie` | `full` | camera / lens / env（**刻意不写"对镜"** —— 镜子是场景里的东西，没说就不该凭空添） |
| `third` | `medium` | camera（腰以上、手入画、偏离中心） |
| `third` | `close` | camera / lens / light / env |
| `scene` | `close` | camera / lens / env（一个字都不提人） |
| `scene` | `full` | camera / lens / env（一个字都不提人） |

- 缺省：`selfie → medium`、`third → full`、`scene → medium`（`DEFAULT_FRAME`）。
- 特写那档：自拍把"臂展"换成"一只手举近"（近距离下臂展物理不成立，三个自拍信号一个不少）；他拍的 `light` 特写另外给（拍手 / 拍疤没有脸，"一边脸更亮"是错的）。
- **再往下一层还有 `BODY_DETAIL`**（2026-10-09）：特写里"这一格落在身上"时，它再覆盖 `medium` / `pin` / `camera` 三样并摘掉 `anchor`（见 4.2.8）。它是 `FRAMING` 的**子集**。
- 被覆盖的空位遵循同一句纪律：**camera 那两句刻意不再重复"填满画面"** —— 那是 `frame` 层的活。

**为什么缺省档刻意没有条目**：这一位不存在时，拼出来的提示词必须**逐字**等于改造前那三句。单测里有一条直接断言两串相等（不是"差不多"），因为**这是景别改动唯一真正的风险**。

### 4.4 视角与景别的判定

两者是**正交**的两位（"谁拿的相机" × "离得多近"），但判据是同一套写法：**工具给的 > 场景文本 > 缺省**。

#### 4.4.1 视角 `shot`（四级，先命中者赢）

1. 工具参数 `photo.shot` 说 `selfie` / `third` → 就是它（模型对"谁拿的相机"的直接回答）；
2. 场景明写自拍（`isSelfie`：mirror / arm's length / 自拍…）→ 自拍；
3. 场景明写"别人拍的"（`isThirdShot`：taken by / 偷拍…）→ 他拍；
4. 一条证据都没有 → **默认自拍**（2026-10-05 从"默认第三人称"改过来 —— 那是"老是出他拍"的根）。

两条纪律：

- **`self = false` 时视角只能是空镜**，由 `self` 定死，**不由任何人推断** —— 一张"我看到的东西"里长出一个人，比视角选错严重得多（哪怕模型报了 `selfie`）。
- **第 2 条压过第 3 条**：一句里同时出现两种字眼，多半是模型在描述画面里的**另一个人**；按自拍画错的方向恰是用户能接受的那一侧。

词表都**取窄**：只认明确说法，宁可漏判（落回默认）也不误判。

#### 4.4.2 景别 `frame`（四级，先命中者赢）

1. 工具参数 `photo.frame` 说 `close` / `medium` / `full` → 就是它；
2. 场景明说（`frameFromScene`）→ 按它（**两边都命中时特写赢** —— 用户报的毛病是拍得太远）；
3. 一条证据都没有 → **这一档视角的缺省**（`DEFAULT_FRAME`）。

- **缺省值随视角变**，不是一个统一默认：自拍半身、他拍全身、空镜中景 —— 它必须逐字等于"这一位不存在时"那三句。
- 词表取窄：`full` / `wide` / `detail` 单独出现时意思不明，一律不认；中文靠 `全身(?!心)` 挡掉"全身心投入"。
- **兼容解析遇到前缀式写法时，前缀必须有分隔符**：老消息里 `close to the window, the rain` 这样的串，若 `close` 不要求后接分隔符，会被剪成 `to the window, the rain`（"离窗很近"变成"窗"）。长写法要排在短的前面，否则 `full-length:` 会被 `full` 吃掉一半。

#### 4.4.3 两条归属纪律

- **视角与景别都由聊天模型说、`planChatPhoto` 定死，摄影指导只被告知。** 摄影指导看不到对话，让它来判，只会猜成他拍与错的距离。
- 上游归一化时，`self` 的判据（由宽到严）：`shot` → `me` / `I'm` 代词 → 场景里点了角色名 → **身体部位词兜底**（`BODY_PART_RE`：指甲 / 手腕 / 肩膀 / 皮肤 / 纹身…）；明确的"没有我"写法挡在最前面。

### 4.5 摄影指导层

在"拼完六层"与"发图"之间，用当前生效的文本模型补场景**没说**的摄影要素。

#### 4.5.1 能补哪四位

`DIRECTOR_SLOTS = camera, lens, light, env`。

**它碰不到**：`medium / scene / anchor / expression / part / pin / frame / action / negative` —— 结构上（槽名过滤）就没有入口。

#### 4.5.2 提示词：事实在前，要求在后

给它的输入 = 场景原文（明说"不许改写"）+ 两件**被告知的事实** + 哪几位场景已覆盖：

```
Scene, exactly as it must appear in the image, do not rewrite it and do not change it:
<scene>
<subject：有人 / 没有人>
<shotBrief：谁拿的相机>
<frameBrief：离得多近>          ← 两个 brief 各多收一个 onBody
<directorBrief：Lens / Light 已被场景覆盖，留空>
Now write the four lines.
```

要求输出固定四行 `Camera: / Lens: / Light: / Environment:`（系统提示见 `ENHANCE_PROMPTS.photo`，温度 0.6）。要键值对而不是散文，是因为**已经说过的那一位要拒绝覆盖**，而那需要知道每一句属于哪一位。

服务端刻意**跳过** `REF_NOTE` 与 `targetNote` —— 前者那句"不要重新描述整个场景"与它"补怎么拍"的职责直接冲突；起稿 / 识图加目标模型偏好会顺手把画面信息也写进去。

#### 4.5.3 逐项验收

解析后**逐项验收**，任一项不过就丢该位（退回模板）：

- 带**时间词**（dawn / dusk / night…）→ 丢整行（丢整行而不是删掉那个词 —— 删完剩半句更糟）；
- 带**焦段 / 光圈**（`85mm`、`f/1.8`）→ 丢整行（那是最容易被"编"出来的一项，而它对画面几乎只有坏处）；
- `n/a` / `none` / `same` → 空；
- 抹掉破坏行结构的字符（`:` `;` 句号 引号 markdown 换行），**逗号保留**；
- 截到 `DIRECTOR_LINE_CHARS = 220`；
- 一位都没解析出来 → 整层当不可用（不是逐位退回，格式已崩）。

#### 4.5.4 合并与降级

- `applyDirector` 只替换 `camera / lens / light / env` 四个槽；
- **场景已覆盖的位不接受覆盖**（判据与模板同一处 `missingSlots`）；
- 没补上或验收不过的位**逐位退回模板**；
- 没配文本模型 / 超时 / 报错一律返回 `null` → 退回模板层，**绝不阻断这张图**。每一处跳过都留一行 `console.debug('[chat] photo director …')`（需开控制台 Verbose）。

**三条硬不变量**（都有单测）：① 视角一个字都改不了（它只被告知）；② 景别一个字都改不了（`frame` 不在 `DIRECTOR_SLOTS`）；③ 只换那四位，其余槽原样不动。

**时间线**：摄影指导与骨架**串行**，不是并行 —— 它改的就是出图要用的那段提示词，并行没有意义（那是"先出图、再改图"才会有的结构）。真正要紧的是**超时**：当前 `DIRECTOR_TIMEOUT_MS = 30_000`。用户看不到这一跳（界面上只有"图在画"），所以卡住时宁可交一张模板拼的图，也不能让骨架一直转。

**开关仍未做**：它自动走"当前生效的文本配置"，没配就在界面上无声回退（控制台那一行是唯一的痕）。如果用户觉得每次出图都多一跳不值得，需要给它一个开关（以及"哪种情况值得跳这一跳"的判据）。

### 4.6 参考图与尺寸

提示词只是"怎么拍"的一半，另一半是**发哪几张参考图**与**用什么尺寸** —— 因为**参考图是 i2i 这条路上最强的机位来源**，提示词改近了、手上却给一张全身参考，取景照样被拽回去。

#### 4.6.1 参考图顺序 `shotViewOrder` / `FRAME_REF_ORDER`

| 情形 | 顺序 |
| --- | --- |
| `shot = 'third'`（未登记景别） | `full, front, closeups` |
| 其余视角（未登记景别） | `front, closeups, full` |
| `frame = 'full'` | `full, front, closeups`（全身像必须打头） |
| `frame = 'close'` | `front, closeups, body`（**全身出局**、`body` 进来，正面打头） |
| `frame = 'close'` **且 `onBody`** | `body, closeups, front`（**正面像从打头降到最末**，`body` 提到最前） |
| `frame = 'medium'` | 不登记 → 逐字等于"这一位不存在时"的顺序 |
| 背景图 `backdropViewOrder()` | `full, front`（只两张，刻意不发两张 2×2 网格） |

上限 `MAX_CHAR_REFS = 4`，实际发出 **3 张**。

**`detail`（四个头角度）全面退出参考图**（2026-10-08）：参考图是 i2i 的"拷贝先验"，给一张 2×2 网格就多一份把画面排成多格、多人、多手的先验 —— **畸形的一大来源**，而负面词对 gpt-image / Gemini 一类效力很弱、兜不住。被摘掉的是语义离"随手拍"最远的那张。结果：**非特写档网格 2 → 1、特写档 3 → 2**。`body` 也从非特写档移出（它本来就取不到，留着会被 `detail` 让出的位子顶上来）。

**`onBody` 那一档为什么把 `front` 降到最末**：`front` 是头肩证件照，放第一位就是让 i2i 最想保住的那张构图变成"一张脸" —— 一边在提示词里写"头出画"，一边在参考图里说"这儿有一张脸"，模型挑参考图。它降到最后仍贡献"还是这个人"（皮肤、体态），但不再决定取景；`body`（2×2 的手 / 前臂 / 腿 / 脚）提到最前，因为拍脚时它是唯一说明"这个人的脚长什么样"的那张。这一档**内容胜过版式**，代价（网格先验）由 negative 那三条兜着。

> **这一条要拿真图验收**：网格先验导致的"多格 / 多人 / 多手"是概率问题，而这一档把一张 2×2 推到了第一位 —— 如果实测发现脚的特写开始出现拼版，第一个该退的是这条（把 `front` 放回第一位，靠提示词那一侧硬扛）。

**T10 之后的两个后果**：`detail` / `closeups` 归 extra、不再默认生成；新角色没有 `closeups`，于是 `frame = 'close'` 那一档对新角色会少一张参考图。**上面这些顺序本身没动** —— 要不要把新增的 `side` / `outfit` 纳进来，得拿真图 A/B 才敢改（[产品路线图.md](产品路线图.md) §7.8）。

#### 4.6.2 尺寸 `chatPhotoSize`

- 按 `shotRatio`（`scene → 3:2`，其余 `2:3`）在**去掉 auto** 的显式比例候选里挑最接近的一档；
- 一个显式比例都没有才退回 `auto`。**绝不主动挑 auto** —— 那等于把自己刚做的决定又交出去；
- 这条**不跟创作区尺寸走**（创作区选的是"这次要多大"，对话图由场景决定）。

#### 4.6.3 扩展参数 `chatExtraParams`

- 画质显式给 `high`（对话此前没有让用户选过 quality，等于交给厂商默认档，多半是给快速预览的）；
- **`background` 一概不带**（签名里就没有这个字段，所以创作区那项漏不进来）；
- 两项都要**过能力表**（没有 quality 字段的厂商一个字节都不发）。

### 4.7 失败降级

#### 4.7.1 契约：要么给图，要么给原因

`generateChatPhoto` 的约定是**绝不 reject**，返回 `ChatPhotoResult`：成功是**一条工作记录** `{ blob, prompt, size, model, configId, elapsedMs }`，失败是 `{ error }`。记录里 `prompt` 是真正发给上游的那一整段、`size` 是这张定的尺寸、`configId` 说明"当时哪条配置出的图"（配置被改被删之后仍说得清）；出图这一层**不碰存储**，由调用方落两处。

#### 4.7.2 失败要说清是哪一种

用户反馈原话：「图片生成失败根本没有详细的提示，只有说明图片生成失败。」根因是从前把**七种完全不同的情形**全压成了一个 `undefined`：

| 真实原因 | 用户该做什么 |
| --- | --- |
| 一条出图配置都没有 | 去设置页配一条 |
| 有配置但没有模型名 | 把模型名填上 |
| 上游说密钥不对 | 换 key |
| 上游 5xx / 超时 | 等一会儿重试 |
| 上游 200 但一张图都没回（多半被安全策略拦了） | 换个说法 |
| 参考图读不出来（IndexedDB 出错） | 一般能自愈，重试 |
| 图**画出来了**却存不下（配额满） | 去清理空间 |

改法：

1. 返回类型从 `Blob | undefined` 改成"要么给图、要么给原因"（`{ blob } | { error }`），逐个失败点写自己的原因，最后的兜底 catch 不再把原因换掉；
2. 配置缺失说清缺什么（`imageConfigGap`）—— "缺模型名"比"没配好"具体；
3. 收口一层 `photoFailureText`（[api.ts](../src/api.ts)）：中止不算失败（说成"生成失败"会让人去查配置）、空话给兜底、超长截断。文案沿用 `failureMessage` 的产出 —— 它已经把"401 其实是部署登录墙"这类特定成因翻成了人话；
4. `ChatMessage.photoError` 存下原因：界面显示它，`title` 里放全文；落盘、导出 / 导入、从库里读回来时都收一道（它会**直接渲染**，一个非字符串就够让那一格显示成 `[object Object]`）；
5. **"画出来了但存不下"不再混进"画不出来"** —— 那是两回事：前者的锅在**浏览器存储配额**（IndexedDB 写不进，图本身是好的），后者的锅在模型与上游。

#### 4.7.3 留痕、重画与读取边界

- **失败的图要留痕、能重来**：失败在消息上记 `photoFailed: true` 并**写回库**，场景描述原样保留（它是重试要用的全部依据）；界面给一行 `Couldn't generate that image.` + `Try again`，重试走 `retryChatPhoto` —— **只重画图，不动文字**（与 `regenerate` 是两件事）。同一个入口还接了"图已经画出来、只是不满意"的重画键（悬停出现的 `.photo-redraw`）：依据一样、走的路一样，差别只在失败那一下 —— 已经有一张好图时**不能拿失败提示去顶掉它**，改成一条转瞬的 `notice`。
- **读取边界上收口**：库里"有 `photo`、没 `photoId`"只有两种可能 —— 还在画、或没画出来。而**还在画的那种不可能被读回来**，所以读取时一律落成 `photoFailed`（`useChat` 的 `settlePhoto`）。只在读取侧收：内存里那份不能碰，那里 `photo` 加 `photoId` 缺席也可能真的是"正在画"。
- **空引用（`photoId` 在、字节没了）**：消息与附图分两张表存，中间没有外键，"字节先写、消息后指"和"先清消息、后写回"两段时间差都会留下悬空引用。已收掉两条：① 撤销"清空对话"时**只往库里加、不先清**，回收留给 `purge`；② 空间体检 `pruneChatImages` 判孤儿的唯一依据是"库里有没有消息指着它"，而写图与挂 `photoId` 是两个事务 —— 现在**刚写过图就先跳过体检**（`CHAT_IMAGE_QUIET_MS = 30_000`），孤儿晚 30 秒再收，代价几秒，收错了是一张图没了。

#### 4.7.4 整条链的降级

```
聊天模型报意图 → 归一化
  ├─ 场景空 → 这一轮不发图（不是失败）
  ├─ 摄影指导缺失 / 超时 / 报错 → 退回模板（console.debug 留痕）
  ├─ 参考图读失败 → 退回纯文生图
  ├─ 上游 200 无图 → 明确 error
  └─ 一律不外抛，返回工作记录 `{ blob, prompt, size, model, configId, elapsedMs }` 或 `{ error }`
```

## 5. 对话背景图路径

`planChatBackdrop`：沉浸页铺满屏幕的那张，**不进消息流**。

层结构（顺序即权重）：

```
medium   ← cinematic film still, wide landscape framing of the whole place,
            the person small in the frame, camera set back across the room, made to sit behind text
scene    ← 场景原文
anchor   ← 身份锚点句
camera   ← 人很小（最多占画面高度 1/3）、站/坐右三分之一、朝左、左三分之二留暗而干净
lens     ← deep focus（不是浅景深：把房间虚掉就等于把戏虚掉了）
light    ← low natural light，最亮处在右侧主体附近
env      ← 房间读得出来、有纵深
negative ← NEGATIVE + no text/watermark/caption + 不许特写/头肩/自拍 + 脸不是主体、不居中、不在左半
```

- 与照片的差别：横构图、**不过摄影指导层**（机位与光已写死，且压在"进沉浸页"这条路上，要尽量短）。
- 尺寸复用"空镜"那档（`chatPhotoSize` 的 3:2）。
- 参考图固定 `[full, front]` 两张（见 4.6.1）。
- 同样"绝不 reject"；工作记录（提示词 / 尺寸 / 模型 / 配置 / 耗时）一起落进历史（`source: 'chat-backdrop'`）。

## 7. 决策记录

### 7.1 构图与光影的十条决定

| # | 决定 | 当时为什么 | 后来怎么改 |
| --- | --- | --- | --- |
| 一 | 拆开「是不是同一张脸」与「怎么拍」 | 两件事被绑在一个布尔上（`self` 同时管拼外貌和发参考图），等于说"只要它在画面里，构图就必须听设定表的"——而设定表里从来没有构图 | 保留拆分，但"怎么拍"的归属换了两次主人（见 7.2） |
| 二 | 外貌从「token 清单」换成「锚点句」 | 清单同时锁表情、姿态、机位；模型看到 `neutral expression, plain background` 级别 token 密度，最省力就是交证件照。锁身份、放开一切会随场景变的东西 | 落地为 `characterAnchor`（9 项）；实现时发现不是"清单加镜头语言"，是直接做减法（见 7.4） |
| 三 | 在意图与出图之间插一层「摄影指导」 | 治"没有光影、场景融不进去、自拍画成他拍"的唯一位置；模板补不上"这个场景具体的光" | 落地走已有 `/api/enhance` 的 `photo` 档；输出从五行收成四行（`Shot:` 删掉） |
| 四 | 自拍 / 他拍各给一套硬模板 | 图像模型没有"自拍"概念，只有"画一个人"；前置、臂展、畸变、手入画是唯一能掰过去的东西 | 他拍补上"手机在别人手上"；模板只覆盖"谁拿的相机"，景别另立第二位维度（见 7.5） |
| 五 | 参考图与提示词分工 | 参考图既是"同一张脸"的唯一保证，又是最强的机位与光线污染源（纯背景、平光、居中的证件照） | 提示词里明说"只取这张脸，不要它的人像构图"；参考图按镜头挑 |
| 六 | 参考图按镜头挑，不固定 headshot 优先 | `front` 永远排第一，等于每张都先把构图锚在证件照上 | 落地为 `extra order`；后来加上景别与 `onBody`（见 4.6.1） |
| 七 | 尺寸按内容挑，别一律方框 | `'auto'` 被降级成 `1024x1024`，横窗竖人全塞进同一个框；降级链没有"按内容挑"的余地 | 落地 `chatPhotoSize`：先在去掉 auto 的候选里挑比例（见 4.6.2） |
| 八 | `quality` 至少给一档显式值 | `quality` 默认 `'auto'` 等于对上游永远缺席，厂商会给快速预览档 | 落地显式 `high`，仍过厂商能力表；写死不是用户可选项 |
| 九 | 视角归摄影指导判，聊天模型只回答"画面里有没有人" | 当时认为"它看得到整个场景"，比客户端词表信息多 | **2026-10-05 推翻**：它只看得到一行场景，猜出来永远是他拍；视角回到聊天模型（见 7.2） |
| 十 | 放宽场景串与提示词上限，扣尾改成按标签起点算 | 摄影指导只能看到那一行场景，场景越薄它越推断不出东西；1200 上限实测会被撞到，垫在最末尾的负面约束被无声砍掉 | 场景 120→400、提示词 1200→6000；扣尾那套随 tool calling 一起失效（见 7.3） |

### 7.2 三次"把判断交给谁"的修正

#### 7.2.1 决定九被推翻：视角回到唯一知道答案的那一层

原先的分工是：聊天模型只回答"我在画面里"，客户端再拿 `isSelfie()` 的词表去场景串里找"自拍"，找不到就当第三人称。后来改成"视角归摄影指导判"，理由是"它看得到整个场景"。

**错在哪**：那句话里的"整个场景"只是一行场景串 —— 它看不到对话、看不到聊天模型写意图时的上下文。在"谁拿的相机"这件事上，它的信息**比聊天模型少**，让它判就是让它猜；而它猜出来的是他拍（它的规则里写着 "somebody else is holding the camera, or when nobody could be"，一行 `me on the balcony` 正好落在"nobody could be"那一侧）。两个后果都实测到了：场景只写"我在阳台"时它猜成 third；场景明写"自拍"时，它的 `Shot:` 行还会把唯一的硬证据覆盖掉。

**改回来**（三处，判据都在纯函数里）：

| 谁 | 现在负责什么 | 为什么 |
| --- | --- | --- |
| 画面里有没有这个人 | 聊天模型（`photoSelf`） | 没变 |
| **谁拿的相机** | **聊天模型**（`photo.shot`），客户端四级判据：`shot` > 场景写着自拍 > 场景写着"别人拍的" > **默认自拍** | 它才知道自己在描述什么；"你看我"本来就是角色发自拍的那个动作 |
| 机位 / 镜头 / 光 / 环境 | 摄影指导（**只补这四位**） | 它的本行；视角由 `shotBrief` 作为**事实**告诉它 |

- **它再也改不了视角**：`applyDirector` 里没有那个入口，`parseDirectorShot` / `SHOT_LABEL` / `rebuildForShot` 一并删掉（留着就是死代码）；
- **每一档都带一条硬约束层** `pin`：空镜"画面里没有人"、自拍"相机在它自己手上"、他拍"手机在别人手上"——同一个机制：摄影指导换得掉 `camera`，换不掉它；
- **photo 档固定输出从五行收成四行**，提示词里明说"谁拿相机是定好的，你的机位句要与它相符，不许换"。

**教训**：把一件事交给"信息更多的那个模型"之前，先确认它**真的**拿得到那些信息。"它看得到整个场景"混淆了"场景"与"上下文"。

#### 7.2.2 "需要改协议"的判断也被推翻过两次

§ 五 原先记着「自拍 / 他拍在剪标签时丢失，绕不过协议层」。第二批实现时按决定九收口，结论是"方向 2，而且连可选增强都不需要"。2026-10-05 又发现欠账不是"协议少一个字段"，而是**把视角从唯一知道答案的那一层手里拿走了** —— 新协议（`selfie:` / `third:`，今天是 `photo.shot`）就是还它的。

2026-10-06 协议还是改了，但补的不是视角，是**景别**：`close` / `medium` / `full` 成为第二位维度。理由与视角同一条（**只有聊天模型知道用户要什么**），只是当年漏判了一件事。两格合起来才是完整的一句话：**"用户要什么"这一类判断，全都归那个看得见对话的层。**

#### 7.2.3 重画时"要不要重跑摄影指导"

`retryChatPhoto` 是从消息上重放的：本地查表（六层）是确定性的，重放结果完全相同；摄影指导不是，同一场景重放会拿到不同提示词。三个选择：重画时跳过摄影指导（一致但质量低）、接受抖动（简单，且"再来一张不一样的"未必是坏事）、把改写结果存到消息上（一致，但要动导出 / 导入契约）。

**落地的是第二个（接受抖动）**：重新画走的是 `drawChatPhoto` → `generateChatPhoto`，每画一次都重拼六层、重跑摄影指导，改写结果不落到消息上。

> 当时那份记录写的是"倾向第一个"，但它给的理由（"用户要的是**一张图**，不是和第一次一样的那张图"）读起来支持的是第二个 —— 而为了对齐去新增一个落盘字段，代价明显大于收益。两者对不上，以代码为准。

### 7.3 协议演进：从正文标签到工具调用

| 阶段 | 形状 | 现在还剩什么 |
| --- | --- | --- |
| 初版（正文标签） | 模型在回复末尾写 `[photo:…]`（+ `[mood:word]`），服务端剪标签、**扣尾**、在 `done` 里送字段 | 只服务历史消息的兼容清理；`splitTags` 仍在这一层 |
| 视角进协议（2026-10-05） | 正文标签多了 `selfie:` / `third:` 前缀 | 同上；`parsePhotoIntent` 另被新协议当作"旧前缀被误写进场景"的兜底 |
| 景别进协议（2026-10-06） | 正文标签多了 `close:` / `medium:` / `full:` | 同上 |
| **tool calling（2026-10-20 起）** | 模型调用 `emit_message_meta`，`tool_calls` 独立信道；服务端归一化成 `photo / photoSelf / photoShot / photoFrame` 经 `done` 下发 | **当前协议**；正文从第一帧起原样流给前端，不扣尾、不剥离 |

**旧说法的归属**（只在历史语境里成立，**新协议已不适用**）：

- `CHAT_TAIL` / `TAG_HOLD` / `tailHold`：都是"正文里可能藏标签，所以末尾要扣住一截"的产物。tool calling 下正文与元数据分信道，正文不再需要预留尾巴；`tailHold` 只留在历史清理路径里。
- `splitPhoto` 一类"把剪取一分为二"的旧说法：现文本侧只剩 `splitTags`（历史兼容），出图主线不再从正文里取意图。
- "只认最后一枚标签"：旧协议一轮只取末尾那一枚；新协议一轮一次工具调用、一张图。

**扣尾这一课值得单独记**：`TAG_HOLD` 原先是 `24 + PHOTO_SCENE_CHARS + 16 = 160`，即按上限预留一整枚标签。场景上限提到 400 后它会变成 440 —— **比一条正常回复还长**，正文完全不流式。改成按"标签从哪开始"算（`tailHold` 返回"可以放出去多长"）才收敛，而收敛前连错四版：

| 版本 | 返回的量 | 怎么错的 |
| --- | --- | --- |
| 一 | `max(未闭合段长度, TAG_HOLD)` | 等于说"标签至少 24 字"，`[ph` 的保留点被抬到 24 —— 比 `[` 还靠后，`[` 被放了出去 |
| 二 | `min(未闭合段长度, floor)` | floor 大于段长时只留 3 个字，又把 `[` 推出保留区 |
| 三 | `max(floor, 未闭合段长度)` | 标签闭合那一瞬间这个量归零，整枚标签被一次性放出去 |
| 四 | ``min(完整标签起点, 未闭合 `[`)`` | 超长场景里末尾刚冒出 `[` 时选中了它，左边那枚完整标签被放出去 |
| **终** | **"放到哪"**：完整标签起点优先，没有它才用未闭合 `[` | 收敛 |

四版都错在同一件事上：**"扣多少"在标签开合之间不连续**。"放到哪"是连续的：它就是标签的起点。这个结论**单测没能自己发现** —— 前三版单测全绿，是端到端探针按 3 个字符一块喂真流才暴露的（见 7.7）。

### 7.4 实现时改了主意的几处

1. **锚点句是直接做减法，不是给清单加镜头语言。** 那份清单**本身就是**画面发僵的原因。所以 `characterFaceDesc` 一个字没动（创作区继续用），另写 `characterAnchor`。
2. **时间与天气不进模板。** 那两样是**事实**，不是修辞，场景没说几点，模板猜"黄昏"就可能和对话矛盾（它明明在值夜班）。保留的只有一个**必然推论**：场景已经在下雨 / 下雪时，补一句"湿处反光"。
3. **"环境纵深"不是"没说才补"，是无条件补。** 几乎每个场景都会提过窗、桌、墙，做成"没说才补"等于永远不出现；而纵深是相机原理，与场景说了什么地点不冲突。
4. **`chatPhotoSize` 刻意不挑回 `auto`。** `auto` 是"上游自己定比例"，而取景正是这一层刚做的决定。
5. **`facialHair` 留在锚点句里，体型垫到最后。** "clean-shaven"不是表情类，它是长相（留空会让模型每张图猜得都不一样）。顺序：脸 → 头发 → 眼睛 → 眉毛 → 鼻嘴 → 胡须 → **体型**（大部分近景里看不见，触上限时第一个出局）。
6. **空镜那句"画面里没有人"必须独立成层。** 它原先并进 `camera`，而摄影指导会整句替换 `camera` —— 于是空镜失去唯一挡得住"风景里凭空长出一个人"的防线，而且**不报错**。现在是 `pin`，不在 `DIRECTOR_SLOTS` 里。
7. **摄影指导不是与骨架并行，而是串行等它 —— 但不能等太久。** 并行没有意义（它改的就是出图要用的提示词），真正要紧的是超时。早期写 15 秒，当前是 `DIRECTOR_TIMEOUT_MS = 30_000`。
8. **视角变化要"重拼"而不是打补丁（历史）。** 视角决定的不是一句话，是一整套（medium / camera / lens / light / env / pin / action），只换 `camera` 会拼出"自称自拍、却按第三人称取景"的图。所以曾经有 `rebuildForShot`，且重拼时**不能用已经解析过的视角当输入**、锚点要原样带过去。这条随"视角归聊天模型、模板在拼装时就选定"而退役，只留作教训。
9. **景别那套只覆盖"谁拿的相机"，没有覆盖"离得多近"** —— 模板的机位句各自写死了一个景别，于是"特写"在整个链路里没有归属，只能靠场景串里那两个字去挤，挤不过一句写死的机位句。这才有了 7.5。

### 7.5 景别与"特写落在身上"

#### 7.5.1 景别：第二位维度，不是第四套模板

用户原话：「让角色拍特写图，总是变成自拍。」

复现（`planChatPhoto('close-up of my eyes, looking right at you', true, ANCHOR, 'selfie')`，不看模型、只看提示词）：场景里的 "close-up of my eyes" 与自拍机位句的"脸和肩膀占满上半幅 / 手臂入画 / 身后的地方看得清"**正面打架**。模型只能挑一边信，而它挑的通常是那条长了十几个词、说得最具体的机位句。

四处病灶，四处都要改：

| 位置 | 症状 |
| --- | --- |
| `TEMPLATES` 的 `camera` 句 | 景别**写死在里面**：自拍半身、他拍全身、空镜中景。场景说特写也没有任何一层能被改写 |
| `env`（无条件补） | 那条"前景 / 中景 / 远景"是为半身人像定的。特写里"身后的地方看得清"是纯噪声；空镜的特写更糟 —— 一颗咖啡豆会拿到"整个房间的纵深" |
| `LENS_RE` / `LENS_ZH` | `close-up` 与 `特写` 在里面 —— 于是**全链路唯一"听见"了特写的地方**，作用是不补景深。而景深正是特写最需要的那一句 |
| `applyDirector` | 摄影指导的 `camera` 句是**整句替换**，而景别从没被告知过它。它写"整个房间都看得见"就能把特写抹掉 |

改法：增 `ChatFrame = 'close' | 'medium' | 'full'`，与 `ChatShot` 正交。三个关键取舍：

1. **缺省值按视角给**（自拍半身、他拍全身、空镜中景）。于是 `FRAMING` 表里只登记"不是缺省的那两档"，缺省那一档压根没有条目 —— "这一位不存在时拼出来的提示词**逐字**等于从前那三句"。
2. **景别单独成一层（`frame`），与 `pin` 并列**。摄影指导整句替换 `camera`，"推多近"必须有一条它碰不到的地方落脚；同时它**被告知**这件事（`frameBrief`），否则它写出来的机位句会与那一层打架。
3. **判据四级，与视角同一套写法**（见 4.4.2）。

三处容易写错：

- `close-up` 从 `LENS_RE` 拿掉之后，特写会开始补景深。那是对的（特写最需要的就是那一句），但意味着**已经出过的特写图会变**，这是有意的。
- **空镜也要有景别**。第一版把 `frame` 与 `shot` 一起按 `self` 收口，于是"拍个特写给我看"最常见的形状（镜头对着一个东西、画面里没有人）落回中景。`shot` 在没有人的时候确实没有意义，`frame` 不是。
- **前缀必须有分隔符，长写法排在短的前面**（否则 `full-length:` 会被 `full` 吃掉一半）。

还有一条纠正：**`selfie:` 不等于"我拍的"**。规则里"不确定谁拿相机就写 `selfie:`"会反噬 —— 镜头对着桌上那杯咖啡时模型也写 `selfie:`，于是提示词里长出一张脸。新增规则：**A close-up of something you are holding or looking at is not a selfie** —— 自己的身子不是那一格的主体，就别写手机前缀，只写 `close:`。

**改完自查抓出的三处**（都用"这句话在物理上说不说得通"过了一遍）：

1. **特写那档的自拍把两个物理互斥的词写在一起**：`selfie taken at arm's length, the front camera pushed right in` —— "手臂伸直"与"贴到眼睛那么近"不可能同时成立。想清楚后不冲突：**"相机在它自己手上"这条事实是 `pin` 保证的**（谁也改不掉），`camera` 只管"怎么拍"，所以特写下把距离换成"一只手举近"是安全的，剩下三个自拍信号一个不动。
2. **全身那档凭空添了一面镜子**：`full-length mirror selfie` 里的镜子是场景里的一件实物，场景没说有镜子就不该添（与"不许编时间、不许编天气"同一条纪律）。`pin` 那层说 `at arm's length **or in a mirror**`，两条路都留着，挑哪条交给出图模型；整串提示词里出现 "mirror" 是对的，那是 `pin` 说的。
3. **半身那一档是死代码**：他拍的缺省就是全身，而 `frameFromScene` 只认特写与全身两组词，规则也只教了 `close:` / `full:` —— "拍张半身照"没有任何入口。补 `FRAME_MEDIUM_RE`（`half-body` / `waist up` / `from the waist` / `半身` / `腰部以上` / `齐腰`）+ 规则里加一句 `"medium:" is that usual distance if you ever need to name it`。`半身` 会顺带命中"上半身"，那是对的；真正会误伤的是"半身裙"，而它猜错的方向（更近一点）正是可接受的那一侧。

#### 7.5.2 特写落在身上：让路清单

用户原话：「要求角色拍摄身体部位特写的时候（比如脚），会把上身也放在图中，从而导致姿势非常怪异。」

那不是模型不听话，是提示词自己在拉：四样东西同时指着上半身，每一样单独看都是对的 —— ① 锚点句的八到十几个词人脸描述（要满足它，最省力的解法就是把脸和上身一起画进来）；② 自拍 `camera` 的"举手机的那只手在画面里"（手连着胳膊连着上身）；③ 自拍 `pin` 的"臂展或镜子"（举着手机拍自己的脚，姿势本身就是拧的）；④ 参考图由 `front`（头肩证件照）打头（i2i 默认保住输入构图）。`partLine` 挡不住它 —— 它管"这一格像不像那个人"，这里的问题是"这一格**多**了一个头"。

改法见 4.2.8。这一档明确**不做第三个协议位**（`body:` 之类）：前两位 + 场景串就定得下来，多一个前缀就多一处要教模型写、要落盘、要兼容老消息的地方。也不动 `chatTags.js` 的 `BODY_PART_*`（那是"有没有人"的判据，与这一格正交；它刻意不收"脚"是为了挡"脚本"）。

### 7.6 已否决 / 明确不做

| 不做 | 为什么 |
| --- | --- |
| 频率兜底（提示词限制 + 客户端 N 轮拦截） | 任何 N 都是替用户做判断；频率该由对话本身决定（4.1.2） |
| 给标签加第三个前缀（`body:` 之类） | 前两位 + 场景串定得下来，多一个前缀多三处维护 |
| 每张都重画角色设定图 | 那是另一个功能的成本结构，而且设定图的立意就是**纯背景单张**，正好是这一套要治的构图 |
| 给外貌清单**再加字段** | 问题不是清单太短，是它在管不该它管的事；继续加字段只会让画面更僵 |
| 把摄影指导当成"可选的锦上添花" | 这一层是**结构性缺失**，不是优化项。没有它，其余几条都只是缓解 |
| 让他拍那档为"专业摄影师 / 胶片机"再加协议词 | 模型自己会权衡；不值得为罕见场景扩协议 |
| 写 `no missing limbs` | 会与特写构图打架 —— 模型读到"不许缺"最省力的解法是把镜头拉远 |
| 在照片的负面约束里写 `no text` | 背景图那层自己带着，写两遍只是重复 |
| 给 `quality` 加设置项 | 当时没加是为了不动参数面板；若证明不合适（某些厂商按 high 计费很贵）再考虑 |
| 把 `style` 写进锚点句 | 媒介归 `medium`；两边都写会重复，措辞不一致时模型丢一个 |

### 7.7 三条教训

1. **"谁看得见什么"比"谁更强"重要。** 决定九的错不是模型不行，是信息归属错了。写"交给更聪明的下游"之前，先数清它手里到底有几行上下文。
2. **单测全绿不等于接缝是好的。** 扣尾四版、单测三版全绿，是端到端探针按 3 个字符一块喂真流才抓出来的：两枚标签相邻时上一枚被放出去、超长场景里跨换行误判、以及"扣多少"这个量本身不连续。边界 bug 只在**增量**上显形，所以 `tailHold` 那组单测现在全部按"分块喂"写。
3. **猜错代价不对称时，默认值要落在伤害小的那一侧。** 场景照没带设定图只是"不像本人"，风景里长出一个人是整张废掉 —— 所以 `self` 缺省是"画面里没有人"；而视角缺省是"自拍"，因为模型写场景时通常不写"自拍"两个字，默认他拍才是"老是出他拍"的根。

## 8. 明确不做 / 验收

### 8.1 范围上明确不做

- **不发设定图、不发已有作品**作为对话图片来源 —— 只做现场生成。
- **不写角色创建向导细节** —— 起稿与向导在《角色创建与形象》。
- **不把发图做成"每句都配图"** —— 保留"图确实有用才发"的判据，但**不设频率上限**。
- **不在这一层管记忆与关系** —— 那是对话链路的事。

### 8.2 单测（纯函数，不需要联网）

- 分层提示词的**层序**：`scene` / `medium` 在身份 token 之前（前段权重更高）；
- 三套模板各自的关键词在位（"前置 / 臂展 / 手入画"与"第三人称 / 纵深 / 手机在别人手上"）；
- 锚点句的**取舍**：给定一份完整 `CharacterFields`，输出只含被判定为不可变的那几项，**表情与背景一个词都不许漏出去**；
- 摄影指导失败时的降级路径：返回的仍然是可用的提示词，**不是空串**；
- 参考图按镜头挑的映射表；景别缺省档逐字不变；`onBody` 该让路的几处都让路、其余各档逐字不变；
- 视角与景别四级判据（含"画面里没有人时它报 selfie 也不算"）；
- 失败文案 `photoFailureText` 与 `chatMessageFromRow` 的读取收口。

### 8.3 端到端探针

`scripts/probe-chat-photo.mjs`：起一个假上游（SSE）+ 真的 KImage 服务端，把 `/api/chat → 元数据 → /api/enhance → /api/generate` 整条链跑一遍，**不花钱也不联网**。它验的是接缝：正文有没有被停住、photo 档是不是真按四行回、服务端有没有给 photo 档塞 `REF_NOTE`、`/api/generate` 收到的 `size` / `quality` 对不对、带前缀 / 空镜 / 半身 / 没说的 / 中段那枚意图是否都透传。

**已接进 CI**（`check` job 里单独一步，它不需要浏览器，所以不跟性能门混在一起）—— 不然这条链只有人想起来才会跑一次，而它兜的正是"单测全绿但接缝坏掉"那类问题。

### 8.4 手测（判断"图有没有变好"的唯一依据）

同一句场景跑三种拼法，用图说话：

1. 现状（`scene + characterFaceDesc` 时代的拼法，作为对照）；
2. 只换锚点句；
3. 锚点句 + 摄影指导 + 模板。

判定标准要**事先写下来**，否则很容易看完图就改标准：

- 有没有**可指认的光源方向**（脸上 / 身上有明暗面，不是平光）；
- 环境与人物有没有**接触关系**（影子落在地上、衣服被环境色染到、前景有遮挡）；
- 自拍的那张，**手或手臂有没有入画**、脸是不是被近处的光打亮；
- 不看提示词，能不能一眼分出哪张是自拍、哪张是他拍；
- 特写那几张（拍脚、拍手、拍纹身），头有没有真的出画。

**这一条仍未做。** 单测与探针只能保证"提示词拼得对、字段没在接缝上掉"，不能保证"图变好看了"。

### 8.5 冒烟与全量门

- 对只认固定枚举尺寸的厂商发一张对话图：确认**没有非法的 size 值**发出去，且竖幅场景不再落回方框默认；
- 确认 `quality` 按厂商能力表决定发不发；
