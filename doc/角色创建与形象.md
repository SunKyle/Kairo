## 1. 核心概念与数据模型

### 1.1 四个概念

- **正脸（Front）是唯一的锚**：正脸是主视图，其余各张一律以正脸为参考图生成 —— 这是「跨图保持同一张脸」的唯一办法。
- **主视图只有一个：正面。** 没有「选主视图」这件事，只有「正面在不在」（有无即状态，不再存一份「哪张是主视图」）。
- **参考图管「形状」，设定管「语义」**，两者一起注入才谈得上跨图一致。
- **两个输入源分离**：
  - `ref` = 封面 / 头像。正脸生成成功后它就是正脸本身。
  - `sourceRef` = 第一步上传的底图。它服务两处：生成正脸时的参考图；其余四张与正脸一起送出的第二张参考图。正脸生成后 `ref` 被换成正脸，底图靠 `sourceRef` 保住。

### 1.2 数据模型（[types.ts](../src/types.ts)）

| 类型 | 作用 |
| --- | --- |
| `Character` | 角色主记录：`id / name / createdAt / fields / desc / persona / origin / voice / ref / sourceRef / views / staleViews / pinned`；`refKind` 只为读老导出包保留，不再写入 |
| `CharacterFields` | 结构化设定，16 项：`style, gender, identity, face, height, build, muscle, posture, hair, brows, eyes, noseMouth, facialHair, faceMarks, outfit, marks` |
| `CharacterPersona` | 人格六栏：`language / traits / voice / address / boundaries / samples`，只服务对话，不进设定图与出图提示词 |
| `CharacterViewKind` | 默认五类 `'front' \| 'full' \| 'side' \| 'outfit' \| 'body'` + 其他 `'detail' \| 'closeups'` |
| `CharacterView` | 单张设定图：`{ kind, data: Blob }`；`views` 只用于导出打包的往返，界面上的图走 IndexedDB |
| `CharacterDraft` | 一次 AI 起稿结果：`{ name, fields, persona, origin }`（名字不属于 `CharacterFields`，不进提示词） |
| `FieldOrigin` / `FieldOriginMap` | 设定里每一项是谁定的：`user / ai / pending`；没有这一项 = 用户自己写的 |
| `CharacterStat` | 用量（生成次数 / 最后使用），**从历史记录派生，不落盘** |
| `CharacterWork` | 该角色名下的一件作品（历史里带 `characterId` 的记录中的一张图），同样派生 |

### 1.3 字段分两组，行定义只有一份

键、顺序、必填、枚举都只有一份来源：[server/charSpec.js](../server/charSpec.js)。服务端拼起稿提示词用的是它，前端 [api.ts](../src/api.ts) 与 [lib/characterSpec.ts](../src/lib/characterSpec.ts) 也从它取键序与选项。

- 除 `outfit` / `marks` 之外的 14 项 = 面貌与身材特征 → 跟着**每一张成品**走；其中 `height / build / muscle / posture` 是后补的「身材那四行」。
- `outfit` / `marks` = 只喂给设定图，不该进普通创作提示词（行定义里的 `sheetOnly`）。

> 在这之前这几份清单是**各写各的**：服务端两段提示词里各一份行清单与一份必填枚举、前端一份字段顺序、一份标签对照表。加一栏要同时改六处，而漏掉任何一处都不报错 —— 表现只是「模型少回一行，那个字段静静地空着」。现在改一栏只有两处要跟手：行定义 + `types.ts` 的接口（后者的键由单测对着行定义比）。

### 1.4 存储分工

- 目录（`Character[]`）是轻量 JSON，放 localStorage；图是 Blob，按角色 id 存 IndexedDB（`putCharView` / `getCharViews`）。
- 设定图按**显示级**编码：最长边 1280、JPEG q0.88 —— 详情页头像与全屏查看器都要铺到 600 CSS px，512 那种复现用缩略图到这里一眼就糊。
- 启动时不碰这些图（5 张 × N 个角色全读进来太重），进详情页或向导才按角色取一次并缓存；同一 id 的并发读取用 `charViewsLoading` 去重（两个入口同时要同一个角色的图时，不去读两遍 IndexedDB）。

## 2. 三步创建流程

### 2.1 总览

创建是一条**独立流程**，以漂浮卡（模态）形式盖在角色页之上，关掉即回到原样。三步摊成一张卡：**步骤条在头上，内容在中间，进退在脚下**；没做到的那一步在条上是锁的，点不动 —— 顺序靠结构说明，不靠报错。

```
Basics ──► Main view ──► Other views ──► 详情页
（填设定     （生成正脸，      （生成其余       （落地页）
 /传参考图）   其余四张的锚）     四张 2×2）
```

三步的意图（[CharacterPage.vue](../src/components/CharacterPage.vue)）：

| 阶段 | 界面上的位置 | 意图 |
| --- | --- | --- |
| 1 Basics | 第 1 步 `Basics` | 填名字、性别与那份设定（收的全是字） |
| 2 Main view | 第 3 步 `Views` 的第一段 | 一张正脸，后面每张图都从它长出来 |
| 3 Other views | 第 3 步 `Views` 的第二段 | 其余四张视图，一排四格（窄屏 2×2） |

> **与源文档的一处偏差，以代码为准**：步骤条现在是 `Basics / Voice / Views`（`STEPS`）。嗓音那一步（把「这个人是谁」与「它听起来什么样」拆开）不在本篇范围；`Main view` 与 `Other views` 是最后一步屏内的两段题头，不再是两个独立步骤。本篇保留「填设定 → 出正脸 → 出其余四张」这条三步叙事，因为它是角色形象的构造顺序。

**解锁与打勾**（`stepUnlocked` / `stepDone`）：
- 第 1 步始终可进；后两步的前提相同 —— **角色已经在库里**（新建时是第 1 步存下的那条，编辑时就是正在改的这条）。
- 第 3 步**不再要求先有正脸**：正脸就在那一屏里，是它的第一件事；「先出正脸」这句话由屏内两段的顺序说一次，而不是靠锁。
- 做完的步骤在条上打勾（`PhCheck`），与「正在这一步」区分；两段连接线只在前一步做完时点亮。

> 第 1 步的解锁条件曾经只有 `wizardId`，而它**只在新建流程里**（第 1 步存完）才会有值 —— 详情页那枚 `Edit` 走的是 `editingId`，于是「改一条已有角色的嗓子」这条路根本进不去。现在详情页 Voice 那一块多了一枚 **Change voice**（`startVoiceEdit`）：它把 `wizardId` 认成这条角色、步数直接拨到嗓音那一步，所以既进得去、也存得下（存的仍是 `saveFromVoiceStep`，只是存完回详情而不是接着往下走）。`Edit` 那条路保持原样 —— 只改设定的那一轮不该被迫多走一步。

**角色在第 1 步保存时落库** —— 后面的步骤都要 `charId` 才能出图。所以第 1 步存下之后转成**只读摘要**（这一页没有「改角色」，留着可编辑表单只会让人再存一个副本）。`submit()` 只发意图，存完由父组件回调 `onSaved(id)` 推进步骤 —— 因为 `save` 是异步的，现在改步数会在角色还没进列表时先跳过去。

**卡身只有一栏。** 曾经这里有一栏常驻的「这个角色是什么」摘要（名字 + 已填的设定，第 3 步再加一枚主视图缩略），后来去掉了，理由三条：设定就在下面那张表里、而且是可改的，右栏那份只是同一份东西的只读副本，校对时眼睛本来就在可改的那几行上；第 3 步要的「基准图」就在那一屏正中间（主视图那一格比缩略图大得多），再缩到 100px 摆一遍，比的是同一张图；它占掉 248px，而三步里有两步基本空着 —— 空着的那一栏还把「这里应该有点什么」写在脸上。现在是一次回答一件事。

### 2.2 第 1 步：Basics

#### 起稿块（仅新建态）

整张卡上唯一享受「区域」待遇的一块，自带标题与引导语。

- 标题：**"Who are you creating?"**（问的是人，不是工具）；
- 引导语：一句话就能开工，细节只是起点 —— 不描述机器在背后做什么；
- 输入是一个 `textarea`（收的是「一个人的样子」而不是一个词），两行起步、随内容长高（`vGrow`）、6 行封顶后内部滚；
- **回车起稿，Shift+回车换行**（`onIdeaEnter`，带 `isComposing` / `keyCode 229` 输入法保护）；
- 起稿中整块走金色呼吸光晕（`halo-breathe`），因为 `textarea` 是替换元素放不了 `::after`，光晕挂在块上；
- 按钮文案随状态变化：`Draft the spec` → `Drafting…` → `Draft again`（已有内容时）。

#### 上传参考图 → 识图

- 参考图放在表单**最后**（比文字更能定形状，但可选）；
- 空态与有图态**占同样高度**，挑完图整块不跳动；
- 上传后**自动跑一次识图**（`onPickRef` → `draftFromImage`），因为「传张图上去」的意图本来就是照着它填；按钮留着是为了重读 / 改配置后重试；
- **编辑态不自动识图**：用户是来换参考图的，不是让模型把他校对过的那份设定重写一遍；
- 送模型的是**压到最长边 1024 的 JPEG**（`visionCopy`，q=0.85，先铺白底防透明 PNG 变黑）—— 上传原图可能几十 MB，而请求体上限 15MB，原样发会 413；存档用的仍是原图；
- 参考图上限 `MAX_REF_BYTES = 32MB`，且必须 `image/*`；
- 编辑态参考图**只能换、不能删**（底图是其余四张的参考资料，删掉那些图就失去「原本是什么」这一半信息）。

#### 表单分组

| 组 | 标题 | 提示 | 字段 |
| --- | --- | --- | --- |
| Basics | Basics | 卡片上的名字 + 模型用来定脸的那个词 + 用哪种媒介画 | `Name`*、`Gender`*、`Style` |
| Spec | Spec | The face travels with every image you generate. | `identity, face, hair, brows, eyes, noseMouth, facialHair, faceMarks` |
| Body | Body | Height, build, muscle and posture — also kept the same everywhere. | `height, build, muscle, posture` |
| Reference sheet only | Reference sheet only | Shaped into the reference sheet only — never merged into your other prompts. | `outfit, marks` + 自由 `Extra details` |
| Personality | Personality | Who they are and how they talk. Used in Chat only | `language, traits, voice, address, boundaries, samples` |

- **仅两条必填**：姓名（给卡片当标题）与性别（给模型定脸的第一道条件）。其余一律可留空 —— 所以「不标星号」已经说完了「可选」，不必反过来挂 `Optional`；
- 必填靠字段名后一枚**墨色星号**（`aria-hidden`），语义由控件的 `aria-required` 说，不用装饰表达；
- **性别与风格都是下拉，不是一个可以随便写的输入框**：模型只认 `female` / `male` 与那几个媒介词（枚举就在行定义里），留自由文字等于又把这件事交回给模型猜；模型偶尔写出枚举之外的值（如 `non-binary`、`watercolor`）时，把它当成额外一项显示出来（`genderOptions` / `styleOptions`）—— 吞掉它才是错的：界面上看不见，提示词里却还带着；
  - 为什么是下拉而不是一排胶囊：一排胶囊要先画一条灰槽、把选中的那枚涂成实心墨块，两个词的选项于是占掉一整条 46px 高的横档，风格那六枚更是铺成 470px 宽的一整块灰板 —— 而这一步其余每一行都只是「一个灰标签 + 一行字」。这五栏里真正要读的是**值**，不是控件本身；收成一个值的大小，行才回到同一套读法。它同时把「值」这一列留给了文字：`.ed-input` 那套无框无底照旧，右边一枚小箭头说明这里点得开（`.wz-select`）；
- **风格那一栏的第一项是 `Auto`，而且默认就是它**：对应的值是**空串**，空值会被 `filter(Boolean)` 滤掉，于是风格由参考图说了算。有底图时再写死一个媒介词，就是让文字去跟图打架；
- **`Body` 是补上的一组**：`Full body` 那一格的立意是「交代体型与服装轮廓」，而在此之前没有任何一项描述身材 —— 身材每张都是模型现编的，是跨图一致漏得最大的一处。这一组四行（`height / build / muscle / posture`）刻意**没有合成一行**：身高、骨架、肌肉、体态会各自独立漂移，写在一句话里模型会把它们平均成「中等身材」，而这一层的全部意义正是别让它平均。`muscle` 与 `posture` 允许留空（与 `Face marks` 同一条理由）—— 它们常常在这张图里根本看不见，硬要一个值等于逼模型去编；
- 规格字段是**自增高 `textarea`**：字段值上限 12 个词 / 约 70 字符，两列下每栏仅约 338px，`input` 会把边界值截在视野外；封顶三行再多内部滚。

> **`Extra details`（自由补充）**：它落在 `Reference sheet only` 那一组里，是整张表单唯一一处能写「固定栏位装不下的要求」的地方 —— 例如「别画成典型的 AI 脸」。它对应的值仍是 `Character.desc`，只被拼进**设定图**的提示词（`characterDesc`），不进普通创作提示词。组提示从 "never merged into your prompts" 改成 "never merged into your **other** prompts"，就是为了不再让人误读成「这一组填了也不起作用」。

### 2.3 AI 起稿的两条路（共用回填规则）

两条路拿到的是同一份「名字 + 结构化设定」，回填规矩一模一样（`applyDraft`）：

| | 文字起稿 | 识图 |
| --- | --- | --- |
| 函数 | `draftCharacterFields` | `draftCharacterFromImage` |
| 接口 | `/api/enhance` `mode: 'character'` | `mode: 'vision'` |
| 温度 | 0.7（具体又不重复） | 0.4（照图写，放开就会编） |
| 配置 | 文本模型 | 识图模型（能画图的模型未必会看图） |

- **固定行清单**（`Name` + 16 项设定 + 人格几栏，行数由行定义算出），不用 JSON —— 少一整类「围栏 / 多余解释」的解析坑，人也能直接读懂。行清单、必填枚举都由 [server/charSpec.js](../server/charSpec.js) 生成，两段提示词只留各自独有的规则；
- **`character` 允许把没提到的编具体**（模糊才是漂移的源头），但 `Face marks` / `Marks` 只在原句真提到时才写，否则默认给每个人添一道疤是错的；`Language` 同理 —— 只有原句真说了语言才写，**不许从名字、国籍或长相推**；
- **`vision` 只写看得见的**：凭空添疤、加义体等于把用户上传的人改成另一个人；`identity` 在识图档允许留空（`visionOptional`），因为按穿着猜职业正是「把推断当事实」；
- 名字只在还空着时补，用户自己敲进去的不被顶掉。

**来源标记（provenance，2026-10-15 落地）**：回填之后每一栏都带一个来源，落库为 `Character.origin`。

| 态 | 含义 | 界面 |
| --- | --- | --- |
| `user` | 用户给的：描述里说过的，或参考图里直接看得见的 | **不挂牌** |
| `ai` | 模型从用户给的东西里补出来的 | 挂 `AI` 徽标 |
| `pending` | 模型填了值但没有任何依据 —— 要用户自己看一眼 | 挂 `Check` 徽标 |

- 三态客户端推不出来，所以标记**由模型写**：行清单给出槽 `Identity: [user|ai|pending] <...>`，提示词给出分档判据（文字档问「描述里说没说过」，识图档问「图里看不看得见」），解析侧 [api.ts](../src/api.ts) 的 `splitOrigin` 摘掉标记并落表，值里一个标记都不许剩（漏了会被拼进出图提示词）；
- **摘不到标记一律落 `ai`，不进 `pending`**：我们只知道「这是模型写的」，替模型断言「它没依据」与替用户断言「他说过」是同一种错；模型完全没照做时，行为与加这套标记之前一样；
- 用户改一下那一栏，标记就消失（`markEdited` 删掉对应键）—— 「没有徽标 = 这一栏来自你」是确定的答案，不是「未知」；
- 人格那六栏也标（同属起稿填的），否则最容易被编的那一半漏掉了。

### 2.4 状态与并发保护

- **代次作废**（`draftSeq` / `visionSeq`）：等待中关向导、重开一轮、换一张图时，上一次的结果回来会对不上代次，整份丢弃 —— 否则会盖掉用户刚写的内容；
- 作废时要把 loading 一起松开（`cancelDraft` / `cancelVision`），否则按钮从此点不动；
- 一项都没解析出来时如实报错，不假装已经填好。

### 2.5 第 2 步：Main view

- 左图右事：空态 / 生成中 / 已有图**共用同一个框**，点下去画面不跳；
- 这一屏回答两件最该说清的事：
  1. **它会拿哪张图当参考** —— `Generated from`：有参考图 ⇒ `Your reference image`（图生图）；没有 ⇒ `Text only — no reference image`（纯文生图）。
  2. **接下来该点哪里** —— 主按钮永远代表「接下来该做的那件事」：还没有正脸 ⇒ 主按钮是卡身里那个 `Generate main view`（`primary`）；有了正脸 ⇒ 主按钮交给卡脚的 `Done`（卡身按钮降为普通描边，文案变 `Regenerate`）。
- 两个都涂黑会让「下一步做什么」变含糊，所以同一时刻主按钮只有一个；
- 生成中整格换成**停止入口**（暗幕 + CSS 绘制的停止方块 + 呼吸动画），与详情页设定图同一套。

### 2.6 第 3 步：Other views

- 一列四格，**一律以主视图为参考图** —— 这就是「同一张脸」的保证；
  - 实际是**一排四格**（`.wz-grid`）：四格统一用方框，竖幅的 `Full body` 在框里 `contain` 完整放下。照各自的真实比例铺，那一格会高出别人一截，四枚标签落不到同一条基线上 —— 一排里「哪张不齐」会被读成「这张出了问题」。窄屏退回 2×2，同一条规矩；
- 这一屏是**两段**（`Main view` / `Other views`），各有自己的题头，与第 1 步那几段同一套（`.wz-group`）：主视图是基准，其余四张照它长。「一次补齐」挂在 `Other views` 的题头上 —— 说明与动作讲的是同一件事；
- 可**单张生成**，也可**一次补齐**（`generateAll`）；
- 一次补齐的按钮文案：`Generate N remaining`，四张齐了变 `All views ready` 并停下 —— 齐了还能点、点了没反应，看着像坏了；
- 说明里点出策略：一张一张来或一次补齐，**早期失败就停下**，而不是再烧四次调用。

## 3. 设定图：五类视图、参考图、生成链路、尺寸

### 3.1 五类默认视图与两类其他视图

设定图定义在 [api.ts](../src/api.ts) 的 `CHARACTER_VIEWS`，**分两组**（2026-10-15，T10 五类对齐）：默认五类进向导与「一次补齐」，其他设定图只在详情页按需补。分组由 `group` 那一列定。

**默认五类** —— PRD §3.2-A / §8 的那五格，前四格与 PRD 逐字对齐：

| kind | 标签 | 取景 | 补上了什么 |
| --- | --- | --- | --- |
| `front` | Front | square | 一张正脸，定「这个人是谁」（主视图、整条链的锚） |
| `full` | Full body | portrait | 全身，交代体型与服装轮廓 |
| `side` | Side view | portrait | 单张全身侧面，交代侧身线条与朝向（2026-10-15 新增） |
| `outfit` | Outfit | portrait | 穿在身上的完整服装 —— `outfit` 那个字段终于有属于自己的图了（2026-10-15 新增） |
| `body` | Body | square | 肢体 2×2（手 / 前臂 / 腿 / 脚），给「角色发一张自己身体的特写」当参考 |

> **第五格与 PRD 不同是有意的**：PRD §8 写的是「表情设定」，而这里用**肢体** —— 2026-10-06 的决策。界面上如实叫它 `Body`，不借 PRD 那个名字。

**其他设定图** —— 退役的历史键，不删、不迁移，但不再默认生成：

| kind | 标签 | 取景 | 补上了什么 |
| --- | --- | --- | --- |
| `detail` | Angles | square | 头部转面 2×2（左右正侧 + 上下 45° 俯仰），交代鼻梁、下颌线、耳位、发顶 |
| `closeups` | Details | square | 细部特写 2×2（眼 / 皮肤与脸标 / 手 / 面料配件），交代材质与零件 |

- 它们归在详情页的「其他设定图」一排 —— 那一层同时就是 PRD 要的「可自由增加其他设定图」的容器。**不参与「还差几张」的计数**：那是个待办数字，而这两张是「想加就加」（`filledCount` / `missingCount` 只算默认组）。
- 按角色自定义设定图（用户自己命名、自己写提示词）**未做**：那要把 `CHARACTER_VIEWS` 从常量改成「按角色算」并新增存储，容器已就位，内容还没做。

### 3.2 `kind` 是索引里的键

- `kind` 可以改 label 与提示词，**别改这个字符串** —— 改了库里已存的图会对不上（`getCharViews` 按已知 kind 过滤，认不出的键**静默**丢掉：图还在、界面上凭空少一格）。
- 唯一的例外是 2026-10-06 那次：`expression`（表情 2×2）**换成了 `body`**。换 key 而不是改语义，是因为这次换的是**另一类内容**（脸 → 肢体），老图留着会被当成「肢体参考」发出去；那一格宁可为空。与 `detail` 那次不同 —— 那次换的只是同一类内容里的另一种拍法（3/4 头像 → 转面头像）。
- T10 加 `side` / `outfit` 也照这条走：库里没有任何存量图，所以谈不上迁移；而「把 `detail` 改造成侧面」属于内容类别变了（2×2 网格 ≠ 单张侧面），不能复用键 —— 复用会让库里已存的网格被当成「单张侧面」发出去。
- 修饰词里**绝不能出现 "character reference sheet"**：它在图像模型那里是很强的排版概念，写进去模型真会画一张拼版而不是单人图。新增那两格各压了 `not a grid` / `not multiple panels`：默认五类里已经有一张 2×2 网格，模型看到 side view / outfit 很容易顺手交一张多格图。

### 3.3 参考图规则（`genCharView`）

- **正脸**：有 `sourceRef`（或老数据的 `ref`）就以它为参考图，没有就是纯文生图 —— 底图是怎么来的（这次上传的，还是老角色沿用的旧封面）都不改变这条流水线；
- **其余四张**：一律以正脸为参考图；正脸与底图一起送（底图补正面头像交代不了的发型轮廓、体态、服装轮廓）；
- 不认多图的模型（`caps.multiImage === 'no'`）**只送正脸** —— 宁可少一张，也不能为了多送一张把整个请求弄失败。

### 3.4 「参考图只管这个人是谁，不管这一张怎么拍」

用户报过：「上传的参考图是侧面图，则生成的正面图也是侧面的」。

根因不是「正面」两个字没写 —— 那句一直在 —— 而是**参考图在 i2i 那条路上是最强的机位来源**：图像编辑的默认行为就是保住输入的姿态，一句 `front-facing headshot` 拗不过它。构图那一篇当初把这条写成了「参考图同时是同一张脸的唯一保证，又是最强的机位与光线污染源」，但只落进了提示词改写那条路，没落到设定图上。

现在一起补（提示词由 `characterViewPrompt` 一处拼，单测直接断言）：

| 补了什么 | 写在哪 |
| --- | --- |
| 正面拆成**可判定**的条件：两眼齐平且都可见、鼻尖朝向镜头、头不转不歪 | `front` 的 suffix |
| 三个否定：`not a profile` / `not a side view` / `not a three-quarter view` | 同上 |
| **把失败场景直接写进去**：`the face turned front-on even if the reference image shows the person from the side` | 同上 |
| `REF_IDENTITY_ONLY`：参考图只管脸 / 特征 / 头发 / 体型，**忽略它们的姿态、机位与光，不许跟着它们朝的方向抄** | 有参考图时追加在末尾。**写成复数**：正脸那格只送一张（底图），其余四格送两张（正脸 + 底图），单数那句到了那四格就指错对象 |

顺序是有意的：`characterViewPrompt` 拼的是「设定 → 取景 → 参考图那句」，那句元指令垫在最末（与对话出图那条路的负面约束同一个排法），不挤掉「画什么」。

**它不适用于转面那一格**：`detail`（Angles）要的正是左右正侧与俯仰 —— 「别抄姿态」说的是「别抄**参考图**的姿态」，不是「别换方向」，单测把这两条钉在一起。

### 3.5 尺寸与取景

- 每一类视图只声明**取景档**：`square` 或 `portrait`；实际像素由 `viewSize(framing)` 在厂商能力表里挑**最接近**的那一档，挑不出来才退回封面尺寸。
- 竖幅的目标比例是 **2:3**：站姿人形只有竖框装得下，9:16 会把人缩得太小、面料与配饰的细节跟着丢，3:4 又偏紧、容易切到脚。
- 像素值写不死 —— 各厂商只认自己那几档，写死一个在只认枚举的厂商那里会整条失败。

### 3.6 状态按「角色 + 视图」维度

这是几条硬约束的落点（曾出现过「生成 A 时切到 B，B 的格子也显示生成中」的问题）：

- `charViewBusy: Record<charId, CharacterViewKind[]>` —— 必须按角色分开；
- 中断手柄 `charViewControllers` 的键 = `` `${charId}:${kind}` ``；
- 同一张重复点无意义（第二次会盖掉第一次），**别的张在跑不影响这一张** —— 它们之间没有依赖。

依赖与守卫：

| 情况 | 行为 |
| --- | --- |
| 正脸未生成 | 其余四格**上锁**（`isLocked`，`PhLockSimple` 图标套圆形底），而不是可点但会报错 —— 把顺序摆在明面上 |
| 正脸正在重跑 | 其余入口**停用**（`viewBlocked`）：那几张拿到的会是上一版正脸，「同一张脸」前提就破了。正脸自己不依赖任何视图 |
| 其余时候 | 几张可同时跑（它们之间没有依赖） |

中断与落库：

- `stopCharView` 只 abort 对应那一张的手柄，别张不受影响；
- **只有成功写入那一刻才作数**，半路掐断不会留下坏图，旧图保留；
- 中断走 `notice` 显示 `Generation stopped.`，**不按报错处理**；
- 正脸生成成功后**写回 `c.ref`**（封面 / 头像 / 列表卡都读它），旧封面 Blob 的 object URL 释放；
- 重跑正脸后其余四张是照上一版正脸出的 ⇒ 提醒一句，但**不替用户删**（删不可逆，「要不要重跑」只有他知道）。

### 3.7 一次补齐与按需加载

- `genRemainingViews` **串行**跑：每张都以前一张为参考图，并行只会互相抢带宽；中途失败（多半是配置或配额）直接停下，免得连错四次。已经自己在跑的那张跳过。
- `loadCharViews(id)` 按角色缓存，已经取过就不再读 IndexedDB；同一 id 通过 `charViewsLoading` Map 去重；**启动时不碰这些图**。

## 4. 详情页、列表与管理

### 4.1 详情页（落地页）

详情页是角色的「家」：完整设定表、大图查看、用它开画。

- **hero**：头像用正脸（圆形容器裁的是一张脸）；名字 + 设定摘要；`heroMeta` 用量行（生成次数 → 创建时间 → 最后使用，没有的部分不占位）；标签（`N / 5 views`、`Main view · Front` 或 `No main view yet`）；右侧一次补齐 CTA（`Generate N more` / `Generate all views`，齐了换成 `All views ready` 并把主操作让给「跟它说话」）。
- **Reference sheet 网格**：**默认五类**五格（主视图 / 全身 / 侧面 / 服装 / 肢体）；下面另起一排「其他设定图」（转面 / 细部，可选，不计数）。
  - 空格点一下即生成；有图点开看大图；
  - 生成中整格换成停止入口；
  - 主视图（正面）带眼睛标 `PhEye`；其余空格在正脸未生成时上锁；
  - 生成进度显示在 panel 标题旁（视线必经位置）；
  - 面板那句说明**第一句说用途**（`These images define how the character looks.`）—— PRD §5.3 要求这一区「明确这些图片用于定义角色形象」，原来那句只讲了视图之间的推导关系（见 `useCharacterDetail` 的 `sheetNote`）。
- **一致性提醒条**（T11，2026-10-15）：基准变了之后，网格**上方**挂着一条持续提醒，点名哪几张跟当前基准对不上，并给两个动作 —— `Regenerate these`（按 `CHARACTER_VIEWS` 顺序串行重跑，正脸打头）/ `Keep them`（撤标记，一张图都不动）。
  - **它是持续态，不是 toast**：用户可能过一会儿才回来处理，「到底哪几张对不上」只有一直摆在这儿才看得见（PRD §3.2-A 的「提示影响 + 保留现有图片 + 由用户决定」）；
  - 基准有两个来源，判据是**清单里有没有 `front`**：重跑正脸 ⇒ 其余每张都过期、正脸不在清单里；改设定 ⇒ **所有已出过的图连正脸一起**过期（正脸也是照旧设定生的）；
  - 标记存在 `Character.staleViews`（可选字段，additive，零迁移），清单与算法见 [lib/staleViews.ts](../src/lib/staleViews.ts)。
- **Made with this character**：该角色出过的图（来自历史，按 `characterId` 归拢），只摆最近 12 张。
  - 多出来的那句 **`N more in History` 是枚按钮**（T12 前是个点不动的 `<p>`）：跳历史页并带上 `#/history/by/<charId>`，于是历史页只显示这个角色的图；
  - **深链不能借 `#/history/<id>` 那一格** —— 它自 S-21 起就是「打开某条记录的预览」，而角色 id 与记录 id 都是同一个生成器给的，混用会静默失效。所以另起 `by` 这个关键字段（见 [lib/router.ts](../src/lib/router.ts)）。
- **Spec**：固定项按顺序排 + 可选 `Notes`（占满整行）。

### 4.2 大图查看器（`viewer`）

- 无底色设计，图片圆角 + 投影，翻页钮压在图两侧；遮罩固定深色（与主题无关）；
- 左右键翻页（到头绕回另一头，循环比禁用更好用），Esc 逐层退；
- 位置指示 `i / n`，只有一张时不显示（「1 / 1」是废话）；
- 动作只剩 **Regenerate**（主视图唯一 = 正面，不存在「设为主视图」）；正脸重跑期间其余视图的 Regenerate 停用；重跑时原地换成 **Stop**；
- **模态焦点管理**：打开时焦点收进来，关闭时归还到原格子；Tab 圈在浮层内（`trapTab`）。

### 4.3 列表与卡片

- 角色海报卡：顶图全出血铺满，**封面 = 主视图**（生成正脸时写回 `ref`，所以列表读 `ref` 就够，不必为每张卡加载设定图）；3:4 比例，圆角、无边框、靠阴影浮起；
- 信息区毛玻璃 + 底部渐变暗幕托起白字（两者同一元素承载，避免边界不重合）；
- 名字与 **Chat** 同排（`createFromCard` → 直接拿这个角色进对话）；窄卡一行放不下整句，所以按钮上只写 `Chat`，整句放在 `aria-label` 里；
- 用量三格（生成次数 / 创建 / 最后使用）+ 竖向分隔；
- 特征胶囊最多三枚（`face → hair → eyes → outfit → marks`，跨场景不变的面貌特征排前面）；
- 管理动作（置顶 / 编辑 / 复制 / 导出 / 删除）收进右上角 `⋮` 菜单 —— 低频动作不该常驻（窄屏上三枚圆钮还会占掉整条上沿），同一时刻只开一个；置顶状态由左上角一枚角标说明，角标本身不做成按钮（卡片已有一层铺满的命中区）。

### 4.4 管理操作

| 操作 | 实现 | 要点 |
| --- | --- | --- |
| 新建 | `saveCharFromPage` → 角色页 `onSaved(id)` | `ref` 与 `sourceRef` **指向同一 Blob 但语义不同**，两个字段都写 |
| 编辑 | `saveCharFromPage`（带 id）→ `onUpdated(id)` | 名字 / 设定照单更新；**封面 `ref` 一律不碰**（换参考图不该顺手把脸换掉）；设定动了且已有设定图时，把已出过的图（连正脸）标进 `staleViews`，由详情页那条提醒条接手 |
| 复制 | `duplicateChar` | Blob 用 `reBlob`（`slice`）换实例 —— 两个角色共用一个 Blob 会共用 object URL，一边释放另一边图就裂了 |
| 导出 | `exportChar` | zip = `character.json` + `ref.*` + 全部设定图（默认五类 + 其他）；导出前先确保取过设定图（懒加载，不取包里会少图） |
| 导入 | `importCharFile` | 文件里的 **id 一律换新**（撞上会让列表出现两条同 id，渲染和删除都错乱）；上限 64MB |
| 删除 | `deleteChar` | 立刻消失 + 几秒内可撤销，窗口结束才真正落盘并释放图；当前套用的角色会被 `detachCharacter` 摘掉 |

> 落盘顺序要求（复制 / 导入）：**先把图写进 IndexedDB，再 `saveCharacters`** —— 后者会按 key 归属清理，顺序反了会把刚写进去的图当成「已不在的角色名下」删掉。

## 5. 形象一致性

### 5.1 先把两个问题拆开

「是不是同一张脸」与「这一张怎么拍」曾经被绑在一个布尔上（同一个开关既管拼不拼外貌、又管发不发参考图）。绑在一起等于说「只要它在画面里，构图就必须听设定表的」—— 而设定表里从来没有构图。正确的分工：

| 问题 | 谁回答 | 默认 |
| --- | --- | --- |
| 画面里有没有这个人 | 聊天模型（出图意图里那一位） | 没有（场景照） |
| 这个人长什么样 | 设定（锚点句）+ 设定图 | 无参考图时纯文字 |
| 这张照片**是怎么拍的** | 出图那一路的构图层（属《角色出图》） | 中性第三人称 |

本篇只负责前两行与「参考图取哪几张」；「怎么拍」的六层拼装、摄影指导、自拍 / 他拍模板都在《角色出图》。

### 5.2 外貌从「token 清单」换成锚点句

**旧做法**：出图提示词是 `scene + ", " + characterFaceDesc` —— 把外貌设定的二十个逗号短语整份接在场景后面，出来是这样一个东西：

```
photorealistic, female, a night-shift nurse in a coastal town,
oval face with high cheekbones, fair skin, late twenties,
tall and lean, black bob, straight brows, dark eyes,
small nose, full lips, clean-shaven
```

**它的代价从来没人算过**：那份清单在锁长相的同时，也把**表情、姿态、机位一起锁住了**。`build` 的 "tall and lean" 与 `face` 的 "oval face with high cheekbones" 之间没有任何分隔语义，它们在模型眼里是同一层权重 —— 「多高」和「鼻子什么样」被并列成了同级信息。这种 token 密度下，模型最省力的解法就是交一张证件照；而参考图恰好也是纯背景、中性表情、居中的证件照，两者互相加强。**死板不是模型的脾气，是缺省值。**

**现在的做法**：只锁骨相、发色发型与一个标识，写进一句自然语言；其余全部放开。

- **锁身份**：颧骨 / 脸型、发色与发型轮廓、一个标识（疤 / 义体 / 配饰）、体型。
- **放开一切会随场景变的东西**：表情、视线、姿态、手在做什么、衣服的褶皱、光在脸上的方向、景深。
- **落点**：`characterAnchor`（[lib/chatPhoto.ts](../src/lib/chatPhoto.ts)）。它只取 9 项 —— `face / hair / eyes / brows / noseMouth / facialHair / faceMarks / marks / build`，**顺序即取舍优先级**（清单变长时砍的是末位）。上限就是清单长度，不另抄一份清单：字段的权威定义仍在 [server/charSpec.js](../server/charSpec.js)。
- **老角色不退回全量描述**：没有结构化字段的角色（加字段之前存的）拿到的锚点句是空串，仍然靠参考图锁脸。这是有意的 —— 老角色的 `desc` 里什么都有（身份、性格、穿什么），把它当锚点句用等于把治好的病再请回来。
- **画面里没有脸的时候不拼锚点句**：特写落在身上（手、脚、纹身）时，那九项全是头部特征，画面里一个字都落不到实处，却仍然在把镜头往回拽。这一档的身份由「这一格是那个人」那一句接管（判据是 `closeOnBody`，属《角色出图》）。

> `characterFaceDesc` 那份全量拼法仍留在 [api.ts](../src/api.ts)（设定图走的是更全的 `characterDesc`，它连 `Extra details` 一起拼），但对话这条路不再用它。

### 5.3 参考图按视图与景别挑

参考图的取舍不是「越多越像」，而是「这一张要拍什么，就挑能回答它的那几张」。

**取图函数**：`charRefSrcsOf(charId, order?)`（[useCharacters.ts](../src/composables/useCharacters.ts)）。

- 传了 `order` 就按它挑，**不传就按 `CHARACTER_VIEWS` 的默认顺序**（`front` 打头）—— 那条路逐字不变；
- 认不出的视图名直接跳过（它指的那张不存在，每 push 一张都要读一次 IndexedDB、转一次 data URL，不认识的键就是白读一次）；
- 最多 `MAX_CHAR_REFS = 4` 张。

**顺序表**：`shotViewOrder(shot, frame?, onBody?)`（[lib/chatPhoto.ts](../src/lib/chatPhoto.ts)）。

| 这一张 | 顺序 | 理由 |
| --- | --- | --- |
| 他拍（默认） | `full, front, closeups` | 站姿 / 走 / 全身由 `full` 交代得住 |
| 自拍 | `front, closeups, full` | 脸是主体，正面像打头 |
| 特写 | `front, closeups, body` | 全身像出局（把取景往回拽）；`body` 进来（这一档画面里常常没有脸）；`closeups` 紧跟（眼、皮肤与脸标、手、面料正是特写的内容） |
| 特写且落在身上 | `body, closeups, front` | `front` 从打头**降到最末**，见下 |

**`front` 为什么会在这一档降到最末**：`front` 是**头肩证件照**，放第一位就是让 i2i 最想保住的那张构图变成「一张脸」—— 一边在提示词里写「头出画」，一边在参考图里说「这儿有一张脸」，模型会挑参考图。它降到最后仍贡献「还是这个人」（皮肤、体态），但不再决定取景；`body`（2×2 的手 / 前臂 / 腿 / 脚）提到最前，因为拍脚时它是唯一说明「这个人的脚长什么样」的那张。

- 这一档与「头一张不留给带版式先验的 2×2 网格」那条纪律冲突：**内容胜过版式**，代价（网格先验带来的多格 / 多人 / 多手）由负面约束兜着；`full` 依然出局，张数仍是 3，`MAX_CHAR_REFS = 4` 不动。
- **这一条要拿真图验收**：如果实测发现脚的特写开始出现拼版，第一个该退的就是这条（把 `front` 放回第一位，靠提示词那一侧硬扛）。
- 顺序只影响两端（特写与全身），**中间那一档逐字等于从前** —— 少传一项就等于上一版。

### 5.4 设定图与聊天出图各自的职责边界

| | 设定图 | 聊天出图 |
| --- | --- | --- |
| 回答 | 这个人是谁、长什么样 | 这一张照片怎么拍 |
| 参考图 | 正脸是锚，其余以正脸为参考 | 按视角 / 景别挑，最多 4 张 |
| 提示词 | 设定 + 取景 + 「参考图只管身份」 | 六层拼装（属《角色出图》） |
| 产物 | 存进角色（库里的设定图） | 存进对话，同时记一条历史归到角色名下 |

- **设定图只在「要同一张脸」时才发**：画面里没有这个人时，**一张参考图都不发**。默认（没说）也是场景照 —— 一张风景里长出一个人是整张废掉，而一张自拍少了参考图只是「不像本人」，猜错的代价不对称，所以默认落在伤害小的那一侧。
- **发的时候只当身份参考**：`REF_IDENTITY_ONLY` 明说忽略参考图的姿态、机位与光（§3.4）。不写的话，模型默认会把参考图的构图一起继承。
- **出图不改设定图、不写回**：聊天图不会污染角色卡；设定图也不替聊天图决定构图。两条路的落点各自独立 —— 字节在 `chat_images`，作品记录在 `history`（`source: 'chat-photo'`，`characterId` 是对话里那个角色），两边生命周期不同，互不引用（清空对话不带走历史，清理历史也不裂掉对话）。
- **识图与出图是两个配置**，各管一段：用户发图那一轮切到识图配置；同一轮角色又回图，就是「识图模型看进来 + 出图模型画出去」，不要把两条配置路径搅在一起。
- 2026-10-20 起协议改为 `emit_message_meta` 工具调用 —— 它改的是「意图怎么传」，不改变上面这条分工。

### 5.5 输入侧附件（已实现，属输入侧）

「用户给角色发图」这条链是完整的，不是半成品；它决定角色「看得见什么」，与输出侧（角色发图）是两件事：

| 环节 | 落点 |
| --- | --- |
| 输入框左侧的附图键 | `ChatPage.vue` 的 `aria-label="Attach an image"` |
| 选图 → 压到长边 1024 → 缩略图预览 / 可撤 | `shrinkForChat`、`attach` |
| 发送时把 Blob 一起交出 | `emit('send', id, text, blob)` |
| 图存 `chat_images`，消息上只挂 `imageId` | `sendChat` → `putChatImage` |
| **这一轮自动切到识图配置**，读回 Blob 转 data URL 一起发 | `runChat` |
| 历史里的图不重发（一张上千 token） | `chatStream({ images })` |
| 气泡渲染、导出 / 导入带图 | `bubble-img`、`ImportedChat.images` |

### 5.6 三条不变量

1. **身份先于拍摄**：先说清「是不是这个人」，再谈「这一张怎么拍」。顺序反了，参考图就会去决定构图。
2. **锚点不补表情**：表情、视线、姿态交给场景与出图模型自己长；再写一遍等于又把它按死成证件照。
3. **降级只降清晰度，不降可出图**：参考图读不出来仍照画（纯文生图），只是「可能不像它」；反过来，缺一张图不该让整条链路失败。

## 6. 交互、状态与无障碍

- **模态焦点陷阱**：向导与查看器都是模态，打开时焦点收进卡片本身（先让读屏念出这是什么），关闭时归还到触发它的按钮；同一时刻只会开一个；
- **Esc 逐层退**：先关大图 → 再关卡片菜单 → 再关向导 → 最后回列表；
- **代次作废在途请求**：起稿 / 识图都有 `seq`，关向导、换图、重开时旧结果整份丢弃；
- **notice 全局提示**：角色页的报错走 `notice`（`fail` 写的是首页那条 `.err`，在角色页不渲染等于没提示）；
- **所有状态按「角色 + 视图」隔离**，不同角色可同时生成设定图，各自独立显示状态与控制入口。

## 7. 明确不做 / 验收

### 7.1 明确不做

| 不做 | 为什么 |
| --- | --- |
| 「选主视图」这个动作 | 主视图写死 `kind === 'front'`，正脸就是唯一基准；`refKind` 只为让老导出包读得进来 |
| 删除或迁移退役的 `detail` / `closeups` | 不删、不迁移，只是不再默认生成；它们仍能在详情页按需补 |
| 复用 `kind` 去承载另一类内容 | `expression → body` 那次换了 key，因为脸与肢体不是同一类；复用会让库里的老图被错误地当成新语义发出去 |
| 「其他设定图」参与「还差几张」的计数 | 那是个待办数字，而这两张是「想加就加」 |
| 在设定图修饰词里写 "character reference sheet" | 它在图像模型那里是很强的排版概念，写进去会画成拼版而不是单人图 |
| 按角色自定义设定图（用户命名 + 写提示词） | **未做**：需要把 `CHARACTER_VIEWS` 从常量改成按角色算并新增存储；容器已就位 |
| 聊天发图协议、频率、失败文案、六层拼装 | 不属本篇，见《角色出图》 |

### 7.2 验收

- **单测该钉住的行为**（纯函数，不联网）：
  - `characterViewPrompt`：`front` 的可判定条件与三个否定；`REF_IDENTITY_ONLY` 的复数写法；`detail` 不受「别换方向」约束；
  - `CHARACTER_VIEWS`：分组、`kind` 唯一、默认组恰好五类、`framing` 只有 square / portrait；
  - `characterAnchor`：只取 9 项、顺序即优先级、老角色返回空串（不退回全量描述）；
  - `shotViewOrder`：两端之外的每一档逐字等于从前；`onBody` 的 `front` 降到最末；
  - `staleViews`：重跑正脸 / 改设定两种基准的清单与「保留」撤标记；
  - `splitOrigin`：三种写法都摘掉标记，值里不残留 `[user]` / `[ai]` / `[pending]`。
- **构建与回归**：`vue-tsc --noEmit`、`npm run lint`、`vitest`；命令与门禁见《贡献与维护规范》。
- **手测**：换参考图重出正脸 → 其余四张是否被点名；改设定 → 是否连正脸一起被点名；`Edit` 与 `Change voice` 两条入口是否都能进出。

## 一句话回顾

> 建角色是「填设定 → 出正脸 → 出其余四张」一条线，拆成三步一张卡；正脸是唯一主视图与整条流水线的锚，其余四张都照它生。设定管「这个人是谁」、参考图管「这个人长什么样」，两者分开存、分开用；而一旦要进画面，先定「是不是同一张脸」，再让别人去管「这一张怎么拍」—— 跨图的同一张脸就是这么来的。
