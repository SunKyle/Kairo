## 0. 一轮对话的生命周期

```
① 输入区     回车 → 本地先拦超长（CHAT_MAX_CHARS = 8000），原文留着
      ↓
② ChatPage   一条 user 消息先进内存 → 取最近 CHAT_WINDOW = 20 条拼上下文
      ↓
③ api.ts     POST /api/chat（character + messages + 对话模型配置）
      ↓
④ server     入口校验 → chatSystemPrompt() 拼 15 块 → 转发上游 SSE
             → 收窄成 NDJSON（{"delta"} / {"done","finish"} / {"error"}）
             → tool_calls 攒成 mood / photo（§2.6）
      ↓
⑤ ChatPage   逐行解析 → 追加到内存里那一个响应式字符串（**不逐块写盘**）
      ↓
⑥ 收尾       putChatMessage 一次（stopped / truncated / mood 一起落）
             · putCharMood（§5.6）· 左栏那行摘要就地更新（chatLast）
      ↓
⑦ 后台       条数够了 → maybeSummarize → chat_summaries（§4）
                           └→ onSummarized ┬ autoExtract（记忆条目）
                                            └ autoEvaluate（关系，§6.4）
```

| 跳 | 归 | 关键不变量 |
| --- | --- | --- |
| ① 输入 | §3.5 | 超长**报错不静默切**，原文留着 |
| ② 上下文 | §3.6 | 只带 20 条，被截掉的**不从库里删** |
| ③④ 服务端 | §2 | 入口是公开的（无鉴权，设计如此），限条数 / 限长 / 限流都在服务端再来一道 |
| ⑤ 渲染 | §3.1 | 几种收场都**不丢已经收到的字**（§3.3） |
| ⑥ 落盘 | §1.2 / §5.5 | 状态与消息**用同一个值**；落笔前比一次 `chatSeq` |
| ⑦ 后台 | §4 / §6.4 | 全程静默：失败就退出，下一轮再试 |

**三条贯穿全程的纪律**：**本地优先**（无账号、无服务端数据库、无常驻进程；密钥在用户手里，
端点没有鉴权 —— 所以限长与 `rateLimit` 都不能省，也正因为没有可信的后台时钟，主动联系被砍，§9）；
**状态按角色分键**（`chatBusy` / `chatControllers` / `chatMood` / `chatLast` / `chatSeqOf`，
不分开就是"A 在说话时切到 B，B 显示正在输入"）；**不丢字、不猜**（见 §3.3 / §4.9 / §5.8）。

## 1. 数据模型

### 1.1 人格字段（`Character.persona`）

```ts
/* 角色的"人格"：聊天才用得上的一组设定。
   刻意与 CharacterFields 分开存 —— 那边是长相，会被 characterFaceDesc 拼进每一张
   出图的提示词；把性格混进去，等于让"它是什么人"去污染"它长什么样"的像素级约束 */
export interface CharacterPersona {
  language?: string   // 说哪种语言。空 = 跟着用户走（兼容性红线，§8.7）
  traits: string      // 性格：是个什么样的人
  voice: string       // 说话方式：怎么说话
  address: string     // 怎么称呼用户、与用户是什么关系
  boundaries: string  // 禁区：这个角色绝不会做的事
  samples?: string    // 两三组示例对（2026-10-08 加）：照着抄口吻，不是描述
}
```

挂载：`Character` 上加 `persona?: CharacterPersona`。加这个字段之前存下来的角色没有它，
读入时补空串（`coerceCharPersona`），所以界面上读的地方可以当它一定存在。

**为什么是分开的几栏，而不是一整段自由文本**：`traits` 与 `voice` 必须分开 ——
"是个什么样的人"和"话怎么说出来"是两件事，写在同一段里模型会把两者平均掉：性格写了、
说话方式被稀释成通用口吻。而"超拟人"恰恰主要靠后者。`language` 同理（§8.7）。

**为什么不复用 `identity`**：`identity` 是给图像模型的（"veteran space smuggler, worn flight jacket"），
它的职责是让画面里的衣服和道具对。拿它当性格用，模型只会演一个职业，不会演一个人。
**为什么不动 `CharacterFields`**：那几个字段的顺序被 `CHAR_FIELD_ORDER` 定死，顺序一变
上游拿到的条件就变，跨图一致性随之失效（[api.ts](../src/api.ts) 那段注释已经说了这件事）。

### 1.2 消息记录（`ChatMessage`）

| 字段 | 说明 |
| --- | --- |
| `id` / `charId` / `role` / `content` / `createdAt` | 基本形状。`charId` 与 `HistoryEntry.characterId` 同一口径：角色被删时它的消息一并清掉 |
| `stopped?` | 用户中途按了 Stop，这条只说到一半。**与"上游报错"分开记**：截断是我们自己按的，不是坏数据，下次拼上下文时它照样是一条正常的历史消息 |
| `truncated?` | 上游撞上 `max_tokens` 而停下（`finish_reason === 'length'`）。与 `stopped` 分开：那个是人按的，这个是额度用完了 |
| `mood?` | 这一轮的情绪，一个小写英文词（服务端 `CHAT_MOOD_RE` 的形状）。它来自正文之外的 `emit_message_meta` 工具调用，正文里永远不含它 |
| `layer?` | 这一条的心理层次 `say` / `think` / `act`（`MessageLayer`）。缺省按 `say` 处理、载入时 coerce；additive 字段，不升 `DB_VERSION`（详见《[对话体验.md](对话体验.md)》§6） |

**没有 `sessionId`**：一期一个角色一条连续对话；将来开多段会话时再加，读入补默认值即可（§1.8）。
**附件不在消息里**：用户发来的那张存 `imageId`、角色回的那张存 `photo`（场景描述）与 `photoId`
（已画出来的字节，字节在 `chat_images` 表）。渲染位置也不同 —— 用户那张压在文字**上面**
（那是这句话的前提），角色那张垫在文字**下面**（先读它说的话）。

### 1.3 摘要（`ChatSummary`）

```ts
export interface ChatSummary {
  charId: string
  text: string        // 简报正文
  upToId: string      // 覆盖到最后哪一条
  upToAt: number      // 那条的时间戳
  covered: number     // 已经被覆盖的条数
  updatedAt: number   // 最后一次压缩的时间
}
```

**为什么不是只存一段文本**：`upToAt` 回答"从哪一条之后还没进摘要"，下一批从这儿往后接；
`covered` 是"已经进去多少条"，配上总条数才知道该不该再压一次。有它就不必为了判断这件事
把消息读一遍 —— 三者缺一个，都会退化成"每次都要全量读"。

### 1.4 心情（`CharacterMood`）

**一条状态，不是一条日志** —— 它回答"它现在是什么心情"，不回答"这些天的心情曲线"，
所以一个角色一条、覆盖写、没有历史。

| 字段 | 说明 |
| --- | --- |
| `charId` | 主键，与 `ChatSummary` 同一口径 |
| `word` | 情绪词，与 `ChatMessage.mood` 是**同一个值**；空串 = 没有（不写这条记录） |
| `at` | 这个词是什么时候的。喂不喂回 system 只看它（6 小时窗口，§5.3） |

与 `ChatSummary` 同一层（都是对话侧的派生状态，都跟着消息一起被清），
但与 `Character` 分开存 —— 那边是"长什么样"的目录，把情绪混进去等于让
"它此刻恼不恼"去污染一份"它长什么样"的档案。

### 1.5 关系（`Character.relationship`）

```ts
export interface RelationshipState {
  familiarity: number   // 0..REL_MAX
  trust: number
  affection: number
  updatedAt: number     // 最近一次评估
}
// Character 追加：relationship?: RelationshipState
```

**additive 字段、零迁移**：挂在 `Character` 上、走 localStorage，与 `origin` / `pinned` /
`staleViews` 同一条路子（新字段被 `JSON.stringify` 自动带上，不动 `DB_VERSION`，导出 zip 自然带走）。
全 0 时字段直接删掉，`hasCloseness` 是"攒出东西了没有"的唯一判据。不进 IndexedDB 的理由：
它是"每个角色一条轻量数值"，条数 = 角色数，生命周期与角色目录一致；进 IDB 反而要为它写一次
版本升级与迁移兜底。**读盘收口**是 `coerceRelationship(raw)`：非有限数、越界、NaN 一律落回
`{0,0,0,updatedAt:0}`，`affection ≤ trust ≤ familiarity` 在这里再夹一次（防御性冗余）。

### 1.6 嗓音（`CharacterVoice`）

音色是**角色的属性**（与 `persona` 同级），不是全局设置。形状与三档来源见 §7.2；
纯 JSON、存 localStorage、跟着导出包走。样本是唯一的二进制，存 `voice_samples` 表。

### 1.7 存储分工

| 数据 | 放哪 | 版本 | 理由 |
| --- | --- | --- | --- |
| `Character.persona` / `voice` / `relationship` | localStorage（跟着 `Character` 走） | 不动 | 几百字节到几条整数，与名字、设定同在一条目录里；additive 字段随序列化自然带走 |
| `ChatMessage` | IDB `chat_messages` | v5 建表 + v6 复合索引 | 消息是只增不减的文本流，几十轮就是几十上百 KB —— 塞进只有 5MB 的 localStorage 迟早撑爆 |
| `ChatSummary` | IDB `chat_summaries` | v7 | 一个角色一条、`keyPath` 是 `charId`，是"这一整段对话的当前状态"，**不需要索引** |
| 聊天的图 | IDB `chat_images` | — | 字节不进消息：消息一次读一屏，图几百 KB，两者读法完全不同 |
| `CharacterMood` | IDB `char_moods` | v13 | 一角色一条、覆盖写；与 `chat_summaries` 同一写法 |
| 嗓音样本 | IDB `voice_samples` | — | Blob 不进 localStorage（与 `charViews` 同一条路） |
| TTS 缓存 | IDB `tts_cache` | — | key = `hash(text + 音色指纹)`；没缓存这功能不成立（§7.2） |

当前 `DB_VERSION = 14`。**版本号只能升不能降**：库里已是更高版本而代码请求低版本时
`indexedDB.open` 直接抛 `VersionError`，而每一处读写都 `catch` 成"读不出来"，
界面上就是"图片和历史全没了"（数据一条没少）。

**没有单独的"会话表"**：一个角色一条对话，会话本身没有可存的东西 —— 标题就是角色名，
时间与条数都能从消息派生（与 `CharacterStat` / `CharacterWork` 同一条规矩：派生得出来的不再存一份）。

### 1.8 暂缓：多段会话（设计已定）

一个角色下开多段互不相干的对话。**暂缓**（先把记忆可编辑做扎实），想清楚的几条记在这里。

**不建会话表**：会话是不是存在，完全由消息决定 —— 一个会话之所以在列表里，正是因为里面有话。

| 决定 | 为什么 |
| --- | --- |
| `sessionId` 走消息与摘要两张表，不另立会话表 | 标题（头一句用户消息）、预览（最后一句）、时间（最后一条）全都派生得出来；多一张表就多一处要与消息保持同步的状态 |
| **默认会话的 id 就是角色 id** | 升级时不必凭空造 id：老消息补上 `sessionId = charId` 就原样落进 `(charId, charId)`；老记忆也天然落在正确的主键上 |
| 摘要表主键从 `charId` 换成 `sessionId` | 记忆必须跟着会话走。把 A 段的事带进 B 段，等于让角色在另一条时间线里提起这边还没发生过的旧事 |
| **保留** `charIdCreated`，另加 `(charId, sessionId, createdAt)` | 左栏那一行问的是**跨会话**的最近一句，和"某段会话里的最近一句"是两个问题 |
| 会话由消息定义 ⇒ 空会话不落盘 | "New chat" 先切到一个空 id，等第一句发出去才在列表里出现；点开没说话就走，它自己消失 |
| 记忆表主键改不了 ⇒ 删表重建 | 升级事务里先把老记录整表读进内存，再 `deleteObjectStore` + 重建 + 回写；同一事务，失败整体回滚 |

撤回时**版本号没有跟着往回改**。`chat_summaries` 的表形状那次被换成了 `sessionId` 主键，
后来**不去改它** —— 改回去要整表删掉重建，在升级事务里做这件事一旦失败会让库彻底打不开。
改为在读写两侧兼容两种形状：`get(charId)` 恰好落在 `sessionId === charId` 那条上，
写的时候顺手补一个 `sessionId` 字段（见 `getChatSummary` / `putChatSummary`）。

## 2. 服务端：`/api/chat`

实现位置：[server/routes/chat.js](../server/routes/chat.js)，与 `/api/enhance`
（[server/routes/enhance.js](../server/routes/enhance.js)）同属 `server/routes/`。

### 2.1 请求与响应

请求体（`character` 只带这几项，`textModel` / `baseUrl` / `apiKey` 来自前端配置）：

```ts
{
  character: { name, identity, outfit, marks, persona: CharacterPersona }
  messages: Array<{ role: 'user' | 'assistant'; content: string }>
  textModel: string
  baseUrl: string
  apiKey: string
}
```

二期陆续补进请求体的还有：上一轮的情绪（§5.4）、关系三轴摊成的那几行（§6.6）、
时间（`nowLocal` / `lastAt`）、见识图与发图各一条配置是否可用。

**人格字段由前端发结构、服务端拼提示词** —— 与 `EDIT_INSTRUCTIONS`、`ENHANCE_PROMPTS`
同一套分工：改措辞不该要求用户重装前端，而那些句子本身就是效果的一部分。
**温度不在请求里**，与 `ENHANCE_TEMPERATURE` 并列写死在服务端（§2.4）。

响应是**按行分隔的 JSON（NDJSON）**，`Content-Type: application/x-ndjson`：

```
{"delta":"你"}\n
{"delta":"好啊"}\n
{"done":true,"finish":"stop"}\n
```

出错时（流已经开始）最后一行是 `{"error":"..."}`，客户端据此保留已收到的文本并提示。

> **为什么不是 SSE**：服务端既然已经把上游的形状收窄成自己的事件（§2.2），前端就没必要再解
> 一层 SSE 的框架 —— `data:` 前缀、事件分隔、注释行都是多余的。按 `\n` 切行、逐行 `JSON.parse`
> 就是全部解析逻辑，少一整类边界情况。

### 2.2 为什么要重新打包而不是原样透传

上游回的是 OpenAI 形状的 SSE（`data: {"choices":[{"delta":{"content":"你"}}]}`）。
服务端读完每一块后**只抽 `choices[0].delta.content`**（以及 `delta.tool_calls`，§2.6），
转成自己的 `{"delta":"…"}` 再往下写。理由与 [api.ts 的 `imagesFrom`](../src/api.ts) 完全一样：
**把上游的形状变化挡在服务端这一处**。中转站的字段名、`reasoning_content` 之类的额外字段、
`[DONE]` 的写法各家都可能不同；前端只认一种事件，就不用为每家中转各写一段解析。

代价是服务端要处理"一块读进来只到半行"：留一个行缓冲，按最后一个 `\n` 切开，
剩下半行留到下一块拼上。这段逻辑跑在服务端，也只有这一处。

### 2.3 `chatSystemPrompt` 的拼装顺序

15 块的**逐字全文与逐块来源**在《[System-Prompt.md](System-Prompt.md)》；
这里只记顺序与"为什么是这个顺序"。

| # | 块 | 由谁拼 | 位置理由 |
| --- | --- | --- | --- |
| 01 | Role Contract（`You are roleplaying as…`） | 写死 | 开场句 |
| 02 | Priority Lens（冲突时谁说了算，`priorityRules()`） | [chatPriority.js](../server/chatPriority.js) | 它是"读法"层不是"事实"层：先给尺子再往下读；刻意排在规则之前 |
| 03 | Identity（`Who you are:` Name / identity / Wearing / marks） | 服务端拼，值来自用户 | 先立住是谁 |
| 04 | Personality & Voice（`How you behave:` language → traits → voice → address → boundaries） | 服务端 | 语言排最前且写成**指令**（`Speak only …`）；空字段整行丢掉 |
| 05 | Voice Samples（`copy this voice, not the topic`） | 服务端 | 它是"照着抄口吻的样本"不是要求，所以单独成段；不点明"只仿语气"，模型会把样例里的**场景**搬进这一轮 |
| 06 | Current Context（`Right now:` / `You two last spoke …`） | `chatTime.js` | 与记忆同层但**必须排在记忆前面**：记忆是成篇叙述，夹在两块短事实中间会被切碎。**不过 `chatOneLine`**（那会把两行压成机器在念表的一句话），只做截断 |
| 07 | Mood（`You are feeling …` + 可以转向那半句） | [chatMood.js](../server/chatMood.js) | 与时间同一层（此刻的事实），同样不过 `chatOneLine`；窗口外整块不出现（§5.3） |
| 08 | Memory Summary（`What you remember:`） | `memoryBrief`（[chatMemory.js](../server/chatMemory.js)） | 讲"发生过什么"，与"你是什么人"同层；上限显式给 `CHAT_MAX_CHARS`，撞上限时末尾留一道截断标记 |
| 09 | Memory Entries | `memorySection`（逐行白名单） | 与 08 同层，但它是**一条条事实**：先铺叙述再列清单，反过来会把叙述切碎 |
| 10 | Relationship | `relationshipSection`（[relationship.js](../server/relationship.js)） | 先记得什么、再熟到什么程度；同样过逐行白名单（§6.6） |
| 11 | Guidance（相处偏好） | `guidanceSection`（[chatGuidance.js](../server/chatGuidance.js)） | 最后一条**软指令**，离硬规则最近；用户一项都没表态时整段不出现 |
| 12 | Rules（`CHAT_RULES`） | [routes/chat.js](../server/routes/chat.js) | 收束（见下表） |
| 13 | Photo protocol（`photoRules()`） | [chatPhoto.js](../server/chatPhoto.js) | 仅 `canDraw` 时注入：没配出图模型时整块消失，既省 token，又不引着模型去报一个画不出来的 photo |
| 14 | Meta tool rule（`CHAT_META_RULE`） | routes/chat.js | 13 先讲 photo 对象怎么填，这一条再把"每轮调用一次 `emit_message_meta`、正文里不许写"钉死。**不由 `canDraw` 门控** —— 心情每轮都要报 |
| 15 | Layer rules（`layerRules(sceneMode)`） | [chatLayers.js](../server/chatLayers.js) | 12 里那句 `Write only what the character would say out loud. No narration…` 会挡掉 `[act]` 旁白，这一条在它之上开一个受控例外。**后说的覆盖先说的** |

一句话：**短事实在前（03–07）、成篇的在后（08–09）、软指令（10–11）垫底、硬规则收束（12–15）**。

`CHAT_RULES` 里那几条不是装饰，都是冲着模型的具体通病去的：

| 规则 | 挡的是什么 |
| --- | --- |
| 不要 markdown | 模型的默认输出习惯。聊天框里冒出 `**加粗**`，拟人感立刻就没了 |
| 一到三句 | 模型爱写小作文。真人不这么打字 |
| 不要每轮反问 | 模型最典型的"助手腔"。"还有什么可以帮你的吗"就是这一条要杀的东西 |
| 允许不友好 / 不配合 | "超拟人"与"AI 助手"的分界线。后者有求必应，前者会嫌你烦 |
| 不要元叙述 | 挡住 `*sighs*`、`（皱眉）` 这类动作描写 —— 该由角色的话本身传达情绪 |

**只喂 `identity` / `outfit` / `marks` 三项外观，不喂逐项面貌特征**：`face` / `hair` / `brows` /
`eyes` / `noseMouth` 是写给图像模型的像素级约束，对聊天是纯噪声，而且会把话题往长相上引。
`identity` 与 `outfit` 不一样 —— 它们回答"这个人是什么身份、穿什么"，角色会主动提到。

### 2.4 温度、长度与窗口

```js
const CHAT_TEMPERATURE = 0.9
const CHAT_MAX_TOKENS = 1500
// 请求体：{ model, messages, temperature: CHAT_TEMPERATURE, max_tokens: CHAT_MAX_TOKENS }
```

温度与 `creative` 档（0.9）齐平、比 `character` 档（0.7）高：拟人化要的是**变化** ——
同一个问题每次问都该给一点不同的反应，温度低了会变成一台复读机。

`max_tokens` 是提示词里"一到三句"的硬兜底 —— 提示词是软的，模型偶尔会不听话，
而这是按 token 计费的地方，不能只靠一句话拦着。

**为什么不是 400**：400 看起来"足够四五行"，但它没算**思考**。o 系、Gemini 2.5 的 thinking、
Claude 的 extended thinking 都把思考 token 记在这同一个额度里 —— 额度被思考吃光，
正文只吐了几个字就被判 `length` 停下。表现出来就是**"提示说截断了，可那句话明明很短"**，
而这个现象在 400 上会变成常态。1500 给思考留出余量，又仍然拦得住跑飞的模型。

窗口是另一件事：前端只带最近 `CHAT_WINDOW = 20` 条（§3.6），服务端再拦一次
`CHAT_MAX_MESSAGES`，因为入口是公开的。

### 2.5 流式转发

与其他三条端点骨架一致的地方：`rateLimit`、`assertSafeTarget`（SSRF）、`dispatchAttempts`
（代理那一跳挂了再直连试一次）、`res.on('close')` 时 abort 上游。三处必须不同：

**① 先判状态码，再开流。** 上游如果是 401 / 404 / 一把 HTML 错误页，此时还没写过任何字节，
应该像其他端点一样回一个正常的 JSON 错误（复用 `looksLikeHtml` / `htmlTitle` / JSON `message`
提取那三段），让前端能用同一套 `failureMessage` 读到。**一旦 `flushHeaders()` 过了，
就只能用 `{"error":…}` 收场。**

**② 超时改成"上游静默超时"，而不是整条请求的总时长。** `UPSTREAM_TIMEOUT_MS`（120s）盖的是
从发起到拿完的全程；流式下这个口径不对 —— 一条正在持续吐字的流不该被总时长掐断。
改成每收到一块就重置计时器，判定的是"**多久没动静**"。

**③ 响应头缺一不可**：`Content-Type: application/x-ndjson; charset=utf-8`、
`Cache-Control: no-cache, no-transform`、`Connection: keep-alive`、
`X-Accel-Buffering: no`（反代不认它就会攒够一批才吐，流式当场退化成"等 10 秒一次性出来"），
最后 `flushHeaders()`。**不加心跳**：SSE 那套 `: ping` 是为了防中间层掐掉长时间静默的连接，
而对话的两个 token 之间最多几百毫秒，没有静默窗口需要垫。

**入口校验**（外部输入，边界上要防）：`messages` 必须是数组、条数 ≤ `CHAT_MAX_MESSAGES`（200）、
每条 `role` 只认 `user` / `assistant`、`content` 是字符串且 ≤ `CHAT_MAX_CHARS`（8000）。
这个端点是公开的（配置全在前端，没有鉴权，设计如此），不设上限就等于给了个免费的大请求放大器。
**超长是报错，不是静默切** —— 切掉的是用户自己写的东西，而他看到的只是"它好像没读到前半截"。

**`finish_reason` 要带出来**：上游最后一帧 delta 是空的、只带一个 `finish_reason`
（`stop` 说完了，`length` 撞上 `max_tokens`）。一路记着，收尾时随 `done` 一起发
（`{"done":true,"finish":"length"}`）。丢掉它等于把"说完了"和"额度用完了"混成同一件事 ——
界面上一模一样，用户会以为角色话说一半是它自己的风格。前端把它落到 `ChatMessage.truncated`。

### 2.6 工具调用：`emit_message_meta`

2026-10-20 起，情绪与发图意图**不再从正文里贴标签**，改走 tool calling：
模型在正文之外调用 `emit_message_meta`，元数据与正文是两条独立信道。

1. **工具定义**（[server/chatTools.js](../server/chatTools.js)）：`metaTool(canDraw)` 声明 `mood`（必填，一个小写英文词）与可选的 `photo` 对象；"该报什么"写在工具描述里，不再由 `CHAT_RULES` 教标签。
2. **服务端收**（routes/chat.js）：流式帧里的 `delta.tool_calls` 按 index 累加（`takeToolCallDeltas`），到 `[DONE]` 再由 `toolMetaFromCalls` 解析成旧的扁平字段（`mood / photo / photoSelf / photoShot / photoFrame`）。
3. **正文不再扣尾取意图**：新协议下正文可以直接流给前端；只保留一层旧标签清理（§2.7），防止模型沿历史习惯漏出的 `[photo:…]` 闪给用户。**旧标签不顶替 tool call。**
4. **前端**：`ChatStreamResult.mood` → `ChatMessage.mood` → 只取**最后一条助手消息**的情绪，渲染在头部名字右边（`:key="mood"` 让同一个词重复出现时也能重播一次入场动画）。模型没调用工具时 `done` 事件带 `metaIssue`，前端提示一次。

旧的 `splitMood` 与按长度扣尾（`CHAT_TAIL = 24`）已删除；[server/chatTags.js](../server/chatTags.js)
现在只负责旧标签的清理与历史消息兼容。

### 2.7 旧标签的三道清理

| 手法 | 管什么 |
| --- | --- |
| `splitTags` | 只认**末尾**那一枚标签 —— 为了不误吃正文里的方括号（`[注]`、`[1]`） |
| `stripStandaloneTags` | **整行只有一枚标签**就摘掉（不限于末尾），意图照样取出来用；夹在句子中间的方括号一律不碰。服务端在**放行每一块增量之前**过一遍（所以不会先露一下再消失），显示层也过一遍 —— 库里已有的老消息还带着它 |
| `tailHold` | 末尾那段空白一律扣住，后面一来非空白字符就跟着放。模型把标签写在单独一行，那个换行**总是比标签先到**；不扣住它就会被当成正文发出去，收尾那次 `trimEnd` 已经追不回来 |

提示词同时收紧：标签（若还有）必须在**最后**，后面不许再有话。显示层对应的是 ChatPage 的
`shownText` —— `white-space: pre-wrap` 会把结尾的 `\n` 如实渲染成一行空行，
**中间的分行照旧保留，收的只有末尾**。

## 3. 前端

### 3.1 `api.ts`：流式读取

```ts
export async function chatStream(opts: {
  character: ChatCharacterPayload
  messages: Array<{ role: 'user' | 'assistant'; content: string }>
  cfg: ApiConfig
  /* 每一块增量。调用方拿到就往气泡上追加 */
  onDelta: (delta: string) => void
  signal?: AbortSignal
}): Promise<void>
```

内部就是 `fetch('/api/chat')` + `resp.body.getReader()`，用 `TextDecoder` 解出文本、
按 `\n` 切行、逐行 `JSON.parse`：`{delta}` → `onDelta`；`{done}` → 正常收尾（带 `finish`）；
`{error}` → 抛错（调用方保留已收到的部分）。

**不能用 `EventSource`**：它只支持 GET，既带不了请求体，也带不了 `Authorization` ——
密钥是每个用户自己配的，必须随请求发。这一段只能手写。

### 3.2 `lib/idb.ts`：表与索引

v5 建表（与 `CHAR_STORE` 同一写法）：

```ts
const CHAT_STORE = 'chat_messages'
if (!db.objectStoreNames.contains(CHAT_STORE)) {
  const store = db.createObjectStore(CHAT_STORE, { keyPath: 'id' })
  store.createIndex('charId', 'charId')   // 按角色取消息、按角色清消息都靠它
}
```

v6 补一条复合索引：`(charId, createdAt)` —— v5 那条只能按 `charId` 取全部，而对话页要的是
**最近这些条**；有了它才能开一个游标从最新往回走，走够一屏就停，不必把几千条历史整个读进内存。

| 函数 | 说明 |
| --- | --- |
| `getChatMessages(charId, limit)` | 走 `charIdCreated` 开一个**倒着走**的游标，取够 `limit`（默认 `CHAT_PAGE = 200`）就停，返回 `{ list, hasMore }`。`hasMore` 多取一条来判 |
| `putChatMessage(msg)` | 追加一条。**流式过程中不逐块写** —— 只在整条回复结束时落一次 |
| `deleteChatMessage(id)` | 删一条（重新生成时删掉最后那条助手消息） |
| `deleteChatOf(charId)` | 按 `charId` 索引整批删。"清空对话"与"删除角色"共用它，且要在一个事务里连消息、摘要、图、心情一起清（§4.7 / §5.2） |
| `getLastChatLine(charId)` | 每个角色只读**最后一条**，供左栏摘要与排序（§3.4） |

> **`CHAT_PAGE` 是显示上限，不是删除**：更早的还在库里，只是这一屏没读 —— 界面顶上给一枚
> `Load earlier messages`。两者是完全不同的语义，措辞上不能混。往上面插内容时浏览器不一定
> 能稳住视口，所以 ChatPage 在读之前先记下 `scrollHeight`，消息回来后按"长高了多少"把
> `scrollTop` 往下推同样一段；读数必须放在 **post-flush** 的 watcher 里（DOM 更新前量到的
> 还是插进来之前的高度）。

**为什么流式过程中不逐块写盘**：一条回复可能产生上百次 `delta`，逐块写就是上百次事务 ——
而中途崩溃丢掉半句话，与"按了 Stop"在用户眼里没有区别。收尾时落一次，
中间只更新内存里那一个响应式字符串。

### 3.3 三种收场要分开

| 情况 | 已收到的文本 | 标记 |
| --- | --- | --- |
| 正常说完 | 全部 | 无 |
| 用户按 Stop | **保留** | `stopped: true` |
| 上游报错 / 断流 | **保留** | 无 `stopped`，但界面上挂一句错误提示 |
| 撞上 `max_tokens` | **保留** | `truncated: true`（`finish === 'length'`），气泡下面一行小注 |

**四种都不丢掉已经收到的字**。用户按 Stop 不是"这次失败了"，是"说到这儿够了" ——
把半句话删掉等于惩罚他按了按钮（与设定图那条"中断后保留旧图、不生成坏图"同一条原则）。
`stopped: true` 要存下来而不是只留在内存里：下次打开这一段还在，而且拼上下文时
它照样是一条**正常的历史消息**，不是坏数据。

### 3.4 `ChatPage.vue` —— 页面

**整页骨架**：对话页是**一级页面**（与 Studio / Characters 平级），两栏 ——
左栏 240px 角色列表（独立滚动）、右栏角色头 + 消息流（独立滚动）+ 输入区。
**只有消息流内部滚动，整页不滚**：底部的输入框跟着页面滚走，等于每打一句都要先滚回去。

事后还补过一处：布局一屏放得下却仍能滑，根因是两个全局设置叠在一起（`scrollbar-width: none` 藏了滚动条、`scroll-behavior: smooth` 让它滑得带惯性），而溢出不到 1px。处理是把这一页钉住（`.shell-wide`）：`height: 100dvh`、`padding-bottom: 0`、`overflow: clip`。
`clip` 这个选择是关键：`hidden` 会把 `.shell` 变成滚动容器，而**聚焦底部输入框时浏览器可能把它滚一下**，整页跟着挪 —— 又成了"滑一下"。屏确实太矮时（`max-height: 520px` 起）把锁解开。

**左栏**：眉标 `CONVERSATIONS`（全大写 + `--ls-eyebrow`）；每行 36px 圆形头像（读 `c.ref`）+ 名字 + 最后一条消息摘要（单行省略），行高 ≥ 52px；**最近活跃在前**（从消息派生，不落盘）；选中态 `--accent-soft` 淡底 + 名字 600 字重，**不用彩色**。**列出全部角色，不是"有对话的才列"** —— 只列聊过的，新角色就永远开不了头。

摘要与排序曾经对**没打开过**的角色都不对：消息按角色懒加载，没打开过的角色在 `chatMessages` 里没有键，于是左栏一律显示 `No messages yet` 并把它排到最后。修法是 `getLastChatLine`：一批角色各开一个倒着走的游标、**只取第一条就停**，全跑在同一个事务里 —— 代价与角色数成正比、与消息条数无关。两个容易漏的点：启动时读一趟就够；**失败时要把那行退回去**（那一轮没留下东西，左栏不该还停在上一次的回复上）。

**角色头**：头像 + 名字 + 一行身份摘要；右侧 `head-acts` 三枚：**模型药丸 · 记忆 · ⋮**。`⋮` 里只有低频动作：`Edit memory` / `Forget memory` / `Clear conversation` —— 三者正好构成"忘一点 / 忘干净 / 全清"的梯度（§4.9）。
清空走 **UndoToast**（与删除角色、清空历史同一套撤销模式），**不用 confirm 弹窗** —— 站内有现成的撤销通道，再开一路确认框是两套规矩。

**消息流**：

- **铺满整块面板**，宽度交给气泡自己的 76% 上限；**外侧那条走道要从这 76% 里扣掉**（`min(76%, 100% - var(--ops-lane))`）—— 两个数得一起算，气泡才不会把动作药丸挤出面板；
- **两侧都是气泡**，靠说话人那一侧的角收窄（`--r-sm`）；角色一侧 `--bg-elev`，自己一侧 `--cta` 实心（与发送键同一个主动色）。**不能两侧都铺灰底** —— 这套调色板里几档灰差得太近，分不出谁是谁，而"谁说的"是对话里最不能含糊的一件事；
- **不逐条显示时间戳**：只在**跨天**或**间隔超过 30 分钟**时插一条居中分隔；
- **自动跟随只在贴底时生效**：距底 < 80px 才跟着新消息走（往上翻历史时被拽回底部，是聊天界面最烦人的一件事）；**流式中**末尾一枚 **CSS 绘制的光标**（呼吸动画），不用图片 / GIF；
- **末尾那条跟着一枚「重来」**：删掉它、用同样的上文重发，用户那条不动；`stopped` 的那条不显示。2026-10-05 起它排在那条消息的悬停动作里、**"删"的后面**（早先挂在流末尾，试过两种按钮样式，都还是"这一条消息顺带能做的事"里多余的一行字）；
- **念 / 删 / 重来装在一枚「动作药丸」里**（2026-10-06 改）。从前三枚光着的图标挂在气泡外侧，实测窄屏溢出 88px、末尾两枚被滚动容器裁掉。三条规矩：① **给它一个底**（`--surface` + `--line` + `--sh-sm`），三枚才是一件事；② **挂得下就挂外侧，挂不下就挂到气泡下面**（≤860 与沉浸页改挂下面，高度由气泡的 `margin-bottom` 让出）—— 横向不够就往下走，不压字、不出面板；③ **可点区域分两档**（鼠标 34px / 触屏 40px），触屏那层底降到 `--bg-elev` 并压暗一档（它从来没有"浮出来"的那一刻）。末尾那条**没有气泡**时（只发了一张图、没有文字），退回消息流末尾（`.regen`），用同一枚药丸、里面只有一枚按钮；
- **顶上一枚 `Load earlier messages`**（`hasMore` 为真时才出现）：它往前翻一页，不是"加载中"、更不是"丢弃"。**懒加载**：进页面按 `charId` 取消息，与 `loadCharViews` 同一套按需加载 + 去重，启动时不碰。

### 3.5 输入区

- **桌面 `--fs-base`(14px)、窄屏才提到 16px**：与气泡正文同号 —— 自己打的字和它说的话一样大。16px 那一档只在窄屏出现，因为**低于 16px 时 iOS Safari 聚焦会放大整页**（站内硬约束）；
- 自增高 `textarea`（与角色向导起稿块共用 `lib/grow.ts` 的 `vGrow`），6 行封顶后内部滚。封顶统一交给样式表的 `max-height`，不在 JS 里再算一遍（`max-height` 压得住内联 `height`）；
- **回车发送、Shift+回车换行**，带 `isComposing` / `keyCode 229` 的输入法保护；
- **生成中把发送键原地换成 Stop**，不是并排多一个按钮（与"设定图格子生成中整格换成停止入口"同一手法）；
- **整块是一张悬浮卡片**：白底 + 一圈极淡的边 + 一层弥散影。输入区那条通栏分隔线因此去掉（卡片的边界由投影给出，再加横线就是两套边界打架）。边与聚焦态都用 `box-shadow` 补、不切 `border`（会让里面整行文字挪一下）；圆角用 `--r`(16px) 与气泡同档 —— `--r-lg`(24px) 是给 Studio 那个有厚度的提示词编辑器定的，铺满全宽的卡片用 24px 会变成一根胶囊；
- **三枚图标全在右端**（附图 / 表情 / 发送）：它们都是"对这一句话做的事"，而不是"开始说一句话"的入口；DOM 次序跟着视觉次序改，Tab 的顺序因此也是"先打字、再挑键"。表情面板的锚点跟着挪到右端（`right: 0`，照旧朝上开），否则会从输入区右缘伸出去；
- **超长拦在本地**（`CHAT_MAX_CHARS`）：挡住发送、原文留着、当场把上限写出来。提示顶掉的是卡片那一格，所以高度与卡片一致（52px），切换时页面不跳；
- **开不了口时整块不可用**，措辞分两种（§3.8）。

### 3.6 上下文怎么拼

每次发请求只带**最近 `CHAT_WINDOW = 20` 条**消息。更早的不发（从 §4 起改由摘要带上）。

- 窗口取的是**消息条数**而不是字数：条数可预期，而字数要靠额外估算；20 条大约十轮来回，够撑起一段有来有回的对话；
- 被截掉的旧消息**不从库里删** —— 它们还在，只是这轮不带，界面上滚上去照样能看到；头几轮的表现也不会因为截断而变差（本来就没到 20 条）。

### 3.7 空态与错误、窄屏

| 情况 | 表现 |
| --- | --- |
| 一个角色都没有 / 没选中角色 | 居中一句 + 去 Characters 的按钮（左栏空着，右栏不该是死的） |
| 选中了但没聊过 | 大头像 + 名字 + **一句本地按 persona 拼的开场白**。不调接口 —— 一进页面就花钱不对 |
| 上游报错 / 断流 | **保留已收到的文本** + 全局 `notice` 一句 |
| 用户点了 Stop | 保留 + 不报错，一句 `Stopped.` 走 `notice`（与设定图的 `Generation stopped.` 同调） |

**所有报错走全局 `notice`**（[App.vue](../src/App.vue)），不在页面里另开一块错误区 ——
角色页已经是这么做的。

**窄屏（≤ 860px）**：左栏隐藏，**角色头变成可点按钮**，点开一个居中的角色选择浮层；
浮层按模态来管焦点（`tabindex="-1"` 让浮层本身能接焦点、打开时焦点收到它身上、`trapTab`
把 Tab 圈在里面、关闭时焦点**归还给打开它的那枚按钮** —— 缺一样，键盘与读屏用户就会被留在
背后的页面上）；挑完人关掉浮层并把焦点交给输入框；消息流内边距收到 `--sp-3`、气泡
`max-width` 提到 88%（窄屏下 76% 太窄），动作药丸同时从外侧改挂到下面；输入区贴底，
`padding-bottom` 带上 `env(safe-area-inset-bottom)`。

### 3.8 多角色状态隔离与 `chatReady`

流式状态按 `charId` 存（`Record<charId, ...>`）—— 和 `charViewBusy` 那次踩过的坑一模一样：
不按角色分开，A 在说话时切到 B，B 的界面会跟着显示"正在输入"。
`chatBusy` 与 `chatControllers` 都按角色分键，`chatMood` 同理（§5.8）。

**"有配置" ≠ "能开口"。** 拆分上线后真实撞到的一处：用户把一条已有配置的用途改成 `Role chat`
存下，模型名却在切换用途时被清空了 —— 配置在列表里顶着「Current」、药丸也写着它的名字，
**一开口却收到服务端那句 "Set a text model in API settings first"**。所以"配全了"是能不能开口的前置：

| 判据 | 落点 |
| --- | --- |
| `chatReady = chatConfig?.baseUrl && chatConfig?.model` | 输入区、`canRegenerate` / `canRetry`、`send()` 都看它（不再只看"配置在不在"） |
| 开不了口时**分两种说** | 一条都没有 → "Add a chat model…"；**有但缺模型名** → "`<名字>` has no model name yet — add one in API settings to start talking." |
| 那枚按钮的落点也不同 | 前者开一张"用途 = 对话"的空表单；后者**直接开这一条**的编辑表单（`editConfig`）—— 问题就在那一格里，把人丢回列表等于让他再找一遍 |
| `App.runChat` / `regenerateChat` 各有一道同样的闸 | 界面之外的第二道：`regenerateChat` 那条尤其要紧 —— 它会先删掉旧回复，发不出去时那条就补不回来了 |
| 附了图的那一轮改看**识图**配置 | 它同样可能缺模型名，而那一处更容易漏 |
| 后台的记忆压缩直接跳过 | 它是静默重试的：不拦的话每轮白花一次注定失败的调用 |

### 3.9 头部的模型药丸（对话模型从此独立）

**问题**：这一页原来答不上"现在是谁在说话"。角色对话用的那个模型，是设置页里 "Prompt enhancing" 那一类的配置 —— 而它的芯片挂在生图那页的参数面板上：想换个聊起来更像个人的模型得跑到画图那一侧去动，而两件事的诉求本来不同。

**处理**：`ApiConfig.kind` 多一类 `chat`（见 [API配置管理设计.md](API配置管理设计.md) §5），角色对话与记忆压缩都走它；对话页头部多一枚药丸，显示**当前用的是哪个模型**，点一下直达设置页。配套：`ChatPage` 的 props 从 `textConfig` 换成 `chatConfig` + `chatBorrowed`，重试 / Regenerate 的门控也一并改看它。

| 决定 | 为什么 |
| --- | --- |
| 药丸放在 `head-acts` 里（模型 · 记忆 · ⋮） | 它回答的与旁边那枚记忆药丸是同一类问题："它现在是什么状态"。放进输入区会每轮都在眼前，放进 ⋮ 又要多点一次才看得见 |
| **`from enhancing` 这句必须写出来** | 没专配过时对话借用改写的模型（存量用户零感知）。不写的话用户会以为它已经独立配过了 —— 而"它到底走的哪个模型"正是要解决的问题本身 |
| 点它：**有专配的 → 回列表；没有 → 直接开一张"用途 = 对话"的表单** | 药丸上写着 `from enhancing` 时，用户点它的动机就是"配一条自己的" |
| 没有专配时**不显示成错误态** | 借用是正常工作状态，不是配置缺失。红色的"未配置"会让人以为聊天坏了 |
| 模型名 `max-width` 18ch（窄屏 10ch）后省略 | 中转上自己写的别名可以很长；不封顶会一路把角色名字挤没，而这一页首先要认得出在跟谁说话 |
| 与记忆药丸**共用一套皮**（`.head-chip`） | 同一排里两枚同形状的控件，只该在内容上不同 |
| 对话模型**不进生图那页的参数面板** | 进了就等于把"和生图独立开"这件事又还回去一半 |

### 3.10 App 与入口的接线

- `type Page` 加 `'chat'`（[App.vue](../src/App.vue)），导航的 `v-else-if` 链里挂上 `ChatPage`；[nav.ts](../src/lib/nav.ts) 的 `NAV_ITEMS` 在 `chars` 之后插 `{ value: 'chat', label: 'Chat' }` —— 两者是同一个对象的两件事，一个造它，一个跟它说话；
- **但导航不止这一处**：`NavSegment.vue` 是按条目配具名槽的（[NavSegment.vue](../src/components/NavSegment.vue) 那一排 `<template #home>` / `#chars` / …），还要补一枚 `<template #chat>` 图标槽，并重新量轨道宽度（`RubberSegment` 的滑块按条目数分格，条目从 6 个变 7 个，窄屏下尤其要确认不挤）；
- 会话状态（与 `charViews` / `charViewBusy` 并列）：

  | 状态 | 作用 |
  | --- | --- |
  | `chatMessages: Record<charId, ChatMessage[]>` | 按角色缓存，进页面时按需从 IDB 取（懒加载，启动时不碰） |
  | `chatBusy: Record<charId, boolean>` | 这个角色正在生成 |
  | `chatControllers: Map<charId, AbortController>` | Stop 的手柄 |
  | `chatLast: Record<charId, …>` | 左栏最后一句与排序，`sendChat` / `runChat` 就地更新 |
  | `chatMood: Record<charId, …>` | 情绪状态（§5） |

- `page.value = 'chat'` 的入口有两个：导航图标，以及**选中某个角色**。后者要带一个 `chatTarget`，页面进去就落在那张脸上；
- **对话模型那一份配置也在这儿接线**：`useChat` 拿 `chatConfig`（专配的，或借来的改写那条），`ChatPage` 拿 `chatConfig` + `chatBorrowed`；
- **删除角色时要级联清对话**：`deleteChar` 本来就是"立刻消失 + 几秒内可撤销 + 窗口结束才真正落盘"，所以 `deleteChatOf(charId)` 要放在**真正落盘那一步**，不是点删除那一刻 —— 否则撤销回来只剩角色、对话没了。

角色页两处小改（[CharacterPage.vue](../src/components/CharacterPage.vue)）：详情页 hero 加一枚 `Chat` 入口（与一次补齐 CTA 同排；卡片 `⋮` 菜单不加，低频动作）；表单加 `Personality` 分组（向导第 1 步，紧跟 Spec 与 Reference sheet only）—— `Language` / `Personality` / `Speech style` / `Address` / `Boundaries` / `Speech samples`，分别对应 `language` / `traits` / `voice` / `address` / `boundaries` / `samples`。

- **另起一段，不并进 Spec**：那两组管"它长什么样"，这一段管"它是个什么样的人"，提示语里也明说 `Used in Chat only — never in your prompts.`；
- 这些字段都可留空 —— 空着就是一个"没设定性格"的角色，照常能聊；
- 保存沿用 `saveCharFromPage`，payload 多带一个 `persona`；角色详情页另有一块**只读**的 Voice 面板，与 Spec 面板平级；
- **起稿与识图都会填这几栏**（§8），`aiFilled` 标记规矩与前两组一致：模型写过的小圆点、改一下就消失；
- `coerceCharPersona` 放在 `coerceCharFields` 旁边（[api.ts](../src/api.ts) 同一处收口）：缺字段补空串、非字符串置空。

> **命名冲突已解决**：`Voice` 这个词**归嗓音**。人格那组的组名是 **`Personality`**，其中 `voice` 字段的标签是 **`Speech style`** —— 它管的是"话怎么说出来"，而一个叫 Voice 的**文字**栏会让人以为在那里写字就能改变角色听起来的声音。

## 4. 长期记忆与摘要压缩

### 4.1 它解决什么

§3.6 的滑动窗口只带最近 20 条，**更早的是真的忘了** —— 库里还在，但不再发送。
这一节补上后半句：让滑出窗口的那些消息压成一段简报，随 system 一起发。
数据与存法见 §1.3（表 `chat_summaries`，v7，`keyPath` 是 `charId`，一个角色一条）。

### 4.2 什么时候压（算法）

```
want = 总条数 − CHAT_WINDOW − covered
want ≥ CHAT_SUMMARIZE_AFTER(20) 才压
```

- **减掉窗口**是因为最近那些条本来就还在上下文里，压了也是白压；
- 压完 `covered` 追到 `总条数 − 20`，要再攒 20 条才触发下一次 ——
  **也就是大约每 10 轮多花一次调用**，而这一批刚好是一整轮新的对话；
- 总条数走 `countChatMessages`，**只看索引、不读记录**。

### 4.3 压哪一段（这一步最容易做错）

`getChatMessagesToSummarize(charId, afterAt, limit)` —— **必须由旧往新收**（游标 `'next'`，
左开区间 `[charId, afterAt]`），单批上限 300 条。

反过来（从最新的往回收）会有一个只在几百条之后才显形的 bug：第一批把最近那些还没摘要的
消息全吃掉，而更早的永远轮不到 —— **对话最开头那一段会被跳过一辈子**。

> 用 500 轮 / 1000 条消息模拟过这条循环：应覆盖 980 条（总数 − 窗口），**漏 0 条**。

### 4.4 提示词

走 `/api/enhance` 的 `mode: 'summary'`，与改写、拆角色共用一套代理与鉴权。温度 **0.3** ——
摘要要的是忠实，温度低了顶多啰嗦，而**编出来的记忆比没有记忆更糟**。

**用的是对话那条配置（`chatConfig`），不是改写那条**：记忆是"这段对话的延续"，它该和回话用同一个
脑子 —— 换个模型压出来的摘要，措辞与取舍都跟正文不是一路。没专配对话模型时 `chatConfig`
借的就是改写那条，行为与拆开之前一模一样。

两条反复强调的规则：**"合并重写，不要追加"**（一旦变成追加，简报会随对话线性膨胀，最后比原文
还长，而且最旧的信息永远压在底下）；**"保留名字、地点、承诺、欠下的账"**（这些正是几轮之后还会
被追着要的东西）。

### 4.5 怎么注入

压在 `Who you are` / `How you behave` 之后、记忆条目之前（§2.3 的 08）—— 它讲的是"发生过什么"，
与"你是什么人"属同一层，而规则要留在最后当收束。

记忆**过一遍 `chatOneLine` 把换行收掉**：它是模型生成的文本，原样带着换行塞回 system，
等于给上一轮的输出一个伪造提示词结构的机会。上限显式给 `CHAT_MAX_CHARS`
（按单字段那档 400 截会拦腰砍断），撞上限时末尾**留一道截断标记** —— 模型不该把一份被腰斩的
记忆当成完整历史，尤其末尾那几笔常是最新的待办。

标签是 **`What you remember`** 而不是 "What has happened so far"：摘要还带一句"它是怎么说话的"，
而口吻不属于"发生过什么"，标签得与内容对得上。

### 4.6 记忆必须跟着对话一起走

`deleteChatOf` 现在跨几张表一个事务：清消息的同时清摘要、图、心情。
**"消息没了而记忆还在"比失忆更糟** —— 下一句开口就会提起一段用户刚刚清掉的旧事。
所以 `clearChat` 也要连记忆一起清，并在撤销时一并恢复（连同库里那份）。

### 4.7 在途压缩的代次（`chatSeq`）

压缩是异步的。用户完全可能在它跑着的时候点"清空"或删角色 —— 回来时若不检查，
这次后台整理会把刚清掉的记忆又写回去。

做法与角色起稿的 `draftSeq` 完全一样：进压之前记下代次，写回之前比一次，对不上就整份丢弃。
`clearChat` 与 `deleteChar` 的 `purge` 各调一次 `bumpChatSeq`。

> 注意 `purge` 要等撤销窗口结束才跑，所以**不能在压缩中途用"角色还在不在列表里"来判断** ——
> 撤销窗口里角色本来就不在列表里，那样会把一份完全有效的记忆丢掉。

### 4.8 界面：可见、可改，但默认折起来

消息流最上面一块 `MEMORY · updated 2m ago`，点开展示正文。摆在最上面是因为它代表
"比这些消息更早的那些"，顺序上就该在最早的那条之前。

- **虚线框**是有意的：它不是对话的一部分，而是一段"关于这段对话"的派生文本，
  实线框会让人以为它也是一条消息；
- **必须让用户看得见**：记忆是有损的，用户得能亲眼看到损掉了什么，才谈得上信它；
- **还得改得动**：压错一处就得能就地改，否则用户唯一的办法是清空整段对话，
  而那把整段历史也一起扔了，代价完全不成比例。

编辑态就地换成一只 `textarea`（不另起浮层，改一段文字不该有弹窗 + 确认的仪式感）：

| 决定 | 为什么 |
| --- | --- |
| 只换正文，`upToAt` / `covered` 一个字不动 | 它们说的是"哪些消息已经进去过了"。改字不改变这件事，动了会让下一轮把老消息重新压一遍 |
| `updatedAt` 跟着刷 | 界面拿它显示"多久没动过了"，用户刚写的那版不该还挂着"3 天前" |
| 上限卡在 `CHAT_MAX_CHARS`（与消息同档） | 服务端对记忆收的正是这个数，改到多少会被截断是可预期的 |
| 不许存空；编辑中不让折叠；换角色自动退出编辑 | 存空等于没说清"想干什么"（想清空得走 `Forget`）；后两条是别把手上正在写的东西藏了 / 那块记忆已经属于另一个人了 |
| 在途压缩遇到"用户刚改过"就放弃本轮 | 用户写的那版比同炉重压的更算数。`covered` 没动，消息一条不少，下一轮连着他的新版本一起再压 |

**忘（`Forget memory`）** —— 难点不在删，**在游标**：压缩是从 `upToAt` 之后接着取的。
只把正文清空、游标不动，下一轮就会把刚刚忘掉的那段**原样重新压回来** —— 这个功能就等于没做。

| 字段 | 忘掉时怎么处理 |
| --- | --- |
| `text` | 置空。界面据此不再显示记忆块（`hasMemory` 看的是**正文非空**，不是记录在不在） |
| `upToAt` / `upToId` | 推到**最后一条消息**。忘掉的那一段从此不再进记忆 |
| `covered` | 置为当前总条数。宁可算多一点：多算只是下一轮少压一次，算少会把忘掉的那段重新捞回来 |
| 记录本身 | **留着** —— 那个"从哪之后不再记得"的游标得有地方待 |
| 消息 | **一条都不删**。"角色不再记得"和"这事发生过"是两回事 |

效果：忘掉之后，**在这之后**说的新话会照常重新积累成记忆 —— 等于从遗忘那一刻起重新认识，
阈值与一段全新对话完全相同（再聊 20 轮）。

入口有两处：展开的记忆块里（`Edit` 旁边）、以及头部的 `⋯` 菜单里。`Forget` 平时与别的次要动作
长得一模一样，**只有悬停才染成危险色** —— 它不该在静止时和"改一改"争同等分量。
与"清空对话"的另一处不同：这一步**立刻落盘**，不等撤销窗口结束（忘掉就该马上生效，
而且只有一条记录，写它不心疼；撤销再把老的那版写回去）。

### 4.9 失败就退出，不打扰

压缩全程静默：失败时 `covered` 不推进，下一轮再试，**不弹提示**。它是一次后台整理，
没有"用户在等"这回事，弹一条错误只会让人莫名其妙。

### 4.10 风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **摘要是有损的** | 压过头会丢关键细节 | 原文一条都不删，随时能翻回去对照；`Memory` 块可展开、可改 |
| **成本** | 每 10 轮多一次调用，且要重发整段旧记忆 | 阈值 20 已把频率压到最低；单次上限 300 条；没配对话模型时整条静默跳过（§3.8） |
| **老用户第一次打开** | 几千条历史要分好几轮才追平 | 一轮吃 300 条，几轮后收敛；期间记忆逐轮变好，不会出错 |
| **压缩时被清空 / 删角色** | 后台任务把刚清掉的记忆写回来 | `chatSeq` 代次作废（§4.7） |
| **压缩与手工编辑撞车** | 重回炉的结果盖掉用户刚写的 | 落笔前比对基准正文，不一致就放弃本轮（§4.8） |
| **手改过的记忆会被下一轮压缩重写** | 压缩是"旧记忆 + 新消息 → 重写一份"，每次都会把用户改过的措辞再润色一遍 | **仍未解决**。要"钉住"得加一层标记：改过之后不再把旧记忆喂回模型，只让新消息往后接 —— 但那等于那段记忆停止进化，是个取舍 |
| **忘掉的那一段就此失忆** | 记忆是模型生成的，忘掉之后拿不回来 | 撤销窗口一过就真的没了。原文还在，但那是"翻记录"，不是"角色记得" |

## 5. 情绪状态（mood）

### 5.1 从"消息上的一个字段"到"角色身上的一条状态"

早先 `mood` 只是 `ChatMessage` 上的一个词：给眼睛看的一枚药丸、给耳朵听的一点语调偏移。三块都是**出口**，缺的是**状态**与**回流** —— 每一轮都从零决定心情，"上一句被气到了，这一句还带着点余怒"演不出来，而且它不影响下一句怎么写、也不进画面。

一句话：**情绪是状态，不是标签。** 标签是每一轮的**输出**，状态是跨轮累积的**输入**。

| 原则 | 意思 | 落点 |
| --- | --- | --- |
| **不做分类表** | 生产情绪的是模型（它自己写那个词），消费情绪的也是模型（下一句怎么写、脸上什么表情）。两个端点都是模型，就不需要一张词表去翻译它 | `CHAT_MOOD_RE` 刻意没有枚举。唯一的例外是**代码**要消费的出口 —— 朗读语调那张 `MOOD_TONE`，而它已经是范本：**认不出就原样返回，绝不猜**，并且做整词匹配（`unamused` 里含 `amused`，两者正好相反） |
| **情绪只能演出来，不能被读出来** | 任何"好感度 72/100""情绪曲线""情绪日志"的界面都是破功（[对话体验.md](对话体验.md) §4.4）。更实际的一层：**情绪一旦变成数字，用户就会开始优化那个数字**，而这件事的全部价值是"它像个人" | 不加任何数值 / 曲线 / 日志界面（§5.8） |
| **零额外调用** | 情绪只能从**已有的那一轮回复**里免费拿到 —— 那个词本来就是模型自己写的，多花一次调用去"识别"它是把免费的答案再买一遍 | 表情那条同理：图本来就要画，只是往提示词里多拼一层（§5.7） |

### 5.2 存法与形状

新表 `char_moods`（v13 建表，与 `chat_summaries` 同一写法，`keyPath` 是 `charId`）：

```ts
const MOOD_STORE = 'char_moods'
if (!db.objectStoreNames.contains(MOOD_STORE)) {
  db.createObjectStore(MOOD_STORE, { keyPath: 'charId' })
}
```

**新增一张表是安全的升级**：建表是同步的结构操作，没有"整表读进内存再重建"那种中途失败的风险。

| 函数 | 说明 |
| --- | --- |
| `getCharMood(charId)` | 读不出来 / 形状不对一律当没有。**这一层不判过没过期** —— 那是读的人的事（服务端按窗口判） |
| `putCharMood(rec)` | 覆盖写。**`at` 由调用方给**，不在这一层取 `Date.now()` |

删除走 `deleteChatOf`（同一个事务），所以不需要单独的 `deleteCharMood`："清空对话"与
"删除角色"两条路都经过它，多一个没有人调的函数只是多一处要维护的东西。
理由与记忆那一处**一字不差**：**"消息没了而情绪还在"比失忆更糟** —— 清空之后下一句开口，
它会端着一份用户刚刚清掉的火气。

**为什么不挂进 `ChatSummary`**（加两个字段就能零升库）：① **语义不同** —— 记忆是"发生过什么"（成篇文字、可展开、可编辑、可忘），心情是"此刻什么状态"（一个词 + 一个时间戳），`Forget memory` 该不该连带清心情会立刻变成一个说不清的边界；② **导出的边界不同** —— 记忆跟着导出包走，瞬时心情**不**跟，同一张记录里一半带走一半留下就是一段特判；③ **升级的代价很小**，而上面两条是一辈子的约束。

### 5.3 怎么进 system

**位置：紧跟在时间之后、记忆之前**（§2.3 的 07）。整条链本身就是一条时间轴
（你是谁 / 你怎么说话 → 样本 → 时间 → 心情 → 记忆 → …），心情是**此刻的事实**，与时间同一层：

```
Right now: 2026-10-07 21:30, Tuesday (the user's local clock, real world only …).
You two last spoke 2 days ago.
You are feeling wary right now.
You already felt that way before they said anything - carry it into your reply, or let what they just said turn it.
What you remember: …
```

- **排在记忆之前**：记忆是一段成篇的叙述，夹在两块短事实中间会把它切碎。
  所有短事实在前、成篇的在后，这条秩序不破；
- **过一遍 `chatOneLine`**：这个词是从前端绕了一圈回来的外部输入，原样带换行塞回 system，
  等于给上一轮的输出一个伪造提示词结构的机会（与记忆那处同一条手法）；
- **认不出就整行丢掉**，不留一句 `How you feel right now:` 的空壳。

**"可以转向"这半句是必须的。** 只写"你正在恼"，模型会一轮一轮地恼下去 —— 那句话给它一个出口：
延续还是改口，由刚才发生了什么定。这也正是"不做数值模型"的代价换来的东西：
**惯性由模型演，不由权重算。**

**喂不喂，只看时间**：`now - at <= CHAT_MOOD_HOLD_MS`（**6 小时**）就拼进去，更久则**整行不出现**
（记录留着，读的时候判）。6 小时是"隔夜就散了" —— 不是"一次会话"，是"同一场戏"：

1. 三天的隔阂之后它还端着你上次惹的火，是**惩罚**，不是拟人（红线见 §5.8）；
2. 真正的"很久没见"已经有出口了 —— `You two last spoke 3 days ago` 本来就在，不需要心情再演一遍；
3. **不做定时清理**：判据是读的时候算的，不写一个后台任务去追着删。

> `CHAT_MOOD_HOLD_MS` 是**服务端**的常量，与 `CHAT_TEMPERATURE` / `CHAT_MAX_TOKENS` 并列 ——
> 那句话本身就是效果的一部分，改阈值不该要求用户重装前端（前端发**结构**，服务端拼**措辞**）。

### 5.4 形状检查：两端共用一把尺子

`CHAT_MOOD_RE` 收的是 `[a-z][a-z-]{1,19}`（小写字母与连字符，2–20 字符）。
存进 `char_moods` 的那个词也要过**同一个形状** —— 而实现上**不抄第二份正则**：
`moodWord()` 就在 [server/chatMood.js](../server/chatMood.js) 里，前端直接 import 它。
于是它有两个调用点，判据天然同源：[chatPhoto.ts](../src/lib/chatPhoto.ts) 的 `planChatPhoto`
（出不出表情层）与 `moodContext`（喂不喂回 system）。

**不过形状就什么都不做**：不喂回 system、不出表情层、不覆盖已有的状态 ——
与 `toneWithMood` 的"认不出就不动，绝不猜"同一条纪律。

### 5.5 什么时候写

`runChat` 收尾那一次 —— 就是现在写 `reply.mood = mood` 的**同一处**（`if (mood) reply.mood = mood`）。

| 规矩 | 为什么 |
| --- | --- |
| **状态与消息用同一个值**，不另算 | 药丸读消息、下一轮读状态。两者一旦能分叉，"它说它恼，可下一句又好好的"就会变成常态 |
| **`at` 取这一轮的收尾时刻**，不取消息的 `createdAt` | 消息的 `createdAt` 是**发给模型那一刻**，而心情是**说完那一刻**的。差几秒，但口径要对 |
| **落笔前比一次代次**（复用 `chatSeq`） | 生成是异步的。用户完全可能点"清空"或删角色 —— 回来时不检查，这次写入会把刚清掉的心情又写回去 |

> **复用同一个计数器是知情的取舍**：`chatSeq` 也会被 `forgetChatSummary` bump（那一次是为了作废
> 在途的压缩），所以判据比"只该在清空 / 删除时作废"更严一点 ——"生成中点了忘掉记忆"会让这一轮
> 的心情更新被丢掉。代价是那一轮的状态没更新，下一轮照常，**而且它是自愈的**；多养一个计数器
> 换这点精度不划算。另一半同样记着：它**只加不减**，撤销"清空对话"也不会退回去。

**一轮说不完（`stopped`）也照记** —— 不额外分叉。"说到一半还在气头上"本来就是真的。
没有词（收在半截上被剪掉、或模型没写）就不写。

### 5.6 表情出口：出图提示词里的那一层

把同一个情绪词拼进**出图提示词**，零额外调用 —— 图本来就要画。
`layers` 是 `[槽名, 值]` 的数组、**顺序就是权重**（[chatPhoto.ts](../src/lib/chatPhoto.ts) 的
`planChatPhoto`），新增一层 `['expression', expressionLine(word)]`。

**位置：`anchor` 之后、`part` 之前。** `anchor` 是"这个人是谁"（那七项头部特征），表情是
"这个人此刻什么样" —— 先立住是谁，再给此刻的样子。`part` 只在特写档出现，而特写档不拼表情，
所以它与 `part` 的先后无所谓。**`expression` 不在 `DIRECTOR_SLOTS` 里**
（那是 `['camera','lens','light','env']`）—— 于是摄影指导那一层**结构上就改不到它**；
与 `pin` / `frame` 同一处理：情绪是**意图**，不是摄影指导可以优化的工艺。

| 护栏 | 条件 | 为什么 |
| --- | --- | --- |
| **画面里得有人** | `self === true` | 一张空镜里没有脸。与 `anchor` 层同一个开关 |
| **特写那一档不拼** | `frame !== 'close'` | 特写档画面里常常只有一只手、一片布料 —— 请模型"在脸上写出神情"，就是请它把一张脸画进来，与"一个局部填满画面"正面打架。这条直接沿用 `action` 层在特写档被去掉的那条判断 |

再加一条与 §5.4 同源的：**词不过形状检查就不拼**。

措辞是 `` `a ${word} expression on the face, not acted out` ``：前半句只说**脸上的神情**
（"on the face"）；后半句是冲着具体毛病去的 —— 只写 `angry`，模型很容易把它演成一个**动作**
（摔东西、吼），而身体那件事由 `action` 层与 `negative` 层管，轮不到情绪插手。

**为什么是一个独立层，而不是让聊天模型把神情写进场景串**：① 场景串的职责是"只写事实、
原样保留"（`planChatPhoto` 的注释：谁都不许改写它），把神情塞进去等于让"这张图画的是什么"
和"这张脸什么表情"混成一件事；② 两件事挤在一个字段里会被平均掉 —— 这条教训在
`traits` / `voice` 上已经吃过一次。**为什么不做"情绪词 → 面部短语"的映射表**：与 §5.1 同一条，
现在的图像模型对 `tired expression` / `amused expression` 这类短语本身就能理解，
而词表一旦出现就要维护、就会在表外词上出错。

**重画那一张也用得上**：`ChatMessage.mood` 本来就跟着消息落盘，而重画（`retryChatPhoto` →
`drawChatPhoto` → `generateChatPhoto`）读的就是那条消息。照 `photoShot` / `photoFrame` 的样子
把 `mood` 一并传下去 —— 于是"这一张当时它正恼着"在重画时**仍然是同一个表情**。

### 5.7 药丸不动，一个字都不改

名字旁那枚药丸已经是情绪的出口了（普通页与沉浸页各一处）。这一版**不加任何新界面**：
药丸读的仍是**最后一条助手消息**的 `mood`，不改成读状态表 —— 两者在同一轮里是同一个值（§5.5），
而在过期之后它们本来就该不同（药丸答的是"那条消息当时什么表情"，那是对的问题）；
心情改到哪儿去了，**体现在它的话里**，那才是主要可感之处。`chatMood` 按 `charId` 分键。

### 5.8 三条红线与失败降级

| 红线 | 为什么 |
| --- | --- |
| **不给用户看数值、曲线、日志** | §5.1。想让它是可见的，就走记忆那一套（一段话、可展开、可改、可忘）—— 那是**可校对**，这是**可优化**，两者不是一回事 |
| **不让情绪变成惩罚** | "它生气了所以不回你"是能动性那根柱子，[对话体验.md](对话体验.md) §5 已经把它标成**最危险**的一根。6 小时窗口就是这条红线的落地 |
| **拿不到就什么都不做** | 词缺失、形状不对、画面里没有人、特写档 —— 四种情况下都**安静地少做一件事**，绝不补一个猜的 |

| 情况 | 表现 |
| --- | --- |
| 读不出来 / 形状不对 | 当没有。不报错、不打扰 —— 与 `getChatSummary` 同一处理 |
| 写不进去（配额满） | **静默**。它是一次收尾时的附加动作，正文已经落盘了；为它弹一条错误只会让人莫名其妙 |
| 模型这一轮没给词 | 不写、不喂、不出表情层，药丸也不渲染 |

## 6. 关系系统

### 6.1 它是什么

§5 那条是**瞬时**的（6 小时就散）。"你俩之间"是另一回事：**熟悉、信任、亲近**，长期累积，
不逐轮跳。两者互相影响，方向相反：关系决定**同一句话怎么落地**（热络时是打趣，冷淡时是挑衅），
心情慢慢**改写关系**（每一次互动都是往一个方向推一点）。

三条共同的边界：

1. **关系与偏好都不许改写人格**。"偏好是指导，不是重写人格的命令"，核心人格稳定 ——
   注入时那句边界话写死在服务端（§6.6）；
2. **颜色与数字不做装饰、不解锁内容**。可见 ≠ 一排仪表盘百分比：三档命名 + 一条细进度，
   而不是三个 0–100 的大数字；**没有任何 UI 处把关系等级做成"解锁 X"的门**；
3. **本地优先**：关系是角色身上的一条轻量状态，不进服务端。

### 6.2 落地形状

| 面 | 实际做法 |
| --- | --- |
| 三轴 | `familiarity` / `trust` / `affection`，内部刻度 `REL_MAX = 100` |
| 对用户可见 | 三档 `Getting to know` / `Warming up` / `Close`（`REL_STAGE_THRESHOLDS = [34, 67]`，名字在 `REL_STAGES`）。角色页只显示档位名与条宽，**任何界面都不出现数字** |
| 单次变化量 | `Δ ∈ [DELTA_MIN, DELTA_MAX]` = `[-3, +8]`，四舍五入取整并 clamp 到 0–100。上限 +8、下限 −3：亲近是攒出来的、不是崩出来的；负值只用于"明确的疏远信号"，刻意给得小 |
| 结构约束 | `familiarity ≥ trust ≥ affection`（取 min 封顶，`enforceOrdering`）。熟悉是攒出来的地基，亲近是最贵的那一格；挡"聊得多就自动亲密"，也挡模型把 `affection` 单独拉高 |
| 衰减 | **不做**。时间流逝只冻结、不扣分 —— 能降的只有模型明确写下的负 Δ |
| 驱动源 | 只在"压了一批记忆"时评估一次，**不逐条消息算** —— 压记忆 = 一段实质对话滑出窗口，正是"有意义互动"的天然节拍 |
| 注入 | `relationshipLines` → [server/relationship.js](../server/relationship.js) 的 `relationshipSection`（最多 6 行 / 单行 200 字符）。从没评估过或三轴全 0 时整块不出现 |
| 触发 | 压完一批记忆后由 `autoEvaluate` 顺手判一次，复用那一批消息与对话模型配置 |
| 失败 | 静默（`console.error`）：不打断对话、不抹掉已有分值；三轴都没挪动就不重写整份角色目录 |

改数字只碰四个常量（`REL_MAX` / `REL_STAGE_THRESHOLDS` / `DELTA_MIN` / `DELTA_MAX`）与
`enforceOrdering()` 里那个不等式 —— **改数字不碰链路**。

### 6.3 评估链路

关系怎么变由模型判（要"AI 情境判断"），但**判完要过一道基础阈值闸门**：

- **AI 给方向与幅度** → 走 `/api/enhance` 新增一档 `mode: 'relationship'`，与 `memory` / `summary`
  档同一套"固定前缀行、坏一行丢一行"（不用 JSON）；`ENHANCE_PROMPTS` 与 `ENHANCE_TEMPERATURE`
  两张表各补一个键，温度取最低一档附近（**0.2**）："编出来的关系比没有关系更糟"。
- **基础阈值做闸门** → 纯逻辑层把模型的 Δ 结合"已有分值 / 是否首次 / 会话数"收口。

输出是固定前缀的三行，坏一行只丢一行，同一根轴以第一次出现为准（照 `parseExtractedMemories`）：

```
familiarity|+2
trust|-1
affection|0
```

前端 `evaluateRelationship(cfg, context)`（[api.ts](../src/api.ts)）形态照 `extractMemories`：
同样传 `known`（当前三轴分值 + 一句"这段关系现在什么状态"的简报）以免震荡重复。
**这是一次独立调用**，不是搭在压缩上顺带重写（§6.8 第三处偏离）。

### 6.4 触发时机

`useChat.maybeSummarize` 压完一批记忆后调 `deps.onSummarized(id, batch)`，**同一根线多接一个下游**：

```
onSummarized(charId, batch)
  ├─ autoExtract(charId, batch)     // 已有：抽记忆条目
  └─ autoEvaluate(charId, batch)    // 新增：判关系（useRelationship）
```

两者互不认识、都尽力而为、都静默（失败就退出，不打断用户）。这一节拍本身就实现了
"非消息数驱动"：**只有一次实质对话滑出窗口才评估一次**。

### 6.5 纯逻辑 `src/lib/relationship.ts`（有单测）

这一层不碰界面、不碰模型、不落盘 —— 它只回答四个问题：

| 函数 | 管什么 |
| --- | --- |
| `coerceRelationship(raw)` | 盘上读回来的一条关系怎么收成合法形状（坏值 / NaN → 全 0；`affection ≤ trust ≤ familiarity` 再夹一次） |
| `parseRelationshipDelta(raw)` | 模型吐回来的那几行怎么读成三个轴的增减，认不出的行跳过 |
| `applyEvaluation(prev, deltas, now)` | 一次评估怎么把 Δ 落到分值上、并守住三条硬规矩 |
| `relationshipLines(state)` / `relationshipStage(v)` | 摊成注入 system 的几行 `- ` 指令 / 分值 → 对用户可见的三档 |
| `hasCloseness(state)` | "攒出东西了没有"的唯一判据 |

三条硬规矩（都在 `applyEvaluation` / `coerce` 里收口，**有单测**）：

| 规矩 | 落法 | 为什么 |
| --- | --- | --- |
| **结构约束** | 熟悉 ≥ 信任 ≥ 亲近 | 挡"聊得多就自动亲密"，也挡模型把某一轴单独拉高 |
| **一次不跨两档** | 单轴结果按"上一档再上一格"的天花板封顶 | 跳档会让关系"一天一个样"，而"我们一起慢慢熟起来"的分量正在于它是一格一格走的 |
| **缺席不降** | 缺轴按 Δ=0；单轴 Δ 封在 `-3..+8`；**没有时间衰减入口** | 你没来，分值就冻在原处；能降的只有模型明确写下的负 Δ |

抽出单独文件的理由与 `memory.ts` / `staleViews.ts` 完全一样：产品不变量必须能被构造数据直接断言，
而不是靠"聊两句看看感觉对不对"来验。

### 6.6 注入

[server/relationship.js](../server/relationship.js) 导出 `relationshipSection(raw)`，与
`chatGuidance.js` **逐行白名单 + 边界话留服务端**两条纪律一模一样：只收 `- ` 开头的行、
行数与行长各自封顶（`CHAT_RELATIONSHIP_MAX_LINES = 6` / `CHAT_RELATIONSHIP_LINE_CHARS = 200`）；
空则整段不出现（不留 `How close you two are:` 的空壳）。边界话写死，例如：

> `How close you two have become — this shapes warmth and familiarity only. It never changes who you are, and you do not perform closeness you have not earned.`

少了它，模型会把"你们很熟"当成对角色本身的改写，于是关系越高越像一个"跟谁都亲"的通用暖男。

**插入位置**：紧跟记忆条目之后、相处偏好之前（§2.3 的 10）—— 关系与记忆同属"你们之间发生过什么、
现在什么状态"这一层，而偏好与关系都是软指令要留在硬规则之前；顺序上先铺"记得什么"、
再讲"熟到什么程度"、最后才是"希望被怎么对待"。`/api/chat` 请求体解构里也要加 `relationship` 字段。

### 6.7 界面

**角色详情页**（[CharacterPage.vue](../src/components/CharacterPage.vue)）有一块「How close you are」：
三轴各一行「档位名 + 细进度条」，**不显示裸 0–100**；进度条复用现有 `.meter` 那套，
不引入 dashboard 卡片。关系**只在角色页出现**，不进设置、不进记忆中心（那是另一条隐私轴）。

### 6.8 与最初设计的三处偏离

| 原文 | 落地 | 为什么 |
| --- | --- | --- |
| **不做数值**（没有 0–100） | 内部有 0–100 的三轴，界面只露档位 | 原意是"不给用户看数字"。要让模型写"这次走近了多少"，总得有一个它能落笔的刻度；把刻度藏进实现比让它自由写一段话更好测。**风险仍在**：哪天把数字画到界面上，这一层的性质就变了 |
| **做成一段话**，复用记忆的"可见、可改、可忘" | 三轴 + 只读档位；**不可改、不可忘** | 这是当前最大的缺口 —— 用户不同意角色"对你好感多少"时没有入口 |
| **搭在记忆压缩上顺带重写**，不新增调用 | 一次独立模型调用 `evaluateRelationship` | 压缩的产物是摘要文本，把关系判断塞进同一个响应会让两种输出格式互相打架。复用同一批消息省掉的是读盘，不是调用 —— 成本 = 每压一批记忆多一次小请求 |

### 6.9 明确不做

关系**不驱动**出图 / 语音 / 其它功能的开关（架构上也不让别处读它当门）；不做关系的**历史曲线**
（要另存时间序列，代价大且 dashboard 化），只存当前态；不逐轮评估（贵，且会让关系"一天一个样"，
反而失真）；不做时间衰减（见 §6.2）。

### 6.10 剩余缺口

- **关系不可编辑、不可清除** —— 与"可见、可改、可忘"还差两步；入口应放在角色页，目前没做。
- **对话页不显示关系档位**：只有角色页显示。`src/lib/relationship.ts` 的注释写着"角色页与对话页
  头部都读它一份"，**以代码行为为准** —— 这是一处注释与实现的偏离。
- **瞬时心情不进导出包，关系跟着 `Character` 走**：`chat.json` 里带的是 `{ messages, memory }`，
  心情不加 —— 它是"你俩此刻"的状态，对方打开时早就过了 6 小时窗口，带出去是一个必然过期的字段；
  而关系是长期的，`writeCharacterZip` 序列化 `Character` 时自然就带上了。
- **情绪影响能动性**（"它生气了所以不回你"）仍不做：本地优先下没有可信的后台时钟，
  主动消息本身已在 2026-10-19 砍掉（§9）。

## 7. 语音、角色卡携带、导出

### 7.1 朗读（Web Speech，已落地）

角色说的话由浏览器自己念出来（[lib/speech.ts](../src/lib/speech.ts)，用自带的 `SpeechSynthesis`）——
不引第三方，所以不需要 key、不联网、不花钱。

**只有"手动念某一条"，没有自动朗读。** 一开始做过一个自动朗读开关（默认关、状态存盘、放头部），
后来去掉了：自动念意味着**每次回复都出声**，而聊天是随手就会发生的动作 —— 它会在你没想到的时候
开口。想听的人自己点那枚喇叭，这一个动作就够了。

**"按角色配音色"在纯前端能做到的是**：从系统音色表里给这个角色**稳定地**挑一个，再把语速与音高
错开一点点。用角色 id 做哈希，所以同一个角色每次听起来都是同一个人、不同角色之间也分得出来。
语速 / 音高只取 0.90~1.07 —— 再放开就开始像卡通配音或机械音了。

| 决定 | 为什么 |
| --- | --- |
| 一次只说一句，新的压掉旧的 | `speak()` 开头先 `cancel()`，否则连点两条消息就是两把嗓子一起说话 |
| 单条朗读用**同一枚按钮**切换念 / 停 | 为一件只有两种状态的事再养一枚"停止"按钮不划算 |
| 那枚按钮**绝对定位**在气泡外侧下角；挂不下时（窄屏 / 沉浸页）改挂气泡下面 | 放进流里会实打实把每个气泡压窄一排，而不悬停时谁也看不见它；外侧那点地方在窄屏只剩 12%，硬挂就是被裁掉 |
| 悬停才浮出；`(hover: none)` 设备常驻但压暗 | 每条消息都挂着一枚喇叭会把对话流弄得很吵；触屏没有 hover，只能常驻 |
| 生成中的那条不给朗读键 | 半句话念出来更难听 |
| 换角色 / 离开页面 / 清空对话 / 重生成都 `stopSpeaking()` | 语音不属于"后台也该继续"的那类东西；念一条马上就不存在的消息没有道理 |
| **不支持就不给入口** | `speechSupported()` 先问一次。一个点了没反应的按钮比没有更糟 |
| 按**角色设的语言**挑（`persona.language`，§8.7），没设才退回按文本二分（有汉字 / 假名 → zh，否则 en） | 同一语言的音色一个都没有时退回全部 —— 口音不对也总比一声不吭强 |
| 音色表异步到达（`voiceschanged`） | 第一次 `getVoices()` 常常返回空数组；拿不到就只报 `lang`，让浏览器自己挑 |
| 进对话页先 `warmUpSpeech()` 预热一次 | 不预热的话**第一次朗读用的是浏览器默认音色**，和它之后的声音不一样 —— 同一个角色第一句和后面几句嗓门不同，很难解释 |

情绪也会叠到语调上（`MOOD_TONE` / `toneWithMood`）：认不出的词原样返回，绝不猜。

**还没做**：**说给它听**（`SpeechRecognition`）。支持面窄（Firefox 没有）、识别质量不稳，
做出来会是一个"有时出现有时不出现"的按钮，先放着。

### 7.2 自定义音色（已落地）

§7.1 那个"按角色哈希挑一个系统音色"只是权宜：能听，但每个角色都不是真的在说话。这一节是
**让角色有一把真正属于它的嗓子**，preset / describe / clone 三档均已可用：前端在
[useCharacterVoice](../src/composables/useCharacterVoice.ts)，后端在 [server/routes/tts.js](../server/routes/tts.js)
的 `/api/tts` 与 `/api/voice/clone`，样本存 `voice_samples` 表（§1.6）。

> 入口的事（2026-10-03）：向导第 2 步就是配嗓音那一屏，但它的解锁条件是 `wizardId`，而详情页那枚
> `Edit` 走的是 `editingId`（空）—— 一个角色的嗓子建完就再也改不了。现在那块多了一枚
> **Change voice**（`startVoiceEdit`，直接落在第 2 步、存完回详情；见 [角色创建与形象.md](角色创建与形象.md)）。

**一句话本质**：现在 `speak()` 是**同步**的（点下去立刻出声、免费、离线）；接上自定义音色后它变成
**请求 → 等首字节 → 拿到音频字节 → 播放**，而且**每次都要钱**。下面每一条都是从这句话推出来的。

| 来源 | 用户做什么 | 上游拿到什么 | 成本 |
| --- | --- | --- | --- |
| `preset` | 从厂商自带 voice 里选一款 | 一个 voice 名（如 `alloy`） | 每句 |
| `describe` | **写一段话**描述这个人听起来什么样 | 默认 voice + `instructions` | 每句 |
| `clone` | **传一段音频样本** | 上游建号时返回的 voice id | **建号一次** + 每句 |

三条路的**差别只在"voice 从哪来"**。一旦拿到那个标识，合成请求是同一个形状
（`{ text, vendorVoice, describe?, speed? }`），所以服务端只需要**一个合成端点**，
克隆多一个"建号"端点。这是这一节最要紧的结构判断 —— 若把 `describe` 和 `clone` 当成两套功能
各写一条链路，缓存、选路、播放、中断全都要写两遍。

数据模型（`CharacterVoice`，挂 `Character.voice`，纯 JSON、存 localStorage、跟着导出包走）：`engine: 'browser' | 'tts'`（缺省 = browser，于是老角色照旧）、`voiceName` / `rate` / `pitch`（browser 档）、`source: 'preset' | 'describe' | 'clone'` + `configId`（tts 档）、`vendorVoice`（preset 的枚举名或 clone 拿到的 id）、`describe`、`sampleId`（clone 的样本引用，建号之后合成不再用它，留它是为了重新克隆 / 删样本 / 界面回显）。
**样本是唯一的二进制**，存 IDB `voice_samples`（key = `sampleId`，value = `{ blob, name, bytes, createdAt }`，§1.6）。

后端两个端点：

```
POST /api/voice/clone
  { sample: dataURL, name, provider, baseUrl, apiKey } → { vendorVoice }

POST /api/tts
  { text, vendorVoice, describe?, speed?, provider, ttsModel, baseUrl, apiKey }
  → 200 audio/mpeg（chunked，边收边 res.write）
```

**上游其实是三条端点，按来源分工**（火山）：`preset` / `clone` 走 `/tts/unidirectional`（`{ user, req_params: { text, speaker, audio_params } }`，音频在**逐行 JSON 的 `data`** 里）；`describe` 走 `/tts/create`（`{ model: 'seed-audio-1.0', text_prompt, audio_config }`，音频在**整个响应体的 `audio`** 里）；克隆建号走 `/tts/voice_clone`。
两条合流在一处：`pipeTtsAudio` 逐行取帧，音频字段名 `data` 优先、`audio` 兜底。**末尾那一段必须补喂一遍** —— 流式那条每行都有换行，而 `/tts/create` 整个响应就是一个 JSON、末尾没有换行，漏掉它就是整段音频一个字节都发不出去。

> **踩过的坑：`describe` 不能用 `/tts/voice_design`。** 那条要求 `speaker_id` 必填、备注还写着
> "控制台购买"—— 得先有一个买过的底子音色才能用，而描述档的卖点就是"不用先准备任何东西"。
> 代价是 `/tts/create` 属于**生成任意音频**的端点（环境音、音效、多人对话都做），所以提示词里必须把
> "只要这一个人说话"说死（`ttsDesignPrompt`）；另外它的**默认输出是 wav**，请求里必须显式要 mp3。

骨架直接复用现有几条：`rateLimit`、`assertSafeTarget`(SSRF)、`dispatchAttempts`、
上游非 2xx 且未写头时回 JSON 错误。

| 决定 | 为什么 |
| --- | --- |
| 样本走 **dataURL**，不走 multipart | 现有端点的 body 都是 JSON，而 `dispatchAttempts`（代理那一跳失败再直连试一次）依赖 **body 字符串可复用** —— multipart 发过一次就消耗掉了。样本一般几百 KB，base64 后约 1.3 倍，可以接受 |
| `/api/tts` 必须挂 `rateLimit` | 它是**唯一按字符付费**的端点，而这个端点没有鉴权（key 在客户端，设计如此） |
| 响应是字节流不是 JSON | 先 `setHeader('Content-Type','audio/mpeg')` 再 flush；中途出错只能断流 —— 与 `/api/chat` 那条"先判状态码再开流"同一个道理 |
| `/api/voice/clone` 要限样本 | 唯一收"文件"的端点。限大小（10MB 一档）、限 MIME、限时长（上游也会拒） |
| 能力表扩一维 | 现在 `Provider` 是纯出图的（`quality/background/sizes/edit/seed`）。TTS 问的是另一组：**认不认 `instructions`、`voice` 是枚举还是任意 id、做不做克隆、鉴权头怎么放**（ElevenLabs 用 `xi-api-key`） |

**前端**：① **选路与降级** —— 没配 tts / 没配 TTS 配置就走浏览器（立刻出声）；配了则 `/api/tts` →
缓存命中？→ 播放。没 key、请求失败、超时都退回浏览器念，并**如实说一句**"用的是浏览器声音"。
② **缓存不是优化，是必需项** —— 同一句话会被反复点（"再听一遍"），每次点都付费：新表 `tts_cache`，
key = `hash(text + 音色指纹)`，指纹含 `vendorVoice / describe / speed / provider`（改了描述就不该命中旧音频），容量上限与历史那套 prune 同一手法。③ **中断** —— `speakingId` 的语义扩到"正在**生成**音频"，点一下**既掐音频也 abort 请求**，那几处 `stopSpeaking()` 调用点一起覆盖。
④ **长文本** —— TTS 有单次字符上限（OpenAI 是 4096）；角色回复只有一到三句，要防的是"朗读记忆"这种长的：**先按单次够用做，超长截断并如实提示**，别一上来就写切分队列。
⑤ **设置页加第四种用途** —— `ApiConfig.kind?: 'image' | 'text' | 'vision' | 'tts'`、新的 active 键 `kimage.apiActiveTts`，`SettingsPage` 的分区与 `App.vue` 那套照抄一份。
⑥ **角色页的音色区** —— 引擎切换 / 来源切换 / **试听** / 描述框 / 上传样本 / 语速。**试听是设计要点**：不改描述就没法调音色，而每改一次都发真请求太贵 → 试听走**固定短句**（如 `Hey, it's me.`），命中率极高、成本几乎为零。

**合规（克隆必须做，不能省）**：上传样本前要有**明确的同意声明**（"我确认有权使用这段声音"）并留时间戳；要能删（删角色连带删样本，另有一条"删除音色"）；**样本与音色都不进导出包** —— 不是怕大，是 `vendorVoice` **只在原账号下有效**，带出去对方也用不了；导入时该角色退回 browser 音色，**界面上要说清**。

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **成本失控** | 唯一按字符付费的端点，而喇叭是随手点的 | 缓存 + 试听固定短句 + 界面如实说明"这句会发一次请求" |
| **延迟** | 首字节可能 1–3 秒，而现在是"点了立刻响" | 按钮进"生成中"态；命中缓存则瞬时。**不要在这个功能上加自动朗读** —— 自动播放策略要求 `play()` 在用户手势内，且几秒延迟的自动播放很难受 |
| **上游鉴权不统一** | ElevenLabs 用 `xi-api-key`，国内几家要签名 | 目前只接火山一家（`X-Api-Key`，部分端点还要 `X-Api-Resource-Id`）；能力表扩一维留给下一家 |
| **克隆按套餐限量** | 免费套餐常常不能建号 | 失败时如实转述上游那句话（复用 `detail` 提取那套），不自己编解释 |
| **两套音色并存** | 配了 TTS 又降级，听起来像换了个人 | 把当前引擎写进按钮的 tooltip；降级时明确提示 |

**顺序**：**先 `describe`（OpenAI 兼容），再 `clone`（ElevenLabs）** —— 两者共用 90% 的链路
（选路、缓存、播放、中断、设置页那第四档、角色页音色区）。先把链路跑通，克隆只是"多一个来源"。

### 7.3 角色卡带上对话（已落地）

导出的 zip 从"设定 + 设定图"扩成"设定 + 设定图 + 对话"。分享一个**养熟了的**角色时，
那段关系本身才是最难重来的东西。包结构没变，只多一个文件
（[api.ts](../src/api.ts) 的 `exportCharacter` / `readCharacterZip`）：

```
character.json     ← manifest，多一项 chat: "chat.json"
chat.json          ← { messages: [...], memory: "…" }
ref.jpg / source.jpg / front.jpg / …
```

| 决定 | 为什么 |
| --- | --- |
| 对话**单独一个文件**，不内嵌进 manifest | 几百条消息塞进 `character.json`，那份"给人看的清单"就变成一坨机器数据了 |
| 消息只带最近 `CHAT_EXPORT_MSGS`（300）条 | 话可以无限长，全带出去包里就是几 MB 纯文本。而分享时真正要传的是**记忆**，消息只是那份记忆的来处 |
| 包里**不带记忆的游标**（`upToAt` / `covered`） | 那些 id 与时间戳在对方那里不成立。带了只会让下一轮压缩要么把导入的这段整段重压一遍，要么一条都不压 |
| 导入时**按收到的消息**重新推平游标 | 记忆当作"已经覆盖了这些消息"，于是它记得从前，而之后新聊的照常累积 |
| 消息 id 一律换新，`charId` 用新建那个角色 | 与角色 id 同一条理由：不沿用外部文件里的标识 |
| 逐条过筛（`coerceImportedChat`） | 包是外部文件：认不出的 role、空正文、坏时间戳都挡掉；时间戳坏了就按次序补一个 —— 整段对话的**相对次序**比绝对时刻要紧 |
| 对话读坏了**只丢对话**；没聊过 / 记忆为空**不写 chat.json** | 角色本身照常导入（与"某一张图丢了"同一处理）；包里多一份空壳，会让"这个包带了对话"这句话变得不可信 |
| **`duplicateChar` 不带对话** | 复制是造一个"同一副皮囊的另一个人"，不是把这段关系也复制一份。分界线在"分享 vs 分身" |

导出回执会把两样都说清：`Exported "X" with 6 images and 128 messages.` —— 一个只有设定没图的
角色，和一个把关系一起带走的角色，导出来的东西差别很大。

瞬时心情不进包（§6.10），关系跟着 `character.json` 走，样本与音色不进包（§7.2）。

### 7.4 导入导出要带上 persona

`Character.persona` 是纯 JSON，跟着 manifest 走即可：`exportCharacter` 的 entry 里加
`...(c.persona ? { persona: c.persona } : {})`；`readCharacterZip` 里用 `coerceCharPersona`
收一遍 —— 包是外部文件，脏数据照样要防。不加这一步的话，导出的角色在对方那里会变成
"没性格的"，而人格恰恰是这个功能里最难重写的一份数据。

## 8. AI 起稿生成人格

### 8.1 它解决什么

起稿那条流水线（[ENHANCE_PROMPTS.character / .vision](../server/enhancePrompts.js)）原本只产出
**12 行长相**，persona 要用户在编辑器里自己写。结果是**所有 AI 建出来的角色一律
"identity 很满、persona 全空"** —— 名字和 identity 能撑起相当鲜明的角色，但**同一类角色之间
拉不开差距**（狮驼岭三王听起来会是同一个人），而名字本身没信息量的角色则毫无特点。

### 8.2 十二行扩到十六行

在 `Marks` 之后追加四行，**接在长相块后面而不是插在中间** —— 让长相那十二行保持连续，
模型不容易把两件事写串：

```
Personality: <what this character is like: a few traits and a disposition>
Voice: <how they talk: register, sentence length, verbal habits, and any word they use for themselves instead of "I">
Address: <how they address the user, and what these two are to each other>
Boundaries: <what this character would never do or say>
```

配套加进提示词的三条规则：

| 规则 | 为什么 |
| --- | --- |
| `Every appearance value … under 12 words` | 原来那条"所有值都是 12 词以内的英文短语"会把人格也框进去 —— 而 `Voice` 天生要写得更长，还可能夹 CJK（自称那类词）。把约束收窄到长相那 12 行 |
| "两半不能互相渗透" | 人格不会被写进长相字段（那会被拼进出图提示词），长相也不会被写进人格 |
| "这四行是给扮演它的模型读的，写成它能照做的指令" | **`Voice` 里一个具体的习惯（自称、句长）顶得上一堆形容词** |

### 8.3 识图那条的例外（要明确标出来）

识图提示词的核心规矩是"**只写看得见的**"。人格恰好是图片里读不出来的东西 —— 所以这是
**唯一一处明确的例外**，并且在提示词里把性质说清楚：

> 是一个静止的画面，所以怎么说话只能从**穿着、站姿、神情**去推；
> 写得平实可信即可，**不要去编一段身世**。

把例外标出来，比让它悄悄违反那条规矩好 —— 后者会让"只写看得见的"整条规矩变得不可信。

### 8.4 解析（`parseCharacterDraft`）

新增**第二张查表**而不是把两张合成一张：两套字段的键不重合，各查各的更清楚。
`personality / voice / address / boundaries` → `traits / voice / address / boundaries`，
与 `name`、长相那 11 项都不碰撞；归一化（去非字母、转小写）之后仍然唯一。

> 实测过一份模型风格的回复：四行全部正确拆出，`本王` / `小子` 这类 CJK 原样保留，
> **标签外面裹了 `**` 也能解**（原有的装饰剥离），最后一行之后的客套话被忽略，
> `Face marks: none` 照旧落成空串。长相那 11 项的行为一字未变。

### 8.5 回填：人格**只有模型真写了才覆盖**

`applyDraft` 里长相是**直接整体替换**的（那 12 行是必答项），人格则多一个 `hasPersona` 判断：

```ts
if (hasPersona(d.persona)) draft.value.persona = { ...d.persona }
```

理由：这几行是**后加的**。老提示词、或模型偶尔漏答时解析结果是空的 —— 直接替换会把用户自己
写好的人格**抹成空白**，比"这次没更新"糟得多。

### 8.6 标记与按钮

`aiFilled` 的键拓宽成 `keyof CharacterFields | keyof CharacterPersona`（两套不重合，标在同一份里
不打架）：人格那几栏也会亮起模型小圆点，改一下那一栏点就消失 —— **与前两组完全一样的规矩**，
用户不用再学一遍。`hasSpec`（决定起稿键显示 `Draft the spec` 还是 `Draft again`）把人格也算进去 ——
它同样是起稿会覆盖的东西。

### 8.7 再后加的那一栏：`Language`

到 §8.2 为止，人格四栏全都关于"这个人怎么说话"—— **但没有一栏管他说哪国话**。提示词里从来没
规定过输出语言，于是它跟着用户走：你写中文，一个设定成英国人的角色也用中文回。

现在 `persona` 多一栏 `language`（行定义里排在人格段的**最前**）：

| 决定 | 为什么 |
| --- | --- |
| 单独成栏，不并进 `Speech style` | 同一栏里模型会把两者平均掉（`traits` / `voice` 那条教训）。而语言的错法比措辞重得多：说错语言不是"这个人不太像"，而是"根本不是同一个人" |
| **默认留空 = 跟随用户** | 这是兼容性红线，不是偏好：默认写成 `English` 就等于把所有存量角色的行为静默改掉 |
| 值写成**指令**而不是标签（`- Speak only English, whatever language the user writes in.`） | 用户填的是 `English` / `简体中文` 这样的名词短语，直接摆进 system 里模型只会当背景资料 |
| `CHAT_RULES` 里补一条兜底 | "用户用什么语言你就用什么语言；`How you behave` 里点了语言则以它为准" —— 规则在最后收束，和其余几条同一位置 |
| 朗诵挑音色也读它（`langTagOf`） | 原来是"按回复文本二分"猜的，只在中文 / 英文上凑合。现在用户明确写了答案，顺带把日语、韩语也照顾到了 —— 注意「日本語」三个字**全是汉字**，所以语言名要先于"按文字判"认，否则会认成中文 |
| **两档起稿都不许从长相推语言** | 识图那档尤其：从长相推国籍 / 语言是最典型的刻板印象。图里唯一站得住的证据是**真的出现了字**（招牌、徽章、制服、印字） |

> §8.2 / §8.6 里"十二行 / 十六行 / 这四行"是当时的现场记录，保留原样。现在的行数是 **22**
> （`Name` + 16 项设定 + 5 项人格），而行清单本身住在 [server/charSpec.js](../server/charSpec.js)
> —— 行数、必填枚举、标签对照表全由它算出来。

## 9. 已砍：主动联系与虚拟生活（决策记录）

**2026-10-19 决策：T6 主动联系与 T8 虚拟生活不做** —— 不是延期，是不做。

原因只有一条，但它是否决性的：**本地优先意味着没有可信的后台时钟。** Kairo 无账号、无服务端数据库、无常驻进程；浏览器页面关掉后角色发不出任何消息，而 Service Worker + Web Push 需要服务器与订阅，直接违背本地优先。所以"主动联系"在物理上只能发生在**应用被打开、且页面可见**的时候 —— 一个只在页面开着时才成立的"主动"，对陪伴产品没有意义。T8 虚拟生活依赖 T6 的消息通道，通道不存在，它跟着一起取消。

**下面这些数字只作决策记录，不要再按它们排期。**

| 当初的默认值（T6） | 值 |
| --- | --- |
| 全局每日上限 | 默认 **1 条 / 天**，可调 0–3，**所有角色共享**这一个配额 |
| 角色优先级 | 三档 `Quiet` / `Balanced` / `Eager`（默认 `Balanced`），权重 `{0.2, 0.5, 1.0}` |
| 免打扰 | 默认**关**；开启时默认 22:00–08:00（用户本地时区），判在前端算 |
| 通知正文 | 默认**只显示角色名**，正文可选（每角色开关）—— 避免锁屏泄露私密对话 |
| 未回复处理 | 同一角色**连续 2 条未回** → 自动降为 `Quiet`，直到用户回话；**不降关系** |
| 触发与投递 | 打开 / 页面转可见时评估，可见期间软轮询不早于 6 小时；消息注入既有对话流 + 未读徽标，不新开收件箱页 |
| 闸门 | 纯逻辑 `canReachOut` / `nextEligible` / `markSent`，不变量用单测钉死 |

（T8 当初打算给 `persona` 加 `habits?` / `goals?` 两个 additive 字段，分享频率走 T6 通道、
资格权重 = `affection` 档 × 角色优先级；一条红线：只分享角色**自己**的虚拟日常，
**绝不虚构发生在用户身上的现实事件**。）

**没有发生的东西**：库仍是 `DB_VERSION = 14`，没有 `inbox` 表（当初计划的 `14 → 15` 没发生）；`src/lib/proactiveGate.ts`、`ProactivePanel.vue`、`proactiveGate.test.ts` **都不存在**；`ENHANCE_PROMPTS` 没有 `proactive` 档，`settingsNav` 没有 `proactive` 分区，`settingsNav.test.ts` 里那条 `not.toContain('proactive')` 也还在；`persona` 没有 `habits` / `goals` 槽。

**仍然有效的两条边界**：**关系仍然无衰减，也不因"未回复"降分** —— 那条纪律当初长在闸门层，闸门没了，这条边界反而更彻底：关系只能被模型明确写下的负 Δ 拉低；**"情绪影响能动性"（它生气了所以不回你）仍不做** —— 与砍掉的主动消息同一条理由：本地优先下没有可信的后台时钟，而"不回你"本质上就是一次主动行为。

## 10. 风险、验收、相关文档

### 10.1 风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **成本性质变了** | 出图是"点一次花一次"，聊天是持续消耗 token，且按轮次累积 | 不做预算控制。`CHAT_MAX_TOKENS = 1500` 是唯一的硬闸（§2.4） |
| **限流更容易撞上** | `RATE_MAX = 30/min` 按 IP（[server/core.js](../server/core.js)） | 一轮 = 1 次请求，正常聊天到不了。把 `/api/chat` 同样挂上 `rateLimit`，不自开小灶 |
| **Serverless 上的流式** | Vercel 有函数执行时长上限，长回复可能被平台掐断 | 短回复（≤1500 token）通常远在上限内。断掉的表现是"说到一半停住"，走 §3.3 |
| **角色扮演被上游拒答** | 虚构角色 + 安全策略，敏感角色可能被拦 | 如实把上游那句话透出来（复用其他端点那套 `detail` 提取），不自己编解释 |
| **上下文膨胀** | 20 条窗口已经封顶，但单条可能很长 | 入口校验里限 8000 字符 / 条；更早的交给摘要（§4） |
| **`max_tokens` 字段名** | 个别中转只认 `max_completion_tokens` | 按最普遍的那个名字发。真撞上，上游会明确报 "unknown parameter"，加分支即可 |
| **多模态** | 发图给角色看：识图链路现成，主要是消息结构要支持附件；**角色回图**：出图链路也现成，但成本与失败率都高 | 仍未做。建议单独立项 |
| **情绪被画成动作** | "angry" 画成摔杯子、砸桌子 | 表情层只写**脸上的神情**；特写档不拼（§5.6） |
| **复读机** | 每轮把同一个词喂回去，它会一轮一轮地恼下去 | 提示词里给"可以转向"的出口；**状态是覆盖写的** —— 模型换了词，状态跟着换 |
| **心情与药丸对不上** | 一个读消息、一个读状态 | 同一轮同一个值（§5.5）。过期后不同，而那是**对的** |
| **在途写入撞上清空** | 生成中点清空 / 删角色，回来把心情写回去 | 落笔前比一次代次（§4.7 / §5.5） |
| **库版本** | 每次新增表 | 只能往上加，回退时也不能改回去（§1.7） |
| **一句话都不说就卡住** | 心情掺进提示词后，模型把"恼"演成"不理你" | 提示词只说"带着它"，**不说**"因此少说"；红线见 §5.8 |

## 11. 一句话回顾

> 对话这条线其实只有四件事：给角色补一组**与长相完全分开的人格字段**、把消息按角色存进 **IndexedDB**、加一条**把上游 SSE 收窄成 NDJSON 的流式端点**、做一个**按角色隔离状态的对话页**。人格提示词里那几条"不要 markdown、一到三句、不要每轮反问、允许不友好"，才是"超拟人"真正的落点 —— 剩下的都是管道。
>
> 长期记忆是把滑出窗口的那些话压成一段**可见、可改、可忘**的简报；情绪是把"消息上的一个字段"升成"角色身上的一条状态"（多一张表、多一行提示词、多一层出图提示词）；关系是把"你俩多熟"从每次现编升成一条长期状态（三个内部分值、三档可见、一次只升一档、缺席不降）。三者都不加界面上的数字 —— 它们该被演出来，不该被读出来。
