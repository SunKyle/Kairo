## 0. 这一期要解决什么

目标一句话：**选一个角色，能像跟人聊天一样跟它说话，它记得住这次对话的上下文，说话像它自己。**

拆开就是四件事，缺一不可：

| # | 事 | 为什么必须有 |
| --- | --- | --- |
| 1 | 人格数据（性格 + 说话方式） | 现在 `CharacterFields` 里没有一个字是性格。不补，模型只能即兴演，每个角色都是同一个味 |
| 2 | 会话落库 | 没有历史 = 每次重新认识你，拟人感无从谈起 |
| 3 | 流式对话端点 | 现有代理一律 `await upstream.text()` 全量缓冲。等 5 秒憋出一整段，拟人感当场崩掉 |
| 4 | 对话页 | 上面三件事的出口 |

**明确不做**（见 §8）：

- 多模态（发图给角色看、角色回图）；
- 语音、表情、主动消息；
- 一个角色多段会话 —— 一期**一个角色一条连续对话**。

**已补做**：长期记忆与摘要压缩（§7）、AI 起稿生成人格（§9）。

## 1. 数据模型

### 1.1 人格字段（`Character.persona`）

```ts
/* 角色的"人格"：聊天才用得上的一组设定。
   刻意与 CharacterFields 分开存 —— 那边是长相，会被 characterFaceDesc
   拼进每一张出图的提示词；把性格混进去，等于让"它是什么人"去污染
   "它长什么样"的像素级约束 */
export interface CharacterPersona {
  // 性格：是个什么样的人。如 "guarded, dry humor, slow to trust"
  traits: string
  // 说话方式：怎么说话。如 "short clipped sentences, rarely asks questions"
  voice: string
  // 怎么称呼用户，以及它与用户是什么关系。如 "calls you 'kid', an old partner"
  address: string
  // 禁区：这个角色绝不会做的事。如 "never breaks character, never mentions AI"
  boundaries: string
}
```

挂载方式（[types.ts](../src/types.ts#L239-L265)）：

```ts
export interface Character {
  // ...现有字段不动
  /* 可选：加这个字段之前存下来的角色没有它，读入时补空串（coerceCharPersona），
     所以界面上读的地方可以当它一定存在 */
  persona?: CharacterPersona
}
```

**四个字段而不是一整段自由文本**：`traits` 与 `voice` 必须分开。"是个什么样的人"和"话怎么说出来"是两件事，
写在同一段里，模型会把两者平均掉 —— 结果是性格写了、说话方式被稀释成通用口吻。而"超拟人"恰恰主要靠后者。

**为什么不复用 `identity`**：`identity` 是给图像模型的（"veteran space smuggler, worn flight jacket"），
它的职责是让画面里的衣服和道具对。拿它当性格用，模型只会演一个职业，不会演一个人。

**为什么不需要新增 `CharacterFields` 的项**：现有字段的顺序被 `CHAR_FIELD_ORDER` 定死了，
顺序一变上游拿到的条件就变，跨图一致性随之失效（[api.ts](../src/api.ts#L1325-L1328) 那段注释已经说了这件事）。
人格另开一个对象，两边互不干扰。

### 1.2 消息记录

```ts
/* 一条对话消息。存在 IndexedDB，按 charId 索引 —— 一期一个角色一条连续对话，
   所以没有 sessionId；将来要开多段会话时再加这个字段，读入时补默认值即可 */
export interface ChatMessage {
  id: string
  /* 属于哪个角色。与 HistoryEntry.characterId 同一个口径：
     角色被删时它的消息一并清掉（见 §3.2） */
  charId: string
  role: 'user' | 'assistant'
  content: string
  createdAt: number
  /* 用户中途按了 Stop，这条只说到一半。
     与"上游报错"分开记：截断是我们自己按的，不是坏数据，
     下次拼上下文时它照样是一条正常的历史消息 */
  stopped?: boolean
}
```

### 1.3 存储分工

| 数据 | 放哪 | 理由 |
| --- | --- | --- |
| `Character.persona` | localStorage（跟着 `Character` 走） | 几百字节的字符串，与名字、设定同在一条目录里，不必再开一处 |
| `ChatMessage` | IndexedDB，新表 `chat_messages`（v5） | 消息是只增不减的文本流，几十轮就是几十上百 KB —— 塞进只有 5MB 的 localStorage 迟早把它撑爆 |

**没有单独的"会话表"**：一期一个角色一条对话，会话本身没有可存的东西 ——
标题就是角色名，时间与条数都能从消息派生（与 `CharacterStat` / `CharacterWork` 同一条规矩：
派生得出来的不再存一份）。多段会话那一期再加表。

## 2. 后端：`/api/chat`

实现位置：[server/index.js](../server/index.js)，跟在 `/api/enhance` 后面。

### 2.1 请求与响应

请求体：

```ts
{
  character: {
    name: string
    identity: string      // 只取这三项外观，见 §2.3
    outfit: string
    marks: string
    persona: CharacterPersona
  }
  messages: Array<{ role: 'user' | 'assistant'; content: string }>
  textModel: string
  baseUrl: string
  apiKey: string
}
```

**人格字段由前端发结构、服务端拼提示词** —— 与 `EDIT_INSTRUCTIONS`、`ENHANCE_PROMPTS` 同一套分工：
改措辞不该要求用户重装前端，而那些句子本身就是效果的一部分。

**温度不在请求里**，与 `ENHANCE_TEMPERATURE` 并列写死在服务端（见 §2.4）。

响应是**按行分隔的 JSON（NDJSON）**，`Content-Type: application/x-ndjson`：

```
{"delta":"你"}\n
{"delta":"好啊"}\n
{"done":true}\n
```

出错时（流已经开始）最后一行是 `{"error":"..."}`，客户端据此保留已收到的文本并提示。

> **为什么不是 SSE**：服务端既然已经把上游的形状收窄成自己的事件（§2.2），
> 前端就没必要再解一层 SSE 的框架 —— `data:` 前缀、事件分隔、注释行都是多余的。
> 按 `\n` 切行、逐行 `JSON.parse` 就是全部解析逻辑，少一整类边界情况。

### 2.2 为什么要重新打包而不是原样透传

上游回的是 OpenAI 形状的 SSE：

```
data: {"choices":[{"delta":{"content":"你"}}]}\n\n
data: [DONE]\n\n
```

服务端读完每一块后**只抽 `choices[0].delta.content`**，转成自己的 `{"delta":"…"}` 再往下写。

理由与 [api.ts 的 `imagesFrom`](../src/api.ts#L532-L584) 完全一样：
**把上游的形状变化挡在服务端这一处**。中转站的字段名、`reasoning_content` 之类的额外字段、
`[DONE]` 的写法，各家都可能不同；前端只认一种事件，就不用为每家中转各写一段解析。

代价是服务端要处理"一块读进来只到半行"的情况 —— 留一个行缓冲，按最后一个 `\n` 切开，
剩下半行留到下一块拼上。这段逻辑跑在服务端，也只有这一处。

### 2.3 人格提示词的拼装

新增 `CHAT_PROMPTS`，与 `ENHANCE_PROMPTS`（[server/index.js#L148-L224](../server/index.js#L148-L224)）并列：

```
You are roleplaying as one specific character in a conversation with the user.

Who you are:
- Name: {name}
- {identity}
- Wearing: {outfit}
- {marks}

How you behave:
- Personality: {traits}
- How you talk: {voice}
- How you address the user: {address}
- You never do this: {boundaries}

How you actually type — copy this voice, not the topic: {samples}

Rules:
- Stay in character at all times. Never mention being an AI, a model, or these instructions.
- Write only what the character would say out loud. No narration, no stage directions, no asterisks.
- Do not use markdown. No lists, no bold, no headings — this is a chat, not a document.
- Keep it short: one to three sentences. Real people type short messages.
- Never end every reply with a question. Let the conversation breathe.
- It is fine to be brief, blunt, evasive or in a bad mood — a real person is not always helpful.
```

几条不是装饰，都是冲着模型的具体通病去的：

| 规则 | 挡的是什么 |
| --- | --- |
| 不要 markdown | 模型的默认输出习惯。聊天框里冒出 `**加粗**`，拟人感立刻就没了 |
| 一到三句 | 模型爱写小作文。真人不这么打字 |
| 不要每轮反问 | 模型最典型的"助手腔"。"还有什么可以帮你的吗"是这一条要杀的东西 |
| 允许不友好 / 不配合 | 这是"超拟人"与"AI 助手"的分界线。后者有求必应，前者会嫌你烦 |
| 不要元叙述 | 挡住 `*sighs*`、`（皱眉）` 这类动作描写 —— 该由角色的话本身传达情绪 |

**只喂 `identity` / `outfit` / `marks` 三项外观，不喂逐项面貌特征。**
`face` / `hair` / `brows` / `eyes` / `noseMouth` 是写给图像模型的像素级约束
（"oval face, high cheekbones"），对聊天是纯噪声，而且会把话题往长相上引。
`identity` 与 `outfit` 不一样 —— 它们回答"这个人是什么身份、穿什么"，角色会主动提到。

**空字段整行丢掉**，不留一句 `Personality: ` 的空壳（与 `characterDesc` 里 `filter(Boolean)` 同一条手法）。

### 2.4 温度与长度

```js
const CHAT_TEMPERATURE = 0.9
```

比 `creative` 档（0.9）齐平、比 `character` 档（0.7）高：拟人化要的是**变化** ——
同一个问题每次问都该给一点不同的反应，温度低了会变成一台复读机。

请求体里另外限一把长度：

```js
{ model: textModel, messages, temperature: CHAT_TEMPERATURE, max_tokens: 1500 }
```

`max_tokens` 是提示词里"一到三句"的硬兜底 —— 提示词是软的，模型偶尔会不听话，
而这是按 token 计费的地方，不能只靠一句话拦着。

**为什么不是 400**：400 看起来"足够四五行"，但它没算**思考**。
o 系、Gemini 2.5 的 thinking、Claude 的 extended thinking 都把思考 token
记在这同一个额度里 —— 额度被思考吃光，正文只吐了几个字就被判 `length` 停下。
表现出来就是**"提示说截断了，可那句话明明很短"**，而这个现象在 400 上会变成常态。
1500 给思考留出余量，又仍然拦得住跑飞的模型（常态输出由提示词那一到三句管）。

### 2.5 流式转发

与其他三条端点的骨架一致的地方：`rateLimit`、`assertSafeTarget`（SSRF）、
`dispatchAttempts`（代理那一跳挂了再直连试一次）、`res.on('close')` 时 abort 上游。

两处必须不同：

**① 先判状态码，再开流。** 上游如果是 401 / 404 / 一把 HTML 错误页，此时还没写过任何字节，
应该像其他端点一样回一个正常的 JSON 错误（复用 `looksLikeHtml` / `htmlTitle` / JSON `message` 提取那三段），
让前端能用同一套 `failureMessage` 读到。**一旦 `flushHeaders()` 过了，就只能用 `{"error":…}` 收场。**

**② 超时改成"上游静默超时"而不是整条请求的总时长。** 现在的 `UPSTREAM_TIMEOUT_MS`（120s）
盖的是从发起到拿完的全程；流式下这个口径不对 —— 一条正在持续吐字的流不该被总时长掐断。
改成每收到一块就重置计时器，判定的是"**多久没动静**"。

响应头：

```js
res.status(200)
res.setHeader('Content-Type', 'application/x-ndjson; charset=utf-8')
res.setHeader('Cache-Control', 'no-cache, no-transform')
res.setHeader('Connection', 'keep-alive')
// 反代（Vercel / nginx）不认这个头就会攒够一批才吐 —— 流式当场退化成"等 10 秒一次性出来"
res.setHeader('X-Accel-Buffering', 'no')
res.flushHeaders()
```

**不加心跳。** SSE 那套 `: ping` 是为了防中间层把长时间静默的连接掐掉，
而对话的两个 token 之间最多几百毫秒，没有静默窗口需要垫。

**入口校验**（外部输入，边界上要防）：`messages` 必须是数组、条数 ≤ 200、
每条 `role` 只认 `user` / `assistant`、`content` 是字符串且 ≤ `CHAT_MAX_CHARS`（8000）。
这个端点是公开的（配置全在前端，没有鉴权，设计如此），不设上限就等于给了个免费的大请求放大器。

> 超长是**报错，不是静默切**。切掉的是用户自己写的东西，而他看到的
> 只是"我发了这么长，它好像没读到前半截"。前端在发之前会先拦一道并保留原文，
> 这里再拦一次是因为入口是公开的。

**`finish_reason` 要带出来。** 上游的最后一帧 delta 是空的、只带一个 `finish_reason`
（`stop` 是正常说完，`length` 是撞上了 `max_tokens`）。一路记着，收尾时随 `done` 一起发：

```
{"done":true,"finish":"length"}
```

丢掉它等于把"说完了"和"额度用完了"混成同一件事 —— 界面上一模一样，
用户会以为角色话说一半是它自己的风格。

## 3. 前端

### 3.1 `api.ts`：流式读取

```ts
export interface ChatStreamOpts {
  character: ChatCharacterPayload
  messages: Array<{ role: 'user' | 'assistant'; content: string }>
  cfg: ApiConfig
  /* 每一块增量。调用方拿到就往气泡上追加 */
  onDelta: (delta: string) => void
  signal?: AbortSignal
}

export async function chatStream(opts: ChatStreamOpts): Promise<void>
```

内部就是 `fetch('/api/chat')` + `resp.body.getReader()`，用 `TextDecoder` 解出文本、
按 `\n` 切行、逐行 `JSON.parse`：

- `{delta}` → `onDelta(delta)`
- `{done}` → 正常收尾
- `{error}` → 抛错（调用方保留已收到的部分）

**不能用 `EventSource`**：它只支持 GET，既带不了请求体，也带不了 `Authorization`
—— 密钥是每个用户自己配的，必须随请求发。这一段只能手写。

### 3.2 `lib/idb.ts`：建表升到 v6

`openDB` 里的版本号 `4 → 5 → 6`。v5 建表（与 `CHAR_STORE` 同一写法）：

```ts
const CHAT_STORE = 'chat_messages'

// v5 新增：角色对话的消息
if (!db.objectStoreNames.contains(CHAT_STORE)) {
  const store = db.createObjectStore(CHAT_STORE, { keyPath: 'id' })
  // 按角色取消息、按角色清消息都靠它
  store.createIndex('charId', 'charId')
}
```

v6 补一条复合索引：

```ts
/* v6 新增：对话消息的复合索引。
   v5 那条只能按 charId 取全部，而对话页要的是**最近这些条** ——
   有了 (charId, createdAt) 才能开一个游标从最新往回走，
   走够一屏就停，不必把这个角色几千条历史整个读进内存 */
if (db.objectStoreNames.contains(CHAT_STORE)) {
  const chat = tx.objectStore(CHAT_STORE)
  if (!chat.indexNames.contains('charIdCreated')) {
    chat.createIndex('charIdCreated', ['charId', 'createdAt'])
  }
}
```

对外四个函数：

| 函数 | 说明 |
| --- | --- |
| `getChatMessages(charId, limit)` | 走 `charIdCreated` 开一个**倒着走**的游标，取够 `limit`（默认 `CHAT_PAGE = 200`）就停，返回 `{ list, hasMore }`。`hasMore` 多取一条来判 |
| `putChatMessage(msg)` | 追加一条。**流式过程中不逐块写** —— 只在整条回复结束时落一次（见 §3.4） |
| `deleteChatMessage(id)` | 删一条（重新生成时删掉最后那条助手消息） |
| `deleteChatOf(charId)` | 按 `charId` 索引整批删。"清空对话"与"删除角色"共用它 |

> **`CHAT_PAGE` 是显示上限，不是删除。** 更早的还在库里，只是这一屏没读 ——
> 界面顶上给一枚 `Load earlier messages`，再抬一档。
> 两者是完全不同的语义，措辞上不能混（这也决定了那枚按钮**不能**用"加载中/丢弃"之类的字眼）。
>
> 往上面插内容时浏览器不一定能稳住视口，所以 ChatPage 在读之前先记下 `scrollHeight`，
> 消息回来后按"长高了多少"把 `scrollTop` 往下推同样一段。
> 读数必须放在 **post-flush** 的 watcher 里 —— 在 DOM 更新前量到的还是插进来之前的高度。

**为什么流式过程中不逐块写盘**：一条回复可能产生上百次 `delta`，
逐块写就是上百次事务 —— 而中途崩溃丢掉半句话，与"按了 Stop"在用户眼里没有区别。
收尾时落一次，中间只更新内存里那一个响应式字符串。

### 3.3 上游出错与"按了 Stop"要分开

这是这一期最容易做错的一处：

| 情况 | 已收到的文本 | 标记 |
| --- | --- | --- |
| 正常说完 | 全部 | 无 |
| 用户按 Stop | **保留** | `stopped: true` |
| 上游报错 / 断流 | **保留** | 无 `stopped`，但界面上挂一句错误提示 |

**三种情况都不丢掉已经收到的字**。用户按 Stop 不是"这次失败了"，
是"说到这儿够了"——把半句话删掉，等于惩罚他按了按钮。
（与设定图那条"中断后保留旧图、不生成坏图"是同一条原则。）

`stopped: true` 要存下来而不是只留在内存里：下次打开这一段还在，
而且拼上下文时它照样是一条**正常的历史消息**，不是坏数据。

### 3.4 `ChatPage.vue` —— 页面设计

#### 3.4.1 整页骨架

对话页是**一级页面**（与 Studio / Characters 平级），骨架是两栏：

```
┌─ 顶部横条（全局，不属本页） ──────────────────────┐
├─ 角色列表 ─┬─ 角色头 ──────────────────────────┤
│ 160px 宽    │ 头像 · 名字 · ⋮                    │ 固定
│            ├────────────────────────────────────┤
│ （独立滚动    │  消息流（独立滚动，居中 720px）      │ 滚动
│   区域）     │   assistant 左 · user 右            │
│            ├────────────────────────────────────┤
│            │  输入区  16px · 自增高 · 回车发送      │ 固定
└────────────┴────────────────────────────────────┘
```

**关键：只有消息流内部滚动，整页不滚。** 页面高度撑满横条以下，
头与输入区各自固定 —— 这是项目里已经定下的规矩（"提示词区域应独立滚动，
而非整个右侧区域滚动"）：底部的输入框跟着页面滚走，等于每打一句都要先滚回去。

#### 3.4.2 左栏 · 角色列表

| 项 | 做法 |
| --- | --- |
| 眉标 | `CONVERSATIONS`，全大写 + `--ls-eyebrow` 字距 —— 站内已确立的眉标样式 |
| 行 | 36px 圆形头像（读 `c.ref`，就是正脸）+ 名字 + 最后一条消息摘要（单行省略） |
| 排序 | **最近活跃在前**，从消息派生（与 `CharacterStat` 同一条规矩，不落盘） |
| 选中态 | `--accent-soft` 淡底 + 名字 600 字重。**不用彩色**，与站内克制的灰度一致 |
| 高度 | 行高 ≥ 52px，满足 40px 触控目标 |
| 宽度 | 240px（图示按比例缩了） |

**列出全部角色，不是"有对话的才列"** —— 只列聊过的，新角色就永远开不了头。

#### 3.4.3 角色头

32px 头像 + 名字 + 一行身份摘要（`identity` 截断）。
右侧一枚 `⋮` 菜单，里面只有一项：**清空对话**。

- 清空走 **UndoToast**（与删除角色、清空历史同一套撤销模式），**不用 confirm 弹窗**
  —— 站内有现成的撤销通道，再开一路确认框是两套规矩；
- 低频动作收进菜单：与角色卡片的 `⋮`（复制 / 导出 / 删除）同一个处理。

#### 3.4.4 消息流

- **铺满整块面板**，宽度交给气泡自己的 76% 上限去控。
  曾短暂试过"收在中间 760px 一列"，那是错的：这块面板只有一个说话对象，
  两侧再空出两百多像素看着就是没铺满；
  **外侧那条走道要从这 76% 里扣掉**（`min(76%, 100% - var(--ops-lane))`，见下面
  那枚动作药丸）—— 两个数得一起算，气泡才不会把药丸挤到面板外面去；
- **两侧都是气泡**，靠说话人那一侧的角收窄（`--r-sm`），气泡才有方向感；
- **角色一侧用 `--bg-elev`**：站内已有的"抬起来"的底色（输入框、标签都用它），不另造色；
- **自己一侧用 `--cta` 实心**：与发送键、Primary 按钮同一个主动色。
  **不能两侧都铺灰底** —— 这套调色板里几档灰差得太近（`--bg-elev` #F5F5F2 与
  `--accent-soft` 叠出来约 #F0F0F0），分不出谁是谁，而"谁说的"是对话里最不能含糊的一件事。
  最初做过"角色侧不加气泡、只靠左右对齐区分"的版本，那是错的：气泡才是谁的标记；
- **不逐条显示时间戳**：那是噪声。只在**跨天**或**间隔超过 30 分钟**时插一条居中分隔
  （`--fs-micro` + `--text-4`）；
- **自动跟随只在贴底时生效**：滚动位置距底 < 80px 才跟着新消息走，否则一动不动。
  用户正在往上翻历史时被拽回底部，是聊天界面最烦人的一件事；
- **流式中**：末尾一枚 **CSS 绘制的光标**（呼吸动画），不用图片/GIF
  —— 与"设定图生成中的停止符号用 CSS 绘制"同一条手法；
- **撞上长度上限时，气泡下面挂一行小注**（`Cut off at the length limit`）。
  `finish_reason === 'length'` 落到 `ChatMessage.truncated` 上并落盘 ——
  不标这一句的话，它和"正常说完"在界面上长得一模一样（见 §2.5）；
- **顶上一枚 `Load earlier messages`**（`hasMore` 为真时才出现）。
  它是往前翻一页，不是"加载中"、更不是"丢弃" —— 库里一条都不会少（见 §3.2）；
- **最后一条消息跟着一枚 Regenerate**：删掉它、用同样的上文重发，用户那条不动。
  `stopped` 的那条不显示（它是"说到这儿够了"，重发会覆盖掉用户的选择）。
  **挂法在 2026-10-05 改过（用户要求）**：它原本独自站在消息流末尾、是一行细字
  （试过 `.ed-btn` 与 `.quiet-btn`，前者和气泡一样抢眼，后者仍是"这一条消息顺带
  能做的事"里多余的一行字），现在排在末尾那条消息的悬停动作里、**"删"的后面**。
- **念 / 删 / 重来装在一枚「动作药丸」里**（2026-10-06 改，用户报"聊天框里 icon
  的布局不合理"）。这一排从前是**三枚光着的图标**挂在气泡外侧：
  ① 每一枚的框都有 40px 而图标只有 15px，图标之间因此空着近 30px ——
  读起来是"三个谁也不挨着谁的点"，不是一条工具；
  ② 它按气泡的**外沿**定位（`left/right: 100%`），而气泡可以长到 76%
  （窄屏 88%），留给它的就只剩 24% / 12%。三枚并排要 124px，窄屏那条只有 40px ——
  实测溢出 88px，末尾两枚被 `.chat-stream` 的滚动容器裁掉，点都点不到
  （触屏上这排还常驻可见，所以那不是"悬停才有"的小毛病，是一块常驻的破损）；
  ③ 到了沉浸页它直接躺在剧照上，而 `--text-3` 是照着面板面调的一档灰。
  现在的三条规矩：
  ① **给它一个底**（`--surface` + `--line` + `--sh-sm`，与 ⋮ 菜单、记忆卡片同一层
  语言）：三枚才是一件事，对比度也不再靠背景的运气；
  ② **挂得下就挂外侧，挂不下就挂到气泡下面**。宽屏：气泡从自己的宽度里让出
  `--ops-lane`（药丸宽 + 缝 + 余量），药丸贴气泡外侧下角、与最后一行字同一条中线；
  窄屏（≤860，气泡放到 88% 之后外侧只剩 12%）与沉浸页（气泡是整列的）：药丸改挂
  气泡下面，高度由气泡的 `margin-bottom` 让出（`--ops-rail`）—— 横向不够就往下走，
  不压字、不出面板、悬停时也不把下面的内容顶走（高度是常备的）。
  占高度而不占宽度是这两种代价里更小的一份：390 的屏上若要留出走道，气泡只剩
  196px，比"76% 太窄"那次否掉的一档还窄；
  ③ **可点区域分两档**（`--ops-btn`）：鼠标 34px（三枚并排少 18px，排在一起才读得出
  是一组），触屏 40px（站内对触控目标的底线）。触屏没有 hover，那层底降到
  `--bg-elev` 并压暗一档 —— 它从来没有"浮出来"的那一刻，常驻的 `--surface`
  只会变成每条消息下面挂的一块牌子；沉浸页是例外，那里背景是照片，底不能收。
  代价与兜底：
  ① 悬停才浮出来（键盘 `focus-within` 也让它浮出来，否则焦点落上去是盲按）；
  ② 名字只剩 `title` / `aria-label` 两处，同一个动作的两种叫法
  （`Regenerate` / `Try again`）因此在界面上看不见 —— 认了，图标本身就是
  "再来一次"的通用写法；
  ③ 末尾那条**没有气泡**时（只发了一张图、没有文字，那种消息不渲染气泡）
  下角无处可挂，它退回消息流末尾（`.regen`），用同一枚药丸、里面只有一枚按钮；
- **中段那枚标签也要摘掉**（2026-10-05 补，用户报"为什么会有这种生成对话记录"）。
  `splitTags` 只认**末尾**那一枚，那是为了不误吃正文里的方括号（`[注]`、`[1]`）——
  可模型并不总把标签写在最后：它会先说一句、再决定给你看张图、然后又补一句收尾的话，
  于是那枚 `[photo:self:…]` 落在**中间**，`splitTags` 够不着，**原样流给了用户看**。
  现在多一道 `stripStandaloneTags`（[server/chatTags.js](../server/chatTags.js)）：
  **整行只有一枚标签**就摘掉（不限于末尾），意图照样取出来用；夹在句子中间的方括号一律不碰。
  服务端在**放行每一块增量之前**过一遍（所以不会先露一下再消失），
  显示层也过一遍 —— 库里已有的老消息还带着它。
  提示词同时收紧：标签必须在**最后**，后面不许再有话；
- **正文末尾的空白要收掉**（2026-10-05 补，用户报"短回复底下多一行空行"）。
  气泡是 `white-space: pre-wrap`，结尾的 `\n` 会被**如实渲染成一行空行**；
  而模型把 `[mood:…]` / `[photo:…]` 写在单独一行，那个换行**总是比标签先到** ——
  按"标签起点"算出的放行边界正好落在它后面，于是它被当成正文发了出去，
  收尾那次 `splitTags` 的 `trimEnd` 已经追不回来（字早发出去了）。
  两处一起改：源头在 `chatTags.js` 的 `tailHold`（末尾那段空白一律扣住，
  后面一来非空白字符就跟着放），显示层在 ChatPage 的 `shownText`
  （**库里已有的老消息也带着它**，不能只修源头）。
  中间的分行照旧保留 —— 收的只有末尾；
- **懒加载**：进页面按 `charId` 取消息，与 `loadCharViews` 同一套按需加载 + 去重，
  启动时不碰（几十个角色的历史全读进来太重）。

#### 3.4.5 输入区

- **桌面 `--fs-base`(14px)、窄屏才提到 16px**：与气泡里的正文同号 ——
  自己打的字和它说的话一样大。16px 那一档只在窄屏出现，
  因为**低于 16px 时 iOS Safari 聚焦会放大整页**（站内硬约束，
  `style.css` 的 `--fs-lg` 注释就是为这件事写的），而桌面没有这个问题；
- 自增高 `textarea`（与角色向导的起稿块共用同一套 `vGrow`），6 行封顶后内部滚；
- **回车发送、Shift+回车换行**，同样要带 `isComposing` / `keyCode 229` 的输入法保护；
- **生成中把发送键原地换成 Stop**，不是并排多一个按钮 ——
  与"设定图格子生成中整格换成停止入口"同一个手法；
- **整块是一张悬浮卡片**：白底 + 一圈极淡的边 + 一层弥散影，
  输入区那条通栏分隔线因此去掉 —— 卡片的边界由它自己的投影给出，
  再加一条横线就是两套边界打架。卡片底下要多留一档内边距，投影才有地方落下去；
  `.chat-main` 也随之不能 `overflow: hidden`（裁切会把投影切掉）；
- 边与聚焦态都用 `box-shadow` 补，不切 `border` —— `border` 会让里面整行文字挪一下；
- **圆角用 `--r`（16px），不用 `--r-lg`（24px）**：后者是给 Studio 那个"有厚度的
  提示词编辑器"定的；这张卡片铺满整块面板又只有一行高，24px 会让两端各看成一个半圆，
  整块变成一根横贯全宽的胶囊。16px 与气泡同档，两者才像同一套东西；
- **内边距横向左右同为 12px、纵向 6px**（卡片总高 52px，其中发送键占 40px）。
  左右不等宽时，一条铺满全宽的卡片会把那点偏差放大成"歪"；
  纵向再厚就只是把卡片撑高 —— 卡里只有一行字；
- **提示语左对齐**。试过空着时居中（`:placeholder-shown` + 补齐发送键那 48px
  把居中点拉回卡片中线），装出来像一条待命的搜索条，但和"这是一个聊天输入框"对不上，
  已经去掉；
- **三枚图标全在右端**（2026-10-06 用户要求"输入框 icon 都移到右边"）：
  字从左边起，附图 / 表情 / 发送收在右边。它们都是"对这一句话做的事"，
  而不是"开始说一句话"的入口 —— 分置两端时视线要来回跳。
  DOM 次序跟着视觉次序改（`textarea → 附图 → 表情 → 发送`），不用 `order` 硬掰：
  Tab 的顺序因此也是"先打字、再挑键"，读屏读到的与看到的同一条。
  **最右那一枚仍永远留给"把这句话发出去"**。
  代价一则：表情面板的锚点跟着挪到右端，展开方向由 `left: 0` 改成 `right: 0`
  （照旧朝上开）—— 否则它会从输入区右缘伸出去，窄屏上直接出屏；
- 单行高度刚好 40px（`line-height: 22` + 上下 `9px`），与发送键一样高，两者中线才齐；
- **超长拦在本地**（`CHAT_MAX_CHARS`）：挡住发送、原文留着、当场把上限写出来。
  服务端也会拒绝（它必须拒绝，入口是公开的），但那时用户手里那条已经被清空了，
  只能把一整段重打一遍。提示顶掉的是卡片那一格，所以高度与卡片一致（52px），
  切换时页面不跳；
- **没有配置对话模型时整块不可用**，给一行去 Settings 的引导
  —— 措辞与角色页 `textConfig` 缺失时同一套。那枚按钮直接开一张
  "用途 = 对话"的表单（见 §3.4.10），不是先落到一串别的用途里挑。
  **配了但没填模型名**是另一种情况（同样是开不了口），措辞与落点都不一样 —— 见 §3.4.11。

#### 3.4.6 空态与错误

| 情况 | 表现 |
| --- | --- |
| 一个角色都没有 | 居中一句 + 去 Characters 的按钮 |
| 没选中角色 | 同上（左栏空着，右栏不该是死的） |
| 选中了但没聊过 | 大头像 + 名字 + **一句本地按 persona 拼的开场白**。不调接口 —— 一进页面就花钱不对 |
| 上游报错 / 断流 | **保留已收到的文本**（见 §3.3）+ 全局 `notice` 一句 |
| 用户点了 Stop | 保留 + 不报错，一句 `Stopped.` 走 `notice`（与设定图的 `Generation stopped.` 同调） |

**所有报错走全局 `notice`**（[App.vue#L121](../src/App.vue#L121)），
不在页面里另开一块错误区 —— 角色页已经是这么做的。

#### 3.4.7 窄屏（≤ 860px）

- 左栏隐藏，**角色头变成可点按钮**，点开一个居中的角色选择浮层；
- 浮层按模态来管焦点（与角色向导、设定图查看器同一套写法）：
  `tabindex="-1"` 让浮层本身能接焦点、打开时焦点收到它身上（先让读屏念出"这是什么"）、
  `trapTab` 把 Tab 圈在里面、关闭时焦点**归还给打开它的那枚按钮**。
  这几样缺一样，键盘与读屏用户就会被留在背后的页面上 ——
  只在打开时"改了个状态"是不够的；
- 从浮层里挑完人：关掉浮层并把焦点交给输入框 —— 刚选完跟谁说话，下一步就是开口；
- 消息流内边距收到 `--sp-3`，气泡 `max-width` 提到 88%（窄屏下 76% 太窄）；
  这一档同时把动作药丸从"气泡外侧"改挂到"气泡下面"（外侧只剩 12%，见 §3.4.4）；
- 输入区贴底，`padding-bottom` 带上 `env(safe-area-inset-bottom)`（iPhone 底部横条）。

#### 3.4.8 导航要补一个槽位

`NavSegment.vue` 是**按 `NAV_ITEMS` 逐项配具名槽**的
（[NavSegment.vue#L41-L61](../src/components/NavSegment.vue#L41-L61) 那一排 `<template #home>` / `#chars` / …），
所以 `nav.ts` 里加一条只是第一步，还得在 `NavSegment.vue` 里补：

```vue
<template #chat>
  <PhChatCircleDots class="seg-ico" aria-hidden="true" />
</template>
```

条目从 6 个变 7 个，**轨道宽度要重新量一遍**（`RubberSegment` 的滑块按条目数分格），
窄屏下尤其要确认不挤。

#### 3.4.9 多角色状态隔离

流式状态按 `charId` 存（`Record<charId, ...>`）
—— 和 `charViewBusy` 那次踩过的坑一模一样：不按角色分开，A 在说话时切到 B，
B 的界面会跟着显示"正在输入"。`chatBusy` 与 `chatControllers` 都要按角色分键。

#### 3.4.10 头部的模型药丸（对话模型从此独立）

**问题**：这一页原来答不上"现在是谁在说话"。角色对话用的那个模型，是设置页里
"Prompt enhancing" 那一类的配置 —— 而它的芯片挂在**生图那页的参数面板**上
（`Image model` / `Text model` / `Vision model` 三组并排）。于是想换个聊起来更像个人的模型，
得跑到画图那一侧去动；而两件事的诉求本来不同：改写的模型按"哪家出的图更好看"挑，
对话的模型按"聊起来像不像个人"挑。

**处理**：`ApiConfig.kind` 多一类 `chat`（见 [API配置管理设计.md](API配置管理设计.md) §5），
角色对话与记忆压缩都走它；对话页头部多一枚药丸，显示**当前用的是哪个模型**，
点一下直达设置页。

| 决定 | 为什么 |
| --- | --- |
| 药丸放在头部的 `head-acts` 里（模型 · 记忆 · ⋮） | 它回答的与旁边那枚记忆药丸是同一类问题："它现在是什么状态"。放进输入区会每一轮都在眼前，放进 ⋮ 菜单又要多点一次才看得见 |
| **`from enhancing` 这句必须写出来** | 没专配过时对话借用改写的模型（存量用户零感知，见 §5.4）。不写的话用户会以为它已经独立配过了 —— 而"它到底走的哪个模型"正是这次要解决的问题本身 |
| 点它：**有专配的 → 回列表；没有 → 直接开一张"用途 = 对话"的表单** | 药丸上写着 `from enhancing` 时，用户点它的动机就是"配一条自己的"；落到一串别的用途里去挑，等于把那句话又说了一遍却没给下一步 |
| 没有专配时**不显示成错误态** | 借用是正常工作状态，不是配置缺失。红色的"未配置"会让人以为聊天坏了 |
| 模型名 `max-width` 18ch（窄屏 10ch）后省略 | 中转上自己写的别名可以很长；不封顶会一路把角色名字挤没，而这一页首先要认得出在跟谁说话 |
| 药丸与记忆药丸**共用一套皮**（`.head-chip`） | 同一排里两枚同形状的控件，只该在内容上不同 |
| 对话模型**不进生图那页的参数面板** | 进了就等于把"和生图独立开"这件事又还回去一半 |

配套：`ChatPage` 的 props 从 `textConfig` 换成 `chatConfig` + `chatBorrowed`；
重试 / Regenerate 的门控也一并改看它（原来那句 "Add a text model…" 改成 "Add a chat model…"）。

#### 3.4.11 "有配置" ≠ "能开口"（`chatReady`）

拆分上线后真实撞到的一处：用户把一条已有配置的用途改成 `Role chat` 存下，
模型名却在切换用途时被清空了（那半句已改，见 [API配置管理设计.md](API配置管理设计.md) §6.6）——
于是配置在列表里顶着「Current」、对话页药丸也写着它的名字，**一开口却收到服务端那句
"Set a text model in API settings first"**。用户的原话是"明明已经设置了模型还是报错"：
那句话既没说是哪条配置，也和他眼前的界面对不上。

所以这一页把"配全了"当成能不能开口的前置条件：

| 判据 | 落点 |
| --- | --- |
| `chatReady = chatConfig?.baseUrl && chatConfig?.model` | 输入区、`canRegenerate` / `canRetry`、`send()` 都看它（不再只看"配置在不在"） |
| 开不了口时**分两种说** | 一条都没有 → "Add a chat model…"；**有但缺模型名** → "`<名字>` has no model name yet — add one in API settings to start talking." |
| 那枚按钮的落点也不同 | 前者开一张"用途 = 对话"的空表单；后者**直接开这一条**的编辑表单（`editConfig`）—— 问题就在那一格里，把人丢回列表等于让他再找一遍 |
| `App.runChat` / `regenerateChat` 各有一道同样的闸 | 界面之外的第二道：`regenerateChat` 那条尤其要紧 —— 它会先删掉旧回复，发不出去时那条就补不回来了 |
| 顺带：附了图的那一轮改看**识图**配置 | 它同样可能缺模型名，而那一处更容易漏（用户刚建好识图配置、还没填模型就先丢一张图进来） |
| 后台的记忆压缩直接跳过 | 它是静默重试的：不拦的话每轮白花一次注定失败的调用 |

### 3.5 上下文怎么拼

每次发请求只带**最近 `CHAT_WINDOW = 20` 条**消息。更早的不发，也不做摘要（那是二期）。

- 窗口取的是**消息条数**而不是字数：条数可预期，而字数要靠额外估算；
- 20 条大约十轮来回，够撑起一段有来有回的对话；
- 被截掉的旧消息**不从库里删** —— 它们还在，只是这轮不带。界面上滚上去照样能看到；
- 头几轮的表现不会因为截断而变差（本来就没到 20 条）；
  真正会"忘事"是几十轮之后，而那正是二期摘要要解决的事。

## 5. 风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **成本性质变了** | 出图是"点一次花一次"，聊天是持续消耗 token，且按轮次累积 | 一期不做预算控制。`max_tokens: 1500` 是唯一的硬闸（见 §2.4） |
| **限流更容易撞上** | `RATE_MAX = 30/min` 按 IP（[server/index.js#L115-L117](../server/index.js#L115-L117)） | 一轮 = 1 次请求，正常聊天到不了。把 `/api/chat` 同样挂上 `rateLimit`，不自开小灶 |
| **Serverless 上的流式** | Vercel 有函数执行时长上限，长回复可能被平台掐断 | 一期接受：短回复（≤1500 token）通常远在上限内。断掉的表现是"说到一半停住"，走 §3.3 的第三条 |
| **角色扮演被上游拒答** | 虚构角色 + 安全策略，敏感角色可能被拦 | 一期如实把上游那句话透出来（复用其他端点那套 `detail` 提取），不自己编解释 |
| **上下文膨胀** | 20 条窗口已经封顶，但单条可能很长 | 入口校验里限 8000 字符/条；真要压，二期接摘要 |
| **`max_tokens` 字段名** | 个别中转只认 `max_completion_tokens` | 一期按最普遍的那个名字发。真撞上，上游会明确报"unknown parameter"，照 §5 的表加分支即可（与厂商能力表同一条路子） |

## 7. 长期记忆与摘要压缩（二期第 1 项）

### 7.1 它解决什么

§3.5 的滑动窗口只带最近 20 条，**更早的是真的忘了** —— 库里还在，但不再发送。
这一节补上后半句：让滑出窗口的那些消息压成一段简报，随 system 一起发。

### 7.2 数据（[types.ts](../src/types.ts#L255-L276)）

```ts
export interface ChatSummary {
  charId: string
  text: string        // 简报正文
  upToId: string      // 覆盖到最后哪一条
  upToAt: number      // 那条的时间戳
  covered: number     // 已经被覆盖的条数
  updatedAt: number   // 最后一次压缩的时间
}
```

**为什么不是只存一段文本**：`upToAt` 回答"从哪一条之后还没进摘要"，下一批从这儿往后接；
`covered` 是"已经进去多少条"，配上总条数才知道该不该再压一次。
有它就不必为了判断这件事把消息读一遍 —— 三者缺一个，都会退化成"每次都要全量读"。

存法：新表 `chat_summaries`（v7），`keyPath` 直接是 `charId`。
一个角色一条，是"这一整段对话的当前状态"，不是按条存的东西，**所以不需要索引**。

### 7.3 什么时候压

```
want = 总条数 − CHAT_WINDOW − covered
want ≥ CHAT_SUMMARIZE_AFTER(20) 才压
```

- **减掉窗口**是因为最近那些条本来就还在上下文里，压了也是白压；
- 压完 `covered` 追到 `总条数 − 20`，要再攒 20 条才触发下一次 ——
  **也就是大约每 10 轮多花一次调用**，而这一批刚好是一整轮新的对话；
- 总条数走 `countChatMessages`，**只看索引、不读记录**。

### 7.4 压哪一段（这一步最容易做错）

`getChatMessagesToSummarize(charId, afterAt, limit)` —— **必须由旧往新收**（游标 `'next'`，
左开区间 `[charId, afterAt]`）。

反过来（从最新的往回收）会有一个只在几百条之后才显形的 bug：
第一批把最近那些还没摘要的消息全吃掉，而更早的永远轮不到 ——
**对话最开头那一段会被跳过一辈子**。

> 用 500 轮 / 1000 条消息模拟过这条循环：应覆盖 980 条（总数 − 窗口），**漏 0 条**。

### 7.5 提示词（[ENHANCE_PROMPTS.summary](../server/index.js#L224-L241)）

走 `/api/enhance` 的 `mode: 'summary'`，与改写、拆角色共用一套代理与鉴权。温度 **0.3** ——
摘要要的是忠实，温度低了顶多啰嗦，而**编出来的记忆比没有记忆更糟**。

**用的是对话那条配置（`chatConfig`），不是改写那条。** 记忆是"这段对话的延续"，
它该和回话用同一个脑子：换个模型压出来的摘要，措辞与取舍都跟正文不是一路。
（两条本来就是同一种模型，所以这一步在参数上没有任何新要求 —— 只是归属问题。
没专配对话模型时 `chatConfig` 借的就是改写那条，行为与拆开之前一模一样。）

两条反复强调的规则：

- **"合并重写，不要追加"**：一旦变成追加，简报会随对话线性膨胀，最后比原文还长，
  而且最旧的信息永远压在底下；
- **"保留名字、地点、承诺、欠下的账"**：这些正是几轮之后还会被追着要的东西。

### 7.6 怎么注入（[chatSystemPrompt](../server/index.js#L278-L320)）

压在 `Who you are` 之后、`Rules` 之前 —— 它讲的是"发生过什么"，与"你是什么人"属同一层，
而规则要留在最后当收束。

记忆**过一遍 `chatOneLine` 把换行收掉**：它是模型生成的文本，
原样带着换行塞回 system，等于给上一轮的输出一个伪造提示词结构的机会。

### 7.7 记忆必须跟着对话一起走

`deleteChatOf` 现在跨两张表一个事务：清消息的同时清记忆。
**"消息没了而记忆还在"比失忆更糟** —— 下一句开口就会提起一段用户刚刚清掉的旧事。

所以 `clearChat` 也要连记忆一起清，并在撤销时一并恢复（连同库里那份）。

### 7.8 在途压缩的代次（`chatSeq`）

压缩是异步的。用户完全可能在它跑着的时候点"清空"或删角色 ——
回来时若不检查，这次后台整理会把刚清掉的记忆又写回去。

做法与角色起稿的 `draftSeq` 完全一样：进压之前记下代次，写回之前比一次，
对不上就整份丢弃。`clearChat` 与 `deleteChar` 的 `purge` 各调一次 `bumpChatSeq`。

> 注意 `purge` 要等撤销窗口结束才跑，所以**不能在压缩中途用"角色还在不在列表里"来判断** ——
> 撤销窗口里角色本来就不在列表里，那样会把一份完全有效的记忆丢掉。

### 7.9 界面：可见、可改，但默认折起来

消息流最上面一块 `MEMORY · updated 2m ago`，点开展示正文。
摆在最上面是因为它代表"比这些消息更早的那些"，顺序上就该在最早的那条之前。

- **虚线框**是有意的：它不是对话的一部分，而是一段"关于这段对话"的派生文本，
  实线框会让人以为它也是一条消息；
- **必须让用户看得见**：记忆是有损的，用户得能亲眼看到损掉了什么，才谈得上信它；
- **还得改得动**。压错一处就得能就地改 —— 否则用户唯一的办法是清空整段对话，
  而那把整段历史也一起扔了，代价完全不成比例。**改得动，这功能才谈得上可信**。

编辑态就地换成一只 `textarea`（不另起浮层，改一段文字不该有弹窗+确认的仪式感）：

| 决定 | 为什么 |
| --- | --- |
| 只换正文，`upToAt` / `covered` 一个字不动 | 它们说的是"哪些消息已经进去过了"。改字不改变这件事，动了会让下一轮把老消息重新压一遍 |
| `updatedAt` 跟着刷 | 界面拿它显示"多久没动过了"。用户刚写的那版不该还挂着"3 天前" |
| 上限卡在 `CHAT_MAX_CHARS`（与消息同档） | 服务端对记忆收的正是这个数，改到多少会被截断是可预期的 |
| 不许存空 | 编辑框里存空等于没说清"想干什么"。想清空得走下面那条 `Forget`（忘掉记忆、留下对话），它比"存一个空串"多做了一件要紧的事 |
| 编辑中不让折叠、换角色自动退出编辑 | 前者是别把手上正在写的东西藏了；后者是那块记忆已经属于另一个人了 |
| 在途压缩遇到"用户刚改过"就放弃本轮 | 用户写的那版比同炉重压的更算数。`covered` 没动，消息一条不少，下一轮连着他的新版本一起再压 |

**忘（`Forget memory`）** —— 与原设想里"只删摘要、消息不动"一致，
但**难点不在删，在游标**：

压缩是从 `upToAt` 之后接着取的。只把正文清空、游标不动，下一轮就会把刚刚忘掉的那段
**原样重新压回来** —— 这个功能就等于没做。所以 `Forget` 必须连游标一起推平：

| 字段 | 忘掉时怎么处理 |
| --- | --- |
| `text` | 置空。界面据此不再显示记忆块（`hasMemory` 看的是**正文非空**，不是记录在不在） |
| `upToAt` / `upToId` | 推到**最后一条消息**。忘掉的那一段从此不再进记忆 |
| `covered` | 置为当前总条数。宁可算多一点：多算只是下一轮少压一次，算少会把忘掉的那段重新捞回来 |
| 记录本身 | **留着**。那个"从哪之后不再记得"的游标得有地方待 |
| 消息 | **一条都不删**。"角色不再记得"和"这事发生过"是两回事 |

效果：忘掉之后，**在这之后**说的新话会照常重新积累成记忆 ——
等于从遗忘那一刻起重新认识。阈值与一段全新对话完全相同（再聊 20 轮）。

入口有两处，与其他记忆操作一致：展开的记忆块里（`Edit` 旁边）、以及头部的 `⋯` 菜单里。
菜单里的三项正好构成"忘一点 / 忘干净"的梯度：`Edit memory` → `Forget memory` → `Clear conversation`。
`Forget` 平时与别的次要动作长得一模一样，**只有悬停才染成危险色** —— 它不该在静止时和"改一改"争同等分量。

与"清空对话"的另一处不同：这一步**立刻落盘**，不等撤销窗口结束。
忘掉就该马上生效，而且只有一条记录，写它不心疼；撤销再把老的那版写回去。

### 7.10 失败就退出，不打扰

压缩全程静默：失败时 `covered` 不推进，下一轮再试，**不弹提示**。
它是一次后台整理，没有"用户在等"这回事，弹一条错误只会让人莫名其妙。

### 7.11 风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **摘要是有损的** | 压过头会丢关键细节 | 原文一条都不删，随时能翻回去对照；`Memory` 块可展开、可改（§7.9） |
| **成本** | 每 10 轮多一次调用，且要重发整段旧记忆 | 阈值 20 已经把频率压到最低；单次上限 300 条防止一次压太多 |
| **老用户第一次打开** | 几千条历史要分好几轮才追平 | 一轮吃 300 条，几轮后收敛；期间记忆逐轮变好，不会出错 |
| **压缩时被清空 / 删角色** | 后台任务把刚清掉的记忆写回来 | `chatSeq` 代次作废（§7.8） |
| **压缩与手工编辑撞车** | 重回炉的结果盖掉用户刚写的 | 落笔前比对基准正文，不一致就放弃本轮（§7.9） |
| **手改过的记忆会被下一轮压缩重写** | 压缩是"旧记忆 + 新消息 → 重写一份"，所以每次都会把用户改过的措辞再润色一遍 | **仍未解决**。要"钉住"得加一层标记：改过之后不再把旧记忆喂回模型，只让新消息往后接 —— 但那等于那段记忆停止进化，是个取舍 |
| **忘掉的那一段就此失忆** | 记忆是模型生成的，忘掉之后拿不回来 | 撤销窗口 4.5 秒；窗口一过就真的没了。原文还在，但那是"翻记录"，不是"角色记得" |

## 8. 其余二期方向

> 已落地的两项抽成了单独的小节：**长期记忆**（§7）、**AI 起稿生成人格**（§9）。

| # | 方向 | 要点 |
| --- | --- | --- |
| 1 | **多段会话** | `ChatMessage` / `ChatSummary` 加 `sessionId`；索引加一条 `(charId, sessionId, createdAt)`；左栏从"角色"变两级 —— **暂缓**，设计已定，见 §8.2 |
| 2 | **情绪与表情** | 让模型在末尾带一个情绪标签，解析后剥掉、界面据此换头像表情。改动小、观感提升大 —— **已落地**，见 §8.1 |
| 3 | **主动消息** | 需要定时触发 + 频次上限 + 明确开关。**做不好会变成骚扰**，用户会直接关掉整个功能 |
| 4 | **多模态** | 发图给角色看：识图链路现成，主要是消息结构要支持附件；**角色回图**：出图链路也现成，但成本与失败率都高，建议单独立项 |
| 5 | **语音** | 朗读已落地（Web Speech，按角色固定音色，见 §8.4）；**说给它听**（SpeechRecognition）还没做 —— 支持面窄、识别质量不稳，先放着。真正定制嗓音要第三方 TTS，见 §8.5 |
| 6 | **角色卡带上对话** | 导出的 zip 现在会把消息与记忆一起带走 —— **已落地**，见 §8.3 |
| 7 | **自定义音色** | 让角色有一把真正属于它的嗓子：**描述**或**音频样本**两条来源。要后端（`/api/tts` + `/api/voice/clone`）。设计已定 —— 见 §8.5 |

### 8.1 情绪与表情（已落地）

让角色每句话带一个情绪，界面据此在名字旁浮出一枚药丸。
**做法是"末尾贴标签、服务端剪掉"**，前端拿不到标签，只拿到情绪词：

1. **提示词**（[CHAT_RULES](../server/index.js)）：要求模型在最后一行写 `[mood:word]`，
   一个小写英文词，描述**发这条消息时**的感受（不是所描述事件的感受）。
2. **服务端剪**（`splitMood`）：
   - 完整标签 → `CHAT_MOOD_RE` 切掉，取出情绪词；
   - **半截标签 → `CHAT_MOOD_PARTIAL_RE` 只擦不取**。断流时 `[mood:gu` 这种残片若不擦，
     会当成正文留在气泡里。
3. **`CHAT_TAIL = 24`：扣着尾巴发**。流出时永远压住最后 24 个字符不推给前端，
   保证一个标签（最长 `[mood:xx-xx]`）不会半路露头。结束时 `flushTail()` 一次放出。
   **`tail` / `flushTail` 必须声明在 `try` 之外** —— 按 Stop 或上游断流时也要把尾巴放出来，
   否则最后 24 个字符会平白消失。
4. **前端**：`ChatStreamResult.mood` → `ChatMessage.mood` → 只取**最后一条助手消息**的情绪，
   渲染在头部名字右边（`:key="mood"` 让同一个词重复出现时也能重播一次入场动画）。

| 决定 | 为什么 |
| --- | --- |
| 取最后一条助手消息的情绪，不做情绪历史 | 它回答的是"它现在是什么神态"。历史情绪堆在头部没有意义 |
| 用户消息不参与 | 情绪是"角色此刻的状态"。用户的情绪若要显示，那是另一件事 |
| 失败时无标签 → `mood` 为空 → 药丸不渲染 | 缺一个标签不该在界面上留一个空壳 |
| 一个词，不做分类枚举 | 枚举要维护一张词表，模型一旦出表外词就出错。自由词 + 渲染兜底更省事 |

### 8.2 多段会话（暂缓，设计已定）

一个角色下开多段互不相干的对话。**暂缓**（先把记忆可编辑做扎实），
但想清楚的几条先记在这里，免得下次从零再推一遍。

**不建会话表。** §1.3 那条"派生得出来的不再存一份"在这里同样成立：
会话是不是存在，完全由消息决定 —— 一个会话之所以在列表里，正是因为里面有话。

| 决定 | 为什么 |
| --- | --- |
| `sessionId` 走消息与摘要两张表，不另立会话表 | 标题（头一句用户消息）、预览（最后一句）、时间（最后一条的时间）全都派生得出来，多一张表就多一处要与消息保持同步的状态 |
| **默认会话的 id 就是角色 id** | 升级时不必凭空造一批新 id：老消息补上 `sessionId = charId` 就原样落进 `(charId, charId)`；老记忆（keyPath 是 charId）也天然落在正确的主键上 |
| 摘要表主键从 `charId` 换成 `sessionId` | 记忆必须跟着会话走。同一个角色两段对话是两段历史，把 A 段的事带进 B 段，等于让角色在另一条时间线里提起这边还没发生过的旧事 |
| **保留** `charIdCreated` 索引，另加 `(charId, sessionId, createdAt)` | 左栏角色那一行问的是**跨会话**的最近一句，和"某段会话里的最近一句"是两个问题。硬用一条索引要做前缀区间，读起来绕 |
| 会话由消息定义 ⇒ 空会话不落盘 | "New chat" 先切到一个空 id，等第一句发出去才在列表里出现。点开没说话就走，它自己消失，不会留一堆空壳 |
| 记忆表主键改不了 ⇒ 删表重建 | 升级事务里先把老记录整表读进内存，再 `deleteObjectStore` + 重建 + 回写。同一个事务，中途失败整体回滚 |

**遗留：库版本已经被这个改动推到了 8。** 撤回时**版本号不能跟着往回改** ——
IndexedDB 的版本只能升不能降，代码里请求 7 而库里已经是 8 时 `open` 直接失败，
而这个失败被每一处读写 `catch` 成"读不出来"，界面上就是"图片和历史全没了"
（数据一条没少）。所以 `DB_VERSION` 现在是 **9**（只为了越过 8），
升级分支里顺手摘掉那次留下的 `charIdSessionCreated` 索引。

`chat_summaries` 的表形状那次被换成了 `sessionId` 主键，**这次不去改它** ——
改回去要整表删掉重建，在升级事务里做这件事一旦失败会让库彻底打不开。
改为在读写两侧兼容两种形状：`get(charId)` 恰好落在 `sessionId === charId` 那条上，
写的时候顺手补一个 `sessionId` 字段（见 `getChatSummary` / `putChatSummary`）。

### 8.3 角色卡带上对话（已落地）

导出的 zip 从"设定 + 设定图"扩成"设定 + 设定图 + 对话"。
分享一个**养熟了的**角色时，那段关系本身才是最难重来的东西。

包结构没变，只多一个文件（[api.ts](../src/api.ts) 的 `exportCharacter` / `readCharacterZip`）：

```
character.json     ← manifest，多一项 chat: "chat.json"
chat.json          ← { messages: [...], memory: "…" }
ref.jpg / source.jpg / front.jpg / …
```

| 决定 | 为什么 |
| --- | --- |
| 对话**单独一个文件**，不内嵌进 manifest | 几百条消息塞进 `character.json`，那份"给人看的清单"就变成一坨机器数据了 |
| 消息只带最近 `CHAT_EXPORT_MSGS`（300）条 | 话可以无限长，全带出去包里就是几 MB 纯文本。而分享时真正要传的是**记忆**，消息只是那份记忆的来处 |
| 包里**不带记忆的游标**（`upToAt` / `covered`） | 那些 id 与时间戳在对方那里不成立。带了只会让下一轮压缩要么把导入的这段整段重压一遍，要么一条都不压 |
| 导入时**按收到的消息**重新推平游标 | 记忆当作"已经覆盖了这些消息"。于是它记得从前，而之后新聊的照常累积 —— 与本地导出方看到的行为一致 |
| 消息 id 一律换新，`charId` 用新建那个角色 | 与角色 id 同一条理由：不沿用外部文件里的标识 |
| 逐条过筛（`coerceImportedChat`） | 包是外部文件。认不出的 role、空正文、坏时间戳都挡掉；时间戳坏了就按次序补一个 —— 整段对话的**相对次序**比绝对时刻要紧 |
| 对话读坏了**只丢对话** | 角色本身照常导入，与"某一张图丢了"同一处理 |
| 没聊过 / 记忆为空的角色**不写 chat.json** | 包里多一份空壳，会让"这个包带了对话"这句话变得不可信 |
| **`duplicateChar` 不带对话** | 复制是造一个"同一副皮囊的另一个人"，不是把这段关系也复制一份。分界线在"分享 vs 分身" |

导出回执会把两样都说清：`Exported "X" with 6 images and 128 messages.` ——
一个只有设定没图的角色，和一个把关系一起带走的角色，导出来的东西差别很大。

### 8.4 语音朗读（已落地）

角色说的话由浏览器自己念出来（[lib/speech.ts](../src/lib/speech.ts)，
用自带的 `SpeechSynthesis`）—— 不引第三方，所以不需要 key、不联网、不花钱。

**只有"手动念某一条"，没有自动朗读。** 一开始做过一个自动朗读开关（默认关、状态存盘、
放头部），后来去掉了：自动念意味着**每次回复都出声**，而聊天是随手就会发生的动作 ——
它会在你没想到的时候开口。想听的人自己点那枚喇叭，这一个动作就够了。

**"按角色配音色"在纯前端能做到的是**：从系统音色表里给这个角色**稳定地**挑一个，
再把语速与音高错开一点点。用角色 id 做哈希，所以同一个角色每次听起来都是同一个人，
不同角色之间也分得出来。语速/音高只取 0.90~1.07 —— 再放开就开始像卡通配音或机械音了。
真正定制一把嗓子要第三方 TTS，那是另一件事。

| 决定 | 为什么 |
| --- | --- |
| 一次只说一句，新的压掉旧的 | `speak()` 开头先 `cancel()`。不掐的话连点两条消息就是两把嗓子一起说话 |
| 单条朗读用**同一枚按钮**切换念/停 | 为一件只有两种状态的事再养一枚"停止"按钮不划算 |
| 那枚按钮**绝对定位**在气泡外侧下角 | 放进流里（哪怕 `opacity: 0` 藏起来）会实打实把每个气泡压窄一排的宽度，而不悬停时谁也看不见它，那份窄就成了一份没来由的窄 |
| 挂不下时（窄屏 / 沉浸页）改挂气泡下面，高度由气泡让出 | 外侧那点地方在窄屏只剩 12%，硬挂就是被裁掉（见 §3.4.4）。横向不够就往下走 —— 占高度不占宽度，是这两种代价里更小的一份 |
| 悬停才浮出；`(hover: none)` 设备常驻但压暗 | 每条消息都挂着一枚喇叭会把对话流弄得很吵；触屏没有 hover，只能常驻 |
| 生成中的那条不给朗读键 | 半句话念出来更难听 |
| 换角色 / 离开页面 / 清空对话 / 重生成都 `stopSpeaking()` | 语音不属于"后台也该继续"的那类东西；念一条马上就不存在的消息没有道理 |
| **不支持就不给入口** | `speechSupported()` 先问一次。一个点了没反应的按钮比没有更糟 |
| 按**角色设的语言**挑（`persona.language`，见 §9.7），没设才退回按文本二分（有汉字/假名 → zh，否则 en） | 加语言那一栏之前，提示词里没规定角色用什么语言回话，它跟着用户走。同一语言的音色一个都没有时退回全部 —— 口音不对也总比一声不吭强 |
| 音色表异步到达（`voiceschanged`） | 第一次 `getVoices()` 常常返回空数组。拿不到就只报 `lang`，让浏览器自己挑 |
| 进对话页先 `warmUpSpeech()` 预热一次 | 不预热的话，**第一次朗读用的是浏览器默认音色**，和它之后的声音不一样 —— 同一个角色第一句和后面几句嗓门不同，很难解释 |

**还没做**：**说给它听**（`SpeechRecognition`）。支持面窄（Firefox 没有）、
识别质量不稳，做出来会是一个"有时出现有时不出现"的按钮，先放着。

### 8.5 自定义音色（设计已定，未实现）

§8.4 那个"从系统音色里按角色哈希挑一个"只是权宜：能听，但每个角色都不是真的在说话。
这一节是**让角色有一把真正属于它的嗓子**。设计已定，还没动手。

> 补一句入口的事（2026-10-03）：向导第 2 步就是配嗓音那一屏，但它原来**只在新建流程里到得了**
> —— 第 2 步的解锁条件是 `wizardId`，而详情页那枚 `Edit` 走的是 `editingId`（空）。
> 所以一个角色的嗓子建完就再也改不了，详情页那块 Voice 只给"听"。
> 现在那块多了一枚 **Change voice**（`startVoiceEdit`，见
> [角色创建流程设计.md](角色创建流程设计.md) 的步骤解锁那一节），直接落在第 2 步、存完回详情。
> §8.5 这套三档来源本来就住在那一步里，所以它跟着一起可达了。

#### 一句话本质

现在 `speak()` 是**同步**的：点下去立刻出声、免费、离线。
接上自定义音色后它变成 **请求 → 等首字节 → 拿到音频字节 → 播放**，而且**每次都要钱**。
下面每一条都是从这句话推出来的 —— 不是从"加一个音色选择器"推出来的。

#### 三种来源，一个出口

| 来源 | 用户做什么 | 上游拿到什么 | 成本 |
| --- | --- | --- | --- |
| `preset` | 从厂商自带 voice 里选一款 | 一个 voice 名（如 `alloy`） | 每句 |
| `describe` | **写一段话**描述这个人听起来什么样 | 默认 voice + `instructions` | 每句 |
| `clone` | **传一段音频样本** | 上游建号时返回的 voice id | **建号一次** + 每句 |

三条路的**差别只在"voice 从哪来"**。一旦拿到那个标识，合成请求是同一个形状：

```
{ text, vendorVoice, describe?, speed? }
```

所以服务端只需要**一个合成端点**，克隆多一个"建号"端点。这是这一节最要紧的结构判断 ——
若把 `describe` 和 `clone` 当成两套功能各写一条链路，缓存、选路、播放、中断全都要写两遍。

#### 数据模型

音色是**角色的属性**（与 `persona` 同级），不是全局设置 —— "这个人怎么说话"本来就属于角色。

```ts
export interface CharacterVoice {
  /* 走哪条路。缺省 = browser，于是老角色、没配过的人照旧 */
  engine: 'browser' | 'tts'
  /* browser 档：系统音色名（getVoices() 的 name）+ 语速音高 */
  voiceName?: string
  rate?: number
  pitch?: number
  /* tts 档：三种来源之一 */
  source?: 'preset' | 'describe' | 'clone'
  configId?: string
  /* preset 的枚举名，或 clone 拿到的 voice id —— 都是"上游那一把嗓子" */
  vendorVoice?: string
  /* describe 档：那段描述。认 instructions 的 TTS 直接吃它 */
  describe?: string
  /* clone 档：本地样本的引用。建号之后合成不再用它，
     留它是为了"重新克隆 / 删掉样本 / 界面上回显是哪一段" */
  sampleId?: string
}
```

挂在 `Character` 上（`voice?: CharacterVoice`），纯 JSON、存 localStorage、跟着导出包走。

**样本是唯一的二进制**，存 IndexedDB 新表 `voice_samples`
（key = `sampleId`，value = `{ blob, name, bytes, createdAt }`）——
与 `charViews` 同一条路：Blob 不进 localStorage。

#### 后端：两个端点

```
POST /api/voice/clone
  { sample: dataURL, name, provider, baseUrl, apiKey } → { vendorVoice }

POST /api/tts
  { text, vendorVoice, describe?, speed?, provider, ttsModel, baseUrl, apiKey }
  → 200 audio/mpeg（chunked，边收边 res.write）
```

**上游其实是三条端点，按来源分工**（火山）：

| 来源 | 端点 | 请求形状 |
| --- | --- | --- |
| `preset` / `clone` | `/tts/unidirectional` | `{ user, req_params: { text, speaker, audio_params } }`，音频在**逐行 JSON 的 `data`** 里 |
| `describe` | `/tts/create` | `{ model: 'seed-audio-1.0', text_prompt, audio_config }`，音频在**整个响应体的 `audio`** 里 |
| `clone`（建号） | `/tts/voice_clone` | `{ speaker_id: 'custom_speaker_id', custom_speaker_id, audio }` |

两条合流在一处：`pipeTtsAudio` 逐行取帧，音频字段名 `data` 优先、`audio` 兜底。
**末尾那一段必须补喂一遍** —— 流式那条每行都有换行，而 `/tts/create` 整个响应就是一个 JSON、末尾没有换行，漏掉它就是整段音频一个字节都发不出去。

> **踩过的坑：`describe` 不能用 `/tts/voice_design`。**
> 音色设计那条要求 `speaker_id` 必填，而且备注写着"控制台购买"——
> 也就是**得先有一个买过的底子音色**才能用。
> 而 `/tts/create` 的参数说明里，"纯文本生成"就是"**不传参考资源**，
> 按 `text_prompt` 中的提示词生成音频"，`speaker` 只是 `references` 里的一个可选项。
> 描述档的卖点本来就是"不用先准备任何东西"，绕道音色设计等于把这个卖点丢了。
>
> 代价是这条端点是**生成任意音频**的（环境音、音效、多人对话都做），
> 所以提示词里必须把"只要这一个人说话"说死，见 `ttsDesignPrompt`。
> 另外它的**默认输出是 wav**，请求里必须显式要 mp3。

骨架直接复用现有四条：`rateLimit`、`assertSafeTarget`(SSRF)、`dispatchAttempts`、上游非 2xx 且未写头时回 JSON 错误。

| 决定 | 为什么 |
| --- | --- |
| 样本走 **dataURL**，不走 multipart | 现有四条端点的 body 都是 JSON，而 `dispatchAttempts`（代理那一跳失败再直连试一次）依赖 **body 字符串可复用** —— multipart 发过一次就消耗掉了。样本一般几百 KB，base64 后约 1.3 倍，可以接受 |
| `/api/tts` 必须挂 `rateLimit` | 它是**唯一按字符付费**的端点，而这个端点没有鉴权（key 在客户端，设计如此） |
| 响应是字节流不是 JSON | 先 `setHeader('Content-Type','audio/mpeg')` 再 flush；中途出错只能断流 —— 与 `/api/chat` 那条"先判状态码再开流"同一个道理 |
| `/api/voice/clone` 要限样本 | 唯一收"文件"的端点。限大小（10MB 一档）、限 MIME、限时长（上游也会拒） |
| 能力表扩一维 | 现在 `Provider` 是纯出图的（`quality/background/sizes/edit/seed`）。TTS 问的是另一组：**认不认 `instructions`、`voice` 是枚举还是任意 id、做不做克隆、鉴权头怎么放**（ElevenLabs 用 `xi-api-key`） |

#### 前端

**① 选路与降级**

```
点喇叭
 ├─ 角色没配 tts / 没配 TTS 配置  → 走浏览器（现状，立刻出声）
 └─ 配了                          → /api/tts → 缓存命中？→ 播放
```

降级必须保留：没 key、请求失败、超时都退回浏览器念，并**如实说一句**"用的是浏览器声音"。
不然用户只会觉得朗读坏了。

**② 缓存不是优化，是必需项**

同一句话会被反复点（"再听一遍"），而每次点都付费 —— 没缓存这功能不成立。

- 新表 `tts_cache`，key = `hash(text + 音色指纹)`，value = `{ blob, bytes, createdAt }`
- 指纹要含 `vendorVoice / describe / speed / provider` —— 改了描述就不该命中旧音频
- 容量上限：与历史那套 prune 同一手法（看配额，超水位线清最旧一批）

**③ 中断**

`speakingId` 的语义要扩：不再只是"正在念哪条"，也包括"正在**生成**音频"。
播放中和生成中都是那枚按钮的"停止"态，点一下**既掐音频也 abort 请求**。
切角色 / 离开页面 / 清空对话 / 重生成这几处现有的 `stopSpeaking()` 调用点要一起覆盖。

**④ 长文本**

TTS 有单次字符上限（OpenAI 是 4096）。角色回复只有一到三句，通常远够；
要防的是"朗读记忆"这种长的。**先按单次够用做，超长截断并如实提示**，别一上来就写切分队列。

**⑤ 设置页加第四种用途**

- `ApiConfig.kind?: 'image' | 'text' | 'vision' | 'tts'`
- 新的 active 键 `kimage.apiActiveTts`
- `SettingsPage` 的分区、`App.vue` 的 `textConfigs` 那套照抄一份

**⑥ 角色页的音色区**

引擎切换 / 来源切换（preset · describe · clone）/ **试听** / 描述框（几行示例当 placeholder）/
上传样本 / 语速。

**试听是必需的，而且是设计要点**：不改描述就没法调音色，但每改一次都发真请求太贵
→ 试听走**固定短句**（如 `Hey, it's me.`），命中率极高、成本几乎为零。

> **命名冲突已解决**：`Voice` 这个词**归嗓音**。角色页原来那组人格字段
> （`traits` / `voice` / `address` / `boundaries`）的组名已从 `Voice` 改成 **`Personality`**，
> 其中 `voice` 字段的标签改成 **`Speech style`** —— 它管的是"话怎么说出来"，
> 而一个叫 Voice 的**文字**栏会让人以为在那里写字就能改变角色听起来的声音。

#### 合规（克隆必须做，不能省）

- 上传样本前要有**明确的同意声明**（"我确认有权使用这段声音"），并在记录里留时间戳
- 要能删：删角色 → 连带删样本；单独一条"删除音色"也要有
- **样本与音色都不进导出包**。原因不是怕大，是 `vendorVoice` **只在原账号下有效** ——
  带出去对方也用不了。导入时该角色退回 browser 音色，**界面上要说清**，
  否则对方会疑惑"为什么它没声音了"

#### 风险与取舍

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **成本失控** | 唯一按字符付费的端点，而喇叭是随手点的 | 缓存 + 试听固定短句 + 界面如实说明"这句会发一次请求" |
| **延迟** | 首字节可能 1–3 秒，而现在是"点了立刻响" | 按钮进"生成中"态；命中缓存则瞬时。**不要在这个功能上加自动朗读** —— 自动播放策略要求 `play()` 在用户手势内，且几秒延迟的自动播放很难受 |
| **上游鉴权不统一** | ElevenLabs 用 `xi-api-key`，国内几家要签名 | 目前只接火山一家（`X-Api-Key` + 部分端点还要 `X-Api-Resource-Id`）；能力表扩一维留给下一家 |
| **克隆按套餐限量** | 免费套餐常常不能建号 | 失败时如实转述上游那句话（复用 `detail` 提取那套），不自己编解释 |
| **两套音色并存** | 配了 TTS 又降级，听起来像换了个人 | 把当前引擎写进按钮的 tooltip；降级时明确提示 |

#### 顺序

**先 `describe`（OpenAI 兼容），再 `clone`（ElevenLabs）** ——
两者共用 90% 的链路（选路、缓存、播放、中断、设置页那第四档、角色页音色区）。
先把链路跑通，克隆只是"多一个来源"。

## 9. AI 起稿生成人格（二期第 2 项）

### 9.1 它解决什么

起稿那条流水线（[ENHANCE_PROMPTS.character / .vision](../server/index.js#L156-L240)）
原本只产出 **12 行长相**，persona 要用户在编辑器里自己写。
结果是**所有 AI 建出来的角色一律"identity 很满、persona 全空"** ——
名字和 identity 能撑起相当鲜明的角色，但**同一类角色之间拉不开差距**
（狮驼岭三王听起来会是同一个人），而名字本身没信息量的角色（比如普通姓名）则毫无特点。

### 9.2 十二行扩到十六行

在 `Marks` 之后追加四行，**接在长相块后面而不是插在中间** ——
让长相那十二行保持连续，模型不容易把两件事写串：

```
Personality: <what this character is like: a few traits and a disposition>
Voice: <how they talk: register, sentence length, verbal habits, and any word they use for themselves instead of "I">
Address: <how they address the user, and what these two are to each other>
Boundaries: <what this character would never do or say>
```

配套加进提示词的三条规则：

| 规则 | 为什么 |
| --- | --- |
| `Every appearance value … under 12 words` | 原来那条"所有值都是 12 词以内的英文短语"会把人格也框进去 —— 而 `Voice` 天生要写得更长，还可能夹 CJK（自称那类词）。把约束收窄到长相那 12 行 |
| "两半不能互相渗透" | 保证人格不会被写进长相字段（那会被拼进出图提示词），长相也不会被写进人格 |
| "这四行是给扮演它的模型读的，写成它能照做的指令" | 与 §7.5 的道理一样：**`Voice` 里一个具体的习惯（自称、句长）顶得上一堆形容词** |

### 9.3 识图那条的例外（要明确标出来）

识图提示词的核心规矩是"**只写看得见的**"。人格恰好是图片里读不出来的东西 ——
所以这是**唯一一处明确的例外**，并且在提示词里把性质说清楚：

> 是一个静止的画面，所以怎么说话只能从**穿着、站姿、神情**去推；
> 写得平实可信即可，**不要去编一段身世**。

把例外标出来，比让它悄悄违反那条规矩好 —— 后者会让"只写看得见的"整条规矩变得不可信。

### 9.4 解析（[parseCharacterDraft](../src/api.ts#L1587-L1644)）

新增**第二张查表**而不是把两张合成一张：两套字段的键不重合，各查各的更清楚。

`personality / voice / address / boundaries` → `traits / voice / address / boundaries`，
与 `name`、长相那 11 项都不碰撞。归一化（去非字母、转小写）之后仍然唯一。

> 实测过一份模型风格的回复：四行全部正确拆出，`本王` / `小子` 这类 CJK 原样保留，
> **标签外面裹了 `**` 也能解**（原有的装饰剥离），最后一行之后的客套话被忽略，
> `Face marks: none` 照旧落成空串。长相那 11 项的行为一字未变。

### 9.5 回填：人格**只有模型真写了才覆盖**

`applyDraft` 里长相是**直接整体替换**的（那 12 行是必答项），人格则多一个 `hasPersona` 判断：

```ts
if (hasPersona(d.persona)) draft.value.persona = { ...d.persona }
```

理由：这四行是**后加的**。老提示词、或模型偶尔漏答时，解析结果是空的 ——
直接替换会把用户自己写好的人格**抹成空白**，比"这次没更新"糟得多。

### 9.6 标记与按钮

- `aiFilled` 的键拓宽成 `keyof CharacterFields | keyof CharacterPersona`
  （两套不重合，标在同一份里不打架）。写着 `Voice` 的那四栏也会亮起模型小圆点，
  改一下那一栏点就消失 —— **与前两组完全一样的规矩**，用户不用再学一遍；
- `hasSpec`（决定起稿键显示 `Draft the spec` 还是 `Draft again`）把人格也算进去 ——
  它同样是起稿会覆盖的东西。

### 9.7 再后加的那一栏：`Language`（说哪种语言）

到 §9.2 为止，人格是四栏，全都关于"这个人怎么说话"—— **但没有一栏管他说哪国话**。
提示词里从来没规定过输出语言，于是它跟着用户走：你写中文，一个设定成英国人的角色也用中文回。

现在 `persona` 多一栏 `Language`（行定义里的第 15 行，排在人格段的**最前**）：

| 决定 | 为什么 |
| --- | --- |
| 单独成栏，不并进 `Speech style` | 同一栏里模型会把两者平均掉（项目在 `types.ts` 为 traits / voice 记过这条教训）。而语言的错法比措辞重得多：说错语言不是"这个人不太像"，而是"根本不是同一个人" |
| **默认留空 = 跟随用户** | 这是兼容性红线，不是偏好：默认写成 `English` 就等于把所有存量角色的行为静默改掉 |
| 值写成**指令**而不是标签（`- Speak only English, whatever language the user writes in.`） | 用户填的是 `English` / `简体中文` 这样的名词短语，直接摆进 system 里模型只会当背景资料 |
| `CHAT_RULES` 里补一条兜底："用户用什么语言你就用什么语言；`How you behave` 里点了语言则以它为准" | 规则在最后收束，和其余几条同一位置 |
| 朗诵挑音色也读它（`lib/speech` 的 `langTagOf`） | 原来是"按回复文本二分"猜的，只在中文/英文上凑合。现在用户明确写了答案，顺带把日语、韩语也照顾到了 —— 注意「日本語」三个字**全是汉字**，所以语言名要先于"按文字判"认，否则会认成中文 |
| **两档起稿都不许从长相推语言** | 识图那档尤其：从长相推国籍/语言是最典型的刻板印象。图里唯一站得住的证据是**真的出现了字**（招牌、徽章、制服、印字），提示词里就这么写的 |

> §9.2 与 §9.6 里"十二行 / 十六行 / 这四行"是当时的现场记录，保留原样。
> 现在的行数是 **22**（`Name` + 16 项设定 + 5 项人格），而行清单本身住在
> [server/charSpec.js](../server/charSpec.js) —— 行数、必填枚举、标签对照表全由它算出来。

## 10. 一期欠账的六处修补

### 10.1 读屏播报（#1）

`role="log"` + `aria-live="polite"` 挂在消息流那个滚动容器上 —— **必须挂在 live region 自己身上**，
挂在里面任何一层都不生效。

真正的难点不是加 `aria-live`，而是**什么时候播报**。流式时容器每个 token 都在变，
`aria-live` 会把整段逐字念一遍，比不播报还糟。所以生成期间挂 `aria-busy="true"`，
收尾放下 —— 浏览器于是只在内容安定下来时播报一次。

另外给每条气泡补了一句只给读屏的"谁说的"：左右对齐与底色**是给眼睛的**，
读屏读不出这两种区别，不补就只剩一堆光秃秃的句子。

> 新增的 `.sr-only` 放在 `style.css`（通用工具类那一带），角色页原来的 `.wz-sr` 一并并了过来 ——
> 同一件事留两份实现，就是 #5 要清的那种。

### 10.2 回到最新（#2）

自动跟随只在贴底时生效，这个决定是对的（用户往上翻时被拽回底部是聊天界面最烦人的一件事），
代价是**底下长出来的东西他看不见**。补一枚按钮，另外报"翻上去之后又来了几条"。

- **数字说的是"几条"，不是"未读"** —— 用户可能刚看过，只是此刻不在底部，
  所以用 `N new` 而不是红点角标；
- **往前读一档不算数**：那是用户自己点出来的，而且内容插在**上面**，
  该做的是稳住视口（`earlierFrom` 那一套），不该报新消息；
- **自己开口了就跟下去**（`send` 里直接 `toEnd`）：不然往上翻着忽然发一句会留在原地，
  然后那枚按钮冒出 "1 new" —— 数的是自己刚说的那句，很怪。

定位用 `bottom: 100%` 挂在输入区的上沿，**不写死像素值**：输入区高矮会变
（多一条超长警告、或没配模型时换成另一块），写死了就会在那些时候错位。

`atBottom` 从普通变量改成了 `ref` —— 界面要据它决定这枚按钮的显隐。

### 10.3 一键重试（#3）

失败时主界面会把那条空壳助手消息摘掉，于是最后一条**回到用户那句**。
所以判据非常干净：

| 最后一条是 | 说明 | 名字（`regenLabel`） |
| --- | --- | --- |
| 助手消息 | 说了一半想重来 | `Regenerate` |
| 用户消息 | 上一轮压根没答上来 | `Try again` |

两者共用同一个 `regenerateChat`，只是名字不同 —— 同一次动作，
在"想换个说法"和"刚才没发出去"两种情境下该叫不同的名字。
**不需要为报错另写一条链路。**
名字自 2026-10-05 起只在 `title` / `aria-label` 上（那枚键只剩图标，见 §3.4.4 那条改法）。

顺带：`regenerateChat` 删掉末尾那条助手消息时，要把左栏那行摘要一并回退到上一条。

### 10.4 服务端逐项限长（#4）

`chatOneLine` 加了一个上限参数，默认 `CHAT_FIELD_CHARS = 400`。
它本来就是所有角色文本的必经之路，收在这里一处就够，不必逐个字段去拦。

**但记忆那一处必须显式给上限**：摘要是一段成篇的文字，按 400 截会拦腰砍断，
所以那里传的是 `CHAT_MAX_CHARS`。

> 实测：identity 5000 字符 → 恰好 400；outfit 3000 → 恰好 400；
> persona 同样 400；**记忆 5000 字符完整保留**。

### 10.5 `v-grow` 合成一份（#5）

收进 [lib/grow.ts](../src/lib/grow.ts)，导出指令 + 一个裸函数。

顺手去掉了一处冗余：对话页原来用 `Math.min(scrollHeight, 132)` 在 JS 里封顶，
**而元素的 CSS 里本来就有 `max-height: 132px`** —— `max-height` 压得住内联的 `height`，
JS 那份是白算的，而且行高一变就会错。现在封顶统一交给样式表。

### 10.6 左栏的摘要与排序（#6）

根因：消息**按角色懒加载**，没打开过的角色在 `chatMessages` 里没有键，
于是左栏一律显示 `No messages yet` 并把它排到最后 —— 明明聊过，看起来却像从没聊过。
这个 bug 只在"聊过的角色不止一个"时才显形。

修法：新增 [getLastChatLine](../src/lib/idb.ts#L355-L400)，
一批角色各开一个倒着走的游标、**只取第一条就停**，全部跑在同一个事务里。
**代价与角色数成正比、与消息条数无关** —— 不会因为某个角色聊了几千轮而变慢。

主界面把它存在 `chatLast` 里，之后每一句都由 `sendChat` / `runChat` **就地更新**，
不必为此重读一遍库。

两个容易漏的点：

- **启动时读一趟就够**，之后不必再整批读 —— 新消息都经过那两条路径；
- **失败时要把那行退回去**（`dropChatLast` + 重读）：那一轮没留下东西，
  左栏不该还停在上一次的回复上。清空、删除角色时同理。

### 10.7 把整页钉死，不许滑（事后补的）

#### 症状

布局明明一屏放得下，整页却还能滑 —— **而且看不到滚动条**。

#### 为什么"看不见滚动条却滑得动"

两个全局设置叠在一起造成的：

```css
html { scroll-behavior: smooth; scrollbar-width: none; }
html::-webkit-scrollbar { display: none; }
```

滚动条被藏了，滚动能力留着。于是那点溢出（高度算式里 `--mast-h` 是 JS 量出来的
`offsetHeight`，取整到像素，末位对不上就会多出不到 1px）**既看不见滚动条、
又能用触控板滑出来**；而 `scroll-behavior: smooth` 让它滑得带惯性 ——
手感正是"整页在滑"，不是"多了一条滚动条"。

#### 处理

不追那不到 1px，直接把这一页钉住（`.shell-wide`）：

| 属性 | 值 | 为什么 |
| --- | --- | --- |
| `height` | `100dvh` | 钉到视口。`height` 走 `border-box`，已含内边距 |
| `padding-bottom` | **`0`** | 底部那点缝改由上面算式里留的 `--sp-4` 承担 —— 少一个耦合项，就少一处能对不上的地方 |
| `overflow` | **`clip`** | 裁掉多余的那点；**不能用 `hidden`** |

`clip` 这个选择是关键的：`hidden` 会把 `.shell` 变成滚动容器，
而**聚焦底部那个输入框时浏览器可能把它滚一下**，整页跟着挪 —— 又成了"滑一下"。
`clip` 只裁切、不产生滚动容器，也就不可能被滚。（老浏览器不认时退回 `hidden`。）

两处仍留了退路：

- **`.chat` 的 `min-height: 420px` 那条理由没有丢** ——
  屏确实太矮时（`max-height: 520px` 起）把锁解开，回到"宁可让整页滚"；
- 面板与视口底边那道 16px 的缝**照旧**，只是从 `.shell-wide` 的 `padding`
  挪进了 `.chat` 的高度算式。两边是一对，注释里互相指认。
