## 0. 这一期要解决什么

一句话：**让角色有"此刻的心情"，并且那个心情真的影响它怎么说、脸上什么表情。**

拆开是三件事：

| # | 事 | 现在为什么做不到 |
| --- | --- | --- |
| 1 | 情绪要有**记忆** | `mood` 只挂在消息上，每一轮都是从零决定心情 —— "上一句被气到了，这一句还带着点余怒"演不出来 |
| 2 | 情绪要**回流** | 它只影响朗读语调，**不影响下一句怎么写** |
| 3 | 情绪要**进画面** | 高兴和生气的自拍长得一模一样 —— 场景串里没有一处写神情 |

**明确不做**（见 §5、§8）：

- **任何界面**。不加数值、不加曲线、不加情绪日志；
- **关系层**（好感 / 信任 / 亲近）—— 二期；
- **情绪影响能动性**（"它生气了所以不回你"）—— 二期之后，见 §8.3。

## 1. 现状：已经有的三块

| 已有 | 位置 | 它管什么 |
| --- | --- | --- |
| 模型在回复末尾写 `[mood:word]`，服务端剪掉单独送 | [chatTags.js](../server/chatTags.js) 的 `MOOD_RE` 与 `splitTags` | 词的来源 |
| 情绪存成 `ChatMessage.mood`，渲染在名字旁一枚药丸 | [types.ts](../src/types.ts) 的 `ChatMessage` | 给眼睛看 |
| 情绪叠到朗读语调上 | [speech.ts](../src/lib/speech.ts) 的 `MOOD_TONE` / `toneWithMood` | 给耳朵听 |

三块都是**出口**，缺的是**状态**与**回流**。这一期补的就是中间那一段。

## 2. 核心判断：情绪是状态，不是标签

标签是每一轮的**输出**，状态是跨轮累积的**输入**。现在每轮从零决定，接上闭环就是把它变成状态。

由此推出三条原则 —— 后面每一个决定都是从这三条推出来的：

### 2.1 不做分类表

生产情绪的是**模型**（它自己写那个词），消费情绪的也是**模型**（下一句怎么写、脸上什么表情）。

两个端点都是模型，就**不需要一张词表去翻译它**。这一点是既成事实，不是新决定：`CHAT_MOOD_RE` 刻意没有枚举（见 [角色对话功能设计.md](角色对话功能设计.md) §8.1 那张表最后一行「一个词，不做分类枚举」），词表一旦出现就要维护，模型一出表外词就出错。

唯一的例外是**代码**要消费的出口 —— 现在只有一处：朗读语调那张 `MOOD_TONE`。而且它已经是范本：**认不出就原样返回，绝不猜**，而且做整词匹配（`unamused` 里含 `amused`，两者正好相反）。

### 2.2 情绪只能演出来，不能被读出来

任何"好感度 72/100""情绪曲线""情绪日志"的界面都是破功 —— 那正是 [对话沉浸感设计.md](对话沉浸感设计.md) §3.4「界面与语言：让界面这一层隐形」要挡的。

它还有一层更实际的理由：**情绪一旦变成数字，用户就会开始优化那个数字**，而这件事的全部价值是"它像个人"，不是"我在刷一个进度条"。

### 2.3 零额外调用

任何"再来一次 LLM 判断情绪"都不做。情绪只能从**已有的那一轮回复**里免费拿到 —— 那个词本来就是模型自己写的，多花一次调用去"识别"它是把免费的答案再买一遍。

同理，表情那条也**不加调用**：图本来就要画，只是往提示词里多拼一层。

## 3. 第一期 A：此刻的心情

### 3.1 数据形状

```ts
/* 角色此刻的心情。**一条状态，不是一条日志** ——
   它回答"它现在是什么心情"，不回答"它这些天的心情曲线"。
   所以一个角色一条，覆盖写，没有历史。

   与 ChatSummary 同一层：都是对话侧的派生状态，都跟着消息一起被清。
   与 Character 分开存：那边是"长什么样"的目录（localStorage，几百字节），
   把情绪混进去，等于让"它此刻恼不恼"去污染一份"它长什么样"的档案。 */
export interface CharacterMood {
  /* 主键，与 ChatSummary 同一口径 */
  charId: string
  /* 情绪词。模型自己写的那个小写英文词，与 ChatMessage.mood 是**同一个值**。
     空串 = 没有（不写这条记录） */
  word: string
  /* 这个词是什么时候的。喂不喂回 system 只看它（见 §3.3） */
  at: number
}
```

### 3.2 存储：新增一张表 `char_moods`

`openDB` 里 `DB_VERSION` **12 → 13**，v13 建表（与 `chat_summaries` 同一写法）：

```ts
const MOOD_STORE = 'char_moods'

// v13 新增：角色此刻的心情
if (!db.objectStoreNames.contains(MOOD_STORE)) {
  db.createObjectStore(MOOD_STORE, { keyPath: 'charId' })
}
```

**新增一张表是安全的升级**：建表是同步的结构操作，没有"整表读进内存再重建"那种中途失败的风险（这一条 [沉浸式对话页面设计.md](沉浸式对话页面设计.md) §4 末尾那段注记已经认定过一次）。

> **版本号只能升不能降**（[优化计划.md](优化计划.md) T3.2）。库里已经是更高的版本而代码请求了低版本时，`indexedDB.open` 直接抛 `VersionError`，
> 而每一处读写都 `catch` 成"读不出来"，界面上就是"图片和历史全没了"（数据一条没少）。

对外两个函数，与 `getChatSummary` / `putChatSummary` 同一套写法：

| 函数 | 说明 |
| --- | --- |
| `getCharMood(charId)` | 读不出来 / 形状不对一律当没有。**这一层不判过没过期** —— 那是读的人的事（服务端按窗口判） |
| `putCharMood(rec)` | 覆盖写。**`at` 由调用方给**，不在这一层取 `Date.now()` |

删除走 `deleteChatOf`（同一个事务），所以不需要单独一个 `deleteCharMood`：
"清空对话"与"删除角色"两条路都经过它，多一个没有人调的函数只是多一处要维护的东西。

**"删角色 / 清空对话"要把这一张表加进 `deleteChatOf` 的同一个事务**：

```ts
const storeNames = [CHAT_STORE, SUMMARY_STORE, CHAT_IMAGE_STORE]
if (db.objectStoreNames.contains(BACKDROP_STORE)) storeNames.push(BACKDROP_STORE)
if (db.objectStoreNames.contains(MOOD_STORE)) storeNames.push(MOOD_STORE)
```

理由与记忆那一处**一字不差**（见 [角色对话功能设计.md](角色对话功能设计.md) §7.7）：
**"消息没了而情绪还在"比失忆更糟** —— 清空之后下一句开口，它会端着一份用户刚刚清掉的火气。

#### 为什么不挂进 `ChatSummary`

考虑过：加两个字段到 `chat_summaries`（那张表已经按 `charId` 存一条），好处是**零升库**（IndexedDB 的记录是任意对象，加字段不需要动版本）。

三条理由否掉它：

| 理由 | 说明 |
| --- | --- |
| **语义不同** | 记忆是"发生过什么"（成篇文字、可展开、可编辑、可忘）；心情是"此刻什么状态"（一个词 + 一个时间戳）。混在一张表里，`Forget memory` 该不该连带把心情也清掉会立刻变成一个说不清的边界 |
| **导出的边界不同** | 记忆跟着导出包走（§6.2），瞬时心情**不**跟。同一张记录里一半带走一半留下，写起来就是一段特判 |
| **升级的代价很小** | 新增一张表是安全的升级，而上面两条是一辈子的约束 |

### 3.3 怎么进 system 提示词

**位置：紧跟在 `time` 之后、记忆之前。**

现在的顺序是 `你是谁 / 你怎么说话 → 时间 → 记忆 → 规则`，本身就是一条时间轴。心情是**此刻的事实**，与时间同一层，于是：

```
You are roleplaying as one specific character …
Who you are: …
How you behave: …
Right now: 2026-10-07 21:30, Tuesday (the user's local clock, real world only — the story may be at another time).
You two last spoke 2 days ago.
You are feeling wary right now.
You already felt that way before they said anything - carry it into your reply, or let what they just said turn it.
What you remember: …
Rules: …
```

- **排在记忆之前**，与时间同一条理由：记忆是一段成篇的叙述，夹在两块短事实中间会把它切碎（那条注释写在 `chatSystemPrompt` 里）。所有短事实在前、成篇的在后，这条秩序不破。
- **过一遍 `chatOneLine`**。这个词是从前端绕了一圈回来的外部输入，原样带换行塞回 system，等于给上一轮的输出一个伪造提示词结构的机会（与记忆那处同一条手法）。
- **认不出就整行丢掉**，不留一句 `How you feel right now:` 的空壳（`filter(Boolean)` 那条规矩）。

**"可以转向"这半句是必须的。** 只写"你正在恼"，模型会一轮一轮地恼下去 —— 那句话给它一个出口：延续还是改口，由刚才发生了什么定。这也正是"不做数值模型"的代价换来的东西：**惯性由模型演，不由权重算。**

#### 喂不喂，只看时间

| 判据 | 处理 |
| --- | --- |
| `now - at <= MOOD_HOLD_MS`（**6 小时**） | 拼进去 |
| 更久 | **整行不出现**。记录留着，读的时候判 |

**6 小时是"隔夜就散了"** —— 不是"一次会话"，是"同一场戏"。理由：

1. 三天的隔阂之后它还端着你上次惹的火，是**惩罚**，不是拟人（红线见 §5.2）；
2. 真正的"很久没见"已经有出口了 —— `chatTime.js` 那行 `You two last spoke 3 days ago` 本来就在，不需要心情再演一遍；
3. **不做定时清理**：判据是读的时候算的，不写一个后台任务去追着删。与"记忆过没过期"同一处理，少一处会与消息不同步的状态。

> `MOOD_HOLD_MS` 是**服务端**的常量，与 `CHAT_TEMPERATURE`、`CHAT_MAX_TOKENS` 并列 ——
> 那句话本身就是效果的一部分，改阈值不该要求用户重装前端（与人格字段同一分工：
> 前端发**结构**，服务端拼**措辞**）。

### 3.4 形状检查：两端共用一把尺子

`CHAT_MOOD_RE` 收的是 `[a-z][a-z-]{1,19}`（小写字母与连字符，2–20 字符）。
存进 `char_moods` 的那个词也要过**同一个形状** —— 而实现上**不抄第二份正则**：
`moodWord()` 就在 [server/chatMood.js](../server/chatMood.js) 里，前端直接 import 它
（与服务端模块"同时给两端用"的先例一致，见 `chatTime.d.ts` 那段注记）。

于是它有两个调用点，判据天然同源：

| 调用点 | 管什么 |
| --- | --- |
| [chatPhoto.ts](../src/lib/chatPhoto.ts) 的 `planChatPhoto` | 出不出表情层 |
| [chatMood.js](../server/chatMood.js) 的 `moodContext` | 喂不喂回 system |

**不过形状就什么都不做**：不喂回 system、不出表情层、不覆盖已有的状态。
与 `toneWithMood` 的"认不出就不动，绝不猜"同一条纪律。

### 3.5 什么时候写

`runChat` 收尾那一次 —— 就是现在写 `reply.mood = mood` 的**同一处**：

```ts
if (mood) reply.mood = mood
```

**三条规矩**：

| 规矩 | 为什么 |
| --- | --- |
| **状态与消息用同一个值**，不另算 | 药丸读消息、下一轮读状态。两者一旦能分叉，"它说它恼，可下一句又好好的"就会变成常态 |
| **`at` 取这一轮的收尾时刻**，不取消息的 `createdAt` | 消息的 `createdAt` 是**发给模型那一刻**，而心情是**说完那一刻**的。差几秒，但口径要对 |
| **落笔前比一次代次**（复用 `chatSeq`） | 生成是异步的。用户完全可能在它跑着的时候点"清空"或删角色 —— 回来时若不检查，这次写入会把刚清掉的心情又写回去。与 §7.8 那条"在途压缩的代次"完全一样 |

> **复用同一个计数器是知情的取舍**：`chatSeq` 也会被 `forgetChatSummary` bump（那一次是为了作废在途的压缩），所以判据比"只该在清空/删除时作废"更严一点 ——
> "生成中点了忘掉记忆"会让这一轮的心情更新被丢掉。代价是那一轮的状态没更新，下一轮照常，**而且它是自愈的**；多养一个计数器换这点精度不划算。
> 另一半同样记着：它**只加不减**，撤销"清空对话"也不会退回去。

**一轮说不完（`stopped`）也照记** —— 不额外分叉。多一个分叉就多一处能对不上的地方，而"说到一半还在气头上"本来就是真的。没有词（收在半截上被剪掉、或模型没写）就不写，与 `if (mood)` 同一条。

### 3.6 多角色状态隔离

`chatMood` 按 `charId` 分键，与 `chatBusy` / `chatControllers` / `charViewBusy` 同一条规矩。

> 这一条踩过：不按角色分开，A 在说话时切到 B，B 的界面会跟着显示"正在输入"（[角色对话功能设计.md](角色对话功能设计.md) §3.4.9）。

## 4. 第一期 B：表情出口

把同一个情绪词拼进**出图提示词**。零额外调用 —— 图本来就要画。

### 4.1 落点：`planChatPhoto` 的一个新槽

`layers` 是 `[槽名, 值]` 的数组，**顺序就是权重**（见 [chatPhoto.ts](../src/lib/chatPhoto.ts) 的 `planChatPhoto`）。新增一层：

```ts
['expression', expressionLine(word)]
```

**位置：`anchor` 之后、`part` 之前。**

`anchor` 是"这个人是谁"（那七项头部特征），表情是"这个人此刻什么样" —— 先立住是谁，再给此刻的样子。`part` 只在特写档出现，而特写档不拼表情（见下），所以它与 `part` 的先后无所谓。

**`expression` 不在 `DIRECTOR_SLOTS` 里**（那是 `['camera','lens','light','env']`）—— 于是摄影指导那一层**结构上就改不到它**。这一点与 `pin` / `frame` 同一处理：情绪是**意图**，不是摄影指导可以优化的工艺。

### 4.2 两个护栏

| 护栏 | 条件 | 为什么 |
| --- | --- | --- |
| **画面里得有人** | `self === true` | 一张空镜里没有脸。这与 `anchor` 层同一个开关 |
| **特写那一档不拼** | `frame !== 'close'` | 特写档的画面里常常只有一只手、一片布料 —— 请模型"在脸上写出神情"，就是请它把一张脸画进来，与"一个局部填满画面"正面打架 |

> 第二条**直接沿用 `action` 层在特写档被去掉的那条判断**（那里的原话是：
> "请模型'看向镜头'，就是请它把一双眼睛画进来，与'一个局部填满画面'正面打架"）。
> 同一个位置、同一条理由，不新造规矩。

再加一条与 §3.4 同源的：**词不过形状检查就不拼**。

### 4.3 措辞

```ts
return `a ${word} expression on the face, not acted out`
```

前半句只说**脸上的神情**（"on the face"）；后半句"not acted out"是冲着具体毛病去的 ——
只写 `angry`，模型很容易把它演成一个**动作**（摔东西、吼），而身体那件事由 `action`
层与 `negative` 层管，轮不到情绪插手。

**为什么是一个独立层，而不是让聊天模型把神情写进场景串** —— 两条理由：

1. **场景串的职责被反复强调为"只写事实、原样保留"**（`planChatPhoto` 的注释：它是这一张的内容，而且"谁都不许改写它"）。把神情塞进去，等于让"这张图画的是什么"和"这张脸什么表情"混成一件事。
2. **两件事挤在一个字段里会被平均掉** —— 这条教训在 `CharacterPersona` 的 `traits` / `voice` 上已经吃过一次（[types.ts](../src/types.ts) 那段注释），没必要再吃一次。

**为什么不做"情绪词 → 面部短语"的映射表**：与 §2.1 同一条。现在的图像模型对 `tired expression` / `amused expression` 这类短语本身就能理解，而词表一旦出现就要维护、就会在表外词上出错。

> 措辞本身就是效果的一部分（`ENHANCE_PROMPTS` / `CHAT_RULES` 都是这么处理的），
> 落地时按实测调 —— 但**不要**在这里加一条"哪些词算情绪"的清单。

### 4.4 重画那一张也用得上

`ChatMessage.mood` 本来就跟着消息落盘了，而重画（`retryChatPhoto` → `drawChatPhoto` → `generateChatPhoto`）读的就是那条消息。所以：

- **不必给 `generateChatPhoto` 加参数**，它从 `charId` 反查那条消息也行 —— 但更干净的是**照 `photoShot` / `photoFrame` 的样子把 `mood` 一并传下去**（那两位就是"重画时要复现同一个意图"的先例）；
- 于是"这一张当时它正恼着"在重画时**仍然是同一个表情**，与"重画这一张"的其余依据（在不在画面里、谁拿的相机、多近）完全同一条口径。

## 5. 界面与红线

### 5.1 药丸不动，一个字都不改

名字旁那枚药丸已经是情绪的出口了（普通页与沉浸页各一处）。这一期**不加任何新界面**：

- 药丸读的仍是**最后一条助手消息**的 `mood`，不改成读状态表。两者在同一轮里是同一个值（§3.5 第一条），而在过期之后它们本来就该不同 —— 药丸答的是"那条消息当时什么表情"，那是对的问题；
- 心情改到哪儿去了，**体现在它的话里**。那才是主要可感之处，也是唯一该有的地方。

### 5.2 三条红线

| 红线 | 为什么 |
| --- | --- |
| **不给用户看数值、曲线、日志** | §2.2。想让它是可见的，就走记忆那一套（一段话、可展开、可改、可忘）—— 那是**可校对**，这是**可优化**，两者不是一回事 |
| **不让情绪变成惩罚** | "它生气了所以不回你"是能动性那根柱子，[对话沉浸感设计.md](对话沉浸感设计.md) §3.3 已经把它标成**最危险**的一根。6 小时窗口（§3.3）就是这条红线的落地 |
| **拿不到就什么都不做** | 词缺失、形状不对、画面里没有人、特写档 —— 四种情况下这一期都**安静地少做一件事**，绝不补一个猜的。`toneWithMood` 的"认不出就原样返回"是范本 |

## 6. 生命周期

### 6.1 清空与删除

`deleteChatOf(charId)` 把 `char_moods` 加进同一个事务（§3.2）。**"清空对话"与"删除角色"共用它**，所以两条路一次覆盖 —— 与记忆那处完全一样。

**撤销要把状态一起恢复**：清空走 `UndoToast`（几秒内可撤销），所以那一刻要像记忆那样先把旧值捞在手里，撤销时写回去。

### 6.2 导出包

**瞬时心情不进包。**

`chat.json` 里现在带的是 `{ messages, memory }`（见 [角色对话功能设计.md](角色对话功能设计.md) §8.3）。心情**不加**：

- 它是"你俩此刻"的状态，对方打开时早就过了 6 小时窗口（§3.3），带出去是一个必然过期的字段；
- 而"养熟了的角色"里真正难重来的那份是**记忆**，那个已经在包里了。

> 二期那条关系简报是另一回事 —— 它是长期的，**要带**。这条分界正好落在 §3.2 那张"为什么另立一张表"的理由上。

### 6.3 失败与降级

| 情况 | 表现 |
| --- | --- |
| 读不出来 / 形状不对 | 当没有。不报错、不打扰 —— 与 `getChatSummary` 同一处理 |
| 写不进去（配额满） | **静默**。它是一次收尾时的附加动作，而正文已经落盘了；为它弹一条错误只会让人莫名其妙 |
| 模型这一轮没给词 | 不写、不喂、不出表情层。药丸也不渲染（现状） |

## 7. 风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **复读机** | 每轮把同一个词喂回去，它会一轮一轮地恼下去 | 提示词里给"可以转向"的出口（§3.3）；**状态是覆盖写的** —— 模型换了词，状态跟着换 |
| **情绪被画成动作** | "angry" 画成摔杯子、砸桌子 | 表情层只写**脸上的神情**；特写档不拼（§4.2 第二条） |
| **心情与药丸对不上** | 一个读消息、一个读状态 | 同一轮同一个值（§3.5）。过期后不同，而那是**对的** |
| **在途写入撞上清空** | 生成中点清空 / 删角色，回来把心情写回去 | 落笔前比一次代次（§3.5，照 `chatSeq`） |
| **一句话都不说就卡住** | 心情掺进提示词后，模型把"恼"演成"不理你" | 提示词只说"带着它"，**不说**"因此少说"；红线见 §5.2 |
| **库版本** | 新增一张表 | 12 → 13。**只能往上加** —— 回退时也不能改回去（§3.2 的注记） |
| **成本** | —— | **零**。情绪从已有的那一轮回复里免费拿到；表情层是纯字符串拼接，图本来就要画 |

## 8. 二期：关系层（设计已定，未实现）

### 8.1 它是什么

`§3` 那条是**瞬时**的（6 小时就散）。"你俩之间"是另一回事：**好感、信任、亲近**，长期累积，不逐轮跳。

两者互相影响，方向相反：

- 关系决定**同一句话怎么落地** —— 热络时是打趣，冷淡时是挑衅；
- 心情慢慢**改写关系** —— 每一次互动都是往一个方向推一点。

### 8.2 三条已定的决定

| 决定 | 为什么 |
| --- | --- |
| **不做数值**（没有 0–100） | §2.2。数值一出现，用户就开始刷它 —— 而这一层的全部价值是"它像个人" |
| **做成一段话，不是一串标量** | 于是它可以复用记忆那一套 UI 与生命周期：**可见、可改、可忘**（[角色对话功能设计.md](角色对话功能设计.md) §7.9）。不可见的长期状态决定角色怎么对你，是这一层最可怕的做法 |
| **搭在记忆压缩上顺带重写**，不新增调用 | 关系不该每一轮都跳（那是瞬时的活），而压缩本来就是"把这一段重写一遍"的时刻 —— 阈值、代次、失败静默全部现成 |

### 8.3 还没想清楚的一处

**关系不该在用户看不见的地方偷偷变坏。** 这条与 §5.2 的第二条红线同源，但在长期层比瞬时层难做到：
记忆可展开可改，那一套够用；可"它对你的态度"要改，改的是一段更抽象的东西。

**先不动它。** 能动性那根柱子（[对话沉浸感设计.md](对话沉浸感设计.md) §3.3）在瞬时层就先别碰，长期层更往后放。

## 10. 一句话回顾

> 一期就是把情绪从"消息上的一个字段"升成"角色身上的一条状态"：
> **多一张表**（一角色一条、覆盖写）、**多一行提示词**（带回去，并且允许它转向）、
> **多一层出图提示词**（同一个词写进脸上）。
> 数据一条、提示词一行、提示词一层 —— 剩下的都是管道。
>
> 而它最终长什么样，取决于那行提示词怎么写 —— 那才是这个功能本身。
