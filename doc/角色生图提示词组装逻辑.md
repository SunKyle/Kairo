## 零、一张图看懂：四条出图路径 + 一条起稿路径

角色生图不是一件事，是**五条独立的链路**，只有第一条的产物（结构化设定）是共享的。

```
        ┌──────────────────────────────────────────────┐
        │  起稿（文本 / 识图，文本模型，不出图）          │
        │  server/charSpec.js 行定义 ← 唯一真源          │
        └───────────────┬──────────────────────────────┘
                        │ 产出：name + CharacterFields + CharacterPersona
                        ▼
        ┌──────────────────────────────────────────────┐
        │  结构化设定（localStorage + IndexedDB 图）      │
        └───┬───────────┬───────────┬───────────┬──────┘
            │           │           │           │
     ①设定图      ②创作区套角色  ③对话发图   ④对话背景图
  characterViewPrompt  composedPrompt  planChatPhoto  planChatBackdrop
   （5 张，不入历史）  （用户提示词   （最复杂：六层  （横构图，给字让位）
                         + 面貌）       + 摄影指导）
```

| # | 路径 | 组装入口 | 提示词来源 | 参考图 | 进历史 |
| --- | --- | --- | --- | --- | --- |
| ① | 角色设定图（5 张） | [genCharView](file:///Users/sunxiaokai/Desktop/project/KImage/src/App.vue#L1415-L1522) | `characterViewPrompt` | 正脸：底图；其余：正脸(+底图) | 否（只存 `char_views`） |
| ② | 创作区套角色 | [composedPrompt](file:///Users/sunxiaokai/Desktop/project/KImage/src/composables/useGeneration.ts#L749-L754) | 用户提示词 + `characterFaceDesc` | 用户挑的 + 角色 4 张 | 是 |
| ③ | 对话里角色发图 | [planChatPhoto](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L678) | 六层模板 + 摄影指导 | 按镜头/景别挑 ≤4 张 | 是（`source: 'chat-photo'`） |
| ④ | 对话背景图 | [planChatBackdrop](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L810) | 固定横构图层 | 固定 2 张（full + front） | 是 |

**共同的纪律**（每条链都遵守，写错任一处都会出现"图不像/图死板"）：

1. **顺序就是权重** —— 越靠前的话对图像模型越硬。所以「这一张要画什么」永远在「这个人是谁」之前。
2. **只补不覆盖** —— 场景/用户已经说过的位，模板不重复写（否则模型挑一处丢掉）。
3. **失败逐层降级，不 reject** —— 摄影指导挂了退回模板，参考图读不出来退回纯文生图。
4. **上限在最后一刻截断** —— 截掉的正是垫在末尾的负面约束，所以上限必须留够（见 `CHAT_PHOTO_PROMPT_CHARS`）。

## 一、权威定义层：`server/charSpec.js`

**一个角色是什么，只有一份定义**，就是这个数组。它同时喂五个消费方，任何一处漏改都**不报错、只静默失配**。

### 1.1 一行的定义

[CHAR_SPEC_LINES](file:///Users/sunxiaokai/Desktop/project/KImage/server/charSpec.js#L34-L229) 每项字段：

| 字段 | 含义 |
| --- | --- |
| `group` | `name` / `field`（长相）/ `persona`（人格，只服务对话） |
| `key` | 在 `CharacterFields` / `CharacterPersona` 里的键 |
| `label` | 提示词里那行的标签，**也是前端解析时认的词**（改它等于改协议） |
| `desc` | `<...>` 里那句"这一栏该写什么"；**给对象则分 `character` / `vision` 两档** |
| `always` | 必须有个值，进 "… must always have a value" 枚举 |
| `sheetOnly` | 只喂设定图、不进普通创作提示词（`outfit` / `marks`） |
| `enumValues` | 模型只能从这几个词里挑（`style` / `gender`） |

### 1.2 行的顺序（= 拼提示词的顺序，也是跨图一致性的基础）

```
Name → Style → Gender → Identity → Face → Height → Build → Muscle → Posture
→ Hair → Brows → Eyes → Nose & mouth → Facial hair → Face marks
→ Outfit → Marks
┈┈ 以上 group=field，共 17 行（含 name） ┈┈
→ Language → Personality → Voice → Address → Boundaries → Speech samples
┈┈ 以上 group=persona，共 6 行 ┈┈
```

- **共 23 行**（`CHAR_SPEC_LINE_COUNT`，由数组算出来，不手工维护）。
- `always` 的 13 项：`Name, Style, Gender, Identity, Face, Height, Build, Hair, Brows, Eyes, Nose & mouth, Facial hair, Outfit`。
- 身材刻意拆四行（Height / Build / Muscle / Posture）：写在一行里模型会平均成"中等身材"，而这正是这条链要治的漂移。
- `Style` 排在最前：它是唯一**能被文字左右、又必须在五张图之间一致**的东西。
- **人格六行不进任何出图提示词**，它是给扮演这个角色的模型读的。

### 1.3 派生的纯函数（所有消费方都走它们，不各抄一份）

| 函数 | 产出 | 谁在用 |
| --- | --- | --- |
| [charSpecLinesText(mode)](file:///Users/sunxiaokai/Desktop/project/KImage/server/charSpec.js#L246-L248) | `Name: <...>\nStyle: <...>` 整块 | 起稿系统提示 |
| [charSpecAlwaysSentence()](file:///Users/sunxiaokai/Desktop/project/KImage/server/charSpec.js#L258-L260) | `Name, Style, … and Outfit` | 起稿系统提示 |
| [charSpecKeys(group)](file:///Users/sunxiaokai/Desktop/project/KImage/server/charSpec.js#L235-L237) | 某组的键序 | `api.ts` 的字段顺序 / 人格键序 |
| [charSpecEnumOf(key)](file:///Users/sunxiaokai/Desktop/project/KImage/server/charSpec.js#L263-L266) | 枚举行 | 前端性别/风格下拉 |

### 1.4 五个消费方（改数组要跟手的地方）

1. 起稿系统提示的**行正文**（`charSpecLinesText`）；
2. `exactly N lines` 里的 **N**；
3. "… must always have a value" 的**枚举**；
4. 前端解析回填的**标签 → 字段对照表**（[parseCharacterDraft](file:///Users/sunxiaokai/Desktop/project/KImage/src/api.ts#L2057-L2099) 动态建表）；
5. 前端字段顺序 / 必填枚举 / sheetOnly 分组（[api.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/api.ts#L1698-L1704)、[characterSpec.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/characterSpec.ts#L93-L99)）。

> `src/types.ts` 的 `CharacterFields` / `CharacterPersona` 键必须与之一一对应，单测 `characterSpec.test.ts` 把关。

## 二、起稿：一句话 / 一张图 → 结构化设定

这一层**不出图**，但它产出的设定就是后面四条链的输入，写歪了后面全歪。

### 2.1 系统提示（服务端，`server/enhancePrompts.js`）

两档系统提示都**引用** `charSpec` 的行清单，各档只写"自己独有的规则"：

| 档位 | 关键规则（摘） | 温度 |
| --- | --- | --- |
| [character](file:///Users/sunxiaokai/Desktop/project/KImage/server/enhancePrompts.js#L48-L65) | 允许把没提到的东西编具体；`Face marks` / `Marks` 无理由就留空；`Facial hair` 必须显式写（包括 none）；绝不编疤痕/义体 | 0.7 |
| [vision](file:///Users/sunxiaokai/Desktop/project/KImage/server/enhancePrompts.js#L77-L94) | **只写看得见的**，绝不编不存在的疤/纹身/义体；人格六行是唯一推断项；语言只在图里真出现字时才写 | 0.4 |

两档共用：`exactly N lines` + 行清单 + 必填枚举 + `Gender` 只能是 `female`/`male` + `Style` 只能取列表里的词 + 外观值 <12 词逗号短语 + 不写背景/光/相机/构图。

### 2.2 路由：`POST /api/enhance` 的 system 拼装

[enhance.js](file:///Users/sunxiaokai/Desktop/project/KImage/server/routes/enhance.js#L69-L81)：

- `character` / `vision` / `summary` / `photo` 四档**只发系统提示本身**；
- 只有 `quick` / `creative` 才追加 `REF_NOTE`（图生图说明）与 `targetNote`（目标模型的结构偏好，见 `TARGET_STYLE`）。
  - 理由：`REF_NOTE` 那句"不要重新描述整个场景"与摄影指导的职责直接冲突；起稿/识图加目标模型偏好会顺手把画面信息也写进去。

`vision` 档的 user 消息是多模态数组：`[{type:'text',...}, {type:'image_url',...}]`，**文字在前、图在后**。

### 2.3 回填解析：`parseCharacterDraft`

[api.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/api.ts#L2057-L2099) 是纯函数，三道归一：

1. **剥装饰**：去掉 `*` 反引号 引号、行首项目符号，再按 `Label: value` 认（标签段允许空格与 `&`，查表时去掉非字母 —— 所以 `Nose & mouth:` 也对得上）；
2. **"没有"归一**（`NONE_ISH`）：`none`/`n/a`/`—` 一律置空，**例外是 `facialHair` → `clean-shaven`**；
3. **"跟着走"归一**：`style` 的 auto 类 → 空串（`STYLE_AUTO_ISH`）；`language` 的"跟着用户"类 → 空串（`LANGUAGE_FOLLOW_ISH`）。

### 2.4 回填到表单：`applyDraft`

[useCharacterDraft.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/composables/useCharacterDraft.ts#L190-L209)：

- **名字只在还空着时补**（不顶掉用户敲的）；
- `fields` 整份覆盖；
- **人格只在模型真写出来时才覆盖**（免得把用户写好的抹空）；
- 记 `aiFilled` 标记，界面据此给"这枚点是模型写的"图例。

另有两道防串台：`draftSeq` / `visionSeq` 代次 —— 等待中换图表单/关向导时，回来的结果整份丢弃。

## 三、结构化设定 → 提示词文本：三种投影

同一份 `CharacterFields`，按**用在哪条链**投影成三种不同的字符串。**这是整条链最重要的接缝。**

### 3.1 `characterDesc`（全量，只给设定图）

[api.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/api.ts#L1776-L1782)：

```
CHAR_FIELD_ORDER 全部 16 项 field 值（空值跳过）, 最后接自由描述 desc
```

只有 [genCharView](file:///Users/sunxiaokai/Desktop/project/KImage/src/App.vue#L1465) 用它 —— 设定图要的就是把 20 个逗号短语全摆出来。老角色（没有 `fields`）整段退回 `desc`。

### 3.2 `characterFaceDesc`（面貌 + 体型，给创作区）

[api.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/api.ts#L1794-L1798)：

```
CHAR_FACE_FIELDS（= 全部 field 项 − sheetOnly 的 outfit/marks）= 14 项
```

即 `style, gender, identity, face, height, build, muscle, posture, hair, brows, eyes, noseMouth, facialHair, faceMarks`。

- 为什么这么细：只给 hair + eyes 时，肤色、骨相、眉形全靠模型从零重编，换个场景就不是同一个人。
- `outfit` / `marks` **不在这里** —— 它们只喂设定图（`sheetOnly`）。
- 老角色退回 `characterDesc`。

### 3.3 `characterAnchor`（锚点句，给对话出图）

[chatPhoto.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L142)：

```
ANCHOR_KEYS = face, hair, eyes, brows, noseMouth, facialHair, faceMarks, marks, build   （9 项，上限=长度）
```

- **刻意只留身份，做减法**：全量清单会把表情、姿态、机位一起锁死，交出来的是一张证件照。
- **刻意不进**：`style`（属于媒介层，由模板给 `photographic`）、`identity`（是身份叙事不是长相，会把模型引去角色扮演式构图）。
- 顺序即优先级（触上限从后往前丢，`build` 垫底）；**没有 `fields` 的老角色返回空串**，不退回全量描述。
- `faceMarks` / `marks` 在 2026-10-08 并入：它们从前到不了锚点（`faceMarks` 不在清单里、`marks` 还标着 `sheetOnly`），于是"小痣 / 银项链"这类身份特征在对话图上只剩参考图一条路。两项常为空，空值被 `filter(Boolean)` 滤掉，填了才占位。
- 性别单独走 [characterGender](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L186-L190)，**只在特写那一档**用（见 `partLine`）。

| 投影 | 项数 | 用在 | 空值/老角色退路 |
| --- | --- | --- | --- |
| `characterDesc` | 16 | 设定图 | 退回 `desc` |
| `characterFaceDesc` | 14 | 创作区套角色 | 退回 `characterDesc` |
| `characterAnchor` | 9 | 对话出图 | 返回空串 |

## 四、① 设定图（5 张）：`characterViewPrompt`

### 4.1 拼装公式

[characterViewPrompt](file:///Users/sunxiaokai/Desktop/project/KImage/src/api.ts#L1945-L1959)：

```
characterDesc(c)  +  ", "  +  view.suffix  +  (hasRef ? ", " + REF_IDENTITY_ONLY : "")
```

顺序：**设定 → 取景 → 参考图那句**。参考图那句压最末，因为它是"怎么读上面那些话"的元指令，排前面会把"画什么"挤下去。

### 4.2 五张视图表 [CHARACTER_VIEWS](file:///Users/sunxiaokai/Desktop/project/KImage/src/api.ts#L1844-L1931)

**顺序 = 生成顺序 = 参考图优先级**（正脸是锚，其余四张都以它为参考）。

| 序 | kind | label | framing | suffix 要点 |
| --- | --- | --- | --- | --- |
| 1 | `front` | Front | square | 单人正面头肩、两眼齐平可见、鼻尖朝镜头；**末尾三个否定**（not profile / side view / three-quarter）+ "即使参考图是侧脸也转正" |
| 2 | `detail` | Angles | square | 2×2 头部转面：左正侧 / 右正侧 / 高角度 45° / 低角度 45°（相机高度，不是让人抬头低头） |
| 3 | `full` | Full body | portrait | 单人全身站姿，头到脚完整入画 + 少许留白 |
| 4 | `closeups` | Details | square | 2×2 细部：眼睛 / 皮肤与脸部标记 / 手 / 面料与配件；**同一人同光同背景**，`no text, no labels` |
| 5 | `body` | Body | square | 2×2 肢体：手 / 前臂 / 腿 / 脚；同上；替掉的是原来的"表情 2×2"（那张永远排第 5、进不了参考图上限） |

**两条禁词（写错就画错）**：

- 绝不出现 `character reference sheet` —— 那是很强的排版概念，模型真会给你拼一张版，而不是一张干净的单人图；
- 不写 `filling the frame` —— 会让人物头顶顶到画面上沿，切掉发型轮廓/帽子这些认人线索。改成"完整入画 + 头顶留白"。

**排最后一位的代价（2026-10-06 更正）**：创作区那条路**不传 order**，取的就是这张表的顺序、而且**只取前 4 张**（`MAX_CHAR_REFS = 4`）—— 所以 `body` 在创作区那条路上**自动出局**。这正是把它排最后的原因。

### 4.3 REF_IDENTITY_ONLY（有参考图才拼的那句）

[api.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/api.ts#L1841-L1842)：

> reference images are only about who this person is: their face, features, hair and build; ignore the pose, the camera angle and the lighting in them, and do not copy the direction the person is facing there

- 来由：上传的底图是侧脸，生成的正脸也是侧脸 —— 根因是 **i2i 默认保住输入姿态**，一句 "front-facing" 拗不过它。所以明说三件事（管什么 / 不管什么 / 不许抄朝向），顺序即重要性。
- **写成复数**是有意的：正脸格只送一张，其余四格送两张。
- `hasRef=false`（纯文生图）时不拼 —— 说了是噪声，模型会去找一张不存在的图。

### 4.4 参考图怎么选（genCharView）

[App.vue L1428-L1449](file:///Users/sunxiaokai/Desktop/project/KImage/src/App.vue#L1428-L1449)：

```
source = c.sourceRef ?? (kind==='front' ? c.ref : undefined)
front 格：refBlobs = source ? [source] : []          ← 没底图就是纯文生图
其余格：front 必须在（没有就直接拦下），refBlobs = multiImage==='no' || !source ? [front] : [front, source]
```

- 正脸用**第一步上传的底图**（`sourceRef`），它就是"这个人原本的样子"；老数据退回 `c.ref`。
- 其余四张送 `[正脸, 底图]`：正脸定"这张脸"，底图补正面头像交代不了的（发型轮廓、体态、服装轮廓）。
- 不认多图的模型只送正脸 —— 正脸是不可少的那个。
- `images` 各转 data URL 后，`hasRef = images.length > 0` 决定拼不拼 `REF_IDENTITY_ONLY`。

### 4.5 尺寸：`viewSize(framing)`

[useCharacters.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/composables/useCharacters.ts#L149-L157)：

- `square → 1:1`，`portrait → 2:3`（`PORTRAIT_RATIO`；9:16 会把人缩小、3:4 容易切脚）；
- 在 `FREE_SIZES`（厂商不限尺寸）或 `allowedSizes`（枚举厂商）里按**对数距离**挑最接近那一档（`sizeClosestTo`）；
- 刻意不沿用创作区当前尺寸（那可能是宽幅，会得到一张横过来的人）；挑不出才退回。

### 4.6 生成后的副作用

- 成功才 `putCharView` 落库；**中断保留旧图**（只有成功写入那一刻才作数）；
- 正脸成功后**写回 `c.ref`**（封面/头像），底图不被顶掉（另存 `sourceRef`）；
- 重跑正脸后若其余四张已存在，给一句提醒但**不替用户删**；
- 状态与中断手柄按 **(角色, 视图)** 维度分开（`charViewBusy` / `charViewControllers`），不同角色可同时生成。

## 五、② 创作区套角色：`composedPrompt`

### 5.1 拼装公式

[useGeneration.ts](file:///Users/sunxiaokai/Desktop/project/KImage/src/composables/useGeneration.ts#L749-L754)：

```
用户提示词  +  ", "  +  characterFaceDesc(activeCharacter)
```

- **顺序不能反**：用户写的是"这一张要画什么"，角色设定是加在场景上的约束，不是反过来。前段权重更高。
- 没角色时原样返回用户提示词。

### 5.2 参考图

[doGenerate](file:///Users/sunxiaokai/Desktop/project/KImage/src/composables/useGeneration.ts#L796-L801)：

```
refList = [用户挑的参考图, ...charRefSrcs()]   （去重，用户那张排最前）
```

- `charRefSrcs()` **不传 order** → 走 `CHARACTER_VIEWS` 原序（正面打头），上限 4 张。
- 上传的底图**不在** `charRefSrcs` 里（它只为生成正脸服务一次，之后 `c.ref` 已是正脸）。

### 5.3 与提示词改写的关系

改写键（`quick` / `creative`）只动**用户提示词本身**；`characterFaceDesc` 是发起生成时才追加的（`composedPrompt`）。改写走 `/api/enhance` 时若 `hasRef` 为真会追加 `REF_NOTE`，并始终追加 `targetNote`（目标厂商的结构偏好）。

对比出图（`doRace`）走同一条 `composedPrompt` + 同样的 `refList` 快照，逐模型套各自的能力表。

## 六、③ 对话里"角色发一张图"：六层拼装（最复杂的一条）

### 6.0 上游：标签协议先定事实

聊天模型在 `CHAT_RULES`（[chat.js](file:///Users/sunxiaokai/Desktop/project/KImage/server/routes/chat.js#L28-L43)）的约束下，把意图写成回复末尾的标签：

手机前缀：selfie: / third: / self:（或 me 开头 / no-self:）

服务端 [splitTags](file:///Users/sunxiaokai/Desktop/project/KImage/server/chatTags.js#L518-L583) + [parsePhotoIntent](file:///Users/sunxiaokai/Desktop/project/KImage/server/chatTags.js#L216-L266) 剪出四个事实：

| 字段 | 含义 | 认不出来时 |
| --- | --- | --- |
| `photo` | 收敛成一行、截到 400 字的场景原文 | 空 = 这一轮不发图 |
| `photoSelf` | 画面里有没有它本人 | 见下（身体部位词兜底） |
| `photoShot` | `selfie` / `third` / 空 | 空 = 客户端判 |
| `photoFrame` | `close` / `medium` / `full` / 空 | 空 = 客户端判 |

`self` 的判据（由宽到严）：手机前缀 → `me`/`I'm` 代词 → 场景里点了角色名 → **身体部位词兜底**（`BODY_PART_RE`：指甲/手腕/肩膀/皮肤/纹身…，中文刻意不收单字"手"以避免"手机/手艺"误判）；`no-self:` 明确挡在前面。

### 6.1 六层结构 [planChatPhoto](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L678)

**顺序即权重，也即语义。**槽名决定"这一位归谁管"（摄影指导只能碰 camera/lens/light/env）。

```
medium      ← 媒介（photographic / 手机前置…）        [模板]
scene       ← 场景原文（永远原样保留，不许改写）        [上游标签]
anchor      ← 身份锚点句（self 且非空才拼）            [characterAnchor]
expression  ← 这一刻的心情（self 且非特写才拼）         [expressionLine]
part        ← 特写时："这一格是那个人身上的局部"        [partLine]
pin         ← 这一档不可让渡的硬约束（谁拿的相机/没有人）[模板]
frame       ← 景别硬约束（不可让渡）                    [frameLine]
camera      ← 机位（景别覆盖）                          [模板 / FRAMING]
lens        ← 景深（场景没说才补；景别覆盖）             [模板 / FRAMING]
light       ← 光（场景没说才补；下雨走 lightWet）        [模板 / FRAMING]
env         ← 纵深（无条件补；景别覆盖）                 [模板 / FRAMING]
action      ← 动作（场景没说动作、非特写、且场景不是中文才补）  [模板]
negative    ← 负面约束（垫最末）                        [NEGATIVE]
```

`composeChatPrompt` 用 `, ` 连接并 `.slice(0, CHAT_PHOTO_PROMPT_CHARS=6000)`。

### 6.2 三套模板 [TEMPLATES](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L424)

| 视角 | medium | pin（不可让渡） | camera 要点 |
| --- | --- | --- | --- |
| `selfie` | `photographic, shot on a phone front camera` | 相机在**它自己手上**（臂展/镜子），不是别人拍的 | 臂展、前置、**从腰以上**（脸与上半身）、略高机位、轻微广角、手臂局部入画 |
| `third` | `photographic, a casual snapshot taken on a phone by somebody else` | 手机在**别人手上**，不是它自拍 | 第三人称、随手拍、偏离中心、全身与手入画、构图随意 |
| `scene` | `photographic` | 画面里**没有人** | 相机架着/稳持，普通视点 |

- 为什么要有 `pin`（单独成层，不并进 camera）：摄影指导换机位是**整句替换 camera**，而这三件事不能被换掉 —— 换掉空镜会凭空长出一个人、自拍会画成别人拿相机、他拍会退回一张谁拍的都不知道的通用照片。
- 每套还有 `lens` / `light` / `lightWet` / `env`（自拍/他拍还有 `action`）。

### 6.3 景别覆盖 [FRAMING](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L505)

- 景别只改 **camera / lens / light / env** 四样；光与"谁拿的相机"跟景别无关。
- **缺省那一档在表里没有条目** → 今天所有图的提示词**逐字不变**（改动不可能弄坏已经对的东西）。
- 缺省：`selfie → medium`、`third → full`、`scene → medium`（[DEFAULT_FRAME](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L352)）。
- 特写那档：自拍把"臂展"换成"一只手举近"（近距离下臂展物理不成立，三个自拍信号一个不少）；他拍的 `light` 特写另外给（拍手/拍疤没有脸，"一边脸更亮"是错的）。

### 6.4 三条独立判断函数

- [frameLine(self, frame)](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L582)：景别的硬约束（人与空镜两套说法）。单独成层，摄影指导改不到。
- [partLine(gender)](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L214)：特写时补"这是同一个人身上的局部"（+ 性别）。治"明明是女生画出一只粗糙的手"。
- [expressionLine(word)](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L237)：`a <word> expression on the face, not acted out`（不做词表；`moodWord` 校验合法性）。

### 6.5 "只补不覆盖"的判据 [missingSlots](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L287)

- 只判两位：`light` / `lens`（词表中英双认，取窄，宁可漏判不误判）。
- **没有"环境"位**：环境是事实，纵深是相机原理，两者不冲突 → 纵深无条件补。
- **没有"时间/天气"位**：那是事实不是修辞，编一个"黄昏"会和对话矛盾。唯一例外是 `isWet`：已在下雨/雪时补"湿处反光"（那是必然推论）。
- `lens` 的判据里**拿掉了 close-up/macro**（归 `frameFromScene` 管）—— 否则场景一写特写，最需要的那句景深反而不补了。
- `action` 只在场景没交代动作（`hasAction`）时才补；**特写不补**（那两句是以"画面里有脸"写的）；**中文场景也不补**（2026-10-08，`hasHan`）——这一层的偏置与其余各层相反，漏判会补出一句与场景打架的动作。

### 6.6 视角与景别的判定归属

**视角（谁拿的相机）四级**（`shot`）：标签 → 场景明写自拍 → 场景明写"别人拍的" → **默认自拍**（2026-10-05 从"默认第三人称"改过来）。

**景别四级**（`resolveFrame`）：标签 → 场景明说（`frameFromScene`，特写赢）→ 这一档视角的缺省。

两者都**不由摄影指导判** —— 它只被告知（见 §七）。

### 6.7 参考图顺序 [shotViewOrder](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L1008-L1012) / [FRAME_REF_ORDER](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L988-L1006)

参考图是**最强的机位来源**（i2i 默认保住输入构图），所以它必须跟着镜头与景别走：

| 情形 | 顺序 |
| --- | --- |
| `shot === 'third'`（未登记景别） | `full, front, closeups` |
| 其余视角（未登记景别） | `front, closeups, full` |
| `frame = full` | `full, front, closeups`（全身像必须打头） |
| `frame = close` | `front, closeups, body`（**全身出局**、`body` 进来，正面打头） |
| `frame = medium` | 不登记 → 逐字等于"这一位不存在时"的顺序 |
| 背景图 [backdropViewOrder](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L1024-L1026) | `full, front`（只两张，刻意不发两张 2×2 网格） |

上限 `MAX_CHAR_REFS = 4`，实际发出 **3 张**。

**`detail`（四个头角度）在 2026-10-08 全面退出参考图**：五张设定图里三张是 2×2 网格（`detail`/`closeups`/`body`），只有两张是单张人像（`front`/`full`）。参考图是 i2i 的"拷贝先验"，网格会带出多格/多人/多手的先验——畸形的一大来源，而负面词对 gpt-image/Gemini 一类效力很弱、兜不住。结果：**非特写档网格 2 → 1、特写档 3 → 2**。`body` 也从非特写档移出（它本来就取不到，留着会被 `detail` 让出的位子顶上来）。`detail` 仍会生成、仍在角色页显示，**创作区那条路**（不传 order）照旧用它。

### 6.8 尺寸 [chatPhotoSize](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/chatPhoto.ts#L1047)

- 按 `shotRatio`（`scene → 3:2`，其余 `2:3`）在**去掉 auto** 的显式比例候选里挑最接近的一档；
- 一个显式比例都没有才退回 `auto`。**绝不挑 auto** —— 那等于把自己刚做的决定又交出去。
- 这条**不跟创作区尺寸走**（创作区选的是"这次要多大"，对话图由场景决定）。

### 6.9 扩展参数 [chatExtraParams](file:///Users/sunxiaokai/Desktop/project/KImage/src/api.ts)

- 画质显式给 `high`（对话此前没有让用户选过 quality，等于交给厂商默认档，多半是给快速预览的）；
- **`background` 一概不带**（签名里就没有这个字段，所以创作区那项再也漏不进来）；
- 两项都要**过能力表**（没有 quality 字段的厂商一个字节都不发）。

### 6.10 生成与失败

[generateChatPhoto](file:///Users/sunxiaokai/Desktop/project/KImage/src/composables/useGeneration.ts#L502-L621)：

- 取参考图那一步也在 `try` 里（会读 IndexedDB、转 data URL，最容易真抛）；读不出来 → 退回纯文生图；

<scene>
<subject：有人 / 没有人>

### 7.3 逐项验收 [parseDirector / lineValue](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/photoDirector.ts#L83-L112)

解析后**逐项验收**，任一项不过就丢该位（退回模板）：

- 带**时间词**（dawn/dusk/night…）→ 丢整行；
- 带**焦段/光圈**（`85mm`、`f/1.8`）→ 丢整行；
- `n/a` / `none` / `same` → 空；
- 抹掉破坏行结构的字符（`:` `;` 句号 引号 markdown 换行），**逗号保留**；
- 截到 `DIRECTOR_LINE_CHARS = 220`。
- 一位都没解析出来 → 整层当不可用（不是逐位退回，格式已崩）。

### 7.4 合并 [applyDirector](file:///Users/sunxiaokai/Desktop/project/KImage/src/lib/photoDirector.ts#L142-L166)

- 只替换 `camera/lens/light/env` 四个槽；
- **场景已覆盖的位不接受覆盖**（判据与模板同一处 `missingSlots`）；
- 没补上或验收不过的位**逐位退回模板**。

### 7.5 三条硬不变量（都有单测）

1. **视角一个字都改不了** —— 它只被告知；
2. **景别一个字都改不了** —— `frame` 不在 DIRECTOR_SLOTS；
3. **只换那四位** —— 其余槽原样不动。
