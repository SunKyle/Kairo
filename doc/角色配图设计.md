# 对话里的「角色发图」设计

> 状态：**已实现**（服务端协议 + 客户端出图与渲染）。Phase 4 切片 6b 之后落地。
> 本文只记决定与坑，不重复代码里已有的说明。

## 一、前提：输入侧已经做完了

「用户给角色发图」这条链**已经完整实现**，不是半成品：

| 环节 | 位置 |
| --- | --- |
| 输入框左侧的附图键 | `components/ChatPage.vue` 的 `aria-label="Attach an image"` |
| 选图 → 压到长边 1024 → 缩略图预览 / 可撤 | `shrinkForChat`、`attach` |
| 发送时把 Blob 一起交出 | `emit('send', id, text, blob)` |
| 图存 `chat_images`，消息上只挂 `imageId` | `sendChat` → `putChatImage` |
| **这一轮自动切到识图配置**，读回 Blob 转 data URL 一起发 | `runChat` |
| 历史里的图不重发（一张上千 token） | `chatStream({ images })` |
| 气泡渲染、导出/导入带图 | `bubble-img`、`ImportedChat.images` |

所以「多模态」要补的只有**输出侧**：角色 → 用户发图。

## 二、四个决定（已确认）

1. **图片来源：现场生成（C）**。不做「发自己的设定图」与「发已有作品」这两条零成本路线。
2. ~~**生成的图只活在对话里**：**不进历史、不进作品集**。想收藏由用户自己下载。~~
   **2026-10-05 改（用户要求）**：**对话里生成的每一张图都进历史，并且归到角色名下** ——
   连带那张单独生成的对话背景图。它同样是一件花了钱的作品，关掉对话页就再也翻不到，
   本来是说不过去的。落点见 [优化计划.md](优化计划.md) 的 **Wave F**：
   `App.saveChatWork` + `HistoryEntry.source/scene` + `lib/chatWork.ts`。
   **字节两处各留一份**（对话那份在 `chat_images`/`chat_backdrops`，作品那份在 `history`），
   这是有意的：两边的生命周期不同（清空对话要回收前者，存储清理会淘汰后者），
   互不牵连才不会因为对方的删除而裂掉。
3. **只在图确实有用时发**：被要求、或场景本身值得看。**不设频率上限**（2026-10-03 改，
   原来这里写的是"不是每句都配图"，那句连带的"每隔几句才准发一次"已经去掉 —— 见三之三）。
4. **排期**：先把 Phase 4 切片 6b 收口，再动这个功能。

## 三、设计要点

### 协议：照搬 `[mood:xxx]` 那套

模型产出不了图片字节，只能产出**意图**，所以本质是「模型表达意图 → 客户端执行」。
本仓已有一个成熟先例：情绪标签（`server/index.js` 的 `splitMood`）——服务端负责剪掉、
流式期间扣留半截标签、`done` 事件里单独送字段。它已经解决了最难的两件事：
**标签绝不漏给用户看**、**流式中途不闪半截**。照搬它，不另造机制。

- 系统提示加一节：在回复最后单独一行写 `[photo:<场景描述>]`，并说明"不要解释这枚标签、
  也不能拿它代替说话"（**不写频率** —— 见三之三）。
- 服务端加 `splitPhoto`，与 `splitMood` 并排；`done` 事件多带一个 `photo` 字段。
- 客户端拿到 `photo` 后：**先出字、图位占一个固定比例的骨架**，图生成完再贴上。

### 必须处理的坑

1. **`CHAT_TAIL` 要重新算**。它现在按 `[mood:amused]`（13 字符）定的 24。
   场景描述比一个单词长得多，两枚标签还可能同时出现 —— 尾巴不够长就会在流式时
   漏出半截标签给用户看见。
2. **场景描述要限长 + 清洗**。它是模型写的自由文本，会进提示词、可能带引号/换行。
   要截断、去控制字符，并且**永远不当作指令**（只当一段被包装过的描述）。
3. **只认最后一枚**标签（与 mood 同一处剪），一轮最多一张图。
4. ~~**频率兜底**：提示词里写"别每句都发"之外，客户端也要拦（例如连续 N 轮最多一张）~~
   —— **决定不做**，2026-10-03 改：见下面「三之三、频率」。
5. **失败不阻断文字**：出图报错/超时就撤掉骨架，改成**一行小字 + 重试**（见 §五 的
   `photoFailed`），正文照旧。**不能只是把骨架悄悄撤掉** —— 那样"没收到图"和
   "本来就没打算发图"在界面上长得一模一样：用户既不知道为什么没图，也没地方让它再来一次。
6. **异步与流式的顺序**：图比文字慢得多。不能等图出来才显示文字，也不能让图到达时
   把已经读完的气泡顶下去 —— 骨架必须是固定比例。
7. **要用哪个配置出图**：当前生效的出图配置（`config`）。
8. **这一张里有没有它本人 —— 决定带不带设定图**（见下面单独一节）。
9. **~~不进历史的落盘路径~~ 两处落盘（2026-10-05 改）**：图字节仍然存 `chat_images`
   （与用户附图同一张表），消息上挂一个**与 `imageId` 分开**的字段
   （`photoId`）—— 语义不同：一个是"对方发来的"，一个是"它给你的"，
   渲染位置、清理时机、撤销语义都不一样。**在此之上**，同一张图再经
   `recordFor` + `persist` 落一条历史记录（`source: 'chat-photo'`，
   `characterId` 是对话里那个角色）—— 它才让这张图在历史页、角色作品墙、
   批量导出里存在。两条路刻意互不引用：历史被清理掉，对话里那张还在；
   清空对话，历史里这张也还在。
10. **导出/导入**：`photoId` 的字节要并进 `ImportedChat.images`（那里已经是
    `{ id, blob }[]`，"谁附的"不影响搬运）；标签本身随消息文本走，零改动。
11. **`types.ts` 里那句「只有用户消息会带 imageId」是文档约束**，加了输出侧之后要改。

## 三之二、这一张里有没有它本人（2026-10-03 补）

### 症状

有一类回复里发的图**跟这个角色长什么样无关** —— 窗外的雨、桌上那杯咖啡。
刚开始的实现是**每张都带**：提示词里拼上 `characterFaceDesc`，设定图当参考图送进去。
结果是这些图被拽着跑偏：模型往那个人的脸、发型、衣着上靠，甚至在一张风景里
凭空长出一个穿那身外套的人。

### 判据由模型给，不由客户端猜

`[photo:…]` 里的描述本来就是"它想给你看什么"。于是给它加一个**前缀**：

| 标签 | 意思 | 出图时 |
| --- | --- | --- |
| `[photo:rain on the window]` | 它**看到**的东西 | 提示词只有场景，**一张参考图都不发**；空镜模板 |
| `[photo:selfie:me on the balcony, hair down]` | 它**在画面里**，**它自己的手机**在它手上 | 拼外貌设定 + 设定图当参考图；自拍模板（前摄、臂展、手入画） |
| `[photo:third:me on stage, taken from the crowd]` | 它**在画面里**，**别人的手机**在别人手上 | 同上，但他拍模板（hand-held phone snapshot、取景随意） |
| `[photo:self:me on the balcony]` | 它**在画面里**，没说谁拿的手机 | 按场景文本判，认不出就**按自拍** |

**两条"手机"是同一个要求的两半**（用户 2026-10-05 原话："要能理解自己用手机拍摄的
视角，和别人用手机拍摄的视角"）：自己拍那半靠"前摄 + 臂展 + 手入画"，
别人拍那半靠"手机在别人手上 + 随手拍、取景不讲究"。两档各有一条硬约束层
（`ShotTemplate.pin`）钉住"手机在谁手上" —— 摄影指导补机位时会整句替换 `camera`，
而它看不见标签，所以这两句话必须独立成层。

**默认（不写前缀）= 场景照。** 取舍的理由：一张风景里长出一个人是**整张废掉**，
而一张自拍少了参考图只是"不像本人"——而模型只要真在说自己，就该写前缀
（提示词里明说了这一点）。猜错的代价不对称，所以默认落在伤害小的那一侧。

**2026-10-05 补：视角也进了标签**（`selfie:` / `third:`）。原来只有"在不在画面里"
这一位，而"谁拿的相机"交给一次**额外的文本调用**（摄影指导）去猜 ——
它只看得到那一句场景、看不到对话，于是猜出来大多是**他拍**。用户的原话：
"角色对话生图的时候，对于自拍的理解总是不好，老是会生成他拍视角的图片。"
现在这件事由**唯一知道答案的那一层**（聊天模型）直接说，四级判据见
`lib/chatPhoto.ts` 的 `planChatPhoto`：标签 > 场景写着自拍 > 场景写着"别人拍的"
> 默认自拍。摄影指导仍然补机位/镜头/光/环境，但**视角它改不了**。

三条容错（模型不总写得一丝不差）：

1. `selfie:` / `self-portrait:` —— 相机在它手上；标记**剪掉**（它不是内容）；
2. `third:` / `third-person:` —— 相机在别人手上；同样剪掉；
3. `self:` / `myself:` / `me:` / `me,`，或直接以 `me at my desk` / `I'm on the balcony`
   开头 —— **在画面里，但没说相机**；纯标记剪掉，代词那几种只置位不剪
   （剪掉就只剩 `at my desk`，画面里少了主语）；`\b` 保证 `meeting` / `selfish`
   不会被误判；
4. 兜底：描述里**点了自己的名字**（`Alice leaning on the railing`）也算它在画面里 ——
   角色名由服务端传进 `splitTags`（它手上有角色卡）。名字这条**不回答相机那一项**。

`scene:` / `view:` 是模型偶尔多写的噪声，抹掉。

### 落点

- 剪取与判据：`server/chatTags.js` 的 `parsePhotoIntent` / `splitTags(s, charName)`
- 提示词：`CHAT_RULES` 里那张标签那一条，明说三个前缀各是什么、拿不准就写 `selfie:`
- 传输：`done` 事件多带 `photoSelf` 与 `photoShot`，`ChatMessage` 上各存一位
  （重画与导出包里的这段对话要保持同一个意图）
- 出图：`lib/chatPhoto.ts` 的 `planChatPhoto(scene, self, anchor, shot)` —— **纯函数**，
  三个决定（拼不拼外貌、发不发参考图、用哪套模板）都在它身上，单测直接断言
- 一句话：**参考图与外貌设定同一个开关**（`photoSelf`）；**视角另一个开关**
  （`photoShot`，标签说的算，它没说才由场景文本兜）

### 还没做的（这一节留的）

- ~~**客户端频率兜底**：提示词里写着"别每句都发"，客户端仍然没拦~~
  —— 不再是欠账：**这一条决定不做**，见下面「三之三、频率」。

### 与识图的合流

用户发图那一轮已经切到识图配置；若同一轮角色又回图，就是「识图模型看进来 + 出图模型
画出去」——两个配置各管一段。产品上最自然的场景（"你看我这张照片" → "（看了）……
我也来一张"）正好落在这条缝里，实现时**不要**把两条配置路径搅在一起。

## 三之三、频率（2026-10-03 改）

**结论：角色对话里发图不设频率上限。** 提示词里那句 "Use the tag rarely, at most once
every few messages" 已经删掉，客户端**也不加**「连续 N 轮最多一张」那类兜底。

| 决定 | 为什么 |
| --- | --- |
| 提示词里的频率那句删掉 | 它是唯一存在过的频率限制。留着的话，"多发几张"这种再自然不过的要求会被一条模型自己都记不牢的规矩压着 —— 而频率该由**对话本身**决定：问它要照片就该给，一句普通寒暄就不该配图 |
| 客户端不加兜底（原第 4 条坑作废） | 兜底要挑一个 N（几轮算合适？），而任何 N 都是替用户做判断。真要被烦到，用户关掉的是这个功能，不是"每三条准发一张" |
| **保留"只有图确实有用时才发"这个判据** | 去掉它才是真的失控：模型会把标签挂在每一句后面。它管的是**相关性**（要照片 / 场景本身值得看），不是频率 |
| 保留"绝不能拿标签代替说话" | 图是补充，不是回复。一轮只有一句话的时候更要想清楚 |
| 一轮一张（协议层）不变 | 只认最末尾那一枚标签，与 mood 同一处剪 —— 这是协议决定的，不是频率限制 |
| 成本仍然是用户的 | 每张图都是一次真出图调用（见 §四的预算与 §五的"失败不阻断文字"）。没有频率上限，就意味着"多聊几句、多要几张"会直接反映在账上 —— 这是有意的：这个功能的卖点就是角色**会**给你看 |

顺带：服务端那条 `/api/generate` 的 `RATE_MAX = 30/min`（按 IP）照旧管着 —— 它是防滥用的，
不是产品意义上的频率限制，正常聊天一秒钟一个请求也撞不到。

## 四、验证方式（实现时）

- 服务端单测：`splitPhoto` 的剪取、白名单/清洗、半截标签的扣留（含两枚标签同时出现时
  的尾巴长度）。
- 浏览器探针：播种一条带 `photoId` 的助手消息 → 断言图**渲染在文字下方**、骨架占位
  不撑跳；再断言流式期间正文里**看不到**半截标签。
- 预算：这一条会新增一次出图调用，`--max-ms` 之类的门禁不受影响，但要确认
  **不阻塞首屏与流式**。


## 五、实现记录

- **服务端**（[server/chatTags.js](../server/chatTags.js)）：标签逻辑抽成独立模块，
  `splitTags` 一次剪下 mood 与 photo（两枚同时出现、顺序任意都认）；
  半截标签只擦不取，前缀放宽到 3 个字母（`[pho` 这种"正好停在半个词上"原来会漏出去）；
  `TAG_HOLD` 从 24 提到 160。12 条单测。
- **客户端**：`chatStream` 把 `photo` 从 `done` 事件带回；`runChat` 在收尾时
  **先挂场景描述**（界面立刻占骨架位）再后台画，画完存 `chat_images` 并挂 `photoId`；
  画失败则挂 `photoFailed`（见 §五 的 2026-10-03 补记），正文照旧。
- **出图**（`useGeneration.generateChatPhoto`）：先问 `planChatPhoto` 要一个方案
  （要不要拼外貌、要不要发参考图，见 §三之二）；出图这一层**仍然不碰存储** ——
  它把 Blob 连同**真正发出去的那套配方**（提示词、尺寸、模型、配置、耗时）一起交回调用方。
- **落两处**（App 的 `drawChatPhoto` → `saveChatWork`）：字节进 `chat_images`（消息要显示它），
  同一条记录再进 `history`（见上面第 2、9 条的 2026-10-05 更正）。
- **渲染**：`.photo` 垫在文字**下面**（用户附图在上面），
  未完成时是固定比例的骨架。
- **验证**：对话探针播种"已画好"与"还在画"两条助手消息，断言
  **图渲染了、且在文字之后**、待画的显示骨架。九道门 + 205 条单测。

### 2026-10-03 补记

- **`photoSelf`**：`[photo:self:…]` 前缀 → `done` 事件 → `ChatMessage.photoSelf`
  → 导出包 → 导入回填，全线打通；默认（不写前缀）是场景照，不带设定图。
- **失败的图要留痕、能重来**：从前 `runChat` 在 `generateChatPhoto` 返回空时
  只把 `photo` 清掉（而且**没有落盘** —— 库里那条仍然带着场景描述，刷新回来
  就是一个永远转下去的骨架）。现在抽成 `drawChatPhoto`：失败在消息上记
  `photoFailed: true` 并**写回库**，场景描述原样保留（它是重试要用的全部依据）；
  界面那条消息下面给一行 `Couldn't generate that image.` + `Try again`，
  重试走 `retryChatPhoto` —— **只重画图，不动文字**（与 `regenerate` 是两件事）。
  导出侧同时收紧：没有 `photoId` 的消息不再带 `photo` / `photoSelf` 进包
  （包里没有"失败"这个状态，带过去只会变成一条永远在画的消息）。
- **读取边界上收口**：库里"有 `photo`、没 `photoId`"只有两种可能 —— 还在画、或没画出来。
  而**还在画的那种不可能被读回来**（出图只活在当前内存里，读取发生在刚进页面或往前翻的时候），
  所以读取时一律落成 `photoFailed`（`useChat` 的 `settlePhoto`）。不收的话，
  中途刷新会留下一个**永远转下去的骨架** —— 生成随页面一起没了，库里那条再没人补全。
  只在读取侧收：内存里那份不能碰，那里 `photo` 加 `photoId` 缺席也可能真的是"正在画"。
- **空引用（`photoId` 在、字节没了）是怎么来的** —— 消息与附图分两张表存，
  中间没有外键替我们挡着，"字节先写、消息后指"和"先清消息、后写回"这两段
  时间差都会留下悬空引用。已收掉的两条：
  1. **撤销"清空对话"**：撤销回调从前先调一次 `deleteChatOf` 再写回消息，
     而 `deleteChatOf` 现在会连附图一起收 —— 消息写回来了，字节却已经走了
     （顺带还带走了比内存那一档更早的消息）。改成**只往库里加、不先清**；
     回收留给 `purge`（那里的注释本来就写着"附图的回收必须留在 purge"）。
  2. **空间体检撞进写入的窗口**：`pruneChatImages` 判孤儿的唯一依据是
     "库里有没有消息指着它"，而 `putChatImage` 与挂 `photoId` 是两个事务。
     写成后者之前做体检查，刚画好的一张就会被收掉。现在**刚写过图就先跳过体检**
     （`CHAT_IMAGE_QUIET_MS`）—— 孤儿晚 30 秒再收，代价几秒，收错了是一张图没了。
- **服务端端到端验过**：起一个假上游（SSE）打 `/api/chat`：
  `[photo:self:me on the balcony, hair down]` → `{"done":true,…,"photo":"me on the balcony, hair down","photoSelf":true}`；
  `[photo:rain on the window at dawn]` → `photoSelf:false`，场景描述原样保留。

## 六、失败要说清是**哪一种**失败（2026-10-04 补）

用户反馈原话：「图片生成失败根本没有详细的提示，只有说明图片生成失败。」

### 根因

`generateChatPhoto` 的约定是"失败只返回 `undefined`、绝不 reject"（本文 §五 定的，
理由是不让它阻断文字）。但 `undefined` 是**一个**值，而这些完全不同的情形
全都压成了它：

| 真实原因 | 用户该做什么 |
| --- | --- |
| 一条出图配置都没有 | 去设置页配一条 |
| 有配置但没有模型名 | 把模型名填上 |
| 上游说密钥不对 | 换 key |
| 上游 5xx / 超时 | 等一会儿重试 |
| 上游 200 但一张图都没回（多半被安全策略拦了） | 换个说法 |
| 参考图读不出来（IndexedDB 出错） | 一般能自愈，重试 |
| 图**画出来了**却存不下（配额满） | 去清理空间 |

界面只能说一句"生成失败"。**用户无从下手，只能来问** —— 而这七种里
有五种是用户自己两分钟能解决的。

### 改法

1. **返回类型从 `Blob | undefined` 改成"要么给图、要么给原因"**
   （`{ blob } | { error }`）。逐个失败点写自己的原因，最后那个兜底 catch
   不再把原因换掉；
2. **配置缺失说清缺什么**（`imageConfigGap`）—— "缺模型名"比"没配好"具体；
3. **收口一层 `photoFailureText`**（[api.ts](../src/api.ts)）：中止不算失败
   （说成"生成失败"会让人去查配置）、空话给兜底、超长截断。
   文案本身沿用 `failureMessage` 的产出 —— 它已经把"401 其实是部署登录墙"
   这类**特定成因**翻成了人话，比另编一套准；
4. **`ChatMessage.photoError`** 存下原因：界面显示它，`title` 里放全文；
   落盘、导出/导入、以及从库里读回来时都收一道（它会**直接渲染**，
   一个非字符串的值就够让那一格显示成 `[object Object]`）；
5. **"画出来了但存不下"不再混进"画不出来"** —— 那是两回事，
   而且后者的锅在浏览器配额，不在模型。

### 验证

- 单测：`photoFailureText` 6 条（中止 / 空话 / 非 Error / 换行 / 超长）、
  `chatMessageFromRow` 5 条（非字符串 / 超长 / 退化输入）；
- 探针新增**用例 6**：假上游对出图回 401 时，断言服务端把上游的原话
  （`Upstream returned an error (401)`）与 `detail`（`invalid api key`）
  都传到了浏览器 —— 传丢了界面上就只剩"生成失败"，所以这一段就是全部。

### 还没验证的

**界面上那一行到底长什么样，要手测。** 探针到不了浏览器；
单测只管"该给的话给对了"。要看的是一句较长的原因在气泡里会不会
把重试键挤到第二行（CSS 已经给了两行截断 + `title` 兜全文）。
