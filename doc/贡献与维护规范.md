# 贡献与维护规范

本文件定义 Kairo 文档的写法、引用方式、版本策略、更新频率与自查方法。
目标是让文档**跟得上代码**，而不是变成一堆过时的散文。

> 本文合并了原《文档一致性清单.md》的自查方法与历史教训；清单原文归档于 `doc/archive/`。

---

## 1. 引用方式

### 1.1 禁止：文件 + 行号

```text
lib/idb.ts:152                        错误：行号随代码漂移
src/api.ts#L2104                      错误：行号随代码漂移
```

### 1.2 应该用：符号名 + 文件名

```text
lib/idb.ts 的 DB_VERSION 常量               正确
src/api.ts 的 getProvider 函数             正确
server/routes/chat.js 的 chatSystemPrompt  正确
```

### 1.3 原理

行号会在代码变更后立刻失效，而符号名（函数名、常量名、变量名）在重构后通常仍可搜索到。符号名不存在时读者能立刻发现并纠正，行号错误只能靠人工核对。

### 1.4 例外

- 引用 git 提交中的特定行（例如 `350c54a:src/api.ts:2104`）
- 引用外部文档的特定位置（例如 Notion PRD 的某一段）

## 2. 版本策略

### 2.1 快照标注

每一份描述代码现状的活文档，都必须在开头注明快照：

```markdown
> 快照：`main` @ `6abb48e`（2026-10-20）
```

### 2.2 漂移补记

文档写完之后代码又变了，**不要改快照正文里的数字或事实**（那等于伪造快照）。正确做法是在快照行之后追加一条：

```markdown
> ⚠️ 此后已漂移（2026-10-20）：`DB_VERSION` 13 → 14（新增 `memories` 表），页面 5 → 6。
> 读到时请以代码为准。
```

若漂移范围大到正文已经整体失实（例如页面结构重做），应当直接重写文档并把快照更新到新提交，而不是叠十几条补记。

### 2.3 数据库版本（DB_VERSION）

- `DB_VERSION` 只加不减，升级必须是 additive（新增表/新增字段），不删除旧表
- 升级后旧数据必须能被新代码读取（读不到的字段要有默认值或收口逻辑）
- 每次升级都要在《架构设计文档》注明版本变化与迁移代价

### 2.4 测试规模

- 测试文件数与用例数是**活跃指标**，不要在正文里写死
- 必须提及时写成「约 N 个用例」并注明日期；真实数量以 `npm test` 输出为准

## 3. 更新频率

### 3.1 代码变动后必须同步的文档

| 代码变动 | 必须更新的文档 |
|---|---|
| 新增 / 删除 / 重命名符号 | 所有引用该符号的文档 |
| 新增 / 删除 / 重命名文件 | 所有引用该文件的文档 |
| 升级 `DB_VERSION` | 架构设计文档、角色对话 |
| 新增页面 / 改变路由 | 架构设计文档、产品路线图、`lib/nav.ts` 相关描述 |
| 新增 / 删除依赖 | 架构设计文档（技术栈） |
| 新增测试门禁 / 脚本 | 贡献与维护规范、README |
| 产品范围或优先级变化 | 产品路线图（§2 对齐表与 §4.5 清单） |

### 3.2 路线图的更新

- 产品路线图是**活文档**。每完成一个任务（T 编号）或一次成批交付，在 §7 追加一条记录
- 记录格式：`§7.N 本轮交付（YYYY-MM-DD）：交付内容 + 验证基线`
- 已完成的任务要从「待办」移到「已闭合 / 已完成」；明确不做的写进「已决策不做」，不要留在待办里当欠账

### 3.3 触发时机

- **代码 PR 合并后**：立即更新对应文档
- **每两周**：按 §7 的自查命令过一遍
- **新人加入时**：新人读文档发现的第一处不一致，就是需要更新的地方

## 4. 目录结构与编号

### 4.1 编号规则

编号由**一段字母 + 一位数字**组成，只为跨文档引用稳定，不表示阅读顺序：

- `P` = 产品（Product）
- `A` = 对话 / 体验（Assistant）
- `C` = 角色 / 创建（Character）
- `G` = 配图（Gallery）
- `I` = 接口 / 发图 / 标签（Interface / Image）
- `S` = System Prompt
- `B` = 架构（Base）
- `D` = 设计 / 维护（Design）

### 4.2 新文档

1. 分配一个新编号，不复用旧编号
2. 在 `doc/README.md` 登记（**唯一入口**，不再维护第二份索引）
3. 选择正确的状态标签（核心 / 功能 / 详情 / 方向 memo / 维护）

### 4.3 旧文档

1. 被合并、被替代或已被代码证伪的，移到 `doc/archive/`
2. 用 `git mv` 保留历史，**不直接删除**
3. 在 `doc/README.md`「归档」表写明原因与「现在看哪里」
4. 归档文档保持原快照，不再更新；与代码冲突时以代码为准

## 5. 写作风格

### 5.1 格式

- Markdown；说明用中文，代码与符号名用英文
- 用表格组织结构化信息，避免大段铺陈
- 用引用块（`>`）标注重要结论、注意事项、用户反馈

### 5.2 结构

- 开头一句话定位：这份文档回答什么问题
- 用 `## 0.` `## 1.` 编号，方便按编号引用
- 每个决策点写清**决定 / 为什么 / 现状**
- 日期格式：`YYYY-MM-DD`

### 5.3 诚实原则

- **已做对的就写已做对的**，不要把「计划做」写成「已经做了」
- **未做就写未做**，不要写「即将做」或「在规划中」（除非确实有排期）
- **用户否掉的就写否掉**，并注明原因，避免下一个人重新提议
- **不确定的就写不确定**，并注明下一步验证方式
- **判定「某功能不存在」之前，先 `git log -S` 查一遍** —— 历史上四次「❌ 未发现」最终都被证伪

## 6. 常见错误

| 错误类型 | 错误示例 | 正确做法 |
|---|---|---|
| 文件 + 行号引用 | `lib/idb.ts:152` | `lib/idb.ts 的 DB_VERSION 常量` |
| 把计划写成已完成 | 「自定义音色待落地」（实际已实现） | 先跑代码确认，再写状态 |
| 把快照当现状 | 「页面共 4 个」（现为 6 个） | 重写或加「此后已漂移」补记 |
| 无日期的事实陈述 | 「测试有 755 个用例」 | 「截至 2026-10-20，约 900 个用例」 |
| 无引用的判断 | 「这个方案不好」 | 「这个方案不好，因为……（见 §N.N）」 |
| 过时的用户决策 | 「用户选择了方案 A」（已改选 B） | 注明「2026-10-15 用户改选方案 B」 |
| 把已决策不做留在待办 | 「主动联系待排期」 | 移到「已决策不做」并写明理由 |
| 双份索引 | `README.md` 与 `文档索引.md` 各登记一次 | 只维护 `doc/README.md` |

## 7. 一致性自查

每次较大改动后跑一遍；发现新不一致，先记下来再决定改文档还是加漂移补记。

### 7.1 关键事实

```bash
# 数据库版本
grep -n "DB_VERSION" src/lib/idb.ts

# 页面清单
grep -n "export type Page" src/lib/nav.ts

# 测试规模（以输出为准）
npm test
```

### 7.2 引用与死链

```bash
# 残留「文件 + 行号」引用
grep -rn "#L[0-9]" doc/

# 列出 doc/ 下所有 .md 相对链接，逐个确认文件存在
grep -rhoE "\]\(([^)#]+\.md)" doc/ | sed 's/^](//' | sort -u

# 已归档 / 已重命名的旧文件名是否还被引用
grep -rn "现状梳理（当前状态）\|架构评审报告\|文档一致性清单\|整体设计风格\|设计系统-本项目落地\|文档索引\|产品愿景与MVP范围\|PRD对齐与后续路线图" --include="*.md" .
```

### 7.3 状态口径

```bash
# 文档里声称「未实现」的东西，先确认代码里真的没有
grep -rn "nextSceneMode\|pauseResume\|virtualScroll" src/ server/

# 已决策不做的功能不应出现在待办
grep -n "T6\|T8" doc/产品路线图.md
```

### 7.4 验收命令

文档改动本身不需要跑测试；若同时改了代码，至少跑：

```bash
npm run typecheck   # vue-tsc --noEmit
npm run lint
npm test
npm run check:server
```
