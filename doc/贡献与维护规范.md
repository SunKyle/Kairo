# 贡献与维护规范

本文件定义了 Kairo 项目文档的写法、引用方式、版本策略与更新频率。
目标是让文档**跟得上代码**，而不是变成一堆过时的散文。

---

## 1. 引用方式

### 1.1 禁止：文件 + 行号

```text
lib/idb.ts:152                        错误：行号随代码漂移
src/api.ts                     错误：行号随代码漂移
```

### 1.2 应该用：符号名 + 文件名

```text
lib/idb.ts 的 DB_VERSION 常量          正确
src/api.ts 的 getProvider 函数        正确
server/routes/chat.js 的 chatSystemPrompt  正确
```

### 1.3 原理

行号会在代码变更后立刻失效，而符号名（函数名、常量名、变量名）在代码重构后通常仍然可搜索到。当符号名不存在时，读者可以立刻发现并纠正，而行号错误只能靠人工核对。

### 1.4 例外

以下场景可以保留行号：
- 引用 git 提交中的特定行（例如 `350c54a:src/api.ts:2104`）
- 引用外部文档的特定位置（例如 Notion PRD 的某个段落）

## 2. 版本策略

### 2.1 快照标注

每一份活文档（P01、P02、A01、A02、C01、C02、I01、G01、G02、G03、A03、B01）必须在开头注明快照：

```markdown
> 快照：`main` @ `350c54a`（2026-10-15）
```

### 2.2 漂移补记

当文档内容之后发生变化，**不要修改快照正文中的数字或事实**（那等于伪造快照）。而是在快照行之后追加一条「漂移补记」：

```markdown
> ⚠️ 此后已漂移（2026-10-15）：`DB_VERSION` 13 → 14（新增 `memories` 表），页面 4 → 5（新增 `memory`）。
> 读到时请以代码为准。
```

### 2.3 数据库版本（DB_VERSION）

- `DB_VERSION` 只加不减，升级必须是 additive（新增表/新增字段），不删除旧表
- 升级时，旧数据必须能被新代码读取（读不到的字段要有默认值或收口逻辑）
- 每次升级后，必须在相关文档中注明 `DB_VERSION` 的变化

### 2.4 测试规模

- 测试文件数与用例数是**活跃指标**，不要在文档中写死（例如「755 个用例」）
- 如果必须写，写成「约 N 个用例」并注明日期
- 真实数量请运行 `npm test` 查看

## 3. 更新频率

### 3.1 代码变动后必须同步的文档

| 代码变动 | 必须更新的文档 |
|---|---|
| 新增/删除/重命名函数、常量 | 所有引用该符号的文档 |
| 新增/删除/重命名文件 | 所有引用该文件的文档 |
| 升级 `DB_VERSION` | 所有引用数据存储的文档 |
| 新增页面 | `现状梳理`、`架构设计文档`、`产品路线图` |
| 新增测试 | 如果文档引用了测试数量，需要同步 |
| 新增/删除依赖 | `现状梳理`（技术栈部分）、`架构设计文档` |
| 改变路由结构 | `现状梳理`、`架构设计文档`、`产品路线图` |

### 3.2 路线图文档的更新

- 产品路线图是**活文档**，每次完成一个任务（T 编号）后，必须在 §7「进度更新」中追加一条记录
- 记录格式：`§7.N 本轮交付（YYYY-MM-DD）：T 编号 + 简要说明`
- 已完成的任务要从「待办」清单中移到「已闭合」清单

### 3.3 文档更新的触发时机

- **代码 PR 合并后**：立即更新对应文档
- **定期检查**（建议每两周一次）：检查文档是否与代码一致
- **新人加入时**：新人读文档时发现的第一处不一致，就是需要更新的地方

## 4. 目录结构与编号

### 4.1 编号规则

编号由**一段字母 + 一位数字**组成：

- `P` = 产品（Product）：产品路线图、现状梳理
- `A` = 对话/角色（Assistant）：角色对话、沉浸式对话、API 配置
- `C` = 创建（Create）：角色创建、情感系统
- `I` = 接口/发图（Image）：发图六层拼装
- `G` = 配图（Gallery）：配图设计、构图光影、提示词组装
- `B` = 架构（Base）：架构设计、架构评审
- `D` = 设计/维护（Design）：设计风格、维护规范

### 4.2 新文档的处理

新增文档时：
1. 分配一个编号（例如 `P03`、`C03`）
2. 在 `README.md` 与 `文档索引.md` 中登记
3. 选择正确的标签（核心 / 功能 / 详情 / 归档 / 评审 / 通用 / 维护）

### 4.3 旧文档的处理

旧文档（例如已被合并或被替代的）应该：
1. 在 git 中保留历史（不要删除 git 历史）
2. 从当前目录中移除，或在开头加「已归档」标注
3. 在 `README.md` 中注明「旧文件已合并/替代」

## 5. 写作风格

### 5.1 格式

- 使用 Markdown 格式
- 使用**中文**写说明，使用**英文**写代码与符号名
- 用表格组织结构化信息，避免大段文字
- 用引用块（`>`）标注重要结论、注意事项、用户反馈

### 5.2 结构

- 每份文档开头必须有**一句话定位**：这份文档回答什么问题
- 用 `## 0.` `## 1.` 编号，让读者可以按编号引用
- 每个决策点必须写清楚**决定 / 为什么 / 现状**三栏
- 日期标注格式：`YYYY-MM-DD`

### 5.3 诚实原则

- **已做对的就写已做对的**，不要把「计划做」写成「已经做了」
- **未做就写未做**，不要写「即将做」或「在规划中」（除非确实有排期）
- **用户否掉的就写否掉**，并注明否掉原因（避免下一个人重新提议）
- **不确定的就写不确定**，并注明下一步验证方式

## 6. 常见错误清单

以下是文档中反复出现的错误，新写文档时请逐条检查：

| 错误类型 | 错误示例 | 正确做法 |
|---|---|---|
| 文件+行号引用 | `lib/idb.ts:152` | `lib/idb.ts 的 DB_VERSION 常量` |
| 把计划写成已完成 | 「记忆中心已落地」 | 「记忆中心待落地」 |
| 把快照当现状 | 「DB 版本是 v13」（已到 v14） | 加「此后已漂移」补记 |
| 无日期的事实陈述 | 「测试有 755 个用例」 | 「截至 2026-10-15，约 755 个用例」 |
| 无引用的判断 | 「这个方案不好」 | 「这个方案不好，因为 XXX（见 §N.N）」 |
| 过时的用户决策 | 「用户选择了方案 A」（已改选 B） | 注明「2026-10-15 用户改选方案 B」 |
